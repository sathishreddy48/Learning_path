Backtracking

Depth-first search over partial answers: choose, explore, un-choose. One skeleton covers subsets, permutations, grid paths and constraint puzzles — so the work is in the pruning, and in knowing when a backtrack can be memoised into a DP and when it cannot.

The template: choose, explore, un-choose

Backtracking is depth-first search over the space of partial answers. You build a candidate one decision at a time; when a decision cannot lead anywhere valid you undo it and try the next. Every problem in this family is the same four-line skeleton with different content in each line, so learn the skeleton as a skeleton and you will never stare at a blank screen.

  1. Base case — the partial answer is complete: record a copy and return.
  2. Loop over the choices available at this depth.
  3. Choose — push onto the path. Recurse. Un-choose — pop it off again.
  4. Prune — skip choices that cannot possibly work, before recursing.

Two details matter more than they look. First, record a copy: the path is mutated all the way down, so appending the live list to your results gives you n references to one list that ends up empty. Second, the un-choose must exactly undo the choose — if you mutated two things on the way in, undo both on the way out. Most backtracking bugs are one of these two.

// The skeleton. Everything in this page is this shape.
static void Backtrack(State state, List<Choice> path, List<List<Choice>> results)
{
    if (IsComplete(state))
    {
        results.Add(new List<Choice>(path));   // ← COPY, not the live list
        return;
    }

    foreach (var choice in ChoicesAt(state))
    {
        if (!IsValid(state, choice)) continue; // ← prune before recursing

        path.Add(choice);                      // choose
        Apply(state, choice);
        Backtrack(state, path, results);       // explore
        Undo(state, choice);                   // un-choose: undo BOTH mutations
        path.RemoveAt(path.Count - 1);
    }
}

// Worked instance: all subsets of a distinct-element array (the power set).
static IList<IList<int>> Subsets(int[] nums)
{
    var results = new List<IList<int>>();
    var path = new List<int>();
    Go(0);
    return results;

    void Go(int start)
    {
        results.Add(new List<int>(path));      // every node is an answer here
        for (int i = start; i < nums.Length; i++)
        {
            path.Add(nums[i]);                 // choose
            Go(i + 1);                         // explore: i+1 forbids reuse
            path.RemoveAt(path.Count - 1);     // un-choose
        }
    }
}

def backtrack(state, path: list, results: list) -> None:
    if is_complete(state):
        results.append(path[:])            # ← COPY, not the live list
        return

    for choice in choices_at(state):
        if not is_valid(state, choice):
            continue                       # ← prune before recursing

        path.append(choice)                # choose
        apply(state, choice)
        backtrack(state, path, results)    # explore
        undo(state, choice)                # un-choose: undo BOTH mutations
        path.pop()

def subsets(nums: list[int]) -> list[list[int]]:

    path: list[int] = []

        results.append(path[:])            # every node is an answer here
        for i in range(start, len(nums)):
            path.append(nums[i])           # choose
            go(i + 1)                      # explore: i+1 forbids reuse
            path.pop()                     # un-choose

    go(0)
    return results
The copy, and the two index idioms

results.Add(path) instead of results.Add(new List<int>(path)) is the single most common bug in this entire family, and it is nasty because the program runs and returns the right number of answers — they are just all empty. In Python the equivalent slip is results.append(path) rather than path[:].

The other thing to get straight once and reuse forever is what you pass as the next start index:

  • Go(i + 1) — each element used at most once (subsets, combinations).
  • Go(i) — each element may be reused (combination sum with unlimited repeats).
  • Go(0) plus a used[] array — order matters (permutations).
Interview angle

Write the skeleton before you think about the problem. Genuinely — type the base case, the loop, the choose/recurse/un-choose, and then fill in what each means. It costs twenty seconds and it means you are never stuck in front of an empty editor, which is where candidates lose these questions. Say the complexity in the honest form: these are exponential, and the bound is number of nodes in the recursion tree × the cost of the work at each node — for subsets, O(n · 2ⁿ), where the n is the copy, not the recursion. People who say just "2ⁿ" have forgotten the copy, and it is a cheap thing for an interviewer to catch.

Practice
  • Write the power set three ways: backtracking, iteratively doubling the result list, and by enumerating bitmasks 0..2ⁿ−1.
  • Deliberately write the no-copy bug, run it, and look at the output — you will never make it again under pressure.
  • For each of the three start-index idioms above, name a problem that uses it.

Subsets and combinations, including duplicates

Combinations are subsets with a size or sum constraint; the only new idea is handling duplicate inputs without emitting duplicate answers, which comes up constantly and has one standard solution worth knowing cold.

Sort the input, then at each level skip a choice that equals the previous one — but only when the previous one was not taken at this level, which the condition i > start expresses exactly. Sorting is what makes duplicates adjacent, and adjacency is what makes the skip cheap.

// Subsets with duplicates in the input: sort, then skip repeats per level.
static IList<IList<int>> SubsetsWithDup(int[] nums)
{
    Array.Sort(nums);                                  // duplicates now adjacent
    var results = new List<IList<int>>();
    var path = new List<int>();
    Go(0);
    return results;

    void Go(int start)
    {
        results.Add(new List<int>(path));
        for (int i = start; i < nums.Length; i++)
        {
            // i > start means "this is not the first choice at this level",
            // so an equal value here would repeat a sibling branch.
            if (i > start && nums[i] == nums[i - 1]) continue;
            path.Add(nums[i]);
            Go(i + 1);
            path.RemoveAt(path.Count - 1);
        }
    }
}

// Combination sum: unlimited reuse of each candidate. Note Go(i), not Go(i+1).
static IList<IList<int>> CombinationSum(int[] candidates, int target)
{
    Array.Sort(candidates);                            // enables the break below
    var results = new List<IList<int>>();
    var path = new List<int>();
    Go(0, target);
    return results;

    void Go(int start, int remaining)
    {
        if (remaining == 0) { results.Add(new List<int>(path)); return; }
        for (int i = start; i < candidates.Length; i++)
        {
            // Sorted, so once one candidate overshoots every later one does:
            // break, not continue. This is the prune that makes it fast.
            if (candidates[i] > remaining) break;
            path.Add(candidates[i]);
            Go(i, remaining - candidates[i]);          // ← i: reuse allowed
            path.RemoveAt(path.Count - 1);
        }
    }
}

// Combination sum II: each candidate once, input may contain duplicates.
// Both tricks at the same time.
static IList<IList<int>> CombinationSum2(int[] candidates, int target)
{
    Array.Sort(candidates);
    var results = new List<IList<int>>();
    var path = new List<int>();
    Go(0, target);
    return results;

    void Go(int start, int remaining)
    {
        if (remaining == 0) { results.Add(new List<int>(path)); return; }
        for (int i = start; i < candidates.Length; i++)
        {
            if (i > start && candidates[i] == candidates[i - 1]) continue;  // dedupe
            if (candidates[i] > remaining) break;                           // prune
            path.Add(candidates[i]);
            Go(i + 1, remaining - candidates[i]);      // ← i+1: each once
            path.RemoveAt(path.Count - 1);
        }
    }
}

// Combinations of size k from 1..n, with the strongest prune on this page:
// stop when too few candidates remain to ever fill the path.
static IList<IList<int>> Combine(int n, int k)
{
    var results = new List<IList<int>>();
    var path = new List<int>();
    Go(1);
    return results;

    void Go(int start)
    {
        if (path.Count == k) { results.Add(new List<int>(path)); return; }
        int need = k - path.Count;
        for (int i = start; i <= n - need + 1; i++)     // ← the bound IS the prune
        {
            path.Add(i);
            Go(i + 1);
            path.RemoveAt(path.Count - 1);
        }
    }
}

def combine(n: int, k: int) -> list[list[int]]:

        if len(path) == k:
            results.append(path[:])
            return

            go(i + 1)
            path.pop()

    go(1)
    return results

Interview angle

The duplicate-skip is the thing being tested, and the thing to be able to justify rather than recall. Say it like this: "sorting puts equal values next to each other; i > start means I already tried this value as the first choice at this level, so taking it again here would regenerate a branch I have already explored." If you cannot explain it, an interviewer will reasonably assume you memorised it — and the natural probe is "why i > start and not i > 0?", which has a precise answer: i > 0 would also skip legitimate repeats that appear deeper in the same combination, so [1,1,2] would lose the answer [1,1]. Also prefer break over continue once the input is sorted, and say why.

Practice
  • Subsets II and combination sum II, then explain the i > start condition from scratch.
  • Letter combinations of a phone number — the simplest multi-choice-per-level case.
  • Palindrome partitioning (every partition into palindromes), reusing the palindrome precompute from the DP page.
  • Generate all valid parentheses for n pairs — the prune is the whole problem, so derive it before coding.

Permutations, with and without duplicates

Permutations differ from combinations in one way: order matters, so you cannot use a start index to move forward through the input — every unused element is a candidate at every level. That means you need a way to know what is still unused, and there are two standard approaches with different trade-offs worth being able to compare.

The used-array version is clearer and extends cleanly to duplicate handling. The swap-in-place version uses no extra array and is slicker, but it reorders the input as it goes, which breaks the sortedness that duplicate-skipping depends on — so for distinct inputs either is fine, and for duplicates use the used-array form.

// Used-array form: clear, and the one that extends to duplicates.
static IList<IList<int>> Permute(int[] nums)
{
    var results = new List<IList<int>>();
    var path = new List<int>();
    var used = new bool[nums.Length];
    Go();
    return results;

    void Go()
    {
        if (path.Count == nums.Length) { results.Add(new List<int>(path)); return; }
        for (int i = 0; i < nums.Length; i++)
        {
            if (used[i]) continue;             // every UNUSED element is a choice
            used[i] = true; path.Add(nums[i]);         // choose (two mutations)
            Go();
            path.RemoveAt(path.Count - 1); used[i] = false;   // un-choose BOTH
        }
    }
}

// Swap form: no used[] array, but it permutes nums itself.
static IList<IList<int>> PermuteSwap(int[] nums)
{
    var results = new List<IList<int>>();
    Go(0);
    return results;

    void Go(int k)
    {
        if (k == nums.Length) { results.Add(new List<int>(nums)); return; }
        for (int i = k; i < nums.Length; i++)
        {
            (nums[k], nums[i]) = (nums[i], nums[k]);   // choose
            Go(k + 1);
            (nums[k], nums[i]) = (nums[i], nums[k]);   // un-choose (swap back)
        }
    }
}

// Permutations II — duplicates in the input. Sort, then at each level use a
// given value at most once. The condition reads: skip nums[i] if it equals
// its predecessor AND that predecessor is not currently in the path, because
// then the predecessor already owned this slot in an earlier sibling branch.
static IList<IList<int>> PermuteUnique(int[] nums)
{
    Array.Sort(nums);
    var results = new List<IList<int>>();
    var path = new List<int>();
    var used = new bool[nums.Length];
    Go();
    return results;

    void Go()
    {
        if (path.Count == nums.Length) { results.Add(new List<int>(path)); return; }
        for (int i = 0; i < nums.Length; i++)
        {
            if (used[i]) continue;
            if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;  // dedupe
            used[i] = true; path.Add(nums[i]);
            Go();
            path.RemoveAt(path.Count - 1); used[i] = false;
        }
    }
}

// Next permutation in place — O(n), no recursion. Worth knowing separately:
// it generates the lexicographic successor rather than the whole set, which
// is the right answer when you are asked to iterate permutations in O(1) space.
static void NextPermutation(int[] nums)
{
    int i = nums.Length - 2;
    while (i >= 0 && nums[i] >= nums[i + 1]) i--;        // find the pivot
    if (i >= 0)
    {
        int j = nums.Length - 1;
        while (nums[j] <= nums[i]) j--;                  // smallest larger value
        (nums[i], nums[j]) = (nums[j], nums[i]);
    }
    Array.Reverse(nums, i + 1, nums.Length - i - 1);     // the suffix is descending
}
def permute(nums: list[int]) -> list[list[int]]:
    results: list[list[int]] = []
    path: list[int] = []
    used = [False] * len(nums)

    def go() -> None:
        if len(path) == len(nums):
            results.append(path[:])
            return
        for i in range(len(nums)):
            if used[i]:
                continue                       # every UNUSED element is a choice
            used[i] = True
            path.append(nums[i])               # choose (two mutations)
            go()
            path.pop()
            used[i] = False                    # un-choose BOTH

    go()
    return results

def permute_swap(nums: list[int]) -> list[list[int]]:
    results: list[list[int]] = []

    def go(k: int) -> None:
        if k == len(nums):
            results.append(nums[:])
            return
        for i in range(k, len(nums)):
            nums[k], nums[i] = nums[i], nums[k]   # choose
            go(k + 1)
            nums[k], nums[i] = nums[i], nums[k]   # un-choose

    go(0)
    return results

def permute_unique(nums: list[int]) -> list[list[int]]:
    nums.sort()
    results: list[list[int]] = []
    path: list[int] = []
    used = [False] * len(nums)

    def go() -> None:
        if len(path) == len(nums):
            results.append(path[:])
            return
        for i in range(len(nums)):
            if used[i]:
                continue
            # skip a value equal to its predecessor when that predecessor is
            # not in the path: it already owned this slot in a sibling branch.
            if i > 0 and nums[i] == nums[i - 1] and not used[i - 1]:
                continue
            used[i] = True
            path.append(nums[i])
            go()
            path.pop()
            used[i] = False

    go()
    return results

def next_permutation(nums: list[int]) -> None:
    i = len(nums) - 2
    while i >= 0 and nums[i] >= nums[i + 1]:
        i -= 1                                  # find the pivot
    if i >= 0:
        j = len(nums) - 1
        while nums[j] <= nums[i]:
            j -= 1                              # smallest larger value
        nums[i], nums[j] = nums[j], nums[i]
    nums[i + 1 :] = reversed(nums[i + 1 :])     # the suffix was descending
Why the permutation dedupe looks different

For combinations the skip is i > start && nums[i] == nums[i-1]; for permutations it is i > 0 && nums[i] == nums[i-1] && !used[i-1]. They are the same idea — "use each distinct value at most once per level" — expressed against different bookkeeping. Combinations advance a start index, so "first at this level" is i == start. Permutations scan the whole array every level, so "first at this level" has to be read off the used array instead: if the identical predecessor is not used, it was available and therefore already took this slot in an earlier sibling. Deriving one from the other is a good way to confirm you understand both.

Interview angle

Offer the used-array version first and mention that the swap version exists with O(1) extra space — knowing both and being able to say when each is appropriate is a stronger signal than producing the clever one. The complexity question is worth rehearsing because people get it wrong: there are n! permutations and each costs O(n) to copy, so O(n · n!), and the recursion tree has O(n!) leaves but more nodes than that in total. The other likely follow-up is "what if you only need the kth permutation?" — do not generate them all; divide by factorials to pick each digit directly, which is O(n²) and a genuinely different technique.

Practice
  • Permutations both ways, then permutations II, then derive the dedupe condition without looking.
  • Next permutation in place — then use it to iterate every permutation with no recursion at all.
  • The kth permutation sequence, computed directly with factorials.
  • Letter case permutation of a string ("a1b2" → every combination of cases) — note the choice set is per-character, not global.

Backtracking on a grid: word search and path counting

On a grid the "path" is the set of cells you are currently standing on, and the choices are the four neighbours. The new idea is that you must mark a cell as visited on the way in and unmark it on the way out — that unmark is what makes this backtracking rather than flood fill, and forgetting it is the defining bug of the family.

The idiomatic trick is to mark in the grid itself rather than allocate a separate visited array: overwrite the cell with a sentinel, recurse, and restore the original character. It is O(1) extra space and it reads as experience — but say out loud that you are mutating the caller's input and restoring it, because an interviewer may consider that a problem.

// Word search: does the word exist as a path of adjacent cells?
// Marks in place with a sentinel, then restores.
static bool Exist(char[][] board, string word)
{
    int rows = board.Length, cols = board[0].Length;
    for (int r = 0; r < rows; r++)
        for (int c = 0; c < cols; c++)
            if (Go(r, c, 0)) return true;
    return false;

    bool Go(int r, int c, int k)
    {
        if (k == word.Length) return true;                     // whole word matched
        if (r < 0 || r >= rows || c < 0 || c >= cols) return false;
        if (board[r][c] != word[k]) return false;              // includes the sentinel

        char saved = board[r][c];
        board[r][c] = '#';                                     // mark: choose
        bool found = Go(r + 1, c, k + 1) || Go(r - 1, c, k + 1)
                  || Go(r, c + 1, k + 1) || Go(r, c - 1, k + 1);
        board[r][c] = saved;                                   // un-mark: un-choose
        return found;
    }
}

// Count paths through every non-obstacle cell exactly once (unique paths III).
// Here the unmark genuinely matters: two different paths reuse the same cells.
static int UniquePathsIII(int[][] grid)
{
    int rows = grid.Length, cols = grid[0].Length;
    int empty = 0, sr = 0, sc = 0;
    for (int r = 0; r < rows; r++)
        for (int c = 0; c < cols; c++)
        {
            if (grid[r][c] == 0) empty++;
            else if (grid[r][c] == 1) { sr = r; sc = c; }
        }
    return Go(sr, sc, empty + 1);      // squares to cover: the 0s plus the start

    // remaining = squares still to step on, counting this one.
    int Go(int r, int c, int remaining)
    {
        if (r < 0 || r >= rows || c < 0 || c >= cols || grid[r][c] == -1) return 0;
        if (grid[r][c] == 2)                                   // the goal
            return remaining == 0 ? 1 : 0;                      // all squares covered?

        int saved = grid[r][c];
        grid[r][c] = -1;                                       // mark
        int total = Go(r + 1, c, remaining - 1) + Go(r - 1, c, remaining - 1)
                  + Go(r, c + 1, remaining - 1) + Go(r, c - 1, remaining - 1);
        grid[r][c] = saved;                                    // un-mark
        return total;
    }
}

// once the body grows, and it generalises to eight directions or a knight.

def exist(board: list[list[str]], word: str) -> bool:
    rows, cols = len(board), len(board[0])

    def go(r: int, c: int, k: int) -> bool:
        if k == len(word):
            return True                               # whole word matched
        if not (0 <= r < rows and 0 <= c < cols):
            return False
        if board[r][c] != word[k]:
            return False                              # includes the sentinel

        saved, board[r][c] = board[r][c], "#"         # mark: choose
        found = (go(r + 1, c, k + 1) or go(r - 1, c, k + 1)
                 or go(r, c + 1, k + 1) or go(r, c - 1, k + 1))
        board[r][c] = saved                           # un-mark: un-choose
        return found

    return any(go(r, c, 0) for r in range(rows) for c in range(cols))

def unique_paths_iii(grid: list[list[int]]) -> int:
    rows, cols = len(grid), len(grid[0])
    empty = sr = sc = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == 0:
                empty += 1
            elif grid[r][c] == 1:
                sr, sc = r, c

    # remaining = squares still to step on, counting this one.
    def go(r: int, c: int, remaining: int) -> int:
        if not (0 <= r < rows and 0 <= c < cols) or grid[r][c] == -1:
            return 0
        if grid[r][c] == 2:                           # the goal
            return 1 if remaining == 0 else 0         # all squares covered?

        saved, grid[r][c] = grid[r][c], -1            # mark
        total = (go(r + 1, c, remaining - 1) + go(r - 1, c, remaining - 1)
                 + go(r, c + 1, remaining - 1) + go(r, c - 1, remaining - 1))
        grid[r][c] = saved                            # un-mark
        return total

    return go(sr, sc, empty + 1)                 # the 0s plus the start square

Flood fill versus backtracking on a grid

These look identical and are not. Counting islands sinks each cell permanently — once visited, never revisited, because no other answer needs it; that is flood fill, it is O(rows × cols), and adding an unmark would make it exponential for no reason. Word search must unmark, because a cell excluded from one candidate path may be essential to another. Ask yourself "can a cell belong to more than one candidate answer?" — yes means backtrack and unmark, no means flood fill and do not. Choosing wrong is not a style preference; one of the two answers will be wrong.

Interview angle

State the complexity carefully, because this is where grid backtracking is graded: word search is O(rows × cols × 4^L) for a word of length L — every cell is a possible start, and from each you branch four ways to depth L (really 3^L after the first step, since you never go straight back, and saying that is a nice touch). The standard follow-up is word search II, many words at once, and the expected answer is a trie: walk the grid once while descending the trie, so shared prefixes are explored once instead of once per word. Recognising that is the whole point of the follow-up, and it connects this page to the trie section on the trees page.

Practice
  • Word search, then word search II with a trie — and measure the difference on a large dictionary.
  • Unique paths III, and explain why the unmark is required here but harmful in "number of islands".
  • Rat in a maze / all paths from corner to corner, returning the paths themselves.
  • The knight's tour on a small board — then add the heuristic of visiting the most-constrained square first and watch the runtime collapse.

Constraint puzzles: N-Queens and Sudoku

These are the problems backtracking was invented for, and they share a structure: a fixed number of slots, a set of values per slot, and constraints that let you reject a partial assignment long before it is complete. The algorithm is the same skeleton; all the engineering is in making the validity check O(1) so the pruning is cheap.

For N-Queens the insight is that one queen per row is forced, so the state is just "which column in each row", and the three conflict tests collapse to set membership: the column, the diagonal row − col, and the anti-diagonal row + col. Each of those is constant along its line, which is the whole trick.

// N-Queens. One queen per row, so the decision at depth r is its column.
// Conflicts are O(1): a column, a diagonal (r-c) and an anti-diagonal (r+c).
static IList<IList<string>> SolveNQueens(int n)
{
    var results = new List<IList<string>>();
    var queenCol = new int[n];
    var cols = new HashSet<int>();
    var diag = new HashSet<int>();      // r - c is constant down a diagonal
    var anti = new HashSet<int>();      // r + c is constant down an anti-diagonal
    Go(0);
    return results;

    void Go(int r)
    {
        if (r == n) { results.Add(Render()); return; }
        for (int c = 0; c < n; c++)
        {
            if (cols.Contains(c) || diag.Contains(r - c) || anti.Contains(r + c))
                continue;                                     // prune: O(1)
            cols.Add(c); diag.Add(r - c); anti.Add(r + c);     // choose (3 marks)
            queenCol[r] = c;
            Go(r + 1);
            cols.Remove(c); diag.Remove(r - c); anti.Remove(r + c);  // un-choose all 3
        }
    }

    List<string> Render() => queenCol
        .Select(c => new string('.', c) + "Q" + new string('.', n - c - 1))
        .ToList();
}

// Just the count (n-queens II) — same search, no rendering.
static int TotalNQueens(int n)
{
    var cols = new HashSet<int>(); var diag = new HashSet<int>(); var anti = new HashSet<int>();
    return Go(0);

    int Go(int r)
    {
        if (r == n) return 1;
        int found = 0;
        for (int c = 0; c < n; c++)
        {
            if (cols.Contains(c) || diag.Contains(r - c) || anti.Contains(r + c)) continue;
            cols.Add(c); diag.Add(r - c); anti.Add(r + c);
            found += Go(r + 1);
            cols.Remove(c); diag.Remove(r - c); anti.Remove(r + c);
        }
        return found;
    }
}

// Sudoku. Fill the first empty cell; try 1-9; recurse; undo on failure.
// Returning bool rather than void is what lets the first solution stop the
// whole search instead of exploring the rest of the tree.
static void SolveSudoku(char[][] board)
{
    Go();

    bool Go()
    {
        for (int r = 0; r < 9; r++)
            for (int c = 0; c < 9; c++)
            {
                if (board[r][c] != '.') continue;
                for (char v = '1'; v <= '9'; v++)
                {
                    if (!IsValid(r, c, v)) continue;
                    board[r][c] = v;                 // choose
                    if (Go()) return true;           // ← stop at the first solution
                    board[r][c] = '.';               // un-choose
                }
                return false;                        // no value fits: dead end
            }
        return true;                                 // no empty cell left: solved
    }

    bool IsValid(int r, int c, char v)
    {
        int boxR = r / 3 * 3, boxC = c / 3 * 3;
        for (int i = 0; i < 9; i++)
        {
            if (board[r][i] == v || board[i][c] == v) return false;
            if (board[boxR + i / 3][boxC + i % 3] == v) return false;   // the 3x3 box
        }
        return true;
    }
}
def solve_n_queens(n: int) -> list[list[str]]:
    results: list[list[str]] = []
    queen_col = [0] * n
    cols: set[int] = set()
    diag: set[int] = set()        # r - c is constant down a diagonal
    anti: set[int] = set()        # r + c is constant down an anti-diagonal

    def go(r: int) -> None:
        if r == n:
            results.append(["." * c + "Q" + "." * (n - c - 1) for c in queen_col])
            return
        for c in range(n):
            if c in cols or (r - c) in diag or (r + c) in anti:
                continue                                  # prune: O(1)
            cols.add(c); diag.add(r - c); anti.add(r + c)  # choose (3 marks)
            queen_col[r] = c
            go(r + 1)
            cols.discard(c); diag.discard(r - c); anti.discard(r + c)  # undo all 3

    go(0)
    return results

def solve_sudoku(board: list[list[str]]) -> None:
    def is_valid(r: int, c: int, v: str) -> bool:
        box_r, box_c = r // 3 * 3, c // 3 * 3
        for i in range(9):
            if board[r][i] == v or board[i][c] == v:
                return False
            if board[box_r + i // 3][box_c + i % 3] == v:   # the 3x3 box
                return False
        return True

    def go() -> bool:
        for r in range(9):
            for c in range(9):
                if board[r][c] != ".":
                    continue
                for v in "123456789":
                    if not is_valid(r, c, v):
                        continue
                    board[r][c] = v                  # choose
                    if go():
                        return True                  # ← stop at first solution
                    board[r][c] = "."                # un-choose
                return False                         # no value fits: dead end
        return True                                  # no empty cell: solved

    go()
Return bool when one answer is enough

Notice the difference between the two shapes on this page. When you want every answer, the recursion returns void and appends to a results list; the search must run to completion. When one answer suffices — Sudoku, "is there a path", "can the board be solved" — the recursion returns bool and the caller does if (Go()) return true;, which unwinds the entire stack the moment a solution is found. Getting this wrong is a real performance bug, not a style choice: a void Sudoku solver explores the whole tree and then has to be stopped with a flag.

Interview angle

N-Queens is a near-certain ask if the interviewer wants to see backtracking specifically, and the discriminator is the r − c / r + c diagonal encoding. If you scan the board to check conflicts you still get a correct answer, but you have shown you did not see the structure — so say "the difference and the sum are each constant along a diagonal, so three hash sets give me O(1) conflict checks." The follow-up is usually the bitmask version, where the three sets become three integers and mask & -mask picks the next free column; mentioning it is worth as much as writing it. For Sudoku the expected improvement is most-constrained-variable ordering: fill the empty cell with the fewest legal values first, rather than the first empty cell in scan order. That is a general constraint-satisfaction heuristic and it is the right thing to name.

Practice
  • N-Queens, then N-Queens II (count only), then the bitmask version.
  • Sudoku, then add most-constrained-variable ordering and compare the node counts.
  • Word break II and "restore IP addresses" — the same skeleton over string splits instead of board cells.
  • Graph colouring with k colours — and notice it is N-Queens with a different conflict test.

Pruning: the difference between hopeless and fast

Every problem on this page is exponential in the worst case. What makes backtracking usable is that good pruning cuts branches near the root, and a branch cut at depth 2 removes everything beneath it. Pruning is not an optimisation you add at the end — in an interview it is often the answer itself, and it is the thing that distinguishes a candidate who has internalised the technique.

Four prunes cover nearly everything:

  1. Infeasibility — this choice already violates a constraint. (N-Queens' conflict sets.)
  2. Bound — even the best completion from here cannot beat the answer I already have. (Branch and bound.)
  3. Counting — too few candidates remain to fill the remaining slots. (n − need + 1 in Combine.)
  4. Symmetry — this branch is a relabelling of one already explored. (The duplicate skip; the first-row-half restriction in N-Queens.)

Ordering helps too, and costs nothing: sort so that the most constraining choice comes first, because failures you can reach quickly are failures you pay for once.

// Branch-and-bound in miniature: partition nums into k equal-sum subsets.
// Four prunes, in the order they pay off most.
static bool CanPartitionKSubsets(int[] nums, int k)
{
    int total = nums.Sum();
    if (total % k != 0) return false;                 // prune 0: arithmetic
    int target = total / k;

    Array.Sort(nums);
    Array.Reverse(nums);                              // prune 1: biggest first
    if (nums[0] > target) return false;               // one item overflows a bucket

    var buckets = new int[k];
    return Go(0);

    bool Go(int i)
    {
        if (i == nums.Length) return true;            // every item placed
        for (int b = 0; b < k; b++)
        {
            if (buckets[b] + nums[i] > target) continue;        // prune 2: infeasible

            // prune 3 (symmetry): two empty buckets are interchangeable, so
            // trying the second one can only regenerate the first one's subtree.
            if (b > 0 && buckets[b] == buckets[b - 1]) continue;

            buckets[b] += nums[i];                    // choose
            if (Go(i + 1)) return true;
            buckets[b] -= nums[i];                    // un-choose
        }
        return false;
    }
}

// Bound pruning: the best score reachable from here cannot beat 'best',
// so stop. The 'optimistic' estimate must never UNDER-estimate, or you
// will prune a branch that actually held the optimum.
static int MaxScore(int[] items, int capacity)
{
    int best = 0;
    var sorted = items.OrderByDescending(x => x).ToArray();
    Go(0, 0, capacity);
    return best;

    void Go(int i, int score, int left)
    {
        if (left < 0) return;
        best = Math.Max(best, score);
        if (i == sorted.Length) return;

        // Optimistic bound: assume every remaining item fits for free.
        int optimistic = score + sorted.Skip(i).Sum();
        if (optimistic <= best) return;               // ← the bound prune

        Go(i + 1, score + sorted[i], left - sorted[i]);   // take
        Go(i + 1, score, left);                            // skip
    }
}
def can_partition_k_subsets(nums: list[int], k: int) -> bool:
    total = sum(nums)
    if total % k:
        return False                                  # prune 0: arithmetic
    target = total // k

    nums.sort(reverse=True)                           # prune 1: biggest first
    if nums[0] > target:
        return False                                  # one item overflows a bucket

    buckets = [0] * k

    def go(i: int) -> bool:
        if i == len(nums):
            return True                               # every item placed
        for b in range(k):
            if buckets[b] + nums[i] > target:
                continue                              # prune 2: infeasible
            # prune 3 (symmetry): equal buckets are interchangeable, so the
            # second one can only regenerate the first one's subtree.
            if b > 0 and buckets[b] == buckets[b - 1]:
                continue
            buckets[b] += nums[i]                     # choose
            if go(i + 1):
                return True
            buckets[b] -= nums[i]                     # un-choose
        return False

    return go(0)

def max_score(items: list[int], capacity: int) -> int:
    best = 0
    sorted_items = sorted(items, reverse=True)
    suffix = [0] * (len(sorted_items) + 1)
    for i in range(len(sorted_items) - 1, -1, -1):
        suffix[i] = suffix[i + 1] + sorted_items[i]

    def go(i: int, score: int, left: int) -> None:
        nonlocal best
        if left < 0:
            return
        best = max(best, score)
        if i == len(sorted_items):
            return
        # Optimistic bound: assume every remaining item fits for free.
        if score + suffix[i] <= best:
            return                                    # ← the bound prune
        go(i + 1, score + sorted_items[i], left - sorted_items[i])   # take
        go(i + 1, score, left)                                        # skip

    go(0, 0, capacity)
    return best

Interview angle

Say the word "prune" and name which of the four you are applying — it is vocabulary that marks you as having done this before. The one correctness trap to be careful about is the bound prune: your optimistic estimate must be a genuine upper bound on what is still achievable, because if it ever under-estimates you will cut the branch containing the real optimum and return a wrong answer confidently. State that property when you write it ("this assumes every remaining item fits, so it can only over-estimate"). The symmetry prune is the one interviewers find most impressive and candidates find hardest to spot; the general form is "if two slots are currently indistinguishable, only try the first."

  • N-Queens restricted to half the first row, doubling the count by symmetry — and work out when the doubling is wrong (odd n).
  • Take any backtracking solution you have written and instrument it with a node counter; then add one prune and compare.

When to memoise a backtrack — and when you cannot

Backtracking and DP are the same search; the difference is whether you can cache by state. Caching works when two different partial paths that arrive at the same state have the same future — and fails when they do not.

The test is mechanical: does the answer from here depend only on a small summary of the path, or on the path itself?

  • Word break — "can s[i..] be segmented?" depends only on i. Cacheable: the exponential backtrack becomes O(n²) DP.
  • Word break II — return every segmentation. The output is exponential, so no cache makes it polynomial; you can still memoise the list of suffix segmentations, which helps in practice but not asymptotically.
  • Word search — the future depends on which cells the path has already consumed, and that set is part of the state. There are 2^(rows·cols) such sets, so memoising is useless. Not cacheable.

So: if you need to enumerate answers, it stays backtracking. If you need to count or optimise and the state is small, memoise it and you have a DP.

// Enumerating: backtracking. Output is exponential, so this is as good
// as it gets asymptotically.
static IList<string> WordBreakAll(string s, IList<string> dict)
{
    var words = new HashSet<string>(dict);
    var memo = new Dictionary<int, List<string>>();   // suffix index -> sentences
    return Go(0);

    List<string> Go(int start)
    {
        if (start == s.Length) return [""];           // one empty completion
        if (memo.TryGetValue(start, out var hit)) return hit;

        var result = new List<string>();
        for (int end = start + 1; end <= s.Length; end++)
        {
            var word = s[start..end];
            if (!words.Contains(word)) continue;
            foreach (var rest in Go(end))
                result.Add(rest.Length == 0 ? word : word + " " + rest);
        }
        return memo[start] = result;
    }
}

// Counting: the same search, memoised on the only thing that matters.
// Now polynomial, and the exponential output problem is gone because we
// never materialise the answers.
static int CountSegmentations(string s, IList<string> dict)
{
    var words = new HashSet<string>(dict);
    var memo = new Dictionary<int, int>();
    return Go(0);

    int Go(int start)
    {
        if (start == s.Length) return 1;
        if (memo.TryGetValue(start, out var hit)) return hit;

        int total = 0;
        for (int end = start + 1; end <= s.Length; end++)
            if (words.Contains(s[start..end])) total += Go(end);
        return memo[start] = total;
    }
}
from functools import lru_cache

def word_break_all(s: str, word_dict: list[str]) -> list[str]:
    words = set(word_dict)
    memo: dict[int, list[str]] = {}

    def go(start: int) -> list[str]:
        if start == len(s):
            return [""]                       # one empty completion
        if start in memo:
            return memo[start]
        result: list[str] = []
        for end in range(start + 1, len(s) + 1):
            word = s[start:end]
            if word not in words:
                continue
            for rest in go(end):
                result.append(word if not rest else word + " " + rest)
        memo[start] = result
        return result

    return go(0)

def count_segmentations(s: str, word_dict: list[str]) -> int:
    words = set(word_dict)

    @lru_cache(maxsize=None)
    def go(start: int) -> int:
        if start == len(s):
            return 1
        return sum(go(end) for end in range(start + 1, len(s) + 1)
                   if s[start:end] in words)

    return go(0)

The sentence that earns this is: "the state here is the index plus the set of used cells, and that set is too big to memoise, so this stays exponential." It tells the interviewer you know why you are not optimising, which is a much stronger position than either optimising blindly or failing to mention it. The reverse case matters as much — if you write an exponential backtrack for a problem whose state is just an index, expect "can you do better?", and the answer is to add a dictionary. So the habit worth building is: after any backtracking solution, say out loud what the state would be, and whether it is small. One sentence, every time, and you will never be caught on the wrong side of this question.
