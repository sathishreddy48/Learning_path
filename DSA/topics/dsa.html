How to run the 45 minutes

The coding round is assessed on more than whether the code works. Interviewers are scoring communication, how you handle a hint, and whether you test your own work — and plenty of people who solve the problem still fail because they solved it in silence.

A structure that works, with rough timings for a 45-minute slot:

  1. Clarify (3–5 min). Repeat the problem in your own words. Ask about input size, duplicates, negatives, empties, nulls, and whether the input is sorted or can be mutated. These questions are scored.
  2. Examples (2 min). Write one normal case and one edge case on the board. They become your test cases later.
  3. Approach (5 min). State the brute force and its complexity first — it shows you understand the problem and gives you a baseline. Then improve it, and say what the improvement costs in space. Get agreement before coding.
  4. Code (20 min). Narrate as you go. Name things properly. Handle the edge cases you listed.
  5. Test (5–8 min). Walk your examples through by hand, out loud. Finding your own bug scores higher than not having one.
  6. Complexity (2 min). State time and space, and say what you would improve with more time.
// WHAT "CLARIFY" SOUNDS LIKE -----------------------------------------------
//  "How large can the input be?"        -> decides O(n log n) vs O(n^2) vs O(n)
//  "Can there be duplicates?"           -> decides set vs dictionary vs sort
//  "Are the values sorted?"             -> unlocks two pointers / binary search
//  "Can I modify the input in place?"   -> decides O(1) vs O(n) space
//  "What should I return for an empty input / no answer?"
//  "Can values be negative? Zero? Null?"
//  "Is the input ASCII, or full Unicode?"   <- the string one people miss

// THE SIGNAL: write the signature and the guards before the algorithm.
public static int[] TwoSum(int[] nums, int target)
{
    // the edge cases you agreed, handled first and visibly
    if (nums is null || nums.Length < 2) return [];

    var seen = new Dictionary<int, int>(nums.Length);   // capacity: free, and noticed
    for (int i = 0; i < nums.Length; i++)
    {
        if (seen.TryGetValue(target - nums[i], out int j)) return [j, i];
        seen[nums[i]] = i;              // after the lookup: handles nums[i]*2 == target
    }
    return [];
}
// Time O(n), space O(n). The brute force is O(n^2) time, O(1) space - say both.

// TESTING OUT LOUD, which is the step people skip ---------------------------
//   nums = [2, 7, 11, 15], target = 9
//   i=0: want 7, not seen. seen = {2:0}
//   i=1: want 2, FOUND at 0 -> [0, 1]            correct
//   edge: [3, 3], target 6 -> i=0 seen={3:0}; i=1 want 3, found -> [0,1]  correct
//   edge: [] -> guard returns []                                          correct

// IF YOU GET STUCK, say what you are stuck on. Silence reads as "no idea";
// "I know this needs better than O(n^2) and I am trying to find what I can
// precompute" reads as progress and usually earns the hint you need.

// IF YOU ARE GIVEN A HINT, take it. Arguing with a hint is scored badly;
// so is ignoring it and continuing with your plan.
# The same structure. Python lets you write less, so there is MORE time for
# the clarify and test steps - use it rather than finishing early in silence.

def two_sum(nums: list[int], target: int) -> list[int]:
    """O(n) time, O(n) space. Brute force is O(n^2) time, O(1) space."""
    if not nums or len(nums) < 2:
        return []

    seen: dict[int, int] = {}
    for i, n in enumerate(nums):
        if (j := seen.get(target - n)) is not None:   # walrus: readable, not clever
            return [j, i]
        seen[n] = i                                   # after the lookup
    return []

# Testing out loud
#   [2, 7, 11, 15], 9
#     i=0 n=2: want 7, miss. seen={2:0}
#     i=1 n=7: want 2, hit at 0 -> [0,1]
#   [3, 3], 6 -> [0, 1]
#   [] -> []

# often encouraged, but say so up front. What is NOT fine is reaching for a
# library that solves the problem outright:
from collections import Counter
#   Counter(s) for an anagram check is fine - it is a frequency map
import itertools

#   asked to write the backtracking. Ask before you use one.
Interview angle

This section is the interview angle. The thing worth internalising: an interviewer cannot see you thinking, so an unspoken correct approach scores below a spoken, partially-correct one. State the brute force and its complexity before optimising — it is the single highest-value habit, because it proves you understood the problem and gives you something to improve from if you run out of time.

Practice
  • Solve a problem you already know while narrating every step out loud, timed to 45 minutes.
  • Write the clarifying questions for three problems before looking at any solution.
  • Practise stating the brute force first, even when you can see the optimal answer immediately.

Big-O: time, space, amortised — and how to say it

Big-O describes how cost grows as input grows, discarding constants and lower-order terms. In an interview you need three things: to compute it quickly, to say it precisely, and to know when it lies.

How to compute it fast: a loop over n is O(n); nested loops over n are O(n²); halving each step is O(log n); a loop that does a log-n operation inside is O(n log n); recursion branching twice to depth n is O(2ⁿ).

When it lies: constants matter at real sizes — an O(n log n) sort beats an O(n) algorithm with a huge constant for small n. Hash operations are O(1) average and O(n) worst case. And "O(1) space" usually excludes the output, which you should state rather than assume.

// Reading complexity off the shape of the code ------------------------------

for (int i = 0; i < n; i++) { }                          // O(n)

for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++) { }                      // O(n^2)

for (int i = 0; i < n; i++)
    for (int j = i + 1; j < n; j++) { }                  // n(n-1)/2 -> still O(n^2)

while (n > 1) n /= 2;                                    // O(log n)

for (int i = 0; i < n; i++)                              // O(n log n)
    BinarySearch(arr, i);

for (int i = 1; i < n; i *= 2)
    for (int j = 0; j < n; j++) { }                      // O(n log n)

// Two sequential loops: O(n) + O(m) = O(n + m), NOT O(n^2).
// Saying "O(n + m)" when there are two different inputs is a small, real signal.
foreach (var a in listA) { }
foreach (var b in listB) { }                             // O(n + m)

// AMORTISED: List<T>.Add is O(1) amortised, not O(1) worst case.
// The array doubles when full, so one Add in n is O(n) - but across n adds the
// total copying is n + n/2 + n/4 + ... < 2n, so the AVERAGE is O(1).
var list = new List<int>();
for (int i = 0; i < n; i++) list.Add(i);                 // O(n) total

// ...which is why giving the capacity up front is a real win: no resizes at all
var sized = new List<int>(capacity: n);

// COMMON RECURRENCES, by the shape of the recursion
//   T(n) = T(n/2) + O(1)      -> O(log n)      binary search
//   T(n) = T(n/2) + O(n)      -> O(n)          quickselect (average)
//   T(n) = 2T(n/2) + O(1)     -> O(n)          tree traversal
//   T(n) = 2T(n/2) + O(n)     -> O(n log n)    merge sort
//   T(n) = 2T(n-1) + O(1)     -> O(2^n)        naive fibonacci / subsets
//   T(n) = nT(n-1)            -> O(n!)         permutations

// SPACE: count what YOU allocate, and say what you are excluding
static int Sum(int[] a)          { int s = 0; foreach (var x in a) s += x; return s; }
//   O(1) extra space

static int[] Doubled(int[] a)    => a.Select(x => x * 2).ToArray();
//   O(n) space - but it is the OUTPUT. Say "O(1) auxiliary, O(n) output".

static int Depth(TreeNode? t)    => t is null ? 0 : 1 + Math.Max(Depth(t.Left), Depth(t.Right));
//   O(h) space on the CALL STACK - O(log n) balanced, O(n) in the worst case.
//   Forgetting recursion's stack space is the most common space-complexity miss.

// WHEN IT LIES -------------------------------------------------------------
// Dictionary is O(1) average, O(n) worst case (every key colliding).
// In practice it is O(1); say "average" and you have covered yourself.
// LINQ hides loops: .Contains() on a List<T> inside a loop is O(n^2).
foreach (var x in a) if (b.Contains(x)) { }              // O(n * m) - List.Contains
var set = b.ToHashSet();
foreach (var x in a) if (set.Contains(x)) { }            // O(n + m)
# Reading complexity off the shape - identical rules

for i in range(n): pass                       # O(n)

for i in range(n):
    for j in range(n): pass                   # O(n^2)

while n > 1: n //= 2                          # O(log n)

sorted(items)                                 # O(n log n) - Timsort

# Two inputs: O(n + m)
for a in list_a: pass
for b in list_b: pass

# AMORTISED: list.append is O(1) amortised (over-allocates and copies on growth)
items = []
for i in range(n): items.append(i)            # O(n) total

# PYTHON-SPECIFIC COSTS people get wrong in interviews:
s = ""
for i in range(n): s += str(i)                # O(n^2) - strings are IMMUTABLE
"".join(str(i) for i in range(n))             # O(n) - do this

items.insert(0, x)                            # O(n) - shifts everything
items.pop(0)                                  # O(n) - same
from collections import deque
dq = deque(); dq.appendleft(x); dq.popleft()  # O(1) - use a deque for a queue

x in some_list                                # O(n)
x in some_set                                 # O(1) average
x in some_dict                                # O(1) average

items[1:]                                     # O(n) - slicing COPIES
min(items), max(items), sum(items)            # O(n) each - three passes if you
                                              #   call all three

# RECURRENCES are the same, with one extra constraint:
import sys
sys.getrecursionlimit()                       # 1000 by default
# A recursion of depth 10^5 is fine in C# and crashes in Python. Say so, and
# convert to an iterative solution with an explicit stack.

# SPACE: the recursion stack counts here too
def depth(node) -> int:
    return 0 if node is None else 1 + max(depth(node.left), depth(node.right))
#   O(h) stack - O(log n) balanced, O(n) for a degenerate tree
Interview angle

Say complexity unprompted at the end of every solution, in the form "O(n) time, O(1) auxiliary space, O(n) for the output" — the precision costs you nothing and is noticed. Two details that separate answers: hash lookups are O(1) average, not worst case, and recursion's stack counts toward space, which is the most common miss. In Python, flag the quadratic string concatenation and the O(n) list.pop(0) before you are caught by them.

  • Find an O(n²) in code you own caused by List.Contains inside a loop.
  • Write the recurrence for merge sort and solve it without looking it up.

Interview angle

A surprising number of problems are solved the moment you pick the right structure, and interviewers notice whether you reach for it immediately or arrive after a detour. Two specific signals: using HashSet.Add's return value instead of a separate Contains check, and using a bounded min-heap of size k for top-k (O(n log k)) rather than sorting everything (O(n log n)). Arrays, List<T> and Span<T>

A detail worth having ready in a C#-flavoured interview, because it is a place where knowing the language beyond the algorithm shows. T[] is a fixed-size contiguous block. List<T> wraps one and grows it by doubling. Span<T> is a view over contiguous memory — array, string, or stack — that slices without copying and cannot be stored on the heap.

For interview purposes the useful point is that slicing an array copies and slicing a span does not, which turns a lot of O(n²) string manipulation into O(n).

int[] arr = [1, 2, 3, 4, 5];

// Array slicing COPIES
int[] middle = arr[1..4];              // new array, O(k)

// Span slicing does NOT - it is a pointer and a length
Span<int> span = arr;
Span<int> view = span[1..4];           // O(1), no allocation
view[0] = 99;                          // writes THROUGH to arr
Console.WriteLine(arr[1]);             // 99

// The classic win: string processing without allocating a substring per step
static int CountWords(string s)
{
    int count = 0;
    ReadOnlySpan<char> rest = s;
    while (!rest.IsEmpty)
    {
        int i = rest.IndexOf(' ');
        if (i < 0) { count++; break; }
        if (i > 0) count++;
        rest = rest[(i + 1)..];        // no allocation per word
    }
    return count;
}
// vs s.Split(' ') which allocates an array plus one string per word

int year = int.Parse("2026-10-07".AsSpan(0, 4));

Recursion, the call stack and depth limits

Recursion shows up on half the pages that follow — trees, graphs, backtracking, divide and conquer. Three things are worth having straight before you meet them.

Every recursion needs a base case that is actually reachable — most infinite recursions are a base case that the recursive step never converges on. The stack is space: depth h costs O(h), which is O(log n) on a balanced tree and O(n) on a degenerate one, and forgetting it is the most common space-complexity error. Depth limits differ by language: .NET gives you roughly 10⁴–10⁵ frames before StackOverflowException (which cannot be caught), while Python stops at 1000 by default and raises a catchable RecursionError.

That last point matters in practice: a recursive DFS over 10⁵ nodes is fine in C# and crashes in Python, so say you would convert it to an explicit stack.

// The shape: base case, work, recurse, combine
static int Depth(TreeNode? node)
{
    if (node is null) return 0;                      // base case
    return 1 + Math.Max(Depth(node.Left), Depth(node.Right));
}
// Time O(n) - every node once. Space O(h) on the call stack.

// StackOverflowException CANNOT be caught in .NET - the process dies. So for an
// input whose depth you do not control, use an explicit stack.
static int DepthIterative(TreeNode? root)
{
    if (root is null) return 0;
    var stack = new Stack<(TreeNode Node, int Depth)>();
    stack.Push((root, 1));
    int best = 0;

    while (stack.Count > 0)
    {
        var (node, d) = stack.Pop();
        best = Math.Max(best, d);
        if (node.Left is not null)  stack.Push((node.Left,  d + 1));
        if (node.Right is not null) stack.Push((node.Right, d + 1));
    }
    return best;
}
// Same O(n) time; the O(h) space is now on the HEAP, which is far larger.

// TAIL RECURSION: C# does NOT guarantee the optimisation. The JIT sometimes
// does it in release builds on x64; never rely on it.
static int SumTail(int[] a, int i = 0, int acc = 0)
    => i == a.Length ? acc : SumTail(a, i + 1, acc + a[i]);     // may still overflow

// Converting recursion to iteration, the general recipe:
//   1. push the initial state
//   2. pop, do the work
//   3. push the sub-states, in REVERSE order if order matters
// For post-order (work after the children), push a visited flag with the node.

// THE PERFORMANCE TRAP: recomputing the same subproblem
static long Fib(int n) => n < 2 ? n : Fib(n - 1) + Fib(n - 2);   // O(2^n)

// Memoise and it collapses to O(n) - this is literally what DP is
static long FibMemo(int n, Dictionary<int, long>? memo = null)
{
    memo ??= [];
    if (n < 2) return n;
    if (memo.TryGetValue(n, out var cached)) return cached;
    return memo[n] = FibMemo(n - 1, memo) + FibMemo(n - 2, memo);
}

// Measuring the real limit on your machine
static int MaxDepth(int d = 0) { try { return MaxDepth(d + 1); } catch { return d; } }
// ...does not work: StackOverflowException is uncatchable. Use a counter and a
// deliberate limit instead, or just know the order of magnitude: ~10^4-10^5.
import sys
from functools import lru_cache, cache

# The shape
def depth(node) -> int:
    if node is None:
        return 0
    return 1 + max(depth(node.left), depth(node.right))

# THE LIMIT that catches people: 1000 frames by default
print(sys.getrecursionlimit())            # 1000

# Raising it is a band-aid: the C stack is still finite and you get a segfault
# rather than a clean exception if you go too far.
sys.setrecursionlimit(10_000)             # fine; 10^6 is not

# RecursionError IS catchable, unlike .NET's StackOverflowException
try:
    depth(very_deep_tree)
except RecursionError:
    pass

# So for anything over ~10^4 deep, go iterative
def depth_iterative(root) -> int:
    if root is None:
        return 0
    stack = [(root, 1)]
    best = 0
    while stack:
        node, d = stack.pop()
        best = max(best, d)
        if node.left:  stack.append((node.left,  d + 1))
        if node.right: stack.append((node.right, d + 1))
    return best

# Python does NOT do tail-call optimisation, deliberately and permanently.
# Guido's position: it makes tracebacks useless. Do not expect it.

# MEMOISATION is one decorator - the single biggest "Python is shorter" win
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)      # O(2^n)

@cache                                    # 3.9+; lru_cache(maxsize=None) before
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)      # O(n)

print(fib.cache_info())                   # hits, misses, size - useful to quote

# Caution: @cache on a method keeps `self` alive forever (it is part of the key).
# For an interview that is fine; in production it is a memory leak.

# Generators are recursion's lazy cousin - yield from flattens nested structure
def flatten(items):
    for item in items:
        if isinstance(item, list):
            yield from flatten(item)      # still costs a frame per level
        else:
            yield item
Interview angle

Two things to say unprompted when you write a recursive solution: the space is O(h) on the call stack, and whether the depth is bounded by the input. "This recurses to the depth of the tree, which is O(n) in the worst case — in Python I would convert it to an explicit stack above about 10⁴ nodes" is a strong sentence because it covers complexity, the failure mode and the language difference in one breath. Also know that .NET's StackOverflowException cannot be caught, so the process dies — which is why the iterative version is not just a style preference.

Practice
  • Convert a recursive tree traversal to an iterative one with an explicit stack, including post-order.
  • Find the actual recursion depth your Python hits before RecursionError.
  • Memoise a naive Fibonacci and watch O(2ⁿ) become O(n).

The other strong signal is the constraint. n ≤ 20 usually means exponential is expected (backtracking or bitmask DP); n ≤ 10³ allows O(n²); n ≤ 10⁵ wants O(n log n); n ≤ 10⁷ wants O(n) and probably no sorting.

// "Longest substring without repeating characters"
// "Longest subarray with at most k distinct"
// "Minimum window containing all of t"
// "Maximum sum of a subarray of size k"
//   -> all sliding window. The window grows on the right, shrinks on the left
//      when the invariant breaks.

static int LongestUnique(string s)
{
    var last = new Dictionary<char, int>();
    int best = 0, start = 0;

    for (int end = 0; end < s.Length; end++)
    {
        if (last.TryGetValue(s[end], out int prev) && prev >= start)
            start = prev + 1;              // shrink past the duplicate
        last[s[end]] = end;
        best = Math.Max(best, end - start + 1);
    }
    return best;
}

# Sliding window, the variable-size template that covers most of them
def longest_unique(s: str) -> int:
    last: dict[str, int] = {}
    best = start = 0
    for end, ch in enumerate(s):
        if ch in last and last[ch] >= start:
            start = last[ch] + 1          # shrink past the duplicate
        last[ch] = end
        best = max(best, end - start + 1)
    return best

# Multi-source BFS, which covers "rotting oranges", "walls and gates",
# "01 matrix" and more - the only change is what goes in the queue first
from collections import deque

def multi_source_bfs(grid, sources):
    q = deque((r, c, 0) for r, c in sources)
    seen = set(sources)
    while q:
        r, c, d = q.popleft()
        for dr, dc in ((1,0), (-1,0), (0,1), (0,-1)):
            nr, nc = r + dr, c + dc
            if 0 <= nr < len(grid) and 0 <= nc < len(grid[0]) and (nr, nc) not in seen:
                seen.add((nr, nc))
                q.append((nr, nc, d + 1))

Interview angle

The pattern-recognition step is what you are being timed on; the coding is usually the easy part. Train the mapping rather than the solutions, and say the recognition out loud — "this is asking for a contiguous subarray with a constraint, so it is a sliding window" tells the interviewer you have classified the problem, which is most of the signal. Reading the constraints for the intended complexity is a second, cheaper signal: if n ≤ 20, they are telling you exponential is acceptable, and spending ten minutes hunting for a polynomial solution is wasted time.
