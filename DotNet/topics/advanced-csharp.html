Reflection, Type, Activator and attributes

Reflection reads an assembly's metadata at run time: types, members, attributes — and lets you construct and invoke without knowing the type at compile time. It powers DI containers, serialisers, ORMs and test runners.

The thing to lead with is the cost, because that is where the follow-up goes. A reflective call is roughly two orders of magnitude slower than a direct one, it defeats inlining, and it is invisible to the trimmer — which is why reflection-heavy code breaks under Native AOT. The mitigation is to do the reflection once and cache a compiled delegate.

// Inspecting
Type t = typeof(Order);
Type t2 = order.GetType();                       // the RUNTIME type, not the static one
Type t3 = Type.GetType("Shop.Domain.Order, Shop.Domain")!;   // by name

var props   = t.GetProperties(BindingFlags.Public | BindingFlags.Instance);
var privates = t.GetFields(BindingFlags.NonPublic | BindingFlags.Instance);
var method  = t.GetMethod(nameof(Order.Pay))!;
bool isList = t.IsGenericType && t.GetGenericTypeDefinition() == typeof(List<>);

// Constructing and invoking

// THE PERFORMANCE FIX: reflect once, cache a delegate, call it forever after
public static class FastAccessor<T>
{
    private static readonly Dictionary<string, Func<T, object?>> _getters = Build();

    private static Dictionary<string, Func<T, object?>> Build() =>
        typeof(T).GetProperties()
            .Where(p => p.CanRead)
            .ToDictionary(p => p.Name, p =>
            {
                // Build:  (T x) => (object)x.Prop
                var param = Expression.Parameter(typeof(T), "x");
                var body  = Expression.Convert(Expression.Property(param, p), typeof(object));
                return Expression.Lambda<Func<T, object?>>(body, param).Compile();
            });

    public static object? Get(T instance, string name) => _getters[name](instance);
}
// ~100x faster than PropertyInfo.GetValue per call. The compile happens once.
// (And Expression.Compile is itself unavailable under Native AOT - a source
//  generator is the AOT-safe version of this trick.)

// CallerArgumentExpression: compile-time metadata, no reflection needed
public static void Require(bool condition,
    [CallerArgumentExpression(nameof(condition))] string? expr = null)
{
    if (!condition) throw new ArgumentException($"failed: {expr}");
}
Require(order.Total > Money.Zero("USD"));   // message names the expression

Expect "when would you use reflection, and what does it cost?" Cover both halves: it is how DI containers, serialisers and ORMs work, and it costs roughly 100x a direct call, blocks inlining, and is invisible to the trimmer so it breaks under trimming and Native AOT. Expression trees and how LINQ providers use them

An expression tree is code as data: Expression<Func<Order, bool>> is not a compiled method, it is an object graph describing one. That distinction is the entire answer to the most common question in this area — why does IQueryable take Expression<Func<...>> while IEnumerable takes Func<...>?

Because EF Core cannot run your lambda; it has to read it and translate it into SQL. IEnumerable.Where gets a delegate and calls it per item in memory; IQueryable.Where gets a tree, walks it, and emits a WHERE clause. Accidentally converting one to the other — by calling .AsEnumerable(), or passing a Func — is the classic bug where filtering silently moves from the database to your process.

// The same lambda, two completely different things
Func<Order, bool>             compiled = o => o.Total > 100;   // a METHOD
Expression<Func<Order, bool>> tree     = o => o.Total > 100;   // a TREE describing it

bool result = compiled(order);            // just runs
BinaryExpression body = (BinaryExpression)tree.Body;
Console.WriteLine(body.NodeType);         // GreaterThan
Console.WriteLine(body.Left);             // o.Total
Console.WriteLine(body.Right);            // 100
var runnable = tree.Compile();            // emit IL at run time, then run it

// THIS is why IQueryable differs from IEnumerable
IQueryable<Order> q = db.Orders;
var fromDb = q.Where(o => o.Total > 100);          // tree -> WHERE total > 100 in SQL

IEnumerable<Order> e = db.Orders.AsEnumerable();   // <- everything is now loaded
var inMemory = e.Where(o => o.Total > 100);        // delegate, filtered in YOUR process

// The silent version of the same bug: a Func cannot be translated
Func<Order, bool> predicate = o => o.Total > 100;
var oops = db.Orders.Where(predicate);             // binds to Enumerable.Where:
                                                   // the whole table comes back
// Fix: keep it an Expression all the way down
Expression<Func<Order, bool>> good = o => o.Total > 100;
var fixedQuery = db.Orders.Where(good);            // translated

// BUILDING a tree by hand - how dynamic filtering is implemented
public static Expression<Func<T, bool>> PropertyEquals<T>(string property, object value)
{
    var param = Expression.Parameter(typeof(T), "x");         // x
    var member = Expression.PropertyOrField(param, property);  // x.Prop
    var constant = Expression.Constant(value, member.Type);    // value
    var body = Expression.Equal(member, constant);             // x.Prop == value
    return Expression.Lambda<Func<T, bool>>(body, param);      // x => x.Prop == value
}

var filter = PropertyEquals<Order>("Status", "paid");
var paid = await db.Orders.Where(filter).ToListAsync(ct);      // real SQL

// COMPOSING predicates, which is what you actually want in a search endpoint
public static Expression<Func<T, bool>> And<T>(
    Expression<Func<T, bool>> a, Expression<Func<T, bool>> b)
{
    var param = Expression.Parameter(typeof(T));
    var body = Expression.AndAlso(
        new Rebind(a.Parameters[0], param).Visit(a.Body)!,
        new Rebind(b.Parameters[0], param).Visit(b.Body)!);
    return Expression.Lambda<Func<T, bool>>(body, param);
}

private sealed class Rebind(ParameterExpression from, ParameterExpression to)
    : ExpressionVisitor
{
    protected override Expression VisitParameter(ParameterExpression node)
        => node == from ? to : base.VisitParameter(node);
}

// In practice: just compose with Where, which EF already ANDs for you

if (from is not null)    query = query.Where(o => o.PlacedAt >= from);

Interview angle

"Why does IQueryable take an Expression<Func<T,bool>> and IEnumerable take a Func<T,bool>?" is one of the best LINQ questions there is, and expression trees are the whole answer: the provider must read the code, not run it. Follow it with the practical consequence — assigning a predicate to a Func variable, or calling AsEnumerable() early, silently moves the filter from SQL into your process and loads the table. Mention that Expression.Compile emits IL at run time and is therefore both slow and AOT-incompatible.

Source generators

A source generator is a compiler plug-in that adds C# during compilation. It is the modern answer to everything people used reflection or runtime emit for: the work happens at build time, so the output is ordinary code — fast, debuggable, trimmable and AOT-safe.

You already use several: System.Text.Json's JsonSerializerContext, [LoggerMessage], [GeneratedRegex], [LibraryImport], and the record/primary-constructor members the compiler writes for you.

Write incremental generators (IIncrementalGenerator), not the obsolete ISourceGenerator — the incremental pipeline caches, so it does not re-run on every keystroke and tank IDE responsiveness. Generators can only add code, never modify existing code, which is why everything they touch must be partial.

// --- Using the ones that ship with .NET ---

// JSON: reflection-free, trim-safe, ~2x faster serialisation
[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(Order))]
[JsonSerializable(typeof(List<Order>))]
internal partial class AppJsonContext : JsonSerializerContext { }

var json = JsonSerializer.Serialize(order, AppJsonContext.Default.Order);

// Logging: no boxing, no allocation when the level is off, checked at compile time
public partial class OrderService
{
    [LoggerMessage(Level = LogLevel.Information, Message = "Order {orderId} placed by {customer}")]
    private partial void LogPlaced(string orderId, string customer);
}

// Regex: the pattern is compiled to C# at BUILD time, not at startup
public partial class Validators
{
    [GeneratedRegex(@"^[\w\.-]+@[\w\.-]+\.\w{2,}$", RegexOptions.IgnoreCase)]
    public static partial Regex Email();
}

// --- Writing one: an incremental generator ---
[Generator]
public class ToStringGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        // 1. a cheap syntactic predicate runs on EVERY keystroke - keep it trivial
        var classes = context.SyntaxProvider.ForAttributeWithMetadataName(
            "Shop.GenerateToStringAttribute",
            predicate: static (node, _) => node is ClassDeclarationSyntax,
            // 2. the semantic transform runs only for matches, and is CACHED
            transform: static (ctx, _) =>
            {
                var symbol = (INamedTypeSymbol)ctx.TargetSymbol;
                var props = symbol.GetMembers().OfType<IPropertySymbol>()
                    .Where(p => p.DeclaredAccessibility == Accessibility.Public)
                    .Select(p => p.Name)
                    .ToImmutableArray();
                // Return a VALUE-EQUATABLE model, never a Symbol or a Compilation,
                // or caching breaks and the generator re-runs constantly.
                return (Namespace: symbol.ContainingNamespace.ToDisplayString(),
                        Name: symbol.Name, Props: props);
            });

        // 3. emit
        context.RegisterSourceOutput(classes, static (spc, model) =>
        {
            var body = string.Join(" + \", \" + ",
                model.Props.Select(p => $"\"{p}=\" + {p}"));

            spc.AddSource($"{model.Name}.ToString.g.cs", $$"""
                // <auto-generated/>
                #nullable enable
                namespace {{model.Namespace}};

                partial class {{model.Name}}
                {
                    public override string ToString() => $"{{model.Name}} {{{{" + {{body}} + "}}}}";
                }
                """);
        });
    }
}

# 1. The dataclass decorator IS a code generator: it builds __init__, __repr__
#    and __eq__ as source and execs them.
from dataclasses import dataclass

@dataclass
class Order:
    id: str
    total: Decimal
# dataclasses.py literally does:
#     txt = f"def __init__(self, {args}): ..."
#     exec(txt, globals, locals)

# 2. Doing it yourself - the same technique
def generate_to_string(cls):
    props = [f.name for f in dataclasses.fields(cls)]
    body = " + ', ' + ".join(f'f"{p}={{self.{p}}}"' for p in props)
    src = f"def __str__(self):\n    return f'{cls.__name__} {{{{' + {body} + '}}}}'"
    ns: dict = {}
    exec(src, {}, ns)
    cls.__str__ = ns["__str__"]
    return cls

@generate_to_string
@dataclass
class Order:
    id: str
    total: Decimal

# 3. The build-time equivalents, when runtime generation costs too much:
#      mypyc      - compile annotated Python to a C extension
#      Cython     - .pyx compiled ahead of time
#      pydantic 2 - the validation core is compiled Rust, not generated Python
#
# Note what .NET gets that Python does not: the generated code is checked by the
# compiler, is steppable in the debugger, and is visible to the trimmer. Python's
# exec'd code is invisible to every static tool you own.
Interview angle

A good "what is new" question. Define it as a compiler plug-in that adds code at build time, then give the why: it replaces runtime reflection and IL emit with ordinary compiled code, which is faster, debuggable, trim-safe and AOT-compatible. dynamic and the DLR

dynamic turns off compile-time binding for an expression: the compiler emits a call site that resolves the member at run time through the Dynamic Language Runtime. It is not object (which binds at compile time to object's members) and it is not var (which is full static typing with inference).

Legitimate uses are narrow: COM interop, genuinely dynamic JSON where the shape is unknown, and interop with dynamic languages. Everywhere else it costs you IntelliSense, refactoring, compile-time errors and about 10–20x the call overhead — and it fails at run time with a RuntimeBinderException that a compiler would have caught.

// The three that get confused
var    a = GetOrder();     // STATIC. The compiler infers Order. Full checking.
object b = GetOrder();     // STATIC, as object. b.Total does not compile.
dynamic c = GetOrder();    // DEFERRED. c.Total compiles; it binds at run time.

c.Total;                   // fine
c.Toatl;                   // ALSO compiles. RuntimeBinderException when it runs.

// ExpandoObject: add and remove members at run time
dynamic expando = new ExpandoObject();
expando.Name = "Ada";
expando.Greet = (Func<string>)(() => "hello");
((IDictionary<string, object>)expando).Remove("Name");
foreach (var kv in (IDictionary<string, object>)expando) { }

// DynamicObject: define what member access MEANS for your type
public class CaseInsensitiveBag : DynamicObject
{
    private readonly Dictionary<string, object?> _data =
        new(StringComparer.OrdinalIgnoreCase);

    public override bool TryGetMember(GetMemberBinder binder, out object? result)
        => _data.TryGetValue(binder.Name, out result) || Ok(out result);

    public override bool TrySetMember(SetMemberBinder binder, object? value)
    {
        _data[binder.Name] = value;
        return true;
    }

    private static bool Ok(out object? r) { r = null; return true; }  // null, not throw
}

dynamic bag = new CaseInsensitiveBag();
bag.Name = "Ada";
Console.WriteLine(bag.NAME);          // "Ada"

// The real-world use: JSON whose shape you do not know
dynamic payload = JsonNode.Parse(body)!;
string channel = payload["metadata"]!["channel"]!.GetValue<string>();

// ...and the modern alternative, which is better in almost every case
var node = JsonNode.Parse(body);
var channel2 = node?["metadata"]?["channel"]?.GetValue<string>();   // null-safe, static

// COM interop, where dynamic genuinely earns its place
dynamic excel = Activator.CreateInstance(Type.GetTypeFromProgID("Excel.Application")!)!;
excel.Visible = true;
excel.Workbooks.Add();                // no interop assembly, no casting every call

// Cost: each call site caches its binding, so a repeated call is ~10x a direct
// call rather than ~100x - but the FIRST call pays full binder cost, and you
// have given up every compile-time guarantee to get there.

// One genuinely clever use: dynamic restores runtime dispatch on overloads
void Handle(Circle c) { } void Handle(Square s) { } void Handle(Shape s) { }
Shape shape = GetShape();
Handle(shape);            // always binds to Handle(Shape) - static overload resolution
Handle((dynamic)shape);   // binds to the RUNTIME type: double dispatch, no visitor

# DynamicObject: __getattr__ / __setattr__ define what member access means
class CaseInsensitiveBag:
    def __init__(self) -> None:
        object.__setattr__(self, "_data", {})

    def __getattr__(self, name: str):            # called only when normal lookup fails
        return self._data.get(name.lower())

    def __setattr__(self, name: str, value) -> None:
        self._data[name.lower()] = value

bag.Name = "Ada"

Interview angle

The reliable question is "dynamic vs var vs object", and the distinction to make crisply is that var is static typing with inference, object is static typing at the base type, and only dynamic defers binding to run time. Then give a position: narrow legitimate uses (COM, genuinely unknown JSON shapes), and otherwise it trades every compile-time guarantee for convenience you can get from JsonNode or a typed model. The (dynamic) double-dispatch trick is a nice thing to know for a visitor-pattern discussion.

Delegates, closures and captured variables

A lambda that references a local variable does not copy it — the compiler hoists the variable into a generated class and both the enclosing method and the lambda use the field. That is why a closure sees later changes to the variable, and why the loop-variable question has the answer it does.

The classic puzzle: in C# 5+ foreach declares a fresh variable per iteration, so capturing it in a loop works as people expect. A C-style for loop has one variable for the whole loop, so every lambda captures the same one and they all see the final value. Knowing that the foreach behaviour changed in C# 5 is the detail that marks real experience.

// The puzzle, both halves
var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i));         // ONE variable i, captured 3 times
actions.ForEach(a => a());                       // 333

var actions2 = new List<Action>();
foreach (var x in Enumerable.Range(0, 3))
    actions2.Add(() => Console.Write(x));        // a NEW x per iteration (C# 5+)
actions2.ForEach(a => a());                      // 012

// The fix for the `for` loop: introduce a per-iteration variable yourself
for (int i = 0; i < 3; i++)
{
    int copy = i;
    actions.Add(() => Console.Write(copy));      // 012
}

// What the compiler actually generates for the first case:
//   private sealed class <>c__DisplayClass0_0 { public int i; }
//   var cls = new <>c__DisplayClass0_0();
//   for (cls.i = 0; cls.i < 3; cls.i++)
//       actions.Add(new Action(cls.<M>b__0));   // all three share `cls`

// Closures allocate. A lambda capturing nothing is cached as a static singleton;
// one that captures gets a display class per entry to the scope.
list.Where(x => x > 0);          // captures nothing: cached, zero allocation
list.Where(x => x > min);        // captures min: allocates a display class
list.Where(static x => x > 0);   // `static` lambda: compile ERROR if it captures

// The allocation trap in a hot loop - capture via state instead
foreach (var item in items)
    queue.Enqueue(() => Process(item));          // one display class per item

// Overloads that take state avoid the capture entirely
Task.Run(() => Process(item));                           // captures
ThreadPool.QueueUserWorkItem(static s => Process(s), item, preferLocal: true);  // no

// Capture in async is the same mechanism and the same leak risk: a long-lived
// delegate keeps everything it captured alive.
public class Subscriber
{
    private readonly byte[] _big = new byte[10_000_000];

    public void Subscribe(EventBus bus)
        => bus.OnMessage += m => Console.WriteLine(m);
    // This lambda captures `this` (it is an instance method's lambda), so the
    // whole Subscriber - including _big - lives as long as the bus does.
    // Unsubscribing requires the same delegate instance, which a lambda makes
    // awkward: store it in a field if you intend to detach.
}

// Delegates: multicast, and what that means for return values and exceptions
Action chain = () => Console.Write("a");
chain += () => Console.Write("b");
chain();                              // "ab" - invoked in order

Func<int> f = () => 1;
f += () => 2;
Console.WriteLine(f());               // 2 - only the LAST return value survives

// An exception in one handler stops the rest. Invoke individually if that matters:
foreach (var d in chain.GetInvocationList().Cast<Action>())
    try { d(); } catch (Exception ex) { log.LogError(ex, "handler failed"); }

Interview angle

The loop-capture question gets asked constantly. Answer it by explaining the mechanism — the compiler hoists the variable into a generated display class shared by every lambda — and then give the for versus foreach difference and note that foreach only behaves this way since C# 5. Strong follow-ups to volunteer: closures allocate (a capture-free lambda is cached, a capturing one is not, and static lambdas let the compiler enforce it), and a long-lived delegate keeps everything it captured alive, which is a common managed memory leak.

  • Find a lambda in a hot path that captures, and remove the allocation with a static lambda plus a state parameter.
  • Subscribe to a long-lived event with a lambda capturing this and watch the object survive in a heap dump.

unsafe, pointers, fixed and P/Invoke

unsafe lets you use pointers, which means you take over from the GC and the bounds checker. It is rarely the right answer any more — Span<T> gives most of the performance with none of the risk — but it remains necessary for interop and for a few genuinely hot paths.

The concept to be able to explain is pinning. The GC compacts the heap, which moves objects; a raw pointer into a managed object would dangle after a collection. fixed pins the object so the GC cannot move it for the duration of the block — and pinning for too long fragments the heap, which is why you pin narrowly.

For P/Invoke, use [LibraryImport] (source-generated marshalling, AOT-safe) over [DllImport] (runtime-generated stubs) in new code.

// csproj: <AllowUnsafeBlocks>true</AllowUnsafeBlocks>

// PINNING: the GC moves objects; a pointer into one must be pinned first
unsafe static int SumUnsafe(int[] data)
{
    fixed (int* p = data)                  // pinned for this block only
    {
        int sum = 0;
        for (int i = 0; i < data.Length; i++)
            sum += p[i];                   // no bounds check, no GC move
        return sum;
    }
}
// Pin narrowly. A long-lived pinned object fragments the heap because the GC
// must compact around it. GCHandle.Alloc(obj, GCHandleType.Pinned) is the
// explicit, long-lived form - and the one that causes the problem.

// Span<T> gets you most of this with none of the risk. Prefer it.
static int SumSafe(ReadOnlySpan<int> data)
{
    int sum = 0;
    foreach (var x in data) sum += x;      // the JIT elides the bounds check here
    return sum;
}

AssemblyLoadContext, plugins and unloading

.NET Framework had AppDomain for isolation and unloading. .NET Core removed it and replaced it with AssemblyLoadContext — which gives you isolation and collectible contexts, but no security boundary. That is the answer to "what replaced AppDomain", and the caveat matters: an AppDomain was a sandbox, an ALC is not.

A collectible ALC can be unloaded, which is how plugin hosts load and reload extensions without restarting. The thing that makes it hard in practice is that unloading happens only when every reference is gone — including a Type you cached, a delegate pointing into the assembly, or a static field somewhere holding one of its instances. A single stray reference leaks the whole context.

// A collectible context that resolves the plugin's own dependencies
public class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath)
        : base(name: Path.GetFileNameWithoutExtension(pluginPath), isCollectible: true)
        => _resolver = new AssemblyDependencyResolver(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        // Return null for shared contracts so they come from the DEFAULT context.
        // Otherwise the plugin loads its own copy of IPlugin and the host's
        // `is IPlugin` check fails against a type with the same name.
        if (name.Name == "Shop.Plugins.Abstractions") return null;

        var path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }

    protected override IntPtr LoadUnmanagedDll(string name)
    {
        var path = _resolver.ResolveUnmanagedDllToPath(name);
        return path is null ? IntPtr.Zero : LoadUnmanagedDllFromPath(path);
    }
}

// Loading, using, unloading. Note [MethodImpl(NoInlining)] - without it the JIT
// may keep a local alive past its last use and the unload never completes.
[MethodImpl(MethodImplOptions.NoInlining)]
static WeakReference LoadAndRun(string path, out string result)
{
    var alc = new PluginLoadContext(path);
    var assembly = alc.LoadFromAssemblyPath(path);

    var type = assembly.GetTypes().First(t => typeof(IPlugin).IsAssignableFrom(t));
    var plugin = (IPlugin)Activator.CreateInstance(type)!;
    result = plugin.Run();

    alc.Unload();                       // REQUESTS unload; does not force it
    return new WeakReference(alc);      // everything above is now out of scope
}

{

    GC.WaitForPendingFinalizers();      // unload completes across several GCs
}

Equals, GetHashCode and the comparison contracts

Getting equality wrong is a silent correctness bug, not a crash: an object goes into a Dictionary or HashSet and can never be found again. The contract is short and is asked almost verbatim.

  • If a.Equals(b) then a.GetHashCode() == b.GetHashCode(). Always. The reverse need not hold — a hash collision is legal.
  • Equality must be reflexive, symmetric, transitive and consistent over time.
  • Never hash on mutable state. Mutate a key after inserting it and the entry lands in the wrong bucket; the object is in the dictionary and ContainsKey returns false.
  • Override Equals(object), implement IEquatable<T> (avoids boxing), override GetHashCode, and if you define == define != too.

Records do all of this for you, which is why "use a record" is the right first answer for a value type.

// The full contract, written by hand
public sealed class Money : IEquatable<Money>, IComparable<Money>
{
    public decimal Amount { get; }          // IMMUTABLE - the hash stays valid
    public string Currency { get; }

    public Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    public bool Equals(Money? other)        // IEquatable<T>: no boxing
        => other is not null
           && Amount == other.Amount
           && Currency == other.Currency;

    public override bool Equals(object? obj) => Equals(obj as Money);

    public override int GetHashCode() => HashCode.Combine(Amount, Currency);
    //   Use HashCode.Combine. Hand-rolled `17 * 31 + x` is fine but Combine is
    //   randomised per process, which defeats hash-flooding attacks.

    public int CompareTo(Money? other)
        => other is null ? 1
         : Currency != other.Currency
             ? throw new InvalidOperationException("different currencies")
             : Amount.CompareTo(other.Amount);

    public static bool operator ==(Money? a, Money? b) => a?.Equals(b) ?? b is null;
    public static bool operator !=(Money? a, Money? b) => !(a == b);
    public static bool operator < (Money a, Money b) => a.CompareTo(b) <  0;
    public static bool operator > (Money a, Money b) => a.CompareTo(b) >  0;
}

// ...or just use a record, which generates all of it correctly

from dataclasses import dataclass
from decimal import Decimal
from functools import total_ordering

@dataclass(frozen=True)          # frozen => __hash__ generated, immutable
class Money:
    amount: Decimal
    currency: str

    def __lt__(self, other: "Money") -> bool:
        if self.currency != other.currency:
            raise ValueError("different currencies")
        return self.amount < other.amount

# By hand
@total_ordering                  # fills in <=, >, >= from __eq__ and __lt__
class Money:
    __slots__ = ("_amount", "_currency")

    def __init__(self, amount: Decimal, currency: str) -> None:
        object.__setattr__(self, "_amount", amount)
        object.__setattr__(self, "_currency", currency)

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Money):
            return NotImplemented            # let the other side try
        return (self._amount, self._currency) == (other._amount, other._currency)

    def __hash__(self) -> int:
        return hash((self._amount, self._currency))   # HashCode.Combine

    def __lt__(self, other: "Money") -> bool:
        return self._amount < other._amount

sorted(items, key=functools.cmp_to_key(my_comparison))  # Comparer.Create
Interview angle

"What is the contract between Equals and GetHashCode?" is a staple, and the complete answer has three parts: equal objects must have equal hashes, unequal hashes guarantee unequal objects while equal hashes guarantee nothing, and the hash must not change while the object is in a hash-based collection. Have the mutable-key bug ready as the concrete consequence — the object is in the HashSet and Contains returns false. Good extras: the default struct Equals uses reflection and boxes, so override it; and string.GetHashCode() is randomised per process, so persisting it is a bug.
