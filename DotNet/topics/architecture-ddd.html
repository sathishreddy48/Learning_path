Clean Architecture & Domain-Driven Design

Design Patterns & SOLID is about the shape of a class; this is about the shape of a solution. It is the hardest area to answer well because the vocabulary is easy and the judgement is not — anyone can define an aggregate, and the interview question is always "where would you draw the boundary here, and what did that cost you". Every section ends with the argument against, because an architecture answer without trade-offs reads as something you have read rather than something you have shipped.

Layered, Onion, Hexagonal and Clean — one idea, four names

These are the same idea drawn differently, and saying so is a better answer than describing any one of them. The idea: dependencies point inward, toward the domain, and the domain depends on nothing. Everything else — the database, HTTP, the message bus, the clock — is a detail that plugs in from outside.

The mechanism is dependency inversion. The domain defines the interface it needs (IOrderRepository); infrastructure implements it; composition at startup wires them together. That is the whole trick, and it is why the domain project has no package references.

Classic layered architecture differs on one point only: its dependencies point down, so the business layer references the data layer and your domain ends up knowing about EF Core. Onion, Hexagonal (ports and adapters) and Clean all invert that last arrow.

Interview angle

The best answer collapses the four names into one rule and then gets concrete: "dependencies point inward, the domain references nothing, infrastructure implements interfaces the domain declares". Expect the pushback — "isn't that a lot of ceremony for a CRUD app?" — and agree where it is true: for a service that is mostly mapping HTTP to SQL, the layers are overhead and a vertical slice is better. The detail that lands: an architecture test, because without one the dependency rule is a convention that survives about two sprints.

Practice
  • Add an architecture test asserting your domain project has no infrastructure dependency; see whether it passes today.
  • Find an IQueryable leaking out of a repository and work out what it lets callers do.
  • Write down what would have to change to swap EF Core for Dapper, and check whether the answer is "one project".

Entities, value objects and invariants

The distinction is identity. An entity has one and is the same thing over time even as its data changes — two orders with identical contents are different orders. A value object has no identity and is defined entirely by its values — two Money(10, "USD") are interchangeable. Value objects are immutable, compared by value, and are where you put validation so an invalid value cannot be constructed at all.

The point of both is the invariant: a rule that must always hold. An anaemic model with public setters cannot hold an invariant, because any caller can break it between two valid states. The fix is a private setter and a method that expresses the operation.

// VALUE OBJECT: no identity, immutable, validated at construction, compared by value
public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (currency is not { Length: 3 })
            throw new ArgumentException("ISO 4217 code required", nameof(currency));
        (Amount, Currency) = (amount, currency.ToUpperInvariant());
    }

    // Operations return new instances; the rule lives here, not in a service
    public static Money operator +(Money a, Money b) =>
        a.Currency == b.Currency
            ? new(a.Amount + b.Amount, a.Currency)
            : throw new InvalidOperationException("cannot add different currencies");

    public static Money Zero(string currency) => new(0, currency);
}

// A strongly-typed id is a value object too, and it removes a whole class of bug
public readonly record struct OrderId(Guid Value)
{
    public static OrderId New() => new(Guid.NewGuid());
    public override string ToString() => Value.ToString();
}
// void Ship(OrderId order, CustomerId customer)  <- cannot transpose the arguments

// ENTITY: has identity, protects its invariants, exposes behaviour not setters
public class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderId Id { get; private init; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;     // expose read-only
    public Money Total => _lines.Aggregate(Money.Zero("USD"), (t, l) => t + l.Subtotal);

    private Order() { }                                  // EF needs one; keep it private

    public static Order Place(CustomerId customer, IEnumerable<OrderLine> lines)
    {
        var list = lines.ToList();
        if (list.Count == 0) throw new DomainException("an order needs at least one line");

        var order = new Order { Id = OrderId.New(), CustomerId = customer,
                                Status = OrderStatus.Pending };
        order._lines.AddRange(list);
        return order;
    }

    // Behaviour, with the rule attached to it
    public void AddLine(Sku sku, int quantity, Money unitPrice)
    {
        if (Status != OrderStatus.Pending)
            throw new DomainException("cannot change a submitted order");
        if (quantity <= 0)
            throw new DomainException("quantity must be positive");

        var existing = _lines.FirstOrDefault(l => l.Sku == sku);
        if (existing is not null) existing.Increase(quantity);
        else _lines.Add(new OrderLine(sku, quantity, unitPrice));
    }

    public void Pay()
    {
        if (Status != OrderStatus.Pending) throw new DomainException("already paid");
        if (_lines.Count == 0) throw new DomainException("nothing to pay for");
        Status = OrderStatus.Paid;
    }
}

// from mutating the object without them. That is the actual argument.
from dataclasses import dataclass, field
from decimal import Decimal
from typing import NewType
import uuid

# VALUE OBJECT: frozen dataclass, validated in __post_init__
@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise ValueError("amount must be non-negative")
        if len(self.currency) != 3:
            raise ValueError("ISO 4217 code required")
        object.__setattr__(self, "currency", self.currency.upper())   # frozen workaround

    def __add__(self, other: "Money") -> "Money":
        if self.currency != other.currency:
            raise ValueError("cannot add different currencies")
        return Money(self.amount + other.amount, self.currency)

    @staticmethod
    def zero(currency: str) -> "Money":
        return Money(Decimal(0), currency)

# Strongly-typed ids: NewType is checked statically, free at runtime
OrderId    = NewType("OrderId", uuid.UUID)
CustomerId = NewType("CustomerId", uuid.UUID)
# def ship(order: OrderId, customer: CustomerId) -> None: ...
#   ship(customer_id, order_id)   # mypy error, even though both are UUIDs

# ENTITY: identity, private state by convention, behaviour not setters
class Order:
    def __init__(self, id: OrderId, customer: CustomerId) -> None:
        self._id = id
        self._customer = customer
        self._status = "pending"
        self._lines: list["OrderLine"] = []

    @property
    def id(self) -> OrderId: return self._id

    @property
    def lines(self) -> tuple["OrderLine", ...]:
        return tuple(self._lines)                  # read-only view

    @property
    def total(self) -> Money:
        return sum((l.subtotal for l in self._lines), Money.zero("USD"))

    @classmethod
    def place(cls, customer: CustomerId, lines: list["OrderLine"]) -> "Order":
        if not lines:
            raise DomainError("an order needs at least one line")
        order = cls(OrderId(uuid.uuid4()), customer)
        order._lines.extend(lines)
        return order

    def add_line(self, sku: str, quantity: int, unit_price: Money) -> None:
        if self._status != "pending":
            raise DomainError("cannot change a submitted order")
        if quantity <= 0:
            raise DomainError("quantity must be positive")
        for line in self._lines:
            if line.sku == sku:
                line.increase(quantity)
                return
        self._lines.append(OrderLine(sku, quantity, unit_price))

    def pay(self) -> None:
        if self._status != "pending":
            raise DomainError("already paid")
        self._status = "paid"

Interview angle

"What is the difference between an entity and a value object?" is the definitional question; identity is the one-word answer. The one that actually probes understanding is "what is an anaemic domain model and why is it a problem?" — public setters mean the invariant lives outside the object, so it holds only as long as every caller remembers it, and nothing in the type system enforces that. Have a concrete invariant ready (an order cannot be modified after payment) and show the method that owns it.

Practice
  • Take a class with public setters and move one real rule into a method with a private setter.
  • Build a Money value object that refuses to add two currencies, and write the test.
  • Introduce a strongly-typed id and find the transposed-arguments bug it would have caught.

Aggregates and aggregate roots

An aggregate is a cluster of objects treated as one unit for data changes, with one entity as its root. Everything outside holds a reference only to the root, and the root enforces the rules for everything inside it. The aggregate is also the transactional boundary: one aggregate, one transaction.

Four rules that answer most aggregate questions: reference other aggregates by id, never by object; one transaction changes one aggregate; keep aggregates small — a big one is a concurrency bottleneck and a loading cost on every operation; use eventual consistency between aggregates, through domain events.

The classic mistake is making the aggregate too big — Customer containing every Order containing every OrderLine — so placing one order loads and locks the customer's entire history.

// The aggregate root is the ONLY entry point. OrderLine has no public constructor
// reachable from outside and no repository of its own.
public class Order : AggregateRoot<OrderId>
{
    private readonly List<OrderLine> _lines = [];

    public CustomerId CustomerId { get; private init; }     // <- an ID, not a Customer
    public IReadOnlyList<OrderLine> Lines => _lines;

    // Rules that span the whole aggregate live on the root
    public void AddLine(Sku sku, int quantity, Money price)
    {
        if (_lines.Count >= 100)
            throw new DomainException("an order cannot exceed 100 lines");
        if (Total + price * quantity > Money.Limit)
            throw new DomainException("order exceeds the value limit");

        _lines.Add(new OrderLine(sku, quantity, price));     // internal ctor
        Raise(new OrderLineAdded(Id, sku, quantity));
    }

    public void RemoveLine(Sku sku)
    {
        var line = _lines.FirstOrDefault(l => l.Sku == sku)
                   ?? throw new DomainException("no such line");
        if (_lines.Count == 1) throw new DomainException("an order needs a line");
        _lines.Remove(line);
    }
}

// Rule 1: reference other aggregates by ID. This is the one people break first.
public class Order
{
    public CustomerId CustomerId { get; private init; }     // GOOD
    // public Customer Customer { get; set; }               // BAD: now one transaction
    //   can change both, the object graph has no edge, and loading an order drags
    //   a customer (and whatever the customer drags) into memory.
}

// Rule 2: one transaction, one aggregate
public async Task Handle(PlaceOrder cmd, CancellationToken ct)
{
    var order = Order.Place(cmd.CustomerId, cmd.Lines);
    await _orders.Add(order, ct);
    await _uow.SaveChanges(ct);          // ONE aggregate saved here

    // NOT: also mutate the Customer's loyalty points in this transaction.
    // That is a second aggregate -> a domain event and a separate transaction.
}

// Rule 3: small. The size test is "what must be consistent IMMEDIATELY?"
//   Must an order's total match its lines at every instant?      yes -> same aggregate
//   Must a customer's lifetime value match instantly?            no  -> separate

// Rule 4: eventual consistency between aggregates, via events
public class OrderPlacedHandler(ICustomerRepository customers, IUnitOfWork uow)
    : INotificationHandler<OrderPlaced>
{
    public async Task Handle(OrderPlaced e, CancellationToken ct)
    {
        var customer = await customers.Get(e.CustomerId, ct);
        customer!.AddLoyaltyPoints(e.Total);         // a SECOND transaction
        await uow.SaveChanges(ct);
    }
}

// Concurrency: the version lives on the ROOT, so any change inside the aggregate
// conflicts with any other change to it. That is the point - and it is why a
// large aggregate becomes a contention hotspot.
public abstract class AggregateRoot<TId>
{
    public TId Id { get; protected init; } = default!;
    [Timestamp] public byte[] Version { get; private set; } = [];

    private readonly List<IDomainEvent> _events = [];
    public IReadOnlyList<IDomainEvent> DomainEvents => _events;
    protected void Raise(IDomainEvent e) => _events.Add(e);
    public void ClearEvents() => _events.Clear();
}
from dataclasses import dataclass, field
from typing import Generic, TypeVar
import uuid

TId = TypeVar("TId")

class AggregateRoot(Generic[TId]):
    def __init__(self, id: TId) -> None:
        self._id = id
        self._events: list["DomainEvent"] = []
        self.version = 0                       # optimistic concurrency, on the ROOT

    @property
    def id(self) -> TId: return self._id

    @property
    def domain_events(self) -> tuple: return tuple(self._events)

    def _raise(self, event: "DomainEvent") -> None: self._events.append(event)
    def clear_events(self) -> None: self._events.clear()


class Order(AggregateRoot[OrderId]):
    MAX_LINES = 100

    def __init__(self, id: OrderId, customer_id: CustomerId) -> None:
        super().__init__(id)
        self.customer_id = customer_id         # an ID, not a Customer object
        self._lines: list[OrderLine] = []

    @property
    def lines(self) -> tuple[OrderLine, ...]: return tuple(self._lines)

    def add_line(self, sku: str, quantity: int, price: Money) -> None:
        if len(self._lines) >= self.MAX_LINES:
            raise DomainError("an order cannot exceed 100 lines")
        self._lines.append(OrderLine(sku, quantity, price))
        self._raise(OrderLineAdded(self.id, sku, quantity))

    def remove_line(self, sku: str) -> None:
        if len(self._lines) == 1:
            raise DomainError("an order needs a line")
        self._lines = [l for l in self._lines if l.sku != sku]


# One transaction, one aggregate
async def place_order(cmd, orders: OrderRepository, uow) -> None:
    order = Order.place(cmd.customer_id, cmd.lines)
    await orders.add(order)
    await uow.commit()                         # ONE aggregate

# The second aggregate changes in its own transaction, driven by the event
async def on_order_placed(event: OrderPlaced, customers, uow) -> None:
    customer = await customers.get(event.customer_id)
    customer.add_loyalty_points(event.total)
    await uow.commit()                         # SECOND transaction
Interview angle

"How do you decide aggregate boundaries?" The answer that shows judgement is the consistency question: what must be true at every instant, versus what can be true a second later. Immediate consistency goes inside one aggregate; everything else becomes a domain event and a second transaction. Then name the cost of getting it wrong in both directions — too large means lock contention and loading a graph you do not need; too small means you cannot enforce a rule that genuinely spans the pieces, and it leaks into a service.

Practice
  • Take a model you know and justify each aggregate boundary with a specific invariant.
  • Find an aggregate holding a reference to another aggregate and replace it with an id; see what breaks.
  • Work out which operations in your system would contend on the same aggregate version under load.

Bounded contexts, ubiquitous language and context mapping

A bounded context is the scope within which a model and its language are consistent. The insight behind it is that "Customer" means different things in different parts of a business — to Sales it is a pipeline with a probability, to Billing an account with a payment method, to Support a person with a ticket history — and trying to build one Customer class that serves all three produces a type with forty properties of which each consumer uses six.

The decision is to let each context have its own model and translate at the boundary. This is also the most defensible way to draw service boundaries — see Microservices — and the anti-corruption layer is how you stop someone else's model leaking into yours.

// Three contexts, three Customers, and that is correct - not duplication to remove

// ANTI-CORRUPTION LAYER: translate at the boundary so their model does not
// become yours. This is where you absorb a legacy schema or a third-party API.
namespace Shop.Billing.Infrastructure;

public class LegacyBillingGateway(ILegacyErpClient erp) : IBillingGateway
{
    public async Task<Invoice> GetInvoice(InvoiceId id, CancellationToken ct)
    {
        // Their shape: flat, cryptic, nullable everywhere, amounts in cents as strings
        var dto = await erp.GetDoc(id.Value, "INV", ct);

        // Translate INTO our language. The ERP's vocabulary stops here.
        return new Invoice(
            Id:       id,
            Customer: new CustomerId(Guid.Parse(dto.CUST_REF!)),
            Amount:   new Money(decimal.Parse(dto.AMT_CENTS!) / 100m, dto.CURR ?? "USD"),
            Status:   dto.STAT switch
            {
                "O" => InvoiceStatus.Open,
                "P" => InvoiceStatus.Paid,
                "V" => InvoiceStatus.Void,
                _   => throw new IntegrationException($"unknown status {dto.STAT}"),
            });
    }
}

class LegacyBillingGateway(BillingGateway):

            customer=CustomerId(uuid.UUID(dto["CUST_REF"])),
            amount=Money(Decimal(dto["AMT_CENTS"]) / 100, dto.get("CURR", "USD")),
            status=status,
        )

Interview angle

A strong, non-obvious answer to "should these services share a Customer model?" is no — and the reason is that the same word means different things to different parts of the business, so one shared model becomes a type nobody can change without coordinating three teams. Mention the anti-corruption layer by name when integration comes up; "we wrapped the legacy ERP in an ACL so its vocabulary stopped at the boundary" is a sentence that reads as experience. Expect the pushback about duplication and have the answer ready: the duplication is three small models that change independently, which is cheaper than one model three teams must agree on.

Practice
  • Find a word in a system you know that means different things to two teams, and model both.
  • Write an anti-corruption layer over a third-party API and keep its DTOs out of your domain.
  • Draw the context map for a system you have worked on and label each relationship.

Domain events and integration events

A domain event is something that happened in the domain, named in the past tense, raised by an aggregate and handled inside the same process and usually the same transaction. An integration event is what you publish to other services, after the transaction commits.

Confusing the two causes the most common bug in this area: publishing to a message bus inside the transaction. If the transaction then rolls back you have told the world about something that did not happen; if you publish after commit without an outbox, a crash between the two loses the event. The transactional outbox — covered on Microservices — writes the event to a table in the same transaction and a separate process publishes it.

// DOMAIN EVENT: past tense, raised by the aggregate, carries the domain's language
public record OrderPlaced(OrderId OrderId, CustomerId CustomerId, Money Total)
    : IDomainEvent;

public class Order : AggregateRoot<OrderId>
{
    public static Order Place(CustomerId customer, IEnumerable<OrderLine> lines)
    {
        var order = new Order { /* ... */ };
        order.Raise(new OrderPlaced(order.Id, customer, order.Total));
        return order;                       // raised, not published - nothing has
    }                                       // happened until SaveChanges succeeds
}

// Dispatch at the transaction boundary, from the DbContext
public class AppDbContext(DbContextOptions options, IPublisher publisher)
    : DbContext(options)
{
    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        var aggregates = ChangeTracker.Entries<IHasDomainEvents>()
            .Where(e => e.Entity.DomainEvents.Count > 0)
            .Select(e => e.Entity)
            .ToList();

        var events = aggregates.SelectMany(a => a.DomainEvents).ToList();
        aggregates.ForEach(a => a.ClearEvents());      // clear BEFORE dispatch, or a
                                                       // handler that saves re-raises
        // Option A: dispatch BEFORE save - handlers join the same transaction,
        // so everything commits or nothing does. Handlers must not do external I/O.
        foreach (var e in events) await publisher.Publish(e, ct);

        var result = await base.SaveChangesAsync(ct);

        // Option B: dispatch AFTER save - handlers see committed state, but a
        // handler failure cannot roll back the write. Pick deliberately.
        return result;
    }
}

public class OutboxPublisher(IServiceScopeFactory scopes, IBus bus) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(1));
        while (await timer.WaitForNextTickAsync(ct))
        {
            using var scope = scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var batch = await db.OutboxMessages
                .Where(m => m.ProcessedAt == null)
                .OrderBy(m => m.OccurredAt).Take(100).ToListAsync(ct);

            foreach (var m in batch)
            {
                await bus.Publish(m.Type, m.Payload, ct);
                m.ProcessedAt = DateTime.UtcNow;
            }
            await db.SaveChangesAsync(ct);
        }
    }
}

Application services, use cases and the MediatR shape

The application layer orchestrates: load the aggregate, call a method on it, save, return. It holds no business rules — if a rule appears here it belongs on the entity. That is the whole test for whether something is in the right layer.

Most .NET teams express a use case as a command plus a handler, dispatched through MediatR, with cross-cutting concerns (validation, logging, transactions) as pipeline behaviours. The thing to be able to discuss is whether the indirection earns its keep: it buys you a uniform pipeline and small testable handlers, and it costs you the ability to find the handler from the call site.

// Cross-cutting concerns as pipeline behaviours - written once, applied to all
public class ValidationBehaviour<TReq, TRes>(IEnumerable<IValidator<TReq>> validators)
    : IPipelineBehavior<TReq, TRes> where TReq : notnull
{
    public async Task<TRes> Handle(TReq request,
        RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        var failures = validators
            .Select(v => v.Validate(new ValidationContext<TReq>(request)))
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Count > 0) throw new ValidationException(failures);
        return await next();
    }
}

public class TransactionBehaviour<TReq, TRes>(AppDbContext db)
    : IPipelineBehavior<TReq, TRes> where TReq : ICommand
{
    public async Task<TRes> Handle(TReq request,
        RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        if (db.Database.CurrentTransaction is not null) return await next();

        await using var tx = await db.Database.BeginTransactionAsync(ct);
        var response = await next();
        await tx.CommitAsync(ct);
        return response;
    }
}

import functools, logging

def validated(validator):
    def decorator(fn):
        @functools.wraps(fn)
        async def wrapper(self, cmd, *a, **kw):
            errors = validator(cmd)
            if errors:
                raise ValidationError(errors)
            return await fn(self, cmd, *a, **kw)
        return wrapper
    return decorator

def transactional(fn):
    @functools.wraps(fn)
    async def wrapper(self, cmd, *a, **kw):
        async with self._uow.transaction():
            return await fn(self, cmd, *a, **kw)
    return wrapper

CQRS: separate models, and how far to take it

CQRS separates the model you write through from the model you read through. The justification is that they have genuinely different needs: writes need invariants, aggregates and transactions; reads need joins, projections and shapes that match a screen. Forcing both through one model means either your reads load aggregates they do not need or your aggregates flatten to serve reads.

There are three levels and they are often conflated. Level 1: separate command and query code paths against one database — writes go through aggregates, reads use Dapper or projected LINQ straight to DTOs. This is cheap and usually enough. Level 2: separate read models (denormalised tables or views) in the same database. Level 3: a separate read store, updated asynchronously — maximum scale, eventual consistency, and a materially harder system to operate.

The strongest CQRS answer separates the three levels, because most people treat CQRS and event sourcing as one thing. Event sourcing: streams, projections and snapshots

Event sourcing stores the events as the source of truth rather than current state. The aggregate is rebuilt by replaying its stream; current state is a cache you can throw away and recompute. You get a complete audit log for free, the ability to answer questions nobody asked when the schema was written, and temporal queries — "what did this look like last Tuesday" becomes a replay.

The costs are real and interviewers want to hear them. Schema evolution: events are immutable and live forever, so a v1 event from 2019 must still deserialise and be upcast. Querying: you cannot query a stream, so every read needs a projection, and projections lag. Rebuild time: a long stream is slow to load, hence snapshots. Deletion: GDPR against an immutable log needs crypto-shredding or a rewrite.

It is the right answer for a genuinely audit-driven domain — finance, compliance, anything where "how did we get here" is a product requirement — and badly oversold everywhere else.

// The aggregate is a fold over its events
public class Order
{
    private readonly List<IDomainEvent> _uncommitted = [];

    public OrderId Id { get; private set; }
    public OrderStatus Status { get; private set; }
    public int Version { get; private set; } = -1;        // for optimistic concurrency

    // 1. REHYDRATE: replay the stream
    public static Order FromHistory(IEnumerable<IDomainEvent> history)
    {
        var order = new Order();
        foreach (var e in history) order.Apply(e, isNew: false);
        return order;
    }

    // 2. DECIDE: a command validates against current state and emits events
    public void Pay(Money amount)
    {
        if (Status != OrderStatus.Pending) throw new DomainException("already paid");
        if (amount != Total) throw new DomainException("amount mismatch");

        Apply(new OrderPaid(Id, amount, DateTime.UtcNow), isNew: true);
    }

    // 3. APPLY: mutate state. NO validation here - replay must never throw.
    private void Apply(IDomainEvent e, bool isNew)
    {
        switch (e)
        {
            case OrderPlaced p: Id = p.OrderId; Status = OrderStatus.Pending; break;
            case OrderPaid:     Status = OrderStatus.Paid; break;
            case OrderShipped:  Status = OrderStatus.Shipped; break;
            default: break;              // an unknown old event must NOT crash replay
        }
        Version++;
        if (isNew) _uncommitted.Add(e);
    }

    public IReadOnlyList<IDomainEvent> Uncommitted => _uncommitted;
}

// The store: append with an expected version - that IS the concurrency control
public interface IEventStore
{
    Task<IReadOnlyList<IDomainEvent>> Read(string stream, int fromVersion, CancellationToken ct);
    Task Append(string stream, int expectedVersion,
                IEnumerable<IDomainEvent> events, CancellationToken ct);
    //   expectedVersion mismatch -> WrongExpectedVersionException -> reload and retry
}

// SCHEMA EVOLUTION: upcast old events on read. This never goes away.
public static IDomainEvent Upcast(StoredEvent stored) => stored switch
{
    { Type: "OrderPaid", Version: 1 } =>
        // v1 had no currency; everything before 2023 was USD
        new OrderPaid(stored.StreamId,
                      new Money(stored.Get<decimal>("amount"), "USD"),
                      stored.OccurredAt),
    { Type: "OrderPaid", Version: 2 } => stored.Deserialize<OrderPaid>(),
    _ => throw new UnknownEventException(stored.Type, stored.Version),
};

// SNAPSHOTS: replaying 40,000 events per load is not viable
public async Task<Order> Load(OrderId id, CancellationToken ct)
{
    var snapshot = await _snapshots.GetLatest(id, ct);
    var from  = snapshot?.Version + 1 ?? 0;
    var since = await _store.Read($"order-{id}", from, ct);

    var order = snapshot is null
        ? Order.FromHistory(since)
        : Order.FromSnapshot(snapshot, since);

    if (order.Version - (snapshot?.Version ?? 0) > 100)
        await _snapshots.Save(order.ToSnapshot(), ct);     // every ~100 events

    return order;
}

// Libraries you would actually use: Marten (on PostgreSQL), EventStoreDB.
from dataclasses import dataclass
from typing import Iterable

# The aggregate as a fold over events
class Order:
    def __init__(self) -> None:
        self._uncommitted: list = []
        self.id: OrderId | None = None
        self.status = "none"
        self.version = -1

    @classmethod
    def from_history(cls, history: Iterable) -> "Order":
        order = cls()
        for e in history:
            order._apply(e, is_new=False)
        return order

    # DECIDE: validate, then emit
    def pay(self, amount: Money) -> None:
        if self.status != "pending":
            raise DomainError("already paid")
        self._apply(OrderPaid(self.id, amount), is_new=True)

    # APPLY: mutate only. Replay must never raise.
    def _apply(self, e, is_new: bool) -> None:
        match e:
            case OrderPlaced():  self.id, self.status = e.order_id, "pending"
            case OrderPaid():    self.status = "paid"
            case OrderShipped(): self.status = "shipped"
            case _:              pass          # unknown old event: ignore, do not crash
        self.version += 1
        if is_new:
            self._uncommitted.append(e)

# Upcasting - the permanent tax of event sourcing
UPCASTERS = {
    ("OrderPaid", 1): lambda d: OrderPaid(d["order_id"],
                                          Money(Decimal(d["amount"]), "USD")),
    ("OrderPaid", 2): lambda d: OrderPaid(d["order_id"],
                                          Money(Decimal(d["amount"]), d["currency"])),
}

def upcast(stored: dict):
    key = (stored["type"], stored["version"])
    try:
        return UPCASTERS[key](stored["payload"])
    except KeyError:
        raise UnknownEvent(key) from None

# Append with an expected version = optimistic concurrency
async def append(conn, stream: str, expected_version: int, events: list) -> None:
    result = await conn.execute(
        """
        INSERT INTO events (stream, version, type, payload)
        SELECT :stream, :expected + row_number() OVER (), :type, :payload
        WHERE (SELECT COALESCE(MAX(version), -1) FROM events WHERE stream = :stream)
              = :expected
        """, ...)
    if result.rowcount == 0:
        raise WrongExpectedVersion(stream, expected_version)

# Projections: rebuildable, which is the whole point
async def rebuild_projection(store, projection) -> None:
    await projection.reset()
    async for event in store.read_all():
        await projection.project(event)
Interview angle

Then give the condition under which it pays — a domain where the history is the product, like ledgers, trading or compliance — and say that CQRS does not require it, which is the conflation most people make. Vertical slice architecture, and the case against layers

The honest counter-argument, and knowing it is a stronger signal than defending Clean Architecture. Layered solutions optimise for swapping a layer — and teams almost never swap a layer. What they do constantly is change one feature, which in a layered solution means editing a file in each of four projects for a change that is conceptually one thing.

Vertical slice architecture organises by feature instead: everything PlaceOrder needs lives in one folder — the request, the handler, the validator, the SQL, the response. Slices are allowed to differ: a complex one uses a rich aggregate, a CRUD one talks to the database directly, and neither is forced to pretend to be the other. Coupling within a slice is fine; coupling between slices is what you police.

The real answer in an interview is that the two compose. Use slices as the top-level organisation, and reach for a domain model inside the slices that have genuine business rules.

// A whole feature in one file. Everything it needs, nothing it does not.
namespace Shop.Api.Features.Orders;

public static class PlaceOrder
{
    public record Request(Guid CustomerId, IReadOnlyList<LineDto> Lines);
    public record Response(Guid OrderId, decimal Total);

    public class Validator : AbstractValidator<Request>
    {
        public Validator()
        {
            RuleFor(x => x.CustomerId).NotEmpty();
            RuleFor(x => x.Lines).NotEmpty().Must(l => l.Count <= 100);
        }
    }

    public class Handler(AppDbContext db, IProductCatalogue catalogue)
    {
        public async Task<Response> Handle(Request request, CancellationToken ct)
        {
            var prices = await catalogue.GetPrices(request.Lines.Select(l => l.Sku), ct);

            // This slice HAS real rules, so it uses the domain model
            var order = Order.Place(
                new CustomerId(request.CustomerId),
                request.Lines.Select(l => new OrderLine(l.Sku, l.Quantity, prices[l.Sku])));

            db.Orders.Add(order);
            await db.SaveChangesAsync(ct);
            return new Response(order.Id.Value, order.Total.Amount);
        }
    }

    public static void Map(IEndpointRouteBuilder app) =>
        app.MapPost("/orders", async (Request r, Handler h, CancellationToken ct)
                => Results.Ok(await h.Handle(r, ct)))
           .WithName("PlaceOrder")
           .WithTags("Orders");
}

// A different slice, deliberately simpler. No aggregate, no repository, no
// mapping layer - because this feature has no rules to protect.
namespace Shop.Api.Features.Orders;

public static class ListOrders
{
    public record Response(Guid Id, string Customer, decimal Total, string Status);

    public class Handler(IDbConnection conn)
    {
        public async Task<IReadOnlyList<Response>> Handle(Guid customerId, CancellationToken ct)
            => (await conn.QueryAsync<Response>(@"
                    SELECT o.id, c.name AS customer, o.total, o.status
                    FROM orders o JOIN customers c ON c.id = o.customer_id
                    WHERE o.customer_id = @customerId
                    ORDER BY o.placed_at DESC", new { customerId })).ToList();
    }

    public static void Map(IEndpointRouteBuilder app) =>
        app.MapGet("/orders", async (Guid customerId, Handler h, CancellationToken ct)
                => Results.Ok(await h.Handle(customerId, ct)));
}

# shop/features/orders/place_order.py  - the whole feature
from dataclasses import dataclass
from pydantic import BaseModel, Field

class Request(BaseModel):
    customer_id: uuid.UUID
    lines: list["LineDto"] = Field(min_length=1, max_length=100)

class Response(BaseModel):
    order_id: uuid.UUID
    total: Decimal

class Handler:
    def __init__(self, session, catalogue) -> None:
        self._session, self._catalogue = session, catalogue

    async def handle(self, request: Request) -> Response:
        prices = await self._catalogue.get_prices([l.sku for l in request.lines])
        order = Order.place(                      # this slice has real rules
            CustomerId(request.customer_id),
            [OrderLine(l.sku, l.quantity, prices[l.sku]) for l in request.lines])
        self._session.add(order)
        await self._session.commit()
        return Response(order_id=order.id, total=order.total.amount)

router = APIRouter()

@router.post("/orders", response_model=Response)
async def place_order(request: Request, handler: Handler = Depends(get_handler)):
    return await handler.handle(request)


# shop/features/orders/list_orders.py  - deliberately simpler
class Response(BaseModel):
    id: uuid.UUID
    customer: str
    total: Decimal
    status: str

@router.get("/orders", response_model=list[Response])
async def list_orders(customer_id: uuid.UUID, conn = Depends(get_conn)):
    rows = await conn.fetch_all(
        """SELECT o.id, c.name AS customer, o.total, o.status
           FROM orders o JOIN customers c ON c.id = o.customer_id
           WHERE o.customer_id = :cid ORDER BY o.placed_at DESC""",
        {"cid": customer_id})
    return [dict(r) for r in rows]

Interview angle

Being able to argue against Clean Architecture is one of the more differentiating things you can do in an architecture interview, because most candidates only defend it. The argument: layers optimise for swapping infrastructure, which teams rarely do, and penalise changing a feature, which they do daily. Then resolve it rather than picking a side — slices as the organisation, a domain model inside the slices that have real invariants, and architecture tests policing that slices do not reference each other. Finish with the rule of thumb: match the ceremony to the complexity of the feature, and do not force a CRUD endpoint through four layers to be consistent.

Practice
  • Restructure one feature into a single-file slice and compare how many files you open to change it.
  • Identify two features in a system you know where one deserves a domain model and the other does not.
  • Add an architecture test asserting that two feature folders do not reference each other.

Persisting the domain without leaking it

The practical problem: a model designed for invariants has private setters, no parameterless constructor, value objects and encapsulated collections — and EF Core wants to materialise entities from a database. Getting this to work without compromising the model is a real and frequently asked question.

EF Core can do more than people expect: it sets private setters and backing fields through reflection, it maps value objects as owned types or with converters, and it can map to a private collection field so the public surface stays IReadOnlyList. The configuration goes in infrastructure, so the domain still has no EF reference.

The alternative — separate persistence models with explicit mapping — gives total freedom and costs you a mapping layer to maintain. Worth having a view on which you would pick and why.

// The domain model, unchanged: private setters, no public ctor, encapsulated list
public class Order : AggregateRoot<OrderId>
{
    private readonly List<OrderLine> _lines = [];

    public CustomerId CustomerId { get; private init; }
    public OrderStatus Status { get; private set; }
    public Money Total { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();

    private Order() { }                       // EF uses this; nothing else can
}

// ALL the EF knowledge lives here, in Infrastructure
public class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.ToTable("orders");

        // Strongly-typed id <-> column, via a value converter
        b.HasKey(o => o.Id);
        b.Property(o => o.Id)
         .HasConversion(id => id.Value, value => new OrderId(value))
         .ValueGeneratedNever();

        b.Property(o => o.CustomerId)
         .HasConversion(id => id.Value, value => new CustomerId(value));

        // Enum as a string, so the database stays readable and reordering is safe
        b.Property(o => o.Status)
         .HasConversion<string>()
         .HasMaxLength(20);

        // Value object as an OWNED type: two columns, no separate table
        b.OwnsOne(o => o.Total, m =>
        {
            m.Property(x => x.Amount).HasColumnName("total_amount").HasPrecision(19, 4);
            m.Property(x => x.Currency).HasColumnName("total_currency").HasMaxLength(3);
        });

        // Map to the BACKING FIELD, so the public IReadOnlyList stays read-only
        b.Metadata.FindNavigation(nameof(Order.Lines))!
         .SetPropertyAccessMode(PropertyAccessMode.Field);

        b.OwnsMany(o => o.Lines, l =>
        {
            l.ToTable("order_lines");
            l.WithOwner().HasForeignKey("order_id");
            l.Property<int>("id");
            l.HasKey("id");
            l.OwnsOne(x => x.UnitPrice);
        });

        // Concurrency token on the ROOT
        b.Property<byte[]>("Version").IsRowVersion();
    }
}

// Global convention so you write the id converter once, not per type
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<OrderId>().HaveConversion<OrderIdConverter>();
    builder.Properties<decimal>().HavePrecision(19, 4);
}

// THE ALTERNATIVE: separate persistence models and explicit mapping.
// Total freedom in the domain, a mapping layer to maintain, and the repository
// is where the translation lives.
public class OrderRecord                       // shaped for the database
{
    public Guid Id { get; set; }
    public Guid CustomerId { get; set; }
    public string Status { get; set; } = "";
    public decimal TotalAmount { get; set; }
    public string TotalCurrency { get; set; } = "";
    public List<OrderLineRecord> Lines { get; set; } = [];
}

public class OrderRepository(AppDbContext db) : IOrderRepository
{
    public async Task<Order?> Get(OrderId id, CancellationToken ct)
    {
        var record = await db.OrderRecords.Include(r => r.Lines)
            .SingleOrDefaultAsync(r => r.Id == id.Value, ct);
        return record is null ? null : OrderMapper.ToDomain(record);
    }
}

// Which to pick: EF-mapped domain for most teams, because the mapping layer is
// real ongoing work and EF can express almost everything the model needs.
// Separate models when the domain shape and the schema genuinely diverge - a
// legacy database you do not control is the usual reason.

// What NOT to do, whichever you pick:
//   - public setters "because EF needs them" (it does not)
//   - [Table]/[Column] attributes on domain types (that is an EF reference)
//   - IQueryable on a repository interface (the abstraction is then fictional)
//   - lazy loading on an aggregate (silent N+1 inside your domain logic)
# SQLAlchemy's imperative (classical) mapping keeps the domain clean - arguably
# a better fit for DDD than the declarative style, because the domain class has
# no ORM base class and no ORM imports.

# shop/domain/orders.py  - pure Python, no SQLAlchemy anywhere
class Order:
    def __init__(self, id: OrderId, customer_id: CustomerId) -> None:
        self._id = id
        self._customer_id = customer_id
        self._status = "pending"
        self._lines: list[OrderLine] = []

    @property
    def lines(self) -> tuple[OrderLine, ...]:
        return tuple(self._lines)              # read-only surface preserved


# shop/infrastructure/mapping.py  - ALL the ORM knowledge, in one place
from sqlalchemy import Table, Column, String, Numeric, ForeignKey, MetaData
from sqlalchemy.orm import registry, relationship, composite

metadata = MetaData()
mapper_registry = registry()

orders = Table(
    "orders", metadata,
    Column("id", UUID, primary_key=True),
    Column("customer_id", UUID, nullable=False),
    Column("status", String(20), nullable=False),
    Column("total_amount", Numeric(19, 4)),
    Column("total_currency", String(3)),
    Column("version", Integer, nullable=False),
)

order_lines = Table(
    "order_lines", metadata,
    Column("id", Integer, primary_key=True),
    Column("order_id", UUID, ForeignKey("orders.id"), nullable=False),
    Column("sku", String(40), nullable=False),
    Column("quantity", Integer, nullable=False),
)

def start_mappers() -> None:
    mapper_registry.map_imperatively(
        OrderLine, order_lines,
        properties={"_sku": order_lines.c.sku, "_quantity": order_lines.c.quantity},
    )
    mapper_registry.map_imperatively(
        Order, orders,
        properties={
            "_id":          orders.c.id,
            "_customer_id": orders.c.customer_id,
            "_status":      orders.c.status,
            # value object across two columns - the OwnsOne equivalent
            "_total": composite(Money, orders.c.total_amount, orders.c.total_currency),
            # maps to the private list, public `lines` stays a read-only tuple
            "_lines": relationship(OrderLine, cascade="all, delete-orphan"),
        },
        version_id_col=orders.c.version,       # optimistic concurrency on the root
    )

# Called once at startup, from the composition root
start_mappers()
Interview angle

A good practical question because it catches people who have only read about DDD. Be concrete: EF Core sets private setters and backing fields by reflection, value objects map as owned types or value converters, strongly-typed ids map with a converter you can register as a convention, and all of that configuration lives in infrastructure so the domain project keeps zero EF references. Then name the two anti-patterns you would refuse: public setters "because EF needs them", and exposing IQueryable from a repository, which makes the abstraction decorative.

Practice
  • Map an entity with private setters, a value object and an encapsulated collection — without changing the domain class.
  • Register a value converter for a strongly-typed id as a global convention and delete the per-entity configuration.
  • Try mapping the same model with separate persistence records and decide which you would maintain.
