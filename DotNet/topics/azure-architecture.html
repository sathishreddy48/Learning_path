Management groups, subscriptions, resource groups, tags

Scope flows down: tenant → management groups → subscriptions → resource groups → resources. Policy and RBAC assigned at a level apply to everything beneath it. Subscriptions are billing and quota boundaries (typical split: per environment or per workload); resource groups hold things with the same lifecycle. Tags (owner, cost-centre, environment, data-classification) drive cost reports and automation — enforce them with policy.

# Management group tree
az account management-group create --name mg-contoso --display-name Contoso
az account management-group create --name mg-platform  --parent mg-contoso
az account management-group create --name mg-workloads --parent mg-contoso
az account management-group subscription add --name mg-workloads --subscription "sub-shop-prod"

# Resource groups per lifecycle, tagged
az group create -n rg-shop-prod-weu -l westeurope --tags env=prod owner=shop-team costcenter=CC123 dataclass=confidential
az tag update --resource-id /subscriptions/<sub>/resourceGroups/rg-shop-prod-weu --operation Merge --tags reviewed=2026-09

# Naming: <type>-<workload>-<env>-<region>-<instance>   e.g. app-shop-prod-weu-01, sql-shop-prod-weu, kv-shop-prod-weu
# Query everything with Resource Graph
az graph query -q "Resources | where tags.env == 'prod' and type =~ 'microsoft.web/sites' | project name, resourceGroup, location, sku=properties.sku"
// Subscription-scoped deployment that creates the RG and then deploys the workload module into it
targetScope = 'subscription'
param location string = 'westeurope'
param env string
var tags = { env: env, owner: 'shop-team', costcenter: 'CC123' }

  name: 'rg-shop-${env}-weu'
  location: location
  tags: tags
}

module shop 'modules/shop.bicep' = {
  scope: rg
  name: 'shop-${env}'
  params: { location: location, env: env, tags: tags }
}

RBAC, Azure Policy and resource locks

RBAC answers who can do what; Azure Policy answers what is allowed to exist (deny public storage, require tags, allowed regions/SKUs, audit missing diagnostics, DeployIfNotExists to auto-remediate). Initiatives bundle policies (e.g. the Microsoft cloud security benchmark). Locks (CanNotDelete / ReadOnly) protect production resources from accidents, including by Owners.

{
  "properties": {
    "displayName": "Storage accounts must disable public network access",
    "mode": "Indexed",
    "policyRule": {
      "if": { "allOf": [
        { "field": "type", "equals": "Microsoft.Storage/storageAccounts" },
        { "field": "Microsoft.Storage/storageAccounts/publicNetworkAccess", "notEquals": "Disabled" } ] },
      "then": { "effect": "[parameters('effect')]" }
    },
    "parameters": { "effect": { "type": "String", "allowedValues": ["Audit", "Deny", "Disabled"], "defaultValue": "Deny" } }
  }
}
# Assign built-ins at the management group: allowed locations, required tag, no public IPs on NICs
az policy assignment create --name allowed-locations --scope /providers/Microsoft.Management/managementGroups/mg-workloads   --policy e56962a6-4747-49cd-b67b-bf8b01975c4c --params '{"listOfAllowedLocations":{"value":["westeurope","northeurope"]}}'
az policy assignment create --name require-env-tag --scope /providers/Microsoft.Management/managementGroups/mg-workloads   --policy 871b6d14-10aa-478d-b590-94f262ecfa99 --params '{"tagName":{"value":"env"}}'

# DeployIfNotExists needs a managed identity to remediate; then create a remediation task for existing resources
az policy assignment create --name diag-to-law --scope /subscriptions/<sub> --policy-set-definition <initiative-id>   --mi-system-assigned --location westeurope --role Contributor
az policy remediation create --name fix-diag --policy-assignment diag-to-law --resource-discovery-mode ReEvaluateCompliance

# Compliance state
az policy state summarize --management-group mg-workloads --query "results.{nonCompliant:nonCompliantResources}"

# Locks
az lock create --name no-delete --lock-type CanNotDelete --resource-group rg-shop-prod-weu

RBAC vs Policy (who vs what); effects (Audit, Deny, Modify, DeployIfNotExists) and evaluation order; how policy interacts with IaC pipelines (fail early with what-if / PSRule); locks vs RBAC deny; exemptions and their expiry.

The Well-Architected Framework

Five pillars you will be asked to apply to your own design: Reliability (define SLOs, remove single points of failure, test failover), Security (identity first, least privilege, private networking, secrets in Key Vault), Cost Optimisation (right-size, scale to zero, reservations), Operational Excellence (IaC, CI/CD, observability, runbooks), Performance Efficiency (scale out, cache, async, measure). Use the Azure Well-Architected Review as a checklist.

PillarQuestions an interviewer asksConcrete Azure answers
ReliabilityWhat is your SLO? What happens if this zone/region goes down?Zone-redundant SKUs, health probes, retries with jitter, Service Bus for decoupling, geo-replication, tested failover
SecurityWhere are the secrets? Who can reach the database?Managed identity, Key Vault, private endpoints, WAF, Defender for Cloud, policy guardrails
CostWhat does it cost idle? At 10× load?Consumption tiers, autoscale rules, reservations/savings plans, budgets and alerts, tagging
Operational excellenceHow do you deploy? How do you know it is broken?Bicep/Terraform, pipelines with gates, App Insights + alerts, runbooks, game days
PerformanceWhere is the bottleneck? How do you find out?Load tests, App Insights profiler, caching (Redis/CDN), async messaging, partitioning

    .AddStandardResilienceHandler(o =>                       // Microsoft.Extensions.Http.Resilience (Polly v8)
    {

    });

app.MapHealthChecks("/health/ready", new() { Predicate = r => r.Tags.Contains("ready") });   // dependencies are up

builder.Host.ConfigureHostOptions(o => o.ShutdownTimeout = TimeSpan.FromSeconds(30));

Regions, availability zones and composite SLAs

A region is a set of datacentres; most have three availability zones with independent power/network. Zone-redundant SKUs (App Service P-tier, SQL Business Critical/Premium, zone-redundant storage, Service Bus Premium) survive a zone loss with no action from you. A second region is for regional disasters and needs data replication plus a failover plan. Composite SLA = product of dependent SLAs; parallel redundancy raises it: 1 − (1−A)(1−B).

# Composite SLA calculator — bring numbers to the design discussion
def series(*slas):      # everything must be up
    p = 1.0
    for s in slas: p *= s
    return p
def parallel(*slas):    # any one being up is enough (independent failures)
    q = 1.0
    for s in slas: q *= (1 - s)
    return 1 - q

app_service, sql, redis, service_bus = 0.9995, 0.9995, 0.999, 0.999
single_region = series(app_service, sql, redis, service_bus)
print(f"single region: {single_region:.4%}  ≈ {(1-single_region)*365*24*60:.0f} min/yr")        # ~99.75% → ~22h/yr

two_regions = parallel(single_region, single_region) * 0.9999                                   # × Front Door SLA
print(f"active/active 2 regions: {two_regions:.4%} ≈ {(1-two_regions)*365*24*60:.0f} min/yr")

# Takeaways: every synchronous dependency multiplies risk; move optional ones behind a queue or a cache; a second region
# helps only if failover is automatic and tested.
# Zone-redundant choices (a few examples)
az appservice plan create -g rg-shop -n asp-shop --sku P1v3 --zone-redundant --number-of-workers 3
az sql db create -g rg-shop -s sql-shop -n shopdb --edition GeneralPurpose --family Gen5 --capacity 4 --zone-redundant true
az storage account create -g rg-shop -n stshop --sku Standard_ZRS
az servicebus namespace create -g rg-shop -n sb-shop --sku Premium --zone-redundant true
az containerapp env create -g rg-shop -n cae-shop --zone-redundant --infrastructure-subnet-resource-id <subnet-id>

# Which regions have zones, and paired regions
az account list-locations --query "[?metadata.regionType=='Physical'].{name:name, zones:length(availabilityZoneMappings || \`[]\`), pair:metadata.pairedRegion[0].name}" -o table

Backup, disaster recovery, RTO and RPO

RPO: how much data you can lose; RTO: how long you can be down. Cheaper as they grow. Options ladder: backup/restore (hours) → pilot light (IaC ready, data replicated) → warm standby (scaled-down copy) → active/active. Azure pieces: Azure Backup, SQL geo-replication and failover groups, Cosmos multi-region, GRS/RA-GZRS storage, Site Recovery for VMs, and a runbook you have actually executed.

# Azure SQL failover group: async replica in the paired region, single listener endpoint for the app
az sql failover-group create -g rg-shop -s sql-shop-weu --partner-server sql-shop-neu -n fog-shop --add-db shopdb   --failover-policy Automatic --grace-period 1
# App connects to fog-shop.database.windows.net (RW) or fog-shop.secondary.database.windows.net (RO)

# Planned failover (no data loss) vs forced (accept RPO)
az sql failover-group set-primary -g rg-shop -s sql-shop-neu -n fog-shop
az sql failover-group set-primary -g rg-shop -s sql-shop-neu -n fog-shop --allow-data-loss

# Cosmos DB: add a region, enable automatic failover; multi-write if the app handles conflicts
az cosmosdb update -g rg-shop -n cosmos-shop --locations regionName=westeurope failoverPriority=0 --locations regionName=northeurope failoverPriority=1 --enable-automatic-failover true

# Storage: geo-redundant with read access; app can read from the -secondary endpoint during an outage
az storage account update -g rg-shop -n stshop --sku Standard_RAGZRS
# Backup vault for Blob / SQL / disks with immutable (WORM) retention against ransomware
az dataprotection backup-vault create -g rg-shop --vault-name bv-shop -l westeurope --storage-setting '[{"type":"LocallyRedundant","datastore-type":"VaultStore"}]' --immutability-state Locked
// The app side of DR: connect via the listener, tolerate the flip, prefer read replicas for reads

builder.Services.AddDbContext<ShopReadDb>(o => o.UseSqlServer(cfg.GetConnectionString("ShopRead")));   // ...;ApplicationIntent=ReadOnly

Cost management and FinOps

Cost is an architecture property. Levers: pick consumption tiers where load is spiky (Functions, Container Apps, serverless SQL), autoscale with sensible minimums, buy reservations / savings plans for the steady baseline, turn off non-prod at night, and stop paying for data egress and logs you never read. Make cost visible: tags → cost analysis → budgets with alerts → Advisor recommendations in the sprint.

# Budget with alerts at 80% and 100% (and a forecast alert)
az consumption budget create-with-rg -g rg-shop-prod-weu --budget-name shop-prod-monthly --amount 5000 --category cost --time-grain monthly   --start-date 2026-09-01 --end-date 2027-08-31   --notifications '{"Actual80":{"enabled":true,"operator":"GreaterThan","threshold":80,"contactEmails":["shop-team@contoso.com"]},
                    "Forecast100":{"enabled":true,"operator":"GreaterThan","threshold":100,"thresholdType":"Forecasted","contactEmails":["shop-team@contoso.com"]}}'

# Where does the money go? (Cost Management query API via CLI)
az costmanagement query --type ActualCost --timeframe MonthToDate --scope /subscriptions/<sub>   --dataset-aggregation '{"totalCost":{"name":"Cost","function":"Sum"}}' --dataset-grouping name=ServiceName type=Dimension -o table

# Advisor: right-sizing and idle resources
az advisor recommendation list --category Cost -o table

# Stop non-prod at night (pipeline or Automation schedule)
az webapp stop -g rg-shop-dev -n shop-api-dev ; az sql db update -g rg-shop-dev -s sql-shop-dev -n shopdb --auto-pause-delay 60

Landing zones and the Cloud Adoption Framework

An Azure landing zone is the pre-built environment a workload lands in: management group hierarchy, policies, hub network with firewall/DNS, identity, logging, and a subscription vending process. The Cloud Adoption Framework describes it; the ALZ Bicep/Terraform accelerators build it. As an application team you consume it: you get a subscription with guardrails, a spoke VNet, private DNS zones already linked, and diagnostics routed to the central workspace.

# What a "vended" subscription typically gives you — check before you design
az account show --query "{sub:name,id:id}"                                   # your own subscription
az network vnet list --query "[].{name:name,rg:resourceGroup,space:addressSpace.addressPrefixes}" -o table     # spoke VNet pre-created
az network vnet peering list -g rg-network --vnet-name vnet-shop -o table    # peered to the hub
az policy assignment list --disable-scope-strict-match --query "[].{name:displayName,scope:scope}" -o table   # inherited guardrails
az monitor diagnostic-settings subscription list                               # activity log → central workspace

# Things you usually cannot do in a landing zone (by design): public IPs, storage with public access, non-approved regions,
# VNets with your own address space, direct internet egress. Ask the platform team; do not fight policy in the pipeline.

Reference architecture: a .NET web workload on Azure

Draw this and be able to justify every box. Traffic: Front Door (WAF) → App Service (zone-redundant, VNet-integrated, private endpoint) or Container Apps. Data: Azure SQL (zone-redundant, failover group) + Redis + Blob, all via private endpoints. Async: Service Bus → worker; Event Grid for fan-out. Cross-cutting: Key Vault, App Configuration, managed identities, App Insights → Log Analytics, Bicep in a pipeline with staging slot + approval.

// modules/shop.bicep — the core of the reference architecture (abridged)
param location string
param env string
param tags object

resource plan 'Microsoft.Web/serverfarms@2023-12-01' = {
  name: 'asp-shop-${env}', location: location, tags: tags
  sku: { name: 'P1v3', capacity: 3 }
  properties: { zoneRedundant: true, reserved: true }
}
resource api 'Microsoft.Web/sites@2023-12-01' = {
  name: 'app-shop-api-${env}', location: location, tags: tags, kind: 'app,linux'
  identity: { type: 'SystemAssigned' }
  properties: {
    serverFarmId: plan.id
    httpsOnly: true
    publicNetworkAccess: 'Disabled'
    virtualNetworkSubnetId: appSubnetId
    siteConfig: {
      linuxFxVersion: 'DOTNETCORE|9.0', vnetRouteAllEnabled: true, healthCheckPath: '/health/ready', minTlsVersion: '1.2', ftpsState: 'Disabled'
      appSettings: [
        { name: 'APPLICATIONINSIGHTS_CONNECTION_STRING', value: appInsights.properties.ConnectionString }
        { name: 'AppConfig__Endpoint', value: appConfig.properties.endpoint }
        { name: 'ConnectionStrings__Shop', value: 'Server=tcp:${sql.properties.fullyQualifiedDomainName};Database=shopdb;Authentication=Active Directory Default;' }
      ]
    }
  }
}
resource staging 'Microsoft.Web/sites/slots@2023-12-01' = { parent: api, name: 'staging', location: location, identity: { type: 'SystemAssigned' }, properties: { serverFarmId: plan.id } }

resource sql 'Microsoft.Sql/servers@2023-08-01-preview' = {
  name: 'sql-shop-${env}', location: location, tags: tags
  properties: { administrators: { administratorType: 'ActiveDirectory', azureADOnlyAuthentication: true, login: 'sql-admins', sid: sqlAdminsGroupId, tenantId: tenant().tenantId }, publicNetworkAccess: 'Disabled' }
}
resource db 'Microsoft.Sql/servers/databases@2023-08-01-preview' = { parent: sql, name: 'shopdb', location: location, sku: { name: 'GP_Gen5_4' }, properties: { zoneRedundant: true } }

// RBAC: the API's identity reads secrets, writes blobs, sends to Service Bus — no keys anywhere
resource kvRole 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  scope: kv, name: guid(kv.id, api.id, 'kv-secrets-user')
  properties: { principalId: api.identity.principalId, principalType: 'ServicePrincipal', roleDefinitionId: subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '4633458b-17de-408a-b874-0445c86b69e6') }
}
