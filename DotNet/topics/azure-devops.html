Boards: work items, sprints and linking

Boards tracks work with a process (Agile: Epic → Feature → User Story → Task/Bug; Scrum uses PBIs). The habits that matter: link every PR and commit to a work item (AB#123 in the commit message or PR), keep the sprint board honest, and use queries/dashboards for visibility. Automation: state transitions on PR completion, and pipeline runs showing linked work items.

C# shows the REST client; Python can use the `azure-devops` package with the same API surface
# Azure DevOps CLI (extension for az)
az extension add --name azure-devops
az devops configure --defaults organization=https://dev.azure.com/contoso project=Shop

# Create and query work items
az boards work-item create --type "User Story" --title "Customers can download invoices" --assigned-to me@contoso.com --iteration "Shop\Sprint 12"
az boards work-item update --id 123 --state Active --fields "System.Tags=payments;api"
az boards query --wiql "SELECT [System.Id],[System.Title] FROM WorkItems WHERE [System.AssignedTo]=@Me AND [System.State]<>'Closed'"

# Link a work item from git: mention AB#123 in the commit / PR description
git commit -m "Add invoice download endpoint AB#123"

# Sprint capacity and iterations
az boards iteration project list --depth 2
az boards iteration team add --team "Shop Team" --id <iteration-id>
// Automating Boards from code: the REST client (Microsoft.TeamFoundationServer.Client)
var connection = new VssConnection(new Uri("https://dev.azure.com/contoso"), new VssBasicCredential(string.Empty, pat));
var wit = connection.GetClient<WorkItemTrackingHttpClient>();

// Create a bug from a production alert
var patch = new JsonPatchDocument
{
    new JsonPatchOperation { Operation = Operation.Add, Path = "/fields/System.Title", Value = $"P1: {alert.Name}" },
    new JsonPatchOperation { Operation = Operation.Add, Path = "/fields/Microsoft.VSTS.Common.Priority", Value = 1 },
    new JsonPatchOperation { Operation = Operation.Add, Path = "/fields/System.Tags", Value = "incident;auto" },
    new JsonPatchOperation { Operation = Operation.Add, Path = "/fields/System.Description", Value = alert.Details }
};
var bug = await wit.CreateWorkItemAsync(patch, "Shop", "Bug");

// Query
var result = await wit.QueryByWiqlAsync(new Wiql { Query = "SELECT [System.Id] FROM WorkItems WHERE [System.State] = 'Active' AND [System.WorkItemType] = 'Bug'" });
var items = await wit.GetWorkItemsAsync(result.WorkItems.Select(w => w.Id), new[] { "System.Title", "System.AssignedTo" });

Repos: branching strategy and branch policies

Trunk-based development with short-lived feature branches and PRs into main is the default that scales. Branch policies on main enforce it: minimum reviewers, linked work items, comment resolution, a required build (the PR validation pipeline), and squash merge to keep history linear. Protect release branches the same way if you use them.

# Branch policies via CLI (or Project Settings → Repos → Policies in the portal)
REPO=$(az repos show --repository Shop --query id -o tsv)

az repos policy approver-count create --repository-id $REPO --branch main --blocking true --enabled true \
  --minimum-approver-count 2 --creator-vote-counts false --allow-downvotes false --reset-on-source-push true

az repos policy work-item-linking create --repository-id $REPO --branch main --blocking true --enabled true
az repos policy comment-required   create --repository-id $REPO --branch main --blocking true --enabled true

# Required build: the PR validation pipeline must pass
az repos policy build create --repository-id $REPO --branch main --blocking true --enabled true \
  --build-definition-id 42 --display-name "PR validation" --queue-on-source-update-only true --valid-duration 720

# Required reviewers for sensitive paths (CODEOWNERS-style)
az repos policy required-reviewer create --repository-id $REPO --branch main --blocking true --enabled true \
  --required-reviewer-ids security-team@contoso.com --path-filter "/src/Shop.Security/*"

# Day-to-day
git switch -c feature/invoice-download
git push -u origin HEAD
az repos pr create --source-branch feature/invoice-download --target-branch main --title "Invoice download AB#123" --auto-complete true --squash true --delete-source-branch true
az repos pr list --status active --creator me@contoso.com

A complete YAML pipeline for a .NET API

Everything else on this page is a zoom-in on this file. It builds once, tests, publishes an artifact, and deploys the same artifact to staging then production with an approval gate. Read it top to bottom; the sections after explain each construct.

# azure-pipelines.yml
trigger:
  branches: { include: [main] }
  paths: { exclude: [docs/*] }
pr: none

variables:
  - group: shop-common                   # variable group (Library): shared non-secret settings
  - name: buildConfiguration
    value: Release
  - name: dotnetVersion
    value: 9.0.x

pool: { vmImage: ubuntu-latest }

stages:
  # ---------------- Build once ----------------
  - stage: Build
    jobs:
      - job: BuildTest
        steps:
          - task: UseDotNet@2
            inputs: { packageType: sdk, version: $(dotnetVersion) }

          - task: Cache@2                           # NuGet cache between runs
            inputs:
              key: 'nuget | "$(Agent.OS)" | **/packages.lock.json'
              path: $(NUGET_PACKAGES)

          - script: dotnet restore --locked-mode
            displayName: Restore

          - script: dotnet build --no-restore -c $(buildConfiguration) /p:Version=1.0.$(Build.BuildId)
            displayName: Build

          - script: dotnet test --no-build -c $(buildConfiguration) --logger trx --collect "XPlat Code Coverage" --results-directory $(Agent.TempDirectory)/tests
            displayName: Test

          - task: PublishTestResults@2
            condition: succeededOrFailed()
            inputs: { testResultsFormat: VSTest, testResultsFiles: '$(Agent.TempDirectory)/tests/**/*.trx', failTaskOnFailedTests: true }

          - script: dotnet publish src/Shop.Api -c $(buildConfiguration) --no-build -o $(Build.ArtifactStagingDirectory)/api
            displayName: Publish

          - publish: $(Build.ArtifactStagingDirectory)/api
            artifact: api                          # pipeline artifact consumed by deploy stages

  # ---------------- Deploy to staging ----------------
  - stage: Staging
    dependsOn: Build
    variables:
      - group: shop-staging                  # linked to Key Vault for secrets
    jobs:
      - deployment: DeployStaging
        environment: shop-staging            # environment = history + checks
        strategy:
          runOnce:
            deploy:
              steps:
                - download: current
                  artifact: api
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: sc-shop-nonprod     # service connection
                    appName: shop-api
                    deployToSlotOrASE: true
                    slotName: staging
                    package: $(Pipeline.Workspace)/api
                - script: curl -fsS https://shop-api-staging.azurewebsites.net/health/ready
                  displayName: Smoke test

  # ---------------- Production with approval ----------------
  - stage: Production
    dependsOn: Staging
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: DeployProd
        environment: shop-production         # has an Approvals check → pauses here
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureAppServiceManage@0     # swap the already-warmed staging slot
                  inputs:
                    azureSubscription: sc-shop-prod
                    Action: Swap Slots
                    WebAppName: shop-api
                    SourceSlot: staging
# Same shape for a FastAPI app — only the Build stage steps differ
stages:
  - stage: Build
    jobs:
      - job: BuildTest
        steps:
          - task: UsePythonVersion@0
            inputs: { versionSpec: '3.12' }

          - task: Cache@2
            inputs:
              key: 'pip | "$(Agent.OS)" | requirements.lock'
              path: $(Pipeline.Workspace)/.pip

          - script: |
              python -m pip install --upgrade pip uv
              uv sync --frozen
            displayName: Install

          - script: |
              uv run ruff check .
              uv run mypy src
            displayName: Lint

          - script: uv run pytest --junitxml=$(Agent.TempDirectory)/junit.xml --cov=src --cov-report=xml:$(Agent.TempDirectory)/coverage.xml
            displayName: Test

          - task: PublishTestResults@2
            condition: succeededOrFailed()
            inputs: { testResultsFormat: JUnit, testResultsFiles: '$(Agent.TempDirectory)/junit.xml' }

          - task: PublishCodeCoverageResults@2
            inputs: { summaryFileLocation: '$(Agent.TempDirectory)/coverage.xml' }

          # Deploy as a container (recommended for Python) rather than a zip
          - task: Docker@2
            inputs:
              command: buildAndPush
              repository: orders-api
              containerRegistry: sc-acr
              tags: |
                $(Build.BuildId)
                latest

  # Deploy stages then use AzureWebAppContainer@1 or az containerapp update --image ...:$(Build.BuildId)

Stages, jobs and steps

Steps run sequentially on one agent. A job is a set of steps on one agent (fresh VM per job); jobs in a stage run in parallel unless they dependsOn each other. A stage groups jobs and is the unit for approvals and conditions. A deployment job targets an environment and records what was deployed where. Use matrix/parallel strategies to fan out.

stages:
  - stage: Test
    jobs:
      # Fan out across OS and SDK versions
      - job: Matrix
        strategy:
          matrix:
            linux_net9:   { image: ubuntu-latest,  sdk: 9.0.x }
            windows_net9: { image: windows-latest, sdk: 9.0.x }
            linux_net8:   { image: ubuntu-latest,  sdk: 8.0.x }
          maxParallel: 3
        pool: { vmImage: $(image) }
        steps:
          - task: UseDotNet@2
            inputs: { packageType: sdk, version: $(sdk) }
          - script: dotnet test

      # Split slow tests across N agents
      - job: Integration
        strategy: { parallel: 4 }
        steps:
          - script: dotnet test --filter "Category=Integration" -- RunConfiguration.TestSessionTimeout=600000
            env: { SLICE: $(System.JobPositionInPhase), SLICES: $(System.TotalJobsInPhase) }

      # Runs after both, even if they failed
      - job: Report
        dependsOn: [Matrix, Integration]
        condition: always()
        steps:
          - script: echo "Matrix=$(MATRIX_RESULT)"
            env: { MATRIX_RESULT: $[ dependencies.Matrix.result ] }

  - stage: Deploy
    dependsOn: Test
    condition: succeeded()
    jobs:
      - deployment: Web
        environment: shop-staging
        timeoutInMinutes: 20
        strategy:
          runOnce:                       # also: rolling, canary (for VM/K8s environments)
            preDeploy:  { steps: [ { script: echo pre } ] }
            deploy:     { steps: [ { script: echo deploy } ] }
            routeTraffic: { steps: [ { script: echo route } ] }
            postRouteTraffic: { steps: [ { script: echo verify } ] }
            on:
              failure: { steps: [ { script: echo rollback } ] }
              success: { steps: [ { script: echo notify } ] }

# Steps: script / bash / pwsh / task@version / checkout / download / publish / template
# Every step supports: displayName, condition, continueOnError, timeoutInMinutes, env, workingDirectory
# Self-hosted agents when you need private network access or custom tooling
# Download the agent from Project Settings → Agent pools → New agent, then:
./config.sh --unattended --url https://dev.azure.com/contoso --auth pat --token $PAT --pool shop-private --agent $(hostname) --acceptTeeEula
sudo ./svc.sh install && sudo ./svc.sh start

# Reference it in YAML:
#   pool: { name: shop-private, demands: [ docker ] }

# Container jobs: run steps inside an image on a hosted agent
#   jobs:
#     - job: InContainer
#       container: mcr.microsoft.com/dotnet/sdk:9.0
#       services:
#         sql: { image: mcr.microsoft.com/mssql/server:2022-latest, env: { ACCEPT_EULA: Y, MSSQL_SA_PASSWORD: P@ssw0rd! }, ports: ['1433:1433'] }

Variables, variable groups and secrets

Variables come from YAML (variables:), variable groups in Library (optionally linked to Key Vault), pipeline UI settings, and runtime expressions. Two syntaxes: $(var) macro (expanded at runtime), ${{ variables.var }} template expression (compile time), $[variables.var] runtime expression (for conditions). Secrets are masked in logs and must be mapped to env: explicitly for scripts.

variables:
  - name: configuration
    value: Release
  - group: shop-common                                   # Library → Variable groups
  - group: shop-keyvault                                 # linked to Key Vault: secrets become variables
  - ${{ if eq(variables['Build.SourceBranchName'], 'main') }}:   # compile-time branch on the branch
      - name: environmentSuffix
        value: prod
  - ${{ else }}:
      - name: environmentSuffix
        value: dev

steps:
  # Macro syntax: expanded before the step runs
  - script: dotnet build -c $(configuration)

  # Secrets are NOT exposed as env vars automatically — map them
  - script: dotnet ef database update
    env:
      ConnectionStrings__Default: $(SqlConnection)      # from the Key Vault group, masked in logs

  # Set a variable for later steps / jobs / stages
  - bash: |
      VERSION=1.0.$(Build.BuildId)
      echo "##vso[task.setvariable variable=version]$VERSION"                      # this job
      echo "##vso[task.setvariable variable=version;isOutput=true]$VERSION"        # other jobs (needs step name)
    name: SetVersion

  - script: echo "Version is $(version)"

jobs:
  - job: Consumer
    dependsOn: Producer
    variables:
      version: $[ dependencies.Producer.outputs['SetVersion.version'] ]        # runtime expression
    steps:
      - script: echo $(version)

# Predefined variables you use constantly:
#   $(Build.BuildId) $(Build.BuildNumber) $(Build.SourceBranch) $(Build.SourceVersion) $(Build.Reason)
#   $(Build.ArtifactStagingDirectory) $(Pipeline.Workspace) $(Agent.TempDirectory) $(System.DefaultWorkingDirectory)

# Runtime parameters (typed, shown in the Run dialog)
parameters:
  - name: deployTo
    type: string
    default: staging
    values: [staging, production]
  - name: runLoadTests
    type: boolean
    default: false
# Manage variable groups from the CLI
az pipelines variable-group create --name shop-common --variables Region=westeurope LogLevel=Information --authorize true
az pipelines variable-group variable create --group-id 7 --name ApiBaseUrl --value https://shop-api.azurewebsites.net
az pipelines variable-group variable create --group-id 7 --name SqlPassword --value 'S3cret!' --secret true

# Pipeline-level secret variable (Edit → Variables in the UI, or:)
az pipelines variable create --pipeline-id 42 --name NUGET_TOKEN --value $TOKEN --secret true

# Key Vault-linked group: Library → + Variable group → "Link secrets from an Azure key vault as variables"
# (needs a service connection with Get/List on secrets; secrets refresh at run start)

# Custom build number
#   name: 1.0.$(Rev:r)                     # top of the YAML
#   name: $(Date:yyyyMMdd)$(Rev:.r)

Templates: reuse across pipelines

Templates factor out steps, jobs, stages or variables into files with typed parameters, often in a central repo consumed via a resources.repositories reference. Extends templates enforce a required skeleton (security scans, approvals) that consuming pipelines cannot bypass — combine with a required-template check on the environment.

# templates/dotnet-build.yml — step template with parameters
parameters:
  - name: project
    type: string
  - name: configuration
    type: string
    default: Release
  - name: runTests
    type: boolean
    default: true

steps:
  - task: UseDotNet@2
    inputs: { packageType: sdk, version: 9.0.x }
  - script: dotnet build ${{ parameters.project }} -c ${{ parameters.configuration }}
  - ${{ if parameters.runTests }}:
      - script: dotnet test ${{ parameters.project }} --no-build -c ${{ parameters.configuration }}

# ---------------------------------------------------------------
# templates/deploy-webapp.yml — job template
parameters:
  - name: environment
    type: string
  - name: serviceConnection
    type: string
  - name: appName
    type: string

jobs:
  - deployment: Deploy_${{ parameters.environment }}
    environment: ${{ parameters.environment }}
    strategy:
      runOnce:
        deploy:
          steps:
            - download: current
              artifact: api
            - task: AzureWebApp@1
              inputs:
                azureSubscription: ${{ parameters.serviceConnection }}
                appName: ${{ parameters.appName }}
                package: $(Pipeline.Workspace)/api

# ---------------------------------------------------------------
# azure-pipelines.yml — consuming templates from a shared repo
resources:
  repositories:
    - repository: templates
      type: git
      name: Platform/pipeline-templates
      ref: refs/tags/v2

stages:
  - stage: Build
    jobs:
      - job: Build
        steps:
          - template: templates/dotnet-build.yml@templates
            parameters: { project: src/Shop.Api, runTests: true }
          - publish: $(Build.ArtifactStagingDirectory)/api
            artifact: api

  - stage: Staging
    jobs:
      - template: templates/deploy-webapp.yml@templates
        parameters: { environment: shop-staging, serviceConnection: sc-shop-nonprod, appName: shop-api }

# ---------------------------------------------------------------
# Extends template: the platform team owns the skeleton; teams fill in `buildSteps`

Environments, approvals and checks

An environment is a named target (staging, production) with deployment history, traceability to work items/commits, and checks: manual approvals, business hours, branch control (only main may deploy), required template, Azure Monitor alert gates, invoke REST/Function gates, and exclusive lock. Checks run before the deployment job starts and are configured on the environment, not in YAML — so nobody can edit them out of a pipeline.

# YAML side: just target the environment
- stage: Production
  jobs:
    - deployment: DeployProd
      environment: shop-production           # checks configured on this environment apply
      strategy:
        runOnce:
          deploy:
            steps:
              - download: current
                artifact: api
              - task: AzureWebApp@1
                inputs: { azureSubscription: sc-shop-prod, appName: shop-api, package: $(Pipeline.Workspace)/api }

# Environment with resources (Kubernetes namespace or VM) → richer strategies
- deployment: DeployK8s
  environment: shop-production.orders        # environment.resource
  strategy:
    canary:
      increments: [10, 50]
      preDeploy:  { steps: [ { script: echo baseline } ] }
      deploy:
        steps:
          - task: KubernetesManifest@1
            inputs:
              action: deploy
              strategy: canary
              percentage: $(strategy.increment)
              manifests: k8s/orders-api.yaml
      postRouteTraffic:
        steps:
          - script: ./scripts/check-error-rate.sh    # fail → automatic rollback of the canary
      on:
        failure:
          steps:
            - task: KubernetesManifest@1
              inputs: { action: reject, strategy: canary, manifests: k8s/orders-api.yaml }
        success:
          steps:
            - task: KubernetesManifest@1
              inputs: { action: promote, strategy: canary, manifests: k8s/orders-api.yaml }
# Environments and checks are configured in the portal (Pipelines → Environments → ... → Approvals and checks)
# or via the REST API. Typical production set:
#   • Approvals: 2 of [release-managers], timeout 24h, approver cannot be the requester
#   • Branch control: refs/heads/main only, require branch protection
#   • Business hours: Mon–Thu 09:00–16:00 CET
#   • Required template: templates/secure-pipeline.yml@templates
#   • Exclusive lock: one deployment at a time
#   • Azure Monitor: no Sev0/1 alerts on the prod resource group in the last 30 min (evaluated after deploy in postRouteTraffic)

# Same checks exist on service connections and agent pools — protect the prod service connection too.

# REST: list environments / deployment history
az devops invoke --area distributedtask --resource environments --route-parameters project=Shop --api-version 7.1-preview -o table
az pipelines runs list --pipeline-ids 42 --branch main --top 5 -o table

Artifacts: pipeline artifacts and Azure Artifacts feeds

Two different things. Pipeline artifacts (publish/download) carry build output between jobs, stages and pipelines — build once, deploy the same bytes everywhere. Azure Artifacts hosts package feeds (NuGet, npm, PyPI, Maven, Universal Packages) with upstream sources to proxy nuget.org/PyPI, and retention/views (@Local, @Prerelease, @Release) for promotion.

# Pipeline artifacts between stages
- publish: $(Build.ArtifactStagingDirectory)/api
  artifact: api

- download: current            # in a later job/stage: everything published by this run
  artifact: api
  # lands in $(Pipeline.Workspace)/api

# Consume an artifact from ANOTHER pipeline (e.g. a shared library build)
resources:
  pipelines:
    - pipeline: shared           # alias
      source: Platform.SharedLib # pipeline name
      branch: main
      trigger: true              # this pipeline runs when that one completes
steps:
  - download: shared
    artifact: lib

# Publish a NuGet package to an Azure Artifacts feed
- script: dotnet pack src/Shop.Contracts -c Release -o $(Build.ArtifactStagingDirectory)/nupkg /p:PackageVersion=1.0.$(Build.BuildId)
- task: NuGetAuthenticate@1
- script: dotnet nuget push "$(Build.ArtifactStagingDirectory)/nupkg/*.nupkg" --source "https://pkgs.dev.azure.com/contoso/_packaging/shop/nuget/v3/index.json" --api-key az

# Restore from the feed (nuget.config in the repo points at the feed; upstream to nuget.org enabled)
- task: NuGetAuthenticate@1
- script: dotnet restore --configfile nuget.config

Service connections and identity

A service connection is how a pipeline authenticates to Azure, ACR, GitHub, SonarQube and so on. For Azure, use workload identity federation (OIDC — no secret to rotate) scoped to a resource group, and protect production connections with approvals and pipeline permissions. Never put subscription-wide Owner on a pipeline identity.

# Create an Azure RM service connection with workload identity federation (recommended)
# Portal: Project Settings → Service connections → New → Azure Resource Manager → Workload Identity federation (automatic)
# CLI (manual federation):
APP_ID=$(az ad app create --display-name sc-shop-prod --query appId -o tsv)
SP_ID=$(az ad sp create --id $APP_ID --query id -o tsv)
az role assignment create --assignee $SP_ID --role Contributor --scope /subscriptions/<sub>/resourceGroups/rg-shop
az ad app federated-credential create --id $APP_ID --parameters '{
  "name": "azdo-shop-prod",
  "issuer": "https://vstoken.dev.azure.com/<org-id>",
  "subject": "sc://contoso/Shop/sc-shop-prod",
  "audiences": ["api://AzureADTokenExchange"] }'
az devops service-endpoint azurerm create --name sc-shop-prod --azure-rm-service-principal-id $APP_ID \
  --azure-rm-subscription-id <sub> --azure-rm-subscription-name Prod --azure-rm-tenant-id <tenant>   # then switch auth to WIF in the portal

# Restrict which pipelines may use it: Service connection → Security → Pipeline permissions (uncheck "Grant access to all")
# Add an approval check to sc-shop-prod so any first use by a pipeline needs sign-off.

# GitHub (for repos/releases), Generic (REST gates), SonarCloud.
# Using the connection in tasks
- task: AzureCLI@2

Deploying: App Service, containers, database migrations

Deploy the artifact, not the source. App Service: zip deploy to a slot, warm up, swap. Containers: push to ACR with the build ID as tag, then update the Container App / AKS manifest. Database: run migrations as an explicit, idempotent step before the app deploy, using a script or bundle produced at build time, from an agent that can reach the database.

Release strategies and rollback

Blue/green: two identical environments, switch traffic (slot swap). Canary: small percentage first, watch metrics, ramp. Rolling: replace instances a few at a time. Feature flags: deploy dark, enable per user/percentage, kill-switch without a deploy. Pick per risk: flags for behaviour changes, canary for infrastructure/runtime changes, blue/green when you need instant rollback. Always have a rehearsed rollback.

# Canary on Container Apps with metric gate and automatic rollback
- stage: Canary
  jobs:
    - deployment: Canary
      environment: shop-production
      strategy:
        runOnce:
          deploy:
            steps:
              - task: AzureCLI@2
                displayName: 10% to new revision
                inputs:
                  azureSubscription: sc-shop-prod
                  scriptType: bash
                  scriptLocation: inlineScript
                  inlineScript: |
                    az containerapp update -g rg-shop -n orders-api --image shopacr.azurecr.io/orders-api:$(Build.BuildId) --revision-suffix b$(Build.BuildId)
                    az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight latest=10
              - task: AzureCLI@2
                displayName: Watch error rate for 10 minutes
                inputs:
                  azureSubscription: sc-shop-prod
                  scriptType: bash
                  scriptLocation: inlineScript
                  inlineScript: |
                    sleep 600
                    ERR=$(az monitor app-insights query --app shop-ai --analytics-query \
                      "requests | where timestamp > ago(10m) and cloud_RoleInstance contains 'b$(Build.BuildId)' | summarize 100.0*countif(success==false)/count()" \
                      --query "tables[0].rows[0][0]" -o tsv)
                    echo "error rate: $ERR%"
                    awk "BEGIN{exit !($ERR > 1.0)}" && { echo "##vso[task.logissue type=error]Error rate too high"; exit 1; } || true
          on:
            failure:
              steps:
                - task: AzureCLI@2
                  displayName: Roll back canary
                  inputs:
                    azureSubscription: sc-shop-prod
                    scriptType: bash
                    scriptLocation: inlineScript
                    inlineScript: |
                      PREV=$(az containerapp revision list -g rg-shop -n orders-api --query "[?properties.trafficWeight==\`90\`].name | [0]" -o tsv)
                      az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight $PREV=100
            success:
              steps:
                - task: AzureCLI@2
                  displayName: Promote to 100%
                  inputs:
                    azureSubscription: sc-shop-prod
                    scriptType: bash
                    scriptLocation: inlineScript
                    inlineScript: az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight latest=100
