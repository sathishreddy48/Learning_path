Almost every Azure conversation ends up at identity: who is calling, what are they allowed to do, and how did they prove it without a password in a config file. Tenants, app registrations, service principals and tokens

A tenant is a directory (users, groups, apps). An app registration is the global definition of an application (its ID, redirect URIs, exposed scopes, app roles). A service principal is that app's identity inside one tenant — the thing you assign roles to. Clients get ID tokens (who the user is, for sign-in) and access tokens (what the caller may do, sent to an API). Access tokens are JWTs whose aud is the API, scp lists delegated scopes and roles lists app roles.

# Create an API app registration that exposes a scope, and a client app that requests it
API_ID=$(az ad app create --display-name shop-api --identifier-uris api://shop-api --query appId -o tsv)
az ad sp create --id $API_ID                                    # service principal in this tenant

# Expose a delegated scope (Orders.Read) and an app role (Orders.Admin) — usually done in the portal blade
# "Expose an API" / "App roles"; from the CLI you patch the manifest:
az ad app update --id $API_ID --set api.oauth2PermissionScopes='[{"id":"'$(uuidgen)'","adminConsentDescription":"Read orders","adminConsentDisplayName":"Read orders","isEnabled":true,"type":"User","value":"Orders.Read"}]'

CLIENT_ID=$(az ad app create --display-name shop-web --web-redirect-uris https://localhost:5001/signin-oidc --query appId -o tsv)
az ad app permission add --id $CLIENT_ID --api $API_ID --api-permissions <scope-id>=Scope
az ad app permission admin-consent --id $CLIENT_ID

Scopes, app roles and consent

Delegated permissions (scopes) are used when a user is present — the effective permission is the intersection of what the user can do and what the app was granted. Application permissions (app roles with allowedMemberTypes: Application) are for daemons with no user. Users or admins must consent; tenant admins can grant consent for everyone. Design your API's permissions as coarse verbs (Orders.Read, Orders.ReadWrite) and keep authorization decisions inside the API.

// Enforce scopes / roles in ASP.NET Core with Microsoft.Identity.Web
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));   // reads TenantId, ClientId, Audience

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("Orders.Read", p => p.RequireScopeOrAppPermission(new[] { "Orders.Read", "Orders.ReadWrite" }, new[] { "Orders.Admin" }));
    o.AddPolicy("Orders.Admin", p => p.RequireRole("Orders.Admin"));            // app role → role claim
});

app.MapGet("/orders", (HttpContext ctx) => ...).RequireAuthorization("Orders.Read");
app.MapDelete("/orders/{id}", ...).RequireAuthorization("Orders.Admin");

// Inside a handler you can also assert:  ctx.VerifyUserHasAnyAcceptedScope("Orders.Read");
// appsettings.json
// "AzureAd": { "Instance": "https://login.microsoftonline.com/", "TenantId": "<tenant>", "ClientId": "<api app id>", "Audience": "api://shop-api" }
# FastAPI: validate the JWT against the tenant's JWKS and check scopes / roles
import httpx, jwt
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer

TENANT, AUDIENCE = "<tenant-id>", "api://shop-api"
ISSUER = f"https://login.microsoftonline.com/{TENANT}/v2.0"
jwks = jwt.PyJWKClient(f"https://login.microsoftonline.com/{TENANT}/discovery/v2.0/keys")
bearer = HTTPBearer()

def current_claims(cred: HTTPAuthorizationCredentials = Security(bearer)) -> dict:
    try:
        key = jwks.get_signing_key_from_jwt(cred.credentials).key
        return jwt.decode(cred.credentials, key, algorithms=["RS256"], audience=AUDIENCE, issuer=ISSUER)
    except jwt.PyJWTError as ex:
        raise HTTPException(401, str(ex))

def require(scopes=(), roles=()):
    def dep(claims: dict = Depends(current_claims)):
        have_scope = set(claims.get("scp", "").split()) & set(scopes)
        have_role = set(claims.get("roles", [])) & set(roles)
        if not (have_scope or have_role):
            raise HTTPException(403, "insufficient permissions")
        return claims
    return dep

@app.get("/orders", dependencies=[Depends(require(scopes={"Orders.Read", "Orders.ReadWrite"}, roles={"Orders.Admin"}))])
async def list_orders(): ...

The three OAuth 2.0 flows you need

Authorization code + PKCE for anything with a user (web apps, SPAs, mobile). Client credentials for daemons and service-to-service calls (prefer managed identity or federated credentials over a client secret). On-behalf-of when an API must call another API as the signed-in user. Implicit and resource-owner-password flows are legacy — do not use them.

Scope "<app-id-uri>/.default" means "everything statically granted to this app"
// 1) Auth code + PKCE — a Razor/Blazor/MVC app signs the user in and gets tokens for the API
builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection("AzureAd"))
    .EnableTokenAcquisitionToCallDownstreamApi(new[] { "api://shop-api/Orders.Read" })
    .AddInMemoryTokenCaches();                               // distributed cache (Redis/SQL) in production

// 2) Client credentials — a worker with no user
var app = ConfidentialClientApplicationBuilder.Create(clientId)
    .WithAuthority($"https://login.microsoftonline.com/{tenantId}")
    .WithClientSecret(secret)                                // or .WithCertificate(cert) / .WithClientAssertion(...)
    .Build();
var result = await app.AcquireTokenForClient(new[] { "api://shop-api/.default" }).ExecuteAsync();
http.DefaultRequestHeaders.Authorization = new("Bearer", result.AccessToken);

// 3) On-behalf-of — the API exchanges the incoming user token for a Graph token
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"))
    .EnableTokenAcquisitionToCallDownstreamApi()
    .AddMicrosoftGraph(builder.Configuration.GetSection("Graph"))     // GraphServiceClient with OBO baked in
    .AddDistributedTokenCaches();

app.MapGet("/me", async (GraphServiceClient graph) => (await graph.Me.GetAsync())!.DisplayName)
   .RequireAuthorization();

# 3) On-behalf-of (API → Graph as the user)

Token caching, Microsoft Graph and downstream APIs

Acquire tokens through a library (MSAL / Microsoft.Identity.Web / azure-identity) and never cache them yourself in a static field. Libraries handle refresh, the cache and retries. Use the downstream API abstraction so handlers ask for a typed client, not a token. For Graph, request the minimum permission (User.Read, not Directory.Read.All).

// Typed downstream API client — token acquisition is invisible to the handler
builder.Services.AddAuthentication(...)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"))
    .EnableTokenAcquisitionToCallDownstreamApi()
    .AddDownstreamApi("Inventory", builder.Configuration.GetSection("InventoryApi"))   // BaseUrl + Scopes
    .AddDistributedTokenCaches();
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = builder.Configuration["Redis"]);   // token cache store

app.MapGet("/orders/{id}/stock", async (int id, IDownstreamApi api) =>
    await api.GetForUserAsync<StockDto>("Inventory", options => options.RelativePath = $"stock/{id}"));

// Daemon calling it as the app itself:
//   await api.GetForAppAsync<StockDto>("Inventory", o => o.RelativePath = "stock/1");

// Handling the classic errors
//   MsalUiRequiredException  → the user must re-consent / re-sign in (send a 401 with a challenge)
//   401 from downstream       → token for the wrong audience; check the scope you requested
# Microsoft Graph SDK with azure-identity (works with MI in Azure, az login locally)
from azure.identity import DefaultAzureCredential
from msgraph import GraphServiceClient

graph = GraphServiceClient(DefaultAzureCredential(), scopes=["https://graph.microsoft.com/.default"])
me_or_app = await graph.users.by_user_id("ada@contoso.com").get()          # needs User.Read.All app permission

# Calling your own API as the app, with a cached token (msal keeps it in memory; persist with SerializableTokenCache)
cache = msal.SerializableTokenCache()
cca = msal.ConfidentialClientApplication(CLIENT_ID, authority=AUTHORITY, client_credential=SECRET, token_cache=cache)
def bearer():
    r = cca.acquire_token_silent(["api://inventory/.default"], account=None) or cca.acquire_token_for_client(["api://inventory/.default"])
    if "access_token" not in r:
        raise RuntimeError(r.get("error_description"))
    return {"Authorization": f"Bearer {r['access_token']}"}

async with httpx.AsyncClient(base_url="https://inventory.contoso.com") as c:
    stock = (await c.get("/stock/1", headers=bearer())).json()

Azure RBAC vs app roles vs groups

Azure RBAC controls who can manage or access Azure resources (control plane and data plane: "Storage Blob Data Reader" on a container). App roles control what a user or service can do inside your application. Groups are how you assign either at scale; group claims can be emitted in the token (watch the 200-group overage limit — use app roles or the Graph checkMemberGroups call instead).

# Azure RBAC — resource permissions. Scope: management group / subscription / resource group / resource.
az role assignment create --assignee <object-id-or-upn> --role "Storage Blob Data Contributor"   --scope /subscriptions/<sub>/resourceGroups/rg-shop/providers/Microsoft.Storage/storageAccounts/stshop

# Who can do what here?
az role assignment list --scope /subscriptions/<sub>/resourceGroups/rg-shop --include-inherited -o table

# Custom role with just what a deploy pipeline needs
az role definition create --role-definition '{
  "Name": "Shop Deployer", "IsCustom": true,
  "Actions": ["Microsoft.Web/sites/*", "Microsoft.Web/serverfarms/read", "Microsoft.Resources/deployments/*"],
  "NotActions": ["Microsoft.Web/sites/config/list/action"],
  "AssignableScopes": ["/subscriptions/<sub>/resourceGroups/rg-shop"] }'

# App roles — application permissions. Assign a user/group/SP to a role on the API's service principal.
az rest --method POST --uri "https://graph.microsoft.com/v1.0/servicePrincipals/<api-sp-id>/appRoleAssignedTo"   --body '{"principalId":"<group-id>","resourceId":"<api-sp-id>","appRoleId":"<role-id>"}'
// Group-based authorization without token bloat: map groups to app roles at the tenant, or check membership via Graph
builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("Finance", p => p.RequireClaim("groups", "d0f1…finance-group-id"));   // only if groups claim is emitted
});

// Resource-based authorization: the rule depends on the data (owner of the order), not just a role
public class OrderOwnerHandler : AuthorizationHandler<OperationAuthorizationRequirement, Order>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, OperationAuthorizationRequirement req, Order order)
    {
        var oid = ctx.User.FindFirstValue("http://schemas.microsoft.com/identity/claims/objectidentifier");
        if (order.CustomerOid == oid || ctx.User.IsInRole("Orders.Admin")) ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
// usage: var ok = await authz.AuthorizeAsync(User, order, Operations.Read); if (!ok.Succeeded) return Results.Forbid();

No secrets: managed identity and workload identity federation

Inside Azure use managed identity (see Azure Services). Outside Azure — GitHub Actions, AKS pods, another cloud — use workload identity federation: the external identity provider issues a token, Entra trusts it via a federated credential on the app registration, and exchanges it for an Entra token. No client secret exists to leak or expire.

# Federated credential for GitHub Actions on the main branch of contoso/shop
az ad app federated-credential create --id $APP_ID --parameters '{
  "name": "github-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:contoso/shop:ref:refs/heads/main",
  "audiences": ["api://AzureADTokenExchange"] }'
# For a GitHub environment:  "subject": "repo:contoso/shop:environment:production"

# Federated credential for an AKS workload identity (service account in a namespace)
ISSUER=$(az aks show -g rg-shop -n aks-shop --query oidcIssuerProfile.issuerUrl -o tsv)
az identity federated-credential create --name orders-api -g rg-shop --identity-name id-orders-api   --issuer $ISSUER --subject system:serviceaccount:shop:orders-api --audiences api://AzureADTokenExchange
permissions:
  id-token: write        # allow the job to request an OIDC token
  contents: read

steps:
  - uses: azure/login@v2
    with:
      client-id: ${{ vars.AZURE_CLIENT_ID }}          # not secrets — nothing here is sensitive
      tenant-id: ${{ vars.AZURE_TENANT_ID }}
      subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
  - run: az webapp deploy -g rg-shop -n shop-api --src-path app.zip
# In an AKS pod with workload identity, the projected token + env vars are all you need:
from azure.identity import DefaultAzureCredential          # picks WorkloadIdentityCredential automatically
from azure.keyvault.secrets import SecretClient
client = SecretClient("https://kv-shop.vault.azure.net", DefaultAzureCredential())
print(client.get_secret("DbPassword").value)

# Env vars set by the webhook: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_FEDERATED_TOKEN_FILE, AZURE_AUTHORITY_HOST
# Pod spec needs:  serviceAccountName: orders-api   and label  azure.workload.identity/use: "true"

External ID (B2C) for customer-facing apps

Employee identities live in your workforce tenant; customers should not. Microsoft Entra External ID (successor to Azure AD B2C) gives you a separate tenant with sign-up/sign-in user flows, social identity providers, custom branding and custom attributes. Your API code is the same JWT-bearer validation — only the authority and claims differ.

// appsettings.json for an External ID (CIAM) tenant
// "AzureAd": {
//   "Instance": "https://contosocustomers.ciamlogin.com/",
//   "TenantId": "<tenant-id>", "ClientId": "<client-id>",
//   "CallbackPath": "/signin-oidc", "SignedOutCallbackPath": "/signout-callback-oidc" }
builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApp(builder.Configuration.GetSection("AzureAd"));

// Custom attributes come through as extension claims:
var tier = User.FindFirst("extension_LoyaltyTier")?.Value;

// Legacy B2C with user flows adds the policy name to the authority:
// "Instance": "https://contoso.b2clogin.com", "Domain": "contoso.onmicrosoft.com", "SignUpSignInPolicyId": "B2C_1_susi"
# Streamlit/Flask/FastAPI web app against External ID with msal — only the authority changes
AUTHORITY = "https://contosocustomers.ciamlogin.com/<tenant-id>"
cca = msal.ConfidentialClientApplication(CLIENT_ID, authority=AUTHORITY, client_credential=SECRET)
flow = cca.initiate_auth_code_flow(scopes=[], redirect_uri="https://shop.contoso.com/callback")   # openid/profile implied
# ... on callback:
result = cca.acquire_token_by_auth_code_flow(flow, request.args)
claims = result["id_token_claims"]         # sub/oid, email, extension_LoyaltyTier, ...

Conditional Access, MFA and PIM

Identity is the perimeter. Conditional Access policies evaluate signals (user, device, location, risk) and require MFA, a compliant device or block. PIM makes privileged roles just-in-time with approval and audit. Developers feel this as claims challenges (acrs) and as "why did my daemon get blocked" — service principals are governed by separate workload-identity policies.

// Continuous Access Evaluation / claims challenge: Graph says "step up", your API relays it to the client
try
{
    return await graph.Me.Messages.GetAsync();
}
catch (ServiceException ex) when (ex.ResponseHeaders.WwwAuthenticate.Any())
{
    var claims = WwwAuthenticateParameters.GetClaimChallengeFromResponseHeaders(ex.ResponseHeaders);
    if (claims is not null)
    {
        Response.Headers.WWWAuthenticate = $"Bearer realm=\"\", error=\"insufficient_claims\", claims=\"{claims}\"";
        return Results.Unauthorized();       // client re-authenticates with the claims parameter
    }
    throw;
}
# Read-only look at Conditional Access policies (needs Policy.Read.All)
az rest --method GET --uri "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies" --query "value[].{name:displayName,state:state}" -o table

# PIM: activate an eligible role for 2 hours with a justification (Graph beta / portal)
az rest --method POST --uri "https://graph.microsoft.com/v1.0/roleManagement/directory/roleAssignmentScheduleRequests" --body '{
  "action": "selfActivate", "principalId": "<me>", "roleDefinitionId": "<role>", "directoryScopeId": "/",
  "justification": "Rotate prod cert", "scheduleInfo": { "expiration": { "type": "afterDuration", "duration": "PT2H" } } }'
