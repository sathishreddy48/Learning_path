Azure Networking for App Developers

You will not design the corporate network, but you will be asked why the API cannot reach the database, why the private endpoint resolves to a public IP, or which load balancer sits in front of the app. This page gives you the model and the CLI/Bicep to build a private, zone-redundant web tier — with the .NET and Python bits where the app has to cooperate.

VNets, subnets and Network Security Groups

A VNet is a private address space in a region; subnets carve it up and are where resources get NICs. NSGs are stateful allow/deny rules attached to a subnet or NIC, evaluated by priority; service tags (AzureCloud, Storage) and ASGs save you from IP lists. Many PaaS services need a delegated subnet of their own.

az network vnet create -g rg-shop -n vnet-shop --address-prefixes 10.10.0.0/16   --subnet-name snet-app --subnet-prefixes 10.10.1.0/24
az network vnet subnet create -g rg-shop --vnet-name vnet-shop -n snet-pe   --address-prefixes 10.10.2.0/24
az network vnet subnet create -g rg-shop --vnet-name vnet-shop -n snet-appsvc --address-prefixes 10.10.3.0/24   --delegations Microsoft.Web/serverFarms                 # required for App Service VNet integration

# NSG: allow HTTPS from the Application Gateway subnet only, deny everything else inbound
az network nsg create -g rg-shop -n nsg-app
az network nsg rule create -g rg-shop --nsg-name nsg-app -n AllowAppGw --priority 100 --direction Inbound   --source-address-prefixes 10.10.0.0/24 --destination-port-ranges 443 --protocol Tcp --access Allow
az network nsg rule create -g rg-shop --nsg-name nsg-app -n DenyAllIn --priority 4096 --direction Inbound --access Deny --protocol '*'
az network vnet subnet update -g rg-shop --vnet-name vnet-shop -n snet-app --network-security-group nsg-app

# Debug "why can't A reach B": effective rules and Network Watcher
az network nic list-effective-nsg --ids <nic-id>
az network watcher test-ip-flow --vm vm-app --direction Outbound --protocol TCP --local 10.10.1.4:5000 --remote 10.10.2.5:1433
resource vnet 'Microsoft.Network/virtualNetworks@2023-11-01' = {
  name: 'vnet-shop'
  location: location
  properties: {
    addressSpace: { addressPrefixes: [ '10.10.0.0/16' ] }
    subnets: [
      { name: 'snet-app',    properties: { addressPrefix: '10.10.1.0/24', networkSecurityGroup: { id: nsg.id } } }
      { name: 'snet-pe',     properties: { addressPrefix: '10.10.2.0/24', privateEndpointNetworkPolicies: 'Enabled' } }
      { name: 'snet-appsvc', properties: { addressPrefix: '10.10.3.0/24', delegations: [ { name: 'web', properties: { serviceName: 'Microsoft.Web/serverFarms' } } ] } }
    ]
  }
}

Private Link and Private Endpoints

A private endpoint puts a NIC in your subnet with a private IP that fronts a PaaS resource (SQL, Storage, Key Vault, Cosmos…). Combined with disabling public network access, the service is only reachable from your VNet. The catch is DNS: stshop.blob.core.windows.net must resolve to the private IP, which is what the privatelink.* private DNS zone does. Most "private endpoint doesn't work" tickets are DNS.

# 1) Private endpoint for a storage account's blob sub-resource
az network private-endpoint create -g rg-shop -n pe-stshop-blob --vnet-name vnet-shop --subnet snet-pe   --private-connection-resource-id $(az storage account show -g rg-shop -n stshop --query id -o tsv)   --group-id blob --connection-name stshop-blob

# 2) Private DNS zone + link to the VNet + auto-registered A record
az network private-dns zone create -g rg-shop -n privatelink.blob.core.windows.net
az network private-dns link vnet create -g rg-shop -z privatelink.blob.core.windows.net -n link-vnet-shop -v vnet-shop -e false
az network private-endpoint dns-zone-group create -g rg-shop --endpoint-name pe-stshop-blob -n default   --private-dns-zone privatelink.blob.core.windows.net --zone-name blob

# 3) Close the front door
az storage account update -g rg-shop -n stshop --public-network-access Disabled

# Verify from inside the VNet — should print 10.10.2.x
nslookup stshop.blob.core.windows.net
# Common sub-resource names: sqlServer, vault, blob/queue/table, Sql (Cosmos), sites (App Service), namespace (Service Bus)
// Nothing changes in app code — the SDK still uses the public hostname, DNS does the rest.
var blob = new BlobServiceClient(new Uri("https://stshop.blob.core.windows.net"), new DefaultAzureCredential());

// But local development can no longer reach the resource. Options:
//  • VPN / Bastion into the VNet     • a dev storage account with public access + IP rule
//  • Azurite / SQL in Docker locally  (see Docker & Containers)
if (builder.Environment.IsDevelopment())
    builder.Services.AddSingleton(new BlobServiceClient("UseDevelopmentStorage=true"));   // Azurite

Service endpoints vs private endpoints (source NAT vs private IP; who can use them); the DNS resolution chain with a custom DNS server / on-prem; why you keep one private DNS zone per service in the hub; cost per endpoint.

VNet integration for App Service, Functions and Container Apps

Inbound privacy is a private endpoint on the app; outbound privacy is VNet integration — the app's outbound traffic exits through a delegated subnet so it can reach private endpoints and on-prem. Container Apps environments and AKS live inside a VNet natively. Set WEBSITE_VNET_ROUTE_ALL=1 (now "Route All") so all outbound traffic, not just RFC1918, goes via the VNet.

# App Service: outbound via VNet
az webapp vnet-integration add -g rg-shop -n shop-api --vnet vnet-shop --subnet snet-appsvc
az webapp config set -g rg-shop -n shop-api --vnet-route-all-enabled true

# App Service: inbound only via private endpoint (Premium v2/v3)
az network private-endpoint create -g rg-shop -n pe-shop-api --vnet-name vnet-shop --subnet snet-pe   --private-connection-resource-id $(az webapp show -g rg-shop -n shop-api --query id -o tsv) --group-id sites --connection-name shop-api
az webapp update -g rg-shop -n shop-api --set publicNetworkAccess=Disabled

# Container Apps: environment inside your VNet with an internal-only ingress
az containerapp env create -g rg-shop -n cae-shop --location westeurope   --infrastructure-subnet-resource-id $(az network vnet subnet show -g rg-shop --vnet-name vnet-shop -n snet-aca --query id -o tsv)   --internal-only true
# Sanity-check what the app can reach from inside the platform (run in Kudu / a debug console / a startup probe)
import socket, ssl, sys
def check(host, port=443):
    try:
        ip = socket.gethostbyname(host)
        with socket.create_connection((ip, port), timeout=3) as s:
            if port == 443:
                ssl.create_default_context().wrap_socket(s, server_hostname=host).close()
        print(f"OK   {host} -> {ip}:{port}")
    except Exception as ex:
        print(f"FAIL {host}: {ex}")
for h in ["stshop.blob.core.windows.net", "sql-shop.database.windows.net", "kv-shop.vault.azure.net"]:
    check(h, 1433 if "database" in h else 443)
# Private IPs (10.x) mean DNS + integration are working; public IPs mean the private DNS zone is not linked.
Interview angle

Inbound vs outbound privacy and which feature covers each; the delegated subnet sizing rule (/26 minimum for scale-out); Route All and what breaks when NAT gateway is not attached (SNAT port exhaustion).

Choosing a load balancer

Four services, two axes: global vs regional and HTTP(S) vs any TCP/UDP. Front Door — global, layer 7, CDN + WAF + TLS at the edge. Application Gateway — regional, layer 7, WAF, in your VNet. Load Balancer — regional, layer 4, fastest, used inside AKS and for VMs. Traffic Manager — global DNS-based routing for anything. Typical web stack: Front Door → App Gateway (or directly to App Service / Container Apps via Private Link origin).

ServiceScopeLayerUse when
Azure Front DoorGlobal (edge PoPs)7 (HTTP/S)Multi-region web apps, caching, WAF at the edge, Private Link to origins
Application GatewayRegional, in VNet7 (HTTP/S)Path/host routing inside a VNet, WAF, mTLS, AKS ingress (AGIC / App Gateway for Containers)
Load BalancerRegional (Standard also cross-region)4 (TCP/UDP)VMs, AKS Services of type LoadBalancer, non-HTTP protocols, lowest latency
Traffic ManagerGlobal (DNS)DNSRouting by geography/performance/priority for any endpoint type; no data path
# Front Door Standard with a WAF policy, routing to an App Service origin, health-probed on /health
az afd profile create -g rg-shop --profile-name fd-shop --sku Standard_AzureFrontDoor
az afd endpoint create -g rg-shop --profile-name fd-shop --endpoint-name shop --enabled-state Enabled
az afd origin-group create -g rg-shop --profile-name fd-shop --origin-group-name og-api   --probe-path /health --probe-protocol Https --probe-interval-in-seconds 30 --sample-size 4 --successful-samples-required 3 --additional-latency-in-milliseconds 50
az afd origin create -g rg-shop --profile-name fd-shop --origin-group-name og-api --origin-name api-weu   --host-name shop-api.azurewebsites.net --origin-host-header shop-api.azurewebsites.net --priority 1 --weight 1000 --enabled-state Enabled
az afd route create -g rg-shop --profile-name fd-shop --endpoint-name shop --route-name api --origin-group og-api   --supported-protocols Https --https-redirect Enabled --forwarding-protocol HttpsOnly --patterns-to-match "/api/*"

# Lock the origin so only Front Door can reach it (App Service access restriction on the AFD service tag + X-Azure-FDID header)
az webapp config access-restriction add -g rg-shop -n shop-api --rule-name afd --priority 100 --service-tag AzureFrontDoor.Backend   --http-header x-azure-fdid=$(az afd profile show -g rg-shop --profile-name fd-shop --query frontDoorId -o tsv)
// Behind any layer-7 proxy the app must trust forwarded headers to see the real scheme/host/client IP
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto | ForwardedHeaders.XForwardedHost;
    o.KnownNetworks.Clear(); o.KnownProxies.Clear();     // App Service/AGW front the app; tighten in self-hosted scenarios
});
var app = builder.Build();
app.UseForwardedHeaders();      // before UseHttpsRedirection / auth — otherwise redirects loop and cookies fail
app.UseHttpsRedirection();

// Health endpoint the probes hit: cheap, no auth, checks dependencies you can actually recover from
app.MapHealthChecks("/health", new() { Predicate = r => r.Tags.Contains("ready") }).AllowAnonymous();
// Reject traffic not from Front Door as defence in depth
app.Use(async (ctx, next) =>
{
    if (ctx.Request.Headers["X-Azure-FDID"] != builder.Configuration["FrontDoorId"]) { ctx.Response.StatusCode = 403; return; }
    await next();
});

Front Door vs Application Gateway (global/edge vs regional/VNet) and when you would use both; layer 4 vs 7; how you prevent origin bypass; health probe design; session affinity and why you'd rather not need it.

Application Gateway and the Web Application Firewall

Application Gateway v2 is a regional reverse proxy: listeners (host + port + cert), rules (path-based routing), backend pools (App Service, VMs, AKS, IPs) and HTTP settings (probe, cookie affinity, connection draining). The WAF applies the OWASP Core Rule Set in Detection or Prevention mode; tune false positives with exclusions and custom rules rather than disabling rule groups.

az network application-gateway create -g rg-shop -n agw-shop --sku WAF_v2 --capacity 2 --zones 1 2 3   --vnet-name vnet-shop --subnet snet-agw --public-ip-address pip-agw --priority 100   --frontend-port 443 --http-settings-port 443 --http-settings-protocol Https   --servers shop-api.azurewebsites.net --key-vault-secret-id https://kv-shop.vault.azure.net/secrets/cert-shop

# Path-based routing: /api/* → API pool, everything else → SPA pool
az network application-gateway address-pool create -g rg-shop --gateway-name agw-shop -n pool-spa --servers shop-web.azurewebsites.net
az network application-gateway url-path-map create -g rg-shop --gateway-name agw-shop -n paths --rule-name api --paths "/api/*"   --address-pool appGatewayBackendPool --http-settings appGatewayBackendHttpSettings --default-address-pool pool-spa --default-http-settings appGatewayBackendHttpSettings

# WAF policy: Prevention mode, CRS 3.2, exclude a noisy rule for one header
az network application-gateway waf-policy create -g rg-shop -n waf-shop
az network application-gateway waf-policy policy-setting update -g rg-shop --policy-name waf-shop --mode Prevention --state Enabled --request-body-check true
az network application-gateway waf-policy managed-rule rule-set add -g rg-shop --policy-name waf-shop --type OWASP --version 3.2
az network application-gateway waf-policy managed-rule exclusion add -g rg-shop --policy-name waf-shop   --match-variable RequestHeaderNames --selector-match-operator Equals --selector "x-custom-json"
// What is the WAF blocking?  (diagnostic setting → Log Analytics)
AzureDiagnostics
| where Category == "ApplicationGatewayFirewallLog" and action_s == "Blocked"
| summarize hits = count() by ruleId_s, Message, requestUri_s
| order by hits desc
| take 20
Interview angle

Listeners vs rules vs HTTP settings; end-to-end TLS vs TLS termination; WAF Detection → Prevention rollout and how you tune false positives; App Gateway for Containers as the AKS ingress; zone redundancy and autoscaling of v2.

Azure DNS, private DNS zones and custom domains

Public Azure DNS hosts your zones (A/AAAA/CNAME/TXT, alias records to Azure resources). Private DNS zones resolve names inside VNets (and are how private endpoints work). With on-prem DNS in the mix, DNS Private Resolver forwards queries between the two. Custom domains on App Service / Front Door need a TXT (verification) and CNAME/A, plus a managed or Key Vault certificate.

# Public zone and records
az network dns zone create -g rg-dns -n contoso.com
az network dns record-set cname set-record -g rg-dns -z contoso.com -n www --cname shop.z01.azurefd.net
az network dns record-set txt add-record -g rg-dns -z contoso.com -n _dnsauth.www --value "<afd-validation-token>"
az network dns record-set a create -g rg-dns -z contoso.com -n apex --target-resource $(az network public-ip show -g rg-shop -n pip-agw --query id -o tsv)   # alias record

# Custom domain + managed cert on Front Door
az afd custom-domain create -g rg-shop --profile-name fd-shop --custom-domain-name www --host-name www.contoso.com   --certificate-type ManagedCertificate --minimum-tls-version TLS12
az afd route update -g rg-shop --profile-name fd-shop --endpoint-name shop --route-name api --custom-domains www

# Private DNS: one zone per service, linked to every spoke VNet
for z in privatelink.database.windows.net privatelink.vaultcore.azure.net privatelink.blob.core.windows.net; do
  az network private-dns zone create -g rg-hub -n $z
  az network private-dns link vnet create -g rg-hub -z $z -n link-shop -v $(az network vnet show -g rg-shop -n vnet-shop --query id -o tsv) -e false
done
# Automate DNS from a pipeline / script with the management SDK
from azure.identity import DefaultAzureCredential
from azure.mgmt.dns import DnsManagementClient

dns = DnsManagementClient(DefaultAzureCredential(), SUBSCRIPTION_ID)
dns.record_sets.create_or_update("rg-dns", "contoso.com", "api", "CNAME",
    {"ttl": 300, "cname_record": {"cname": "shop.z01.azurefd.net"}})
for rs in dns.record_sets.list_by_dns_zone("rg-dns", "contoso.com"):
    print(rs.name, rs.type.split("/")[-1], rs.ttl)
Interview angle

Alias records vs CNAME at the apex; TTL and cutover planning; how private endpoint DNS works end to end including on-prem resolvers; certificate renewal (managed vs Key Vault) and where it breaks.

Hub-spoke, Azure Firewall and hybrid connectivity

Enterprises put shared services (firewall, VPN/ExpressRoute gateway, DNS, Bastion) in a hub VNet and each workload in a spoke peered to it. User-defined routes send spoke egress through Azure Firewall for inspection and FQDN filtering. VPN Gateway (encrypted over internet) or ExpressRoute (private circuit) connect on-prem. As a developer you mostly need to know: egress may be filtered by FQDN, and NAT gateway solves SNAT exhaustion.

# Peer spoke ↔ hub (both directions), let the spoke use the hub's gateway
az network vnet peering create -g rg-hub  -n hub-to-shop --vnet-name vnet-hub  --remote-vnet $(az network vnet show -g rg-shop -n vnet-shop --query id -o tsv) --allow-vnet-access --allow-gateway-transit
az network vnet peering create -g rg-shop -n shop-to-hub --vnet-name vnet-shop --remote-vnet $(az network vnet show -g rg-hub -n vnet-hub --query id -o tsv) --allow-vnet-access --use-remote-gateways

# Force spoke egress through the firewall (UDR on the app subnet)
FW_IP=$(az network firewall show -g rg-hub -n fw-hub --query "ipConfigurations[0].privateIPAddress" -o tsv)
az network route-table create -g rg-shop -n rt-shop
az network route-table route create -g rg-shop --route-table-name rt-shop -n default --address-prefix 0.0.0.0/0 --next-hop-type VirtualAppliance --next-hop-ip-address $FW_IP
az network vnet subnet update -g rg-shop --vnet-name vnet-shop -n snet-app --route-table rt-shop

# Allow the app to reach NuGet/PyPI and Microsoft endpoints by FQDN
az network firewall policy rule-collection-group collection add-filter-collection -g rg-hub --policy-name fwpol-hub --rcg-name apps   --name allow-package-feeds --collection-priority 200 --action Allow --rule-type ApplicationRule --rule-name feeds   --protocols Https=443 --source-addresses 10.10.0.0/16 --target-fqdns api.nuget.org pypi.org files.pythonhosted.org "*.blob.core.windows.net"

# NAT gateway for predictable outbound IPs and 64k SNAT ports per IP
az network nat gateway create -g rg-shop -n nat-shop --public-ip-addresses pip-nat --idle-timeout 4
az network vnet subnet update -g rg-shop --vnet-name vnet-shop -n snet-appsvc --nat-gateway nat-shop
// SNAT exhaustion shows up as random timeouts under load. The fix is in the app, not just the network:
//   1. One HttpClient per destination via IHttpClientFactory (connection pooling) — never new HttpClient() per call
builder.Services.AddHttpClient("inventory", c => c.BaseAddress = new Uri("https://inventory.contoso.com"))
    .SetHandlerLifetime(TimeSpan.FromMinutes(5))
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(2), MaxConnectionsPerServer = 100 });
//   2. Private endpoints for Azure services (traffic never SNATs to the internet)
//   3. NAT gateway on the integration subnet for whatever is left
Interview angle

Hub-spoke rationale; peering is non-transitive (why spoke-to-spoke goes via the hub/firewall); UDR + firewall for egress control; VPN vs ExpressRoute; SNAT exhaustion symptoms and the three fixes.
