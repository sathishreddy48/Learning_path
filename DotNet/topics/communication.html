APIs Beyond REST: gRPC, SignalR, GraphQL

Web API covers REST over HTTP, which is the right default and the wrong answer about a third of the time. This page is the other protocols and the decision between them — because the question is rarely "how does gRPC work" and almost always "why would you use gRPC here instead of REST", which is a design answer with latency, payload size, client reach and tooling in it.

Choosing between REST, gRPC, GraphQL and messaging

Lead with this, because every other question on the page is downstream of it. The four options differ along axes that are easy to name: who the client is, whether the call is request/response or a stream, whether the caller or the server decides the shape of the payload, and whether the caller needs an answer at all.

The honest default: REST at the edge, gRPC between your own services when the call volume justifies it, messaging whenever the caller does not need the answer now, GraphQL when you have several client teams with genuinely different data needs and you are prepared to own the N+1 and query-cost problems it brings.

Interview angle

Expect "when would you choose gRPC over REST?" and treat it as a trade-off question, not a feature list. Strong answer: internal service-to-service where the call is hot and both ends are yours, because you get a compiled contract, a smaller payload and HTTP/2 multiplexing; weak answer anywhere a browser, a third party or a human with curl is the client. Be ready for the counter-question — "what do you lose?" — human-readable payloads, trivial caching, and the ability for anyone to call it without the proto.

Practice
  • Take an existing REST endpoint and write down what would change if it were gRPC: contract, payload size, client, error handling.
  • Find a call in a system you know that should be a message rather than a synchronous request.
  • Argue the case against GraphQL for a single-client API.

gRPC in .NET: proto, codegen and the four call types

The .proto file is the contract, and it is compiled — both the server base class and the client are generated at build time, so a field rename is a compile error on both sides rather than a null at runtime. That is the main thing gRPC is buying you.

Four call shapes: unary (one in, one out), server streaming (one in, many out), client streaming (many in, one out), bidirectional (both, independently). Interviewers like asking which to use for a given scenario.

syntax = "proto3";

option csharp_namespace = "Shop.Grpc";
package shop.orders.v1;                    // version in the package, not the path

import "google/protobuf/timestamp.proto";

service Orders {
  rpc Get        (OrderRequest)        returns (OrderReply);              // unary
  rpc Watch      (OrderRequest)        returns (stream OrderEvent);       // server streaming
  rpc Import     (stream OrderRequest) returns (ImportSummary);           // client streaming
  rpc Sync       (stream OrderEvent)   returns (stream OrderEvent);       // bidirectional
}

message OrderRequest {
  string id = 1;                           // the FIELD NUMBER is the wire identity
}

message OrderReply {
  string id = 1;
  double total = 2;
  google.protobuf.Timestamp placed_at = 3;
  repeated OrderLine lines = 4;            // repeated == a list
  optional string coupon = 5;              // explicit presence: can tell unset from ""
}

message OrderLine {
  string sku = 1;
  int32 quantity = 2;
}

// Compatibility rules, which is what gets asked:
//   SAFE:   add a new field with a NEW number; rename a field (names are not on the wire)
//   BREAKS: change a field's number; change its type; reuse a deleted number
//   deleting: mark it so nobody reuses it
//   reserved 6, 7;
//   reserved "legacy_code";
// csproj: codegen happens at build
//   <ItemGroup>
//     <Protobuf Include="Protos/orders.proto" GrpcServices="Both" />
//   </ItemGroup>

// --- Server ---
public class OrderGrpcService(IOrderService svc) : Orders.OrdersBase
{
    // unary
    public override async Task<OrderReply> Get(OrderRequest req, ServerCallContext ctx)
        => Map(await svc.Get(req.Id, ctx.CancellationToken));

    // server streaming: push events as they happen, one connection
    public override async Task Watch(OrderRequest req,
        IServerStreamWriter<OrderEvent> stream, ServerCallContext ctx)
    {
        await foreach (var e in svc.WatchAsync(req.Id, ctx.CancellationToken))
            await stream.WriteAsync(e, ctx.CancellationToken);
    }

    // client streaming: a bulk upload that returns one summary
    public override async Task<ImportSummary> Import(
        IAsyncStreamReader<OrderRequest> stream, ServerCallContext ctx)
    {
        int count = 0;
        await foreach (var req in stream.ReadAllAsync(ctx.CancellationToken))
        {
            await svc.Import(req.Id, ctx.CancellationToken);
            count++;
        }
        return new ImportSummary { Imported = count };
    }
}

import grpc
from grpc import aio
import orders_pb2, orders_pb2_grpc

# --- Server ---
class OrderServicer(orders_pb2_grpc.OrdersServicer):
    async def Get(self, request, context):                      # unary
        order = await svc.get(request.id)
        return orders_pb2.OrderReply(id=order.id, total=float(order.total))

    async def Watch(self, request, context):                    # server streaming
        async for event in svc.watch(request.id):
            yield orders_pb2.OrderEvent(id=event.id, kind=event.kind)

    async def Import(self, request_iterator, context):          # client streaming
        count = 0
        async for req in request_iterator:
            await svc.import_(req.id)
            count += 1
        return orders_pb2.ImportSummary(imported=count)

async def serve():
    server = aio.server()
    orders_pb2_grpc.add_OrdersServicer_to_server(OrderServicer(), server)
    server.add_insecure_port("[::]:5001")
    await server.start()
    await server.wait_for_termination()

# --- Client --- one channel, reused; the same rule as .NET
channel = aio.insecure_channel("orders.internal:5001", options=[
    ("grpc.keepalive_time_ms", 60000),
    ("grpc.max_receive_message_length", 8 * 1024 * 1024),
])
client = orders_pb2_grpc.OrdersStub(channel)

reply = await client.Get(orders_pb2.OrderRequest(id=order_id), timeout=5.0)

    handle(event)
Interview angle

Two questions recur. "What are the four call types and when would you use each?" — have a scenario per type (unary: a lookup; server streaming: a live feed; client streaming: a bulk upload; bidirectional: a chat or a long-running negotiation). And "what can you change in a .proto without breaking clients?" — add fields with new numbers and rename freely, because names are not on the wire and field numbers are; never change or reuse a number, and reserved is how you stop someone doing it by accident.

Practice
  • Write a four-RPC proto and implement all four shapes against one service.
  • Change a field number in a running system and watch what the client decodes.
  • Create a client per request instead of reusing the channel, and measure what it costs.

Deadlines, interceptors, errors and gRPC-Web

The operational half. Deadlines are the single most important gRPC practice and the one most often skipped: without one a call waits forever, and the deadline propagates — a downstream service sees how long it has left and can give up rather than doing work nobody will read.

Errors are status codes, not exceptions: the server throws RpcException with a StatusCode, the client catches RpcException and reads .StatusCode. Mapping those to domain failures sensibly (and never leaking stack traces via EnableDetailedErrors in production) is the part people get wrong.

// --- Deadlines: always set one. It propagates to downstream calls. ---
var reply = await client.GetAsync(req, deadline: DateTime.UtcNow.AddSeconds(5));

// Server side: how much time is left, and did the caller give up?
public override async Task<OrderReply> Get(OrderRequest req, ServerCallContext ctx)
{
    if (ctx.Deadline < DateTime.UtcNow.AddMilliseconds(100))
        throw new RpcException(new Status(StatusCode.DeadlineExceeded, "not enough time"));

    // ctx.CancellationToken fires when the deadline passes or the client disconnects
    return await _svc.Get(req.Id, ctx.CancellationToken);
}

// --- Errors: status codes, with trailers for detail ---
throw new RpcException(new Status(StatusCode.NotFound, "order not found"),
    new Metadata { { "order-id", req.Id } });

try { await client.GetAsync(req); }
catch (RpcException ex) when (ex.StatusCode == StatusCode.NotFound)   { /* 404 */ }
catch (RpcException ex) when (ex.StatusCode == StatusCode.Unavailable) { /* retry */ }
catch (RpcException ex) when (ex.StatusCode == StatusCode.DeadlineExceeded) { /* give up */ }

// --- Interceptors: the middleware pipeline equivalent, both ends ---
public class LoggingInterceptor(ILogger<LoggingInterceptor> log) : Interceptor
{
    public override async Task<TResponse> UnaryServerHandler<TRequest, TResponse>(
        TRequest request, ServerCallContext ctx,
        UnaryServerMethod<TRequest, TResponse> next)
    {
        using var scope = log.BeginScope("{Method}", ctx.Method);
        try { return await next(request, ctx); }
        catch (Exception ex) when (ex is not RpcException)
        {
            log.LogError(ex, "unhandled");
            throw new RpcException(new Status(StatusCode.Internal, "internal error"));
        }
    }
}
builder.Services.AddGrpc(o => o.Interceptors.Add<LoggingInterceptor>());

// --- Retries: a policy on the channel, not hand-rolled ---
var channel = GrpcChannel.ForAddress(uri, new GrpcChannelOptions
{
    ServiceConfig = new ServiceConfig
    {
        MethodConfigs = { new MethodConfig
        {
            Names = { MethodName.Default },
            RetryPolicy = new RetryPolicy
            {
                MaxAttempts = 3,
                InitialBackoff = TimeSpan.FromMilliseconds(200),
                BackoffMultiplier = 2,
                RetryableStatusCodes = { StatusCode.Unavailable },   // idempotent only
            },
        }},
    },
});

import grpc
from grpc import aio

reply = await client.Get(request, timeout=5.0)

# Server side
async def Get(self, request, context):
    remaining = context.time_remaining()          # ctx.Deadline
    if remaining is not None and remaining < 0.1:
        await context.abort(grpc.StatusCode.DEADLINE_EXCEEDED, "not enough time")
    return await svc.get(request.id)

# --- Errors: abort() with a status code, trailing metadata for detail ---
await context.abort(grpc.StatusCode.NOT_FOUND, "order not found")

try:
    await client.Get(request, timeout=5.0)
except grpc.aio.AioRpcError as e:
    if e.code() == grpc.StatusCode.NOT_FOUND:        pass
    elif e.code() == grpc.StatusCode.UNAVAILABLE:    pass      # retry
    elif e.code() == grpc.StatusCode.DEADLINE_EXCEEDED: pass   # give up

# --- Interceptors ---
class LoggingInterceptor(aio.ServerInterceptor):
    async def intercept_service(self, continuation, handler_call_details):
        log.info("rpc %s", handler_call_details.method)
        return await continuation(handler_call_details)

server = aio.server(interceptors=[LoggingInterceptor()])

Interview angle

"How do you stop a gRPC call hanging forever?" — a deadline, set by the caller, propagated automatically to everything downstream; and ServerCallContext.CancellationToken so the server stops working when the caller has gone. Then expect the browser question: a browser cannot do raw HTTP/2 framing, so you need gRPC-Web plus a proxy, or JSON transcoding, or a REST edge in front — knowing there are three answers beats knowing one.

Practice
  • Call a deliberately slow service with and without a deadline and watch the difference in thread/connection usage.
  • Add a server interceptor that converts every unhandled exception into StatusCode.Internal without leaking the message.
  • Configure a retry policy and confirm it does not retry a non-idempotent method.

SignalR: hubs, groups and scale-out

SignalR is a push abstraction: the server calls methods on the client. It negotiates the best available transport — WebSockets, then server-sent events, then long polling — so you write one API and it degrades.

The question that separates answers is scale-out. A hub keeps connection state in the process. With two instances behind a load balancer, a message sent from instance A never reaches a client connected to instance B, and a client whose transport falls back to long polling may hit a different instance on every poll. Fixes: a backplane (Redis or Azure SignalR Service) so instances forward to each other, plus sticky sessions for the fallback transports.

public class OrderHub(IOrderService svc) : Hub<IOrderClient>   // strongly-typed client
{
    public override async Task OnConnectedAsync()
    {
        // Context.UserIdentifier comes from authentication - groups per tenant/user
        await Groups.AddToGroupAsync(Context.ConnectionId, $"tenant:{TenantId}");
        await base.OnConnectedAsync();
    }

    public override async Task OnDisconnectedAsync(Exception? ex)
    {
        // Group membership is cleaned up automatically; your own state is not
        await base.OnDisconnectedAsync(ex);
    }

    // Client -> server
    public async Task Watch(string orderId)
        => await Groups.AddToGroupAsync(Context.ConnectionId, $"order:{orderId}");

    // Server -> client, typed
    public async Task Broadcast(string message)
        => await Clients.All.OrderUpdated(message);
}

public interface IOrderClient          // the methods the CLIENT must implement
{
    Task OrderUpdated(string message);
    Task PriceChanged(string sku, decimal price);
}

// Pushing from anywhere else in the app - inject the hub context, not the hub
public class OrderService(IHubContext<OrderHub, IOrderClient> hub)
{
    public async Task Complete(Order o)
    {
        await hub.Clients.Group($"order:{o.Id}").OrderUpdated("completed");
        await hub.Clients.User(o.CustomerId).OrderUpdated("your order shipped");
    }
}

// Targeting
// Clients.All / .Caller / .Others
// Clients.Group("name") / .Groups([...]) / .GroupExcept("name", connectionIds)
// Clients.User(userId) / .Users([...])        - every connection of that user
// Clients.Client(connectionId)

// --- Scale-out: the part that matters ---
// Option 1: Redis backplane - every instance forwards to every other
builder.Services.AddSignalR().AddStackExchangeRedis(redisConnectionString);

// Option 2: Azure SignalR Service - connections terminate outside your app
builder.Services.AddSignalR().AddAzureSignalR(connectionString);

// Without either, with >1 instance, messages reach only the clients on the
// instance that sent them. Sticky sessions are still needed for SSE/long polling:
//   session affinity on the ingress, or ARRAffinity on App Service.

builder.Services.AddSignalR(o =>
{
    o.KeepAliveInterval = TimeSpan.FromSeconds(15);
    o.ClientTimeoutInterval = TimeSpan.FromSeconds(30);    // must be >= 2x KeepAlive
    o.MaximumReceiveMessageSize = 64 * 1024;
    o.EnableDetailedErrors = builder.Environment.IsDevelopment();
});

app.MapHub<OrderHub>("/hubs/orders").RequireAuthorization();
# Python has no SignalR; the equivalents are raw WebSockets plus a pub/sub
# backplane you assemble yourself - which makes the scale-out problem explicit.

from fastapi import FastAPI, WebSocket, WebSocketDisconnect
import redis.asyncio as redis, json, asyncio

app = FastAPI()
r = redis.from_url("redis://localhost")

class ConnectionManager:                 # this is the Hub's connection registry
    def __init__(self) -> None:
        self.groups: dict[str, set[WebSocket]] = {}

    async def join(self, group: str, ws: WebSocket) -> None:
        self.groups.setdefault(group, set()).add(ws)

    async def leave(self, group: str, ws: WebSocket) -> None:
        self.groups.get(group, set()).discard(ws)

    async def send_local(self, group: str, message: dict) -> None:
        dead = []
        for ws in self.groups.get(group, set()):
            try: await ws.send_json(message)
            except Exception: dead.append(ws)
        for ws in dead: await self.leave(group, ws)

manager = ConnectionManager()

# The backplane: publish to Redis, every instance relays to its own sockets
async def publish(group: str, message: dict) -> None:
    await r.publish("hub", json.dumps({"group": group, "message": message}))

async def backplane_listener() -> None:
    pubsub = r.pubsub()
    await pubsub.subscribe("hub")
    async for raw in pubsub.listen():
        if raw["type"] == "message":
            payload = json.loads(raw["data"])
            await manager.send_local(payload["group"], payload["message"])

@app.websocket("/hubs/orders")
async def orders(ws: WebSocket):
    await ws.accept()
    await manager.join(f"tenant:{tenant_id(ws)}", ws)
    try:
        while True:
            msg = await ws.receive_json()
            if msg["type"] == "watch":
                await manager.join(f"order:{msg['orderId']}", ws)
    except WebSocketDisconnect:
        pass
    finally:
        for g in list(manager.groups): await manager.leave(g, ws)

# Note what SignalR gave you for free: transport negotiation and fallback,
# automatic reconnect with state, typed client methods, user-level targeting.
Interview angle

Almost guaranteed: "you scale SignalR to three instances and some clients stop getting messages — why?" Connection state is per-process; you need a backplane (Redis or Azure SignalR) so instances relay to each other, and sticky sessions for the non-WebSocket transports. Good extras: IHubContext is how you push from outside a hub, group membership dies with the connection so it must be re-established on reconnect, and Clients.User targets every connection a user has, not one.

Practice
  • Run two instances behind a load balancer with no backplane and reproduce the missing-message bug.
  • Add the Redis backplane and confirm it is fixed.
  • Push a message from a BackgroundService using IHubContext rather than from inside a hub method.

Raw WebSockets and server-sent events

Sometimes SignalR is more than you need. Server-sent events are one-directional server→client over plain HTTP: no handshake, automatic reconnection built into the browser, works through every proxy, and costs you one line of content type. If the client never needs to send anything, SSE is usually the right answer and people reach for WebSockets out of habit.

Raw WebSockets are right when you need bidirectional binary framing and you do not want SignalR's protocol or client library — a non-browser client, or a protocol you do not control.

// --- Server-sent events: one-directional, plain HTTP, free reconnection ---
app.MapGet("/orders/{id}/events", async (string id, HttpContext ctx,
    IOrderService svc, CancellationToken ct) =>
{
    ctx.Response.Headers.ContentType = "text/event-stream";
    ctx.Response.Headers.CacheControl = "no-cache";
    ctx.Response.Headers["X-Accel-Buffering"] = "no";     // stop nginx buffering it

    await foreach (var e in svc.WatchAsync(id, ct))
    {
        // the wire format is this simple: "data: <payload>\n\n"
        await ctx.Response.WriteAsync($"id: {e.Sequence}\n");   // enables Last-Event-ID
        await ctx.Response.WriteAsync($"event: {e.Kind}\n");
        await ctx.Response.WriteAsync($"data: {JsonSerializer.Serialize(e)}\n\n");
        await ctx.Response.Body.FlushAsync(ct);                  // flush or nothing ships
    }
});
// Browser:  const es = new EventSource("/orders/1/events");
//           es.onmessage = e => console.log(JSON.parse(e.data));
//           reconnection and Last-Event-ID resume are automatic

// --- Raw WebSockets ---
app.UseWebSockets(new WebSocketOptions { KeepAliveInterval = TimeSpan.FromSeconds(30) });

app.Map("/ws", async (HttpContext ctx) =>
{
    if (!ctx.WebSockets.IsWebSocketRequest) { ctx.Response.StatusCode = 400; return; }

    using var socket = await ctx.WebSockets.AcceptWebSocketAsync();
    var buffer = new byte[4 * 1024];

    while (socket.State == WebSocketState.Open)
    {
        var result = await socket.ReceiveAsync(buffer, ctx.RequestAborted);
        if (result.MessageType == WebSocketMessageType.Close)
        {
            await socket.CloseAsync(WebSocketCloseStatus.NormalClosure, null, default);
            break;
        }
        // echo
        await socket.SendAsync(buffer.AsMemory(0, result.Count),
            result.MessageType, result.EndOfMessage, ctx.RequestAborted);
    }
});

// You now own: framing for messages larger than the buffer, reconnection,
// heartbeats, backpressure, and per-connection state. That list is the argument
// for SignalR.
# --- Server-sent events ---
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json, asyncio

@app.get("/orders/{order_id}/events")
async def events(order_id: str):
    async def gen():
        async for e in svc.watch(order_id):
            yield f"id: {e.sequence}\n"
            yield f"event: {e.kind}\n"
            yield f"data: {json.dumps(e.as_dict())}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache",
                                      "X-Accel-Buffering": "no"})

# --- Raw WebSockets ---
from fastapi import WebSocket, WebSocketDisconnect

@app.websocket("/ws")
async def ws_endpoint(ws: WebSocket):
    await ws.accept()
    try:
        while True:
            data = await ws.receive_bytes()
            await ws.send_bytes(data)              # echo
    except WebSocketDisconnect:
        pass

# Heartbeats are yours to implement, same as .NET
async def heartbeat(ws: WebSocket) -> None:
    while True:
        await asyncio.sleep(30)
        await ws.send_json({"type": "ping"})
Interview angle

The useful question to be able to answer unprompted: "why not just use WebSockets for everything?" SSE is simpler, survives proxies that mangle upgrades, reconnects and resumes by itself via Last-Event-ID, and is one-directional — which is all a notification feed, a progress bar or a live dashboard needs. Reach for WebSockets when the client must send too, and for SignalR when you want transport fallback, reconnection and targeting handed to you.

Practice
  • Build a progress endpoint with SSE and watch the browser reconnect by itself when you restart the server.
  • Forget FlushAsync and work out why nothing arrives until the stream closes.
  • List what you would have to write yourself to replace SignalR with raw WebSockets.

GraphQL with HotChocolate: schema, resolvers and DataLoader

GraphQL inverts who decides the response shape: the client asks for exactly the fields it wants, from a single endpoint, against a typed and introspectable schema. That solves over-fetching and under-fetching for a product with several client teams.

It also brings two problems you must be able to name, because they are the interview: N+1 (a field resolver that runs once per parent row, so 50 orders means 51 queries — solved with DataLoader, which batches and caches per request) and query cost (a client can request a deeply nested graph that costs you a tablescan, so you need depth limits, complexity analysis and persisted queries).

// Schema-first via code: types are inferred from your C#
public class Query
{
    [UseProjection, UseFiltering, UseSorting]
    public IQueryable<Order> GetOrders(AppDbContext db) => db.Orders;

    public async Task<Order?> GetOrder(string id, IOrderService svc, CancellationToken ct)
        => await svc.Get(id, ct);
}

public class Mutation
{
    public async Task<Order> PlaceOrder(PlaceOrderInput input, IOrderService svc)
        => await svc.Place(input);
}

public class Subscription
{
    [Subscribe, Topic]
    public OrderEvent OnOrderUpdated([EventMessage] OrderEvent e) => e;
}

// --- The N+1 problem and its fix ---

// BAD: this resolver runs once per order in the result set
[ExtendObjectType<Order>]
public class OrderResolvers
{
    public async Task<Customer> GetCustomer([Parent] Order order, AppDbContext db)
        => await db.Customers.FindAsync(order.CustomerId);      // 1 query PER ORDER
}

// GOOD: a DataLoader batches every key requested in one tick into one query,
// and caches within the request
public class CustomerByIdDataLoader(IBatchScheduler scheduler, IDbContextFactory<AppDbContext> f,
    DataLoaderOptions options) : BatchDataLoader<string, Customer>(scheduler, options)
{
    protected override async Task<IReadOnlyDictionary<string, Customer>> LoadBatchAsync(
        IReadOnlyList<string> keys, CancellationToken ct)
    {
        await using var db = await f.CreateDbContextAsync(ct);
        return await db.Customers.Where(c => keys.Contains(c.Id))
                                 .ToDictionaryAsync(c => c.Id, ct);   // ONE query
    }
}

[ExtendObjectType<Order>]
public class OrderResolvers2
{
    public Task<Customer> GetCustomer([Parent] Order order, CustomerByIdDataLoader loader,
        CancellationToken ct) => loader.LoadAsync(order.CustomerId, ct);
}

async def load_customers(keys: list[str]) -> list["Customer"]:
    rows = await db.fetch_all(
        "SELECT * FROM customers WHERE id = ANY($1)", keys)    # ONE query
    by_id = {r["id"]: Customer(**r) for r in rows}
    return [by_id.get(k) for k in keys]                        # order must match keys

    id: str
    total: float

        return await info.context["customer_loader"].load(self.customer_id)

    return {"customer_loader": DataLoader(load_fn=load_customers)}

Interview angle

"What is the N+1 problem in GraphQL and how do you fix it?" is close to guaranteed. Explain the shape (a nested field resolver runs once per parent, so a list of 50 becomes 51 queries), name DataLoader, and say the two properties that make it work: it batches all keys requested in one execution tick into a single call, and it caches per request — a DataLoader registered as a singleton is a correctness bug, because one user sees another's cached data. Then be ready for "how do you stop a client taking your service down?": depth limits, complexity scoring, pagination, and persisted queries in production.

Practice
  • Build a two-level GraphQL query, log the SQL, and count the queries. Add a DataLoader and count again.
  • Register a DataLoader as a singleton and work out exactly how it leaks data between users.
  • Write a query that would be expensive and confirm your depth and cost limits reject it.

Streaming responses and backpressure

The common thread under all of this: do not buffer what you can stream. Returning IAsyncEnumerable<T> from a minimal API streams the JSON array as it is produced, so memory stays flat whether the result is 100 rows or 10 million and the client sees the first byte almost immediately.

The thing to be able to discuss is backpressure: if the producer is faster than the consumer, something must slow down or memory grows. gRPC gets it from HTTP/2 flow control, Channel<T> gets it from a bounded capacity, and plain HTTP gets it from the TCP window once you stop buffering.

// Streaming JSON: the response starts before the query finishes
app.MapGet("/orders/export", (AppDbContext db, CancellationToken ct) =>
    db.Orders.AsNoTracking().AsAsyncEnumerable());     // serialised as it is read

// NOT this: materialises everything, then serialises. Peak memory = the whole set.
app.MapGet("/orders/bad", async (AppDbContext db, CancellationToken ct) =>
    await db.Orders.ToListAsync(ct));

// NDJSON for very large exports - one object per line, trivially resumable
app.MapGet("/orders/ndjson", async (HttpContext ctx, AppDbContext db, CancellationToken ct) =>
{
    ctx.Response.ContentType = "application/x-ndjson";
    await foreach (var o in db.Orders.AsNoTracking().AsAsyncEnumerable().WithCancellation(ct))
    {
        await JsonSerializer.SerializeAsync(ctx.Response.Body, o, cancellationToken: ct);
        await ctx.Response.Body.WriteAsync("\n"u8.ToArray(), ct);
    }
});

// Backpressure with a bounded channel: the producer BLOCKS when the consumer lags
var channel = Channel.CreateBounded<Order>(new BoundedChannelOptions(capacity: 1_000)
{
    FullMode = BoundedChannelFullMode.Wait,        // not DropOldest: do not lose work
    SingleReader = true,
});

// producer - WriteAsync waits once 1,000 are queued
_ = Task.Run(async () =>
{
    await foreach (var o in Source(ct)) await channel.Writer.WriteAsync(o, ct);
    channel.Writer.Complete();
});

// consumer
await foreach (var o in channel.Reader.ReadAllAsync(ct)) await Handle(o, ct);

// Unbounded is where OOM comes from
var bad = Channel.CreateUnbounded<Order>();        // no backpressure, ever

// Large file downloads: stream, do not read into a byte[]
app.MapGet("/files/{name}", (string name) =>
    Results.Stream(File.OpenRead(Path.Combine(dir, name)), "application/octet-stream",
        enableRangeProcessing: true));             // ranges = resumable downloads

from fastapi.responses import StreamingResponse

# Backpressure: a bounded queue. put() blocks when full - that IS the mechanism.
import asyncio
queue: asyncio.Queue[Order] = asyncio.Queue(maxsize=1000)

async def producer():
    async for order in source():
        await queue.put(order)        # blocks once 1000 are queued
    await queue.put(None)             # sentinel

async def consumer():
    while (order := await queue.get()) is not None:
        await handle(order)

# asyncio.Queue() with no maxsize is the unbounded channel: no backpressure, OOM
unbounded: asyncio.Queue = asyncio.Queue()

Contracts and versioning across protocols

Every protocol on this page has the same underlying problem — you need to change the shape without breaking the clients you cannot redeploy — and four different answers. Being able to compare them is a strong architecture signal.

How you versionBreaking change looks like
RESTURL segment (/v2/), header, or media typeRemoving a field, tightening validation, changing a status code
gRPCPackage name (shop.orders.v2); add fields freelyChanging or reusing a field number, changing a type
GraphQLNo versions — add fields, @deprecated the old onesRemoving a field someone still selects
MessagingEvent type/version in the envelope; consumers ignore unknownsChanging the meaning of a field, which nothing detects

The underlying rule is the same in all four: additive changes are safe, removals and redefinitions are not, and you need telemetry on usage before you can remove anything.

// --- REST: explicit versions, and deprecate with a header ---
builder.Services.AddApiVersioning(o =>
{
    o.DefaultApiVersion = new ApiVersion(1, 0);
    o.ReportApiVersions = true;                     // api-supported-versions response header
    o.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("api-version"));
});

var v1 = app.NewVersionedApi("orders").MapGroup("/v{version:apiVersion}/orders")
            .HasApiVersion(1.0).HasDeprecatedApiVersion(0.9);

// --- gRPC: version in the proto package; adding a field is not breaking ---
//   package shop.orders.v1;   ->   package shop.orders.v2;
//   run both services side by side until v1 traffic is zero
//   reserved 5, 6;            // never let anyone reuse a retired field number

// --- GraphQL: no versions. Add, deprecate, measure, then remove. ---
public class Order
{
    [GraphQLDeprecated("Use totalMoney, which carries the currency.")]
    public decimal Total { get; init; }
    public Money TotalMoney { get; init; } = default!;
}
// Field-level usage telemetry is what tells you when removal is safe.

// --- Messaging: version the envelope, tolerate unknown fields ---
public record OrderPlacedV2(string OrderId, decimal Total, string Currency)
{
    public const string Type = "order.placed.v2";
}

// Consumers upcast old events rather than the producer emitting both forever
public static OrderPlacedV2 Upcast(OrderPlacedV1 old)
    => new(old.OrderId, old.Total, Currency: "USD");

// And deserialise permissively so a new producer field does not break old consumers
var options = new JsonSerializerOptions
{
    UnmappedMemberHandling = JsonUnmappedMemberHandling.Skip,   // the default; keep it
};

# Same prerequisite for removal: per-field / per-version usage telemetry
Interview angle

A strong architecture answer compares the four rather than describing one. The punchline worth landing: GraphQL has no versioning because the client already told you which fields it wants, so you can deprecate per field and measure usage — which is also why GraphQL removals need field-level telemetry that REST removals do not. And for messaging, note that the dangerous change is not adding or removing a field but redefining one, because no schema check catches a field that still deserialises and now means something else.

Practice
  • Add a field to a proto message and prove an old client still works; then change a field number and watch it decode garbage.
  • Deprecate a GraphQL field and find out whether your server can tell you who still selects it.
  • Write the deprecation policy you would want: how long, what headers, what telemetry gates the removal.
