.NET Framework, .NET Core and .NET 5–10

One of the most common opening questions, and one people answer badly by reciting history. The useful framing is three lineages: .NET Framework (4.8.1, Windows-only, in support indefinitely but closed to new features), .NET Core (1.0–3.1, the cross-platform rewrite), and .NET 5 onwards (the unified continuation — there is no ".NET Core 5"). Even-numbered releases are LTS with 3 years of support; odd-numbered are STS with 18 months.

What actually matters in an interview is the migration conversation: what does not come across. ASP.NET Web Forms has no path. WCF server-side is community-only (CoreWCF). AppDomain, .NET Remoting and binary serialisation are gone. System.Drawing.Common is Windows-only. Everything else is largely a retarget plus a csproj rewrite.

dotnet --info                       # SDKs, runtimes, RID, and the resolved SDK
dotnet --list-sdks
dotnet --list-runtimes

# The modern csproj - compare this to a .NET Framework one (hundreds of lines,
# every file listed explicitly, packages.config, no implicit globbing)
cat Shop.Api.csproj

# Migration tooling

# Find the API calls that will not survive the move
dotnet tool install -g dotnet-apiport

Interview angle

"We are on .NET Framework 4.8 — how would you approach moving to .NET 8?" Answer with a plan, not a feature list: inventory with upgrade-assistant / API Port, retarget leaf libraries to netstandard2.0 first so both worlds can consume them, move the web layer last, and name the things that have no path (Web Forms, WCF hosting, AppDomain, binary serialisation) rather than discovering them mid-project.

Practice
  • Run dotnet --info and explain every line of the output.
  • Multi-target a small library at net8.0 and netstandard2.0 and use #if to light up a newer API.
  • Name the current LTS release and its end-of-support date without looking.

SDKs, runtimes, TFMs and global.json

Three separate things people conflate: the SDK builds (one install can build many targets), the runtime executes, and the target framework moniker in the csproj says which API surface you compile against. global.json pins the SDK for a repo so a developer with a newer SDK does not silently change build behaviour.

The deployment distinction matters as much: framework-dependent output needs a runtime on the box and is small; self-contained ships the runtime and is ~70 MB but needs nothing installed.

# Pin the SDK for everyone who clones the repo
dotnet new globaljson --sdk-version 8.0.400 --roll-forward latestFeature
cat global.json
# { "sdk": { "version": "8.0.400", "rollForward": "latestFeature" } }

# Framework-dependent (default): small, needs the runtime installed
dotnet publish -c Release -o out
#   -> out/Shop.Api.dll + Shop.Api (apphost), ~2 MB

# Self-contained: ships the runtime, runs anywhere for that RID
dotnet publish -c Release -r linux-x64 --self-contained true -o out
#   -> ~70 MB

# Single file, trimmed
dotnet publish -c Release -r linux-x64 --self-contained true \
  -p:PublishSingleFile=true -p:PublishTrimmed=true

# Which runtimes can host this app? Roll-forward policy decides.
DOTNET_ROLL_FORWARD=LatestMajor dotnet Shop.Api.dll

Interview angle

A clean three-sentence separation of SDK / runtime / TFM is worth more than any detail here. Then expect the deployment question: framework-dependent vs self-contained, and what you would ship in a container (framework-dependent on an aspnet base image is the usual answer — the base layer is cached and shared, so self-contained mostly buys you a bigger image).

Practice
  • Add a global.json and prove that a newer SDK on the machine is no longer used.
  • Publish the same app both ways and compare output size and start-up time.
  • Set up Directory.Packages.props for a two-project solution and remove every inline version.

The generic host, IHostedService and BackgroundService

Every modern .NET app — web, worker, console — is a host: a container holding DI, configuration, logging and a set of IHostedService implementations, with one well-defined startup and shutdown sequence. Understanding that sequence is what the question is really about.

On StartAsync, hosted services start in registration order, sequentially, and the host does not begin serving until each returns. On shutdown they stop in reverse order, each given ShutdownTimeout (30s default) before being abandoned. The classic bug: doing long work directly in StartAsync, which blocks startup; and in BackgroundService, an unhandled exception in ExecuteAsync tears down the entire host from .NET 6 onwards (it was silently swallowed before).

// A worker: the whole app is a host with one hosted service
var builder = Host.CreateApplicationBuilder(args);
builder.Services.AddHostedService<OutboxPublisher>();
builder.Services.AddSingleton<IClock, SystemClock>();
await builder.Build().RunAsync();

// BackgroundService is IHostedService with the loop boilerplate written for you
public class OutboxPublisher(IServiceScopeFactory scopes, ILogger<OutboxPublisher> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // Return quickly or yield: ExecuteAsync is awaited by StartAsync until the
        // first await that actually yields, so synchronous work here blocks startup.
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(5));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                // A singleton cannot inject a scoped DbContext - create a scope per tick
                using var scope = scopes.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await Publish(db, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;                                   // normal shutdown, not an error
            }
            catch (Exception ex)
            {
                // Swallow deliberately: an escape from ExecuteAsync kills the host
                log.LogError(ex, "outbox tick failed");
            }
        }
    }

    public override async Task StopAsync(CancellationToken ct)
    {
        log.LogInformation("draining");                  // runs before the token is cancelled
        await base.StopAsync(ct);
    }
}

// Opt into the old forgiving behaviour explicitly, if you must
builder.Services.Configure<HostOptions>(o =>
{
    o.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.Ignore;
    o.ShutdownTimeout = TimeSpan.FromSeconds(60);
});

// Graceful shutdown hooks
app.Lifetime.ApplicationStopping.Register(() => log.LogInformation("stopping"));
# Python has no host abstraction; asyncio.TaskGroup + lifespan hooks are the
# closest equivalent, and you assemble the pieces yourself.
import asyncio, contextlib, logging

log = logging.getLogger(__name__)

async def outbox_publisher(stopping: asyncio.Event, session_factory) -> None:
    while not stopping.is_set():
        try:
            async with session_factory() as db:        # a "scope" per tick
                await publish(db)
        except asyncio.CancelledError:
            break                                      # normal shutdown
        except Exception:
            log.exception("outbox tick failed")         # never let it escape
        with contextlib.suppress(asyncio.TimeoutError):
            await asyncio.wait_for(stopping.wait(), timeout=5)

# Startup / shutdown ordering is explicit, in the order you write it
async def main() -> None:
    stopping = asyncio.Event()
    async with asyncio.TaskGroup() as tg:              # 3.11+
        tg.create_task(outbox_publisher(stopping, session_factory))
        tg.create_task(serve_http())
        await shutdown_signal()
        stopping.set()
    # TaskGroup cancels and awaits every child here - the reverse-order stop

# FastAPI/Starlette give you the lifespan hook, the nearest thing to IHostedService
from contextlib import asynccontextmanager
@asynccontextmanager
async def lifespan(app):
    task = asyncio.create_task(worker())               # startup
    yield
    task.cancel()                                       # shutdown
    with contextlib.suppress(asyncio.CancelledError):
        await task
Interview angle

Three questions come up almost every time. "What happens if ExecuteAsync throws?" — from .NET 6 the host stops; name BackgroundServiceExceptionBehavior. "Why can't I inject a DbContext into a BackgroundService?" — the service is a singleton and the context is scoped; use IServiceScopeFactory per unit of work. "How do you make shutdown graceful?" — honour stoppingToken, keep work under ShutdownTimeout, and do draining in StopAsync.

Practice
  • Write a BackgroundService with a PeriodicTimer that exits cleanly on Ctrl-C with no exception logged.
  • Inject a scoped service into one, see it fail, then fix it with a scope factory.
  • Throw from ExecuteAsync and watch the host exit; then configure it not to.

Configuration providers and precedence

Configuration is a layered key-value store, not a file. Providers are added in order and later ones win; the result is flattened to colon-delimited keys (Logging:LogLevel:Default). Knowing the default order for CreateApplicationBuilder by heart is a reasonable thing to be asked.

The order is: appsettings.json → appsettings.{Environment}.json → user secrets (Development only) → environment variables → command-line arguments. The double-underscore convention exists because most shells cannot put a colon in a variable name: Logging__LogLevel__Default maps to Logging:LogLevel:Default.

var builder = WebApplication.CreateBuilder(args);

// The defaults are already added, in this order (last wins):
//   1. appsettings.json
//   2. appsettings.{Environment}.json
//   3. user secrets               (Development only)
//   4. environment variables
//   5. command-line args

// Adding your own - order of the AddX calls is the precedence
builder.Configuration
    .AddJsonFile("shared.json", optional: true, reloadOnChange: true)
    .AddAzureKeyVault(new Uri(vaultUri), new DefaultAzureCredential())
    .AddEnvironmentVariables(prefix: "SHOP_");       // SHOP_Db__Timeout -> Db:Timeout

// Reading: flattened colon-delimited keys, whatever the provider
string? cs      = builder.Configuration["ConnectionStrings:Default"];
string? cs2     = builder.Configuration.GetConnectionString("Default");   // same thing
int timeout     = builder.Configuration.GetValue<int>("Db:Timeout", 30);  // with default
var section     = builder.Configuration.GetSection("Db");
var endpoints   = builder.Configuration.GetSection("Endpoints").Get<string[]>();

// Required, fail fast at startup rather than null at 3am
string required = builder.Configuration.GetValue<string>("Db:Host")
    ?? throw new InvalidOperationException("Db:Host is not configured");

// Arrays and dictionaries flatten by index
//   { "Endpoints": ["a", "b"] }  ->  Endpoints:0 = a, Endpoints:1 = b
//   env var: Endpoints__0=a

// Environment, and how it is chosen (ASPNETCORE_ENVIRONMENT / DOTNET_ENVIRONMENT)
if (builder.Environment.IsDevelopment()) { }
if (builder.Environment.IsEnvironment("Staging")) { }

// Dumping the resolved configuration is the fastest way to debug precedence
foreach (var (k, v) in builder.Configuration.AsEnumerable().OrderBy(p => p.Key))
    Console.WriteLine($"{k} = {v}");
# Environment variables: __ (double underscore) becomes the : separator,
# because most shells will not allow a colon in a name
export Logging__LogLevel__Default=Debug
export ConnectionStrings__Default="Server=db;Database=shop"
export Endpoints__0=https://a.example.com
export Endpoints__1=https://b.example.com

# Command line wins over everything
dotnet run --Db:Timeout=60 --environment Staging

# Which environment am I in?
export ASPNETCORE_ENVIRONMENT=Staging        # web
export DOTNET_ENVIRONMENT=Staging            # worker / generic host

# User secrets: Development only, stored OUTSIDE the repo
#   ~/.microsoft/usersecrets/<UserSecretsId>/secrets.json
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:Default" "Server=localhost;Database=shop"
dotnet user-secrets list

# In a container, the same keys arrive as env vars - nothing app-side changes
docker run -e ConnectionStrings__Default="Server=db" shop-api
import os, json, tomllib
from pathlib import Path

# Python has no layered configuration abstraction in the stdlib; the usual
# pattern is explicit layers merged in precedence order - exactly what the
# .NET provider list does for you.
def load_config() -> dict:
    cfg: dict = {}
    for layer in ("settings.json", f"settings.{os.getenv('ENVIRONMENT', 'dev')}.json"):
        p = Path(layer)
        if p.exists():
            cfg = deep_merge(cfg, json.loads(p.read_text()))
    # env vars last, so they win
    for key, value in os.environ.items():
        if key.startswith("SHOP_"):
            set_path(cfg, key[5:].lower().split("__"), value)
    return cfg

    model_config = SettingsConfigDict(env_prefix="SHOP_DB__", env_nested_delimiter="__")

Interview angle

"Where does configuration come from, and what wins?" Recite the five default layers in order. The two follow-ups: why environment variables use __ (shells and colons), and how you would get a secret in without putting it in appsettings.json (user secrets locally, Key Vault or the platform's own secret store in production — and note that user secrets are Development-only and unencrypted, just outside the repo).

Practice
  • Set the same key in appsettings.json, an environment variable and a command-line argument, and confirm which wins.
  • Bind a string[] from an environment variable using the index convention.
  • Dump the whole resolved configuration at startup and find a key you did not know was set.

The options pattern: IOptions, IOptionsSnapshot, IOptionsMonitor and validation

Injecting IConfiguration everywhere means every consumer does its own string lookups and type conversions, and nothing fails until the code path runs. The options pattern binds a section to a typed class once, validates it, and injects that.

The three interfaces differ only in lifetime and reload behaviour, and this is the question: IOptions<T> is a singleton bound once at startup and never reloads; IOptionsSnapshot<T> is scoped and consistent for the duration of a request; IOptionsMonitor<T> is a singleton that exposes CurrentValue and an OnChange callback, and is the only one usable from a singleton that must see updates.

// 1. The typed class, with validation attributes
public class DbOptions
{
    public const string Section = "Db";

    [Required] public string Host { get; init; } = "";
    [Range(1, 300)] public int TimeoutSeconds { get; init; } = 30;
    public bool EnableRetry { get; init; } = true;
}

// 2. Bind + validate, and fail at STARTUP rather than on first use
builder.Services
    .AddOptions<DbOptions>()
    .Bind(builder.Configuration.GetSection(DbOptions.Section))
    .ValidateDataAnnotations()
    .Validate(o => !o.Host.Contains("localhost") || builder.Environment.IsDevelopment(),
              "localhost is not allowed outside Development")
    .ValidateOnStart();                      // <- without this, errors wait for the first inject

// 3. Consume. Pick the interface by what you need:
public class Repo(IOptions<DbOptions> options)            // singleton, never reloads
{
    private readonly DbOptions _o = options.Value;        //   bound once at startup
}

public class Handler(IOptionsSnapshot<DbOptions> options) // scoped, stable per request
{
    public void Do() { var o = options.Value; }
}

public class Publisher(IOptionsMonitor<DbOptions> options) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var _ = options.OnChange(o => log.LogInformation("timeout now {T}", o.TimeoutSeconds));
        while (!ct.IsCancellationRequested)
        {
            var current = options.CurrentValue;            // re-read every tick
            await Task.Delay(current.TimeoutSeconds * 1000, ct);
        }
    }
}

// Named options: several instances of the same shape
builder.Services.Configure<DbOptions>("primary", builder.Configuration.GetSection("Db:Primary"));
builder.Services.Configure<DbOptions>("replica", builder.Configuration.GetSection("Db:Replica"));
var primary = monitor.Get("primary");

// Post-configuration runs after all binding - good for derived values
builder.Services.PostConfigure<DbOptions>(o => { /* normalise */ });

// A source-generated, DI-free alternative for simple cases
var db = builder.Configuration.GetSection("Db").Get<DbOptions>()!;
from pydantic import Field, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict

# pydantic-settings is the direct analogue: bind a section, validate, inject
class DbOptions(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="DB_", frozen=True)

    host: str                                     # [Required]
    timeout_seconds: int = Field(default=30, ge=1, le=300)   # [Range(1,300)]
    enable_retry: bool = True

    @field_validator("host")
    @classmethod
    def not_localhost_in_prod(cls, v: str) -> str:
        import os
        if "localhost" in v and os.getenv("ENVIRONMENT") != "dev":
            raise ValueError("localhost is not allowed outside dev")
        return v

# ValidateOnStart equivalent: construct it at import/startup, not lazily
db_options = DbOptions()                          # raises now, not at 3am

# The IOptions / IOptionsSnapshot / IOptionsMonitor distinction has no direct
# equivalent because there is no built-in reload. You build it:
class OptionsMonitor:
    def __init__(self, factory):
        self._factory, self._current = factory, factory()
        self._callbacks: list = []

    @property
    def current_value(self):                      # IOptionsMonitor.CurrentValue
        return self._current

    def reload(self) -> None:                     # hook to SIGHUP or a file watcher
        self._current = self._factory()
        for cb in self._callbacks:
            cb(self._current)

    def on_change(self, cb) -> None:
        self._callbacks.append(cb)
Interview angle

This is a favourite because the answer is short and most people get it half right. Be exact: IOptions — singleton, bound once, no reload. IOptionsSnapshot — scoped, recomputed per scope, stable within a request. IOptionsMonitor — singleton, CurrentValue re-reads, has OnChange, the only option for a singleton or hosted service. Then volunteer ValidateOnStart(): the difference between a pod that fails to start and one that serves 500s.

Practice
  • Bind a section with a deliberately invalid value and prove ValidateOnStart turns it into a startup failure.
  • Inject IOptions into a singleton, change appsettings.json, and confirm nothing updates. Switch to IOptionsMonitor.
  • Register two named options from two sections and resolve both with Get(name).

ILogger, log levels, scopes and structured logging

ILogger<T> is an abstraction over providers (console, file, Application Insights, Serilog, OpenTelemetry). Two things distinguish someone who has operated a service: using the message template rather than string interpolation, and knowing what a scope is for.

log.LogInformation("Order {OrderId} failed", id) sends a template plus a named value, so a log backend can index and query on OrderId. log.LogInformation($"Order {id} failed") sends one opaque string and throws the structure away — and formats it even when the level is disabled.

public class OrderService(ILogger<OrderService> log)      // T sets the category
{
    public async Task Handle(Order order)
    {
        // Structured: template + named values. NOT string interpolation.
        log.LogInformation("Processing order {OrderId} for {Customer}", order.Id, order.Customer);
        // log.LogInformation($"Processing order {order.Id}");   // <- loses all structure

        // A scope attaches properties to every log inside it, including from
        // code that knows nothing about them
        using (log.BeginScope("Order {OrderId}", order.Id))
        {
            await _repo.Save(order);                   // its logs carry OrderId too
        }

        // Exceptions go in the first parameter, never into the message
        try { await Charge(order); }
        catch (Exception ex)
        {
            log.LogError(ex, "Charge failed for {OrderId}", order.Id);
        }

        // Guard genuinely expensive work
        if (log.IsEnabled(LogLevel.Debug))
            log.LogDebug("Payload {Payload}", Expensive(order));

        // Source-generated logging: no boxing, no allocation, compile-time checked
        LogOrderReceived(log, order.Id);
    }

    [LoggerMessage(Level = LogLevel.Information, Message = "Order {orderId} received")]
    static partial void LogOrderReceived(ILogger logger, string orderId);
}

// Levels, and what each is for in practice
//   Trace       - firehose, never on in production
//   Debug       - developer detail, on when diagnosing
//   Information - business events: an order was placed
//   Warning     - degraded but handled: a retry fired
//   Error       - this request failed
//   Critical    - the process or a dependency is down

// Configuration is per category, most specific prefix wins
// appsettings.json:
// "Logging": { "LogLevel": {
//     "Default": "Information",
//     "Microsoft.AspNetCore": "Warning",
//     "Microsoft.EntityFrameworkCore.Database.Command": "Information" } }
import logging, logging.config

log = logging.getLogger(__name__)              # module name == the C# category

# Structured logging: %-style args are the message-template equivalent.
# Pass the values, do not format them in.
log.info("Processing order %s for %s", order.id, order.customer)
# log.info(f"Processing order {order.id}")     # <- same mistake, same cost

# Scopes: `extra` per call, or a contextvar-backed filter for ambient properties
log.info("Processing order", extra={"order_id": order.id})

import contextvars
_order_id = contextvars.ContextVar("order_id", default=None)

class ContextFilter(logging.Filter):           # the BeginScope equivalent
    def filter(self, record):
        record.order_id = _order_id.get()
        return True

# Exceptions: exc_info / .exception(), never str(ex) in the message
try:
    charge(order)
except Exception:
    log.exception("Charge failed for %s", order.id)   # includes the traceback

# Guard expensive work
if log.isEnabledFor(logging.DEBUG):
    log.debug("Payload %s", expensive(order))

# Per-logger levels, same most-specific-prefix rule
logging.config.dictConfig({
    "version": 1,
    "loggers": {
        "":            {"level": "INFO",    "handlers": ["console"]},
        "urllib3":     {"level": "WARNING"},
        "sqlalchemy.engine": {"level": "INFO"},
    },
})

# structlog is what you reach for when you want real structured output
import structlog
structlog.get_logger().info("order_processed", order_id=order.id, total=order.total)
Interview angle

The reliable one is "what is wrong with LogInformation($\"...{id}...\")?" — it destroys the structured properties your log backend would have indexed, and it pays the formatting cost even when the level is off. Follow-ups: what a scope buys you (correlation across code that does not take the id as a parameter), and why [LoggerMessage] exists (source-generated, allocation-free, checked at compile time).

Practice
  • Log the same event interpolated and templated, then query both in your log backend and compare.
  • Wrap a request in BeginScope and confirm a nested service's logs carry the id.
  • Convert a hot-path log call to a [LoggerMessage] partial method.

DI beyond lifetimes: captive dependencies, keyed services, factories

Web API covers singleton / scoped / transient. This is the next layer: what goes wrong and how you work around the container's limits.

The captive dependency is the bug worth being able to name on the spot: a singleton that depends on a scoped service captures the first scope's instance and holds it forever — a DbContext that lives for the lifetime of the process, is not thread-safe, and accumulates tracked entities. The built-in container catches this at build time when scope validation is on (it is by default in Development only).

// The captive dependency - a singleton capturing something scoped
builder.Services.AddSingleton<CacheWarmer>();        // singleton
builder.Services.AddScoped<AppDbContext>();          // scoped
// CacheWarmer(AppDbContext db)  ->  InvalidOperationException at Build() when

Interview angle

"What is a captive dependency?" is close to a standard question. Give the definition, the concrete example (singleton holding a DbContext), the symptom (stale data, thread-safety errors, growing memory) and the guard (ValidateScopes / ValidateOnBuild, which you should turn on in every environment rather than Development only). Keyed services are a good "what is new in .NET 8" answer.

Practice
  • Create a captive dependency deliberately, see the Development-time error, then set ValidateScopes = false and watch it break at runtime instead.
  • Register three implementations of one interface and resolve a specific one both with keys and with IEnumerable<T>.
  • Register an instance you constructed yourself and verify the container never disposes it.

JIT, tiered compilation, ReadyToRun and Native AOT

IL is compiled to machine code at run time by the JIT. Tiered compilation means it is compiled twice: tier 0 quickly and unoptimised so start-up is fast, then tier 1 fully optimised once a method proves hot (30 calls, or loop-driven via OSR). This is why a .NET service is slow for its first few seconds and why a benchmark without warm-up is meaningless.

ReadyToRun pre-compiles to native code at publish time but keeps the JIT for re-optimisation — better start-up, bigger binary. Native AOT compiles entirely ahead of time: millisecond start-up, tiny memory, no JIT at all — and therefore no runtime code generation, which rules out reflection-heavy serialisation, Expression.Compile, most dynamic proxies and much of EF Core.

# See the tiers at work
export DOTNET_TieredCompilation=0        # disable: slower start, best steady-state
export DOTNET_TieredPGO=1                # profile-guided re-optimisation (default on)
export DOTNET_ReadyToRun=0               # ignore precompiled code, JIT everything

# ReadyToRun: precompile at publish, keep the JIT
dotnet publish -c Release -r linux-x64 -p:PublishReadyToRun=true

# Native AOT: no JIT, no IL, a native executable
dotnet publish -c Release -r linux-x64 -p:PublishAot=true
#   start-up  ~5 ms   vs ~70 ms JIT
#   memory    ~12 MB  vs ~45 MB
#   size      ~12 MB single native binary
#   build     slow, and must be on the target platform/arch

# The AOT warnings are the useful part - they tell you what will break
dotnet publish -p:PublishAot=true 2>&1 | grep -E "IL2|IL3"
#   IL2026: reflection on a trimmed member
#   IL3050: RequiresDynamicCode - Expression.Compile, MakeGenericType

# Measure, do not guess
dotnet-counters monitor -n Shop.Api --counters System.Runtime
dotnet tool install -g BenchmarkDotNet.Tool
// Analyse before committing to AOT - these turn the problems into build errors
// csproj:
//   <PublishAot>true</PublishAot>
//   <IsAotCompatible>true</IsAotCompatible>        (libraries)
//   <EnableTrimAnalyzer>true</EnableTrimAnalyzer>

// What AOT forbids, and the AOT-safe replacement:

// 1. Reflection-based JSON -> source-generated contracts

//    [RequiresDynamicCode] marks the APIs that will throw

static void Bind<T>() { }

// Minimal APIs are AOT-friendly; MVC controllers are not
var builder = WebApplication.CreateSlimBuilder(args);     // the AOT-shaped builder
builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));

Interview angle

"Why is the first request slow?" is the way in: tier 0 code, cold caches, and lazy initialisation. Then "what is Native AOT and when would you not use it?" — great for CLI tools, serverless and sidecars where start-up and memory dominate; wrong for anything depending on runtime code generation (reflection-based serialisation, Expression.Compile, dynamic proxies, EF Core) and for MVC. Mentioning that PublishReadyToRun is the low-risk middle ground is a good sign.

Practice
  • Publish the same minimal API normally, with ReadyToRun, and with AOT; compare start-up, RSS and size.
  • Turn on the AOT analyzers in an existing project and read the IL2026/IL3050 warnings.
  • Benchmark a method with and without warm-up and explain the difference by tier.

Trimming, single-file and container-ready publishing

Trimming removes IL the static analyser cannot see being used. It works well until reflection is involved, at which point the member is gone and you get a MissingMethodException in production rather than a build error — which is why the trim analyzer warnings matter more than the size saving.

For containers, the thing worth knowing is that framework-dependent publish onto an aspnet base image is usually right: the runtime layer is shared and cached across all your images, so a self-contained publish often makes the total registry and pull cost worse, not better.

<PropertyGroup>
  <!-- Trimming -->
  <PublishTrimmed>true</PublishTrimmed>
  <TrimMode>full</TrimMode>              <!-- 'partial' trims only opted-in assemblies -->
  <EnableTrimAnalyzer>true</EnableTrimAnalyzer>   <!-- the point: warnings, not size -->
  <SuppressTrimAnalysisWarnings>false</SuppressTrimAnalysisWarnings>

  <!-- Single file -->
  <PublishSingleFile>true</PublishSingleFile>
  <IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>

  <!-- Size wins that are not trimming -->
  <InvariantGlobalization>true</InvariantGlobalization>   <!-- drops ICU, ~28 MB -->
  <UseSystemResourceKeys>true</UseSystemResourceKeys>     <!-- drops localised messages -->
  <EventSourceSupport>false</EventSourceSupport>
</PropertyGroup>

<!-- Protect types used only through reflection -->
<ItemGroup>
  <TrimmerRootAssembly Include="Shop.Plugins" />
</ItemGroup>
<!-- or ILLink.Descriptors.xml, embedded as an EmbeddedResource:
<linker>
  <assembly fullname="Shop.Plugins">
    <type fullname="Shop.Plugins.*" preserve="all" />
  </assembly>
</linker> -->
# Multi-stage, framework-dependent: the runtime layer is shared across images
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Restore as its own layer so code changes do not re-download packages
COPY *.sln Directory.Packages.props Directory.Build.props ./
COPY src/Shop.Api/*.csproj src/Shop.Api/
RUN dotnet restore src/Shop.Api/Shop.Api.csproj

COPY . .
RUN dotnet publish src/Shop.Api/Shop.Api.csproj -c Release -o /app --no-restore

# chiseled: no shell, no package manager, non-root by default
FROM mcr.microsoft.com/dotnet/aspnet:8.0-jammy-chiseled AS final
WORKDIR /app
COPY --from=build /app .

USER $APP_UID
ENV ASPNETCORE_URLS=http://+:8080 \
    DOTNET_gcServer=1
EXPOSE 8080
ENTRYPOINT ["./Shop.Api"]

Interview angle

The trimming question is really about reflection: "what breaks when you trim?" — anything resolved by name at run time, and the failure is a runtime MissingMethod/MissingType rather than a build error, so you run the analyzer and treat its warnings as errors. On containers, the strong answer is that framework-dependent on a shared aspnet base beats self-contained for a fleet of services, plus chiseled/distroless, non-root, and a restore layer separate from the source layer.

Practice
  • Trim an app that uses reflection-based JSON, watch it fail at run time, then fix it with a source-generated context.
  • Set InvariantGlobalization and measure the image size change — then work out what you gave up.
  • Rewrite a single-stage Dockerfile as multi-stage with a separate restore layer and compare rebuild times after a one-line code change.

The dotnet CLI and what to reach for when

Worth being fluent in, because it comes up as "how would you find out?" rather than as a question of its own. The diagnostic tools in particular — dotnet-counters, dotnet-dump, dotnet-trace — are the credible answer to "the service is using 4 GB in production, what do you do?"

# Project and solution
dotnet new list                             # every template
dotnet new webapi -n Shop.Api --use-minimal-apis
dotnet sln add src/Shop.Api/Shop.Api.csproj

dotnet test --filter "Category!=Integration"
dotnet watch run                             # hot reload

# Format and analyse

dotnet build -warnaserror

Interview angle

Rather than CLI trivia, expect an operational scenario: "memory keeps climbing in production — walk me through it." Say dotnet-counters first to see whether it is managed heap, Gen2, or handles; then dotnet-dump collect and analyse the heap offline rather than attaching a debugger to production; then name the usual culprits (static collections, event handlers never unsubscribed, HttpClient misuse, a captive DbContext).
