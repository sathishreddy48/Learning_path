Infrastructure as Code: Bicep & Terraform

Every environment on this site — the App Service, the SQL server, the private endpoints — should exist because a file in git says so. This page teaches the two tools you will meet on Azure, Bicep and Terraform, with the same workload written in both, and the pipeline pattern that makes infrastructure changes reviewable and reversible.

Why IaC, and ARM → Bicep → Terraform

Infrastructure as code gives you review, repeatability, drift detection and disaster recovery for free. Azure's native engine is ARM (JSON templates, deployment API). Bicep is a DSL that compiles to ARM — first-party, no state file, day-zero support for new resources. Terraform is multi-cloud with a state file and a plan/apply workflow, the azurerm provider (curated) and azapi (raw ARM for anything new).

# Tooling
az bicep install && az bicep version
brew install terraform tflint           # or winget / apt
terraform -version

# The same intent, three ways
az deployment group create -g rg-shop --template-file main.bicep --parameters env=dev        # Bicep → ARM deployment
az bicep build --file main.bicep                                                            # see the ARM JSON it produces
terraform -chdir=infra init && terraform -chdir=infra plan -var env=dev                      # Terraform → provider API calls

# Decompile existing ARM / export a resource group as a starting point (rarely clean, always a starting point)
az group export -g rg-shop > rg.json && az bicep decompile --file rg.json
Interview angle

Declarative vs imperative; idempotency; why Bicep has no state (ARM is the state) and what that costs (no delete of removed resources without stacks/complete mode); provider lag and azapi; where you would still click in the portal (nowhere in prod).

Bicep: resources, parameters, modules, existing

A Bicep file declares resources with symbolic names; references between them create implicit dependencies. Parameters (with decorators for validation and @secure()), variables, outputs, modules (a file or a registry reference), existing to reference resources you do not own, loops and conditions. Keep environment differences in .bicepparam files.

// main.bicep — App Service + SQL + Key Vault wiring, with a module for the web tier
targetScope = 'resourceGroup'

@allowed(['dev', 'test', 'prod'])
param env string
param location string = resourceGroup().location
@secure()
param sqlAdminPassword string
param tags object = { env: env, owner: 'shop-team' }

var isProd = env == 'prod'
var suffix = '${env}-${uniqueString(resourceGroup().id)}'

resource kv 'Microsoft.KeyVault/vaults@2023-07-01' = {
  name: 'kv-shop-${suffix}'
  location: location
  tags: tags
  properties: { tenantId: tenant().tenantId, sku: { family: 'A', name: 'standard' }, enableRbacAuthorization: true, enablePurgeProtection: isProd ? true : null, publicNetworkAccess: 'Disabled' }
}

resource sql 'Microsoft.Sql/servers@2023-08-01-preview' = {
  name: 'sql-shop-${suffix}'
  location: location
  tags: tags
  properties: { administratorLogin: 'sqladmin', administratorLoginPassword: sqlAdminPassword, minimalTlsVersion: '1.2', publicNetworkAccess: 'Disabled' }
  resource db 'databases' = { name: 'shopdb', location: location, sku: isProd ? { name: 'GP_Gen5_4' } : { name: 'GP_S_Gen5_1' }, properties: { zoneRedundant: isProd } }
}

module web 'modules/web.bicep' = {
  name: 'web-${env}'
  params: { location: location, env: env, tags: tags, sku: isProd ? 'P1v3' : 'B1', instances: isProd ? 3 : 1, keyVaultName: kv.name, sqlFqdn: sql.properties.fullyQualifiedDomainName }
}

// Reference something the platform team owns
resource logs 'Microsoft.OperationalInsights/workspaces@2023-09-01' existing = { name: 'law-platform', scope: resourceGroup('rg-platform-logs') }

// Give the web app's identity access to Key Vault (role assignment names must be deterministic GUIDs)
resource kvSecretsUser 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  scope: kv
  name: guid(kv.id, web.outputs.principalId, 'Key Vault Secrets User')
  properties: { principalId: web.outputs.principalId, principalType: 'ServicePrincipal', roleDefinitionId: subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '4633458b-17de-408a-b874-0445c86b69e6') }
}

// One private endpoint per service, from a loop
var peTargets = [ { name: 'sql', id: sql.id, group: 'sqlServer' }, { name: 'kv', id: kv.id, group: 'vault' } ]
module pe 'br/public:avm/res/network/private-endpoint:0.9.0' = [for t in peTargets: {
  name: 'pe-${t.name}-${env}'
  params: { name: 'pe-${t.name}-shop-${env}', location: location, subnetResourceId: peSubnetId, privateLinkServiceConnections: [ { name: t.name, properties: { privateLinkServiceId: t.id, groupIds: [ t.group ] } } ] }
}]

output webUrl string = web.outputs.url
output sqlFqdn string = sql.properties.fullyQualifiedDomainName
using './main.bicep'

param env = 'prod'
param location = 'westeurope'
param sqlAdminPassword = az.getSecret('<sub-id>', 'rg-platform', 'kv-platform', 'sql-admin-password')   // pulled from Key Vault at deploy time
Interview angle

Implicit vs explicit dependsOn; modules and the public registry (Azure Verified Modules); existing and cross-RG scope; deterministic names for role assignments; idempotent re-runs; what happens when you remove a resource from the file (nothing — see stacks).

Deploying Bicep: what-if, modes and deployment stacks

Deploy at resource group, subscription, management group or tenant scope. what-if previews changes (your "plan"). Incremental mode (default) never deletes; deployment stacks track the resources a template created so removing one from the file deletes it (with deny settings to protect them from out-of-band edits). Deployment history lives on the scope.

# Validate, preview, deploy
az bicep lint --file main.bicep
az deployment group validate -g rg-shop-prod --template-file main.bicep --parameters prod.bicepparam
az deployment group what-if  -g rg-shop-prod --template-file main.bicep --parameters prod.bicepparam --result-format FullResourcePayloads
az deployment group create   -g rg-shop-prod --template-file main.bicep --parameters prod.bicepparam --name "shop-$(date +%Y%m%d%H%M)" --query properties.outputs

# Subscription scope (creates the RG too)
az deployment sub create -l westeurope --template-file main.sub.bicep --parameters env=prod

# Deployment stacks: the file is the whole truth — removed resources get deleted; deny out-of-band writes
az stack group create -g rg-shop-prod -n shop --template-file main.bicep --parameters prod.bicepparam   --action-on-unmanage deleteResources --deny-settings-mode denyWriteAndDelete --deny-settings-excluded-principals <pipeline-sp-oid> --yes
az stack group show -g rg-shop-prod -n shop --query "resources[].id"

# Inspect a failed deployment
az deployment operation group list -g rg-shop-prod -n shop-202609181200 --query "[?properties.provisioningState=='Failed'].{r:properties.targetResource.id, err:properties.statusMessage.error.message}"
# Azure Pipelines: what-if on PR, deploy on main with an approval on the environment
- stage: Preview
  jobs:
    - job: whatif
      steps:
        - task: AzureCLI@2
          inputs:
            azureSubscription: sc-shop-prod
            scriptType: bash
            scriptLocation: inlineScript
            inlineScript: |
              az bicep lint --file infra/main.bicep
              az deployment group what-if -g rg-shop-prod --template-file infra/main.bicep --parameters infra/prod.bicepparam --no-pretty-print > whatif.json
              cat whatif.json
        - publish: whatif.json
          artifact: whatif
- stage: Deploy
  dependsOn: Preview
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
    - deployment: infra
      environment: shop-prod           # approval + check that the what-if artifact was reviewed
      strategy: { runOnce: { deploy: { steps: [
        { task: AzureCLI@2, inputs: { azureSubscription: sc-shop-prod, scriptType: bash, scriptLocation: inlineScript,
          inlineScript: az deployment group create -g rg-shop-prod --template-file infra/main.bicep --parameters infra/prod.bicepparam } } ] } } }
Interview angle

Incremental vs complete mode; what-if limitations (noise, nested modules); deployment stacks vs Terraform state; how you protect prod from portal changes; secrets in parameters (@secure, Key Vault references, never in the pipeline log).

Terraform: providers, resources, variables, modules

Terraform reads *.tf files in a directory, builds a dependency graph, compares it with state and calls provider APIs. Structure: providers.tf, variables.tf, main.tf, outputs.tf, a modules/ directory, and per-environment *.tfvars. Pin provider versions. Use for_each over count for stable addresses.

# providers.tf
terraform {
  required_version = ">= 1.9"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
    azapi   = { source = "azure/azapi",       version = "~> 2.0" }
  }
  backend "azurerm" {}          # values supplied at init (see next section)
}
provider "azurerm" {
  features { key_vault { purge_soft_delete_on_destroy = false } }
  use_oidc = true               # workload identity federation from the pipeline
}

# variables.tf
variable "env"      { type = string; validation { condition = contains(["dev", "test", "prod"], var.env); error_message = "env must be dev|test|prod" } }
variable "location" { type = string; default = "westeurope" }
variable "sql_admin_password" { type = string; sensitive = true }
locals { is_prod = var.env == "prod"; tags = { env = var.env, owner = "shop-team" } }

# main.tf
resource "azurerm_resource_group" "shop" { name = "rg-shop-${var.env}"; location = var.location; tags = local.tags }

resource "azurerm_key_vault" "kv" {
  name                       = "kv-shop-${var.env}-${random_string.suffix.result}"
  location                   = azurerm_resource_group.shop.location
  resource_group_name        = azurerm_resource_group.shop.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = local.is_prod
  public_network_access_enabled = false
  tags = local.tags
}

resource "azurerm_mssql_server" "sql" {
  name = "sql-shop-${var.env}-${random_string.suffix.result}"; location = var.location; resource_group_name = azurerm_resource_group.shop.name
  version = "12.0"; administrator_login = "sqladmin"; administrator_login_password = var.sql_admin_password
  minimum_tls_version = "1.2"; public_network_access_enabled = false
}
resource "azurerm_mssql_database" "db" {
  name = "shopdb"; server_id = azurerm_mssql_server.sql.id
  sku_name = local.is_prod ? "GP_Gen5_4" : "GP_S_Gen5_1"; zone_redundant = local.is_prod
}

module "web" {
  source        = "./modules/web"
  env           = var.env
  location      = var.location
  rg_name       = azurerm_resource_group.shop.name
  sku           = local.is_prod ? "P1v3" : "B1"
  instances     = local.is_prod ? 3 : 1
  key_vault_id  = azurerm_key_vault.kv.id
  sql_fqdn      = azurerm_mssql_server.sql.fully_qualified_domain_name
  tags          = local.tags
}

resource "azurerm_role_assignment" "web_kv" {
  scope = azurerm_key_vault.kv.id; role_definition_name = "Key Vault Secrets User"; principal_id = module.web.principal_id
}

# Private endpoints from a map — stable addresses, easy to add one
locals { pe = { sql = { id = azurerm_mssql_server.sql.id, group = "sqlServer" }, kv = { id = azurerm_key_vault.kv.id, group = "vault" } } }
resource "azurerm_private_endpoint" "pe" {
  for_each = local.pe
  name = "pe-${each.key}-shop-${var.env}"; location = var.location; resource_group_name = azurerm_resource_group.shop.name; subnet_id = var.pe_subnet_id
  private_service_connection { name = each.key; private_connection_resource_id = each.value.id; subresource_names = [each.value.group]; is_manual_connection = false }
}

# Brand-new resource type not in azurerm yet? azapi speaks raw ARM.
resource "azapi_resource" "new_thing" {
  type = "Microsoft.App/sessionPools@2024-10-02-preview"; name = "sp-shop-${var.env}"; parent_id = azurerm_resource_group.shop.id; location = var.location
  body = { properties = { poolManagementType = "Dynamic", containerType = "PythonLTS", scaleConfiguration = { maxConcurrentSessions = 10 } } }
}

# outputs.tf
output "web_url"  { value = module.web.url }
output "sql_fqdn" { value = azurerm_mssql_server.sql.fully_qualified_domain_name }
terraform fmt -recursive && terraform validate
terraform plan  -var-file=env/prod.tfvars -out=prod.tfplan
terraform show -json prod.tfplan | jq '.resource_changes[] | select(.change.actions != ["no-op"]) | {addr: .address, actions: .change.actions}'
terraform apply prod.tfplan                       # applies exactly what was reviewed
terraform output -json

# Day-2
terraform state list ; terraform state show azurerm_key_vault.kv
terraform import azurerm_resource_group.legacy /subscriptions/<sub>/resourceGroups/rg-legacy     # adopt existing resources (or an import {} block)
terraform state mv module.web.azurerm_linux_web_app.api module.web.azurerm_linux_web_app.app       # refactor without recreate (or moved {} block)
terraform plan -destroy -target=module.web       # see the blast radius before removing something
Interview angle

Plan/apply and why you apply a saved plan; for_each vs count; module design and versioning; import/moved blocks for refactoring; sensitive values in state; provider version pinning and upgrade strategy.

Terraform state: backends, locking, workspaces

State maps addresses to real resource IDs and caches attributes — it contains secrets, so it lives in a locked-down remote backend, never in git. On Azure: a storage account with versioning, soft delete and blob leases for locking. One state per environment (separate backends or keys) beats workspaces for anything serious. Drift: plan shows it; refresh-only accepts it.

# Backend storage: versioned, locked down, identity-auth only
az storage account create -g rg-tfstate -n sttfstateshop --sku Standard_GZRS --allow-blob-public-access false --allow-shared-key-access false --min-tls-version TLS1_2
az storage account blob-service-properties update -g rg-tfstate -n sttfstateshop --enable-versioning true --enable-delete-retention true --delete-retention-days 30
az storage container create --account-name sttfstateshop -n tfstate --auth-mode login
az role assignment create --assignee <pipeline-sp> --role "Storage Blob Data Contributor" --scope $(az storage account show -g rg-tfstate -n sttfstateshop --query id -o tsv)

# Init per environment with a partial backend config
terraform init -reconfigure   -backend-config="resource_group_name=rg-tfstate" -backend-config="storage_account_name=sttfstateshop"   -backend-config="container_name=tfstate" -backend-config="key=shop/prod.tfstate" -backend-config="use_azuread_auth=true" -backend-config="use_oidc=true"

# Locks are blob leases: a crashed run leaves one behind
terraform force-unlock <lock-id>

# Drift
terraform plan -refresh-only                       # what changed outside Terraform?
terraform apply -refresh-only                      # accept reality into state (no infra change)
# Layout that scales: one root module per environment, shared modules, no workspaces
# infra/
#   modules/web/  modules/data/  modules/network/
#   envs/dev/   { main.tf, backend.hcl, terraform.tfvars }
#   envs/prod/  { main.tf, backend.hcl, terraform.tfvars }
#
# envs/prod/backend.hcl
resource_group_name  = "rg-tfstate"
storage_account_name = "sttfstateshop"
container_name       = "tfstate"
key                  = "shop/prod.tfstate"
use_azuread_auth     = true

# Read outputs of another state (e.g. the platform team's network) instead of hard-coding IDs
data "terraform_remote_state" "network" {
  backend = "azurerm"
  config  = { resource_group_name = "rg-tfstate", storage_account_name = "sttfstateplatform", container_name = "tfstate", key = "network/prod.tfstate", use_azuread_auth = true }
}

Interview angle

What is in state and why it is sensitive; locking and what happens without it; workspaces vs directories; splitting state to limit blast radius; recovering from a corrupted/lost state (versioning, import); remote state vs data sources for cross-team references.

IaC in the pipeline: plan → review → apply

The pattern is identical for both tools: on PR run lint + validate + plan/what-if and post it to the PR; on merge, apply the same plan after an environment approval. Authenticate with workload identity federation (OIDC), never a secret. Run policy checks against the plan before anyone reviews it.

name: infra
on:
  pull_request: { paths: [infra/**] }
  push: { branches: [main], paths: [infra/**] }
permissions: { id-token: write, contents: read, pull-requests: write }
env: { ARM_USE_OIDC: "true", ARM_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID }}, ARM_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}, ARM_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }} }

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: infra/envs/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.9.5 }
      - run: terraform init -backend-config=backend.hcl
      - run: terraform fmt -check && terraform validate
      - uses: terraform-linters/setup-tflint@v4
      - run: tflint --recursive
      - run: terraform plan -out=tfplan -input=false
      - run: terraform show -json tfplan > tfplan.json
      - uses: bridgecrewio/checkov-action@v12
        with: { file: infra/envs/prod/tfplan.json, framework: terraform_plan, soft_fail: false }
      - uses: actions/upload-artifact@v4
        with: { name: tfplan, path: infra/envs/prod/tfplan }
      - if: github.event_name == 'pull_request'
        run: |
          terraform show -no-color tfplan > plan.txt
          gh pr comment ${{ github.event.pull_request.number }} --body "$(printf '```\n%s\n```' "$(head -c 60000 plan.txt)")"
        env: { GH_TOKEN: ${{ github.token }} }

  apply:
    if: github.ref == 'refs/heads/main'
    needs: plan
    runs-on: ubuntu-latest
    environment: prod                       # required reviewers gate this job
    defaults: { run: { working-directory: infra/envs/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -backend-config=backend.hcl
      - uses: actions/download-artifact@v4
        with: { name: tfplan, path: infra/envs/prod }
      - run: terraform apply -input=false tfplan     # exactly the reviewed plan
# Local pre-commit equivalents (fast feedback before the PR)
pre-commit install
# .pre-commit-config.yaml hooks: terraform_fmt, terraform_validate, terraform_tflint, terraform_docs, checkov
# For Bicep: az bicep lint, PSRule for Azure (Invoke-PSRule -InputPath infra/ -Module PSRule.Rules.Azure)
Interview angle

Why the apply uses the saved plan artifact; how you prevent two pipelines applying concurrently (state lock, concurrency groups); policy-as-code before review; OIDC auth; what you do when apply fails halfway (state is consistent per resource — rerun).

Testing, policy and drift

Layers: lint (bicep lint / tflint), static policy (PSRule for Azure, Checkov, tfsec, Azure Policy in the what-if), plan review, deployment test (deploy to an ephemeral RG, run smoke tests, destroy — Terratest or a script), and drift detection (scheduled plan/what-if that opens an issue on changes). Azure Policy at the subscription remains the last line.

# PSRule for Azure: 300+ Well-Architected rules against Bicep/ARM before deployment
pwsh -c "Install-Module PSRule.Rules.Azure -Scope CurrentUser -Force; Invoke-PSRule -InputPath infra/ -Module PSRule.Rules.Azure -Format File -Outcome Fail,Error"

# Checkov on Terraform source or plan
checkov -d infra/ --framework terraform --check CKV_AZURE_* --skip-check CKV_AZURE_109
checkov -f tfplan.json --framework terraform_plan

# Ephemeral deployment test for Bicep — deploy, smoke, destroy
RG=rg-shop-test-$RANDOM
az group create -n $RG -l westeurope --tags ephemeral=true
az deployment group create -g $RG --template-file infra/main.bicep --parameters env=test sqlAdminPassword="$(openssl rand -base64 24)" -o none
URL=$(az deployment group show -g $RG -n main --query properties.outputs.webUrl.value -o tsv)
curl -fsS "$URL/health/ready" && echo "smoke OK"
az group delete -n $RG --yes --no-wait

# Scheduled drift check (nightly)
terraform plan -detailed-exitcode -input=false >/dev/null; case $? in 0) echo "no drift";; 2) echo "DRIFT" && exit 2;; *) exit 1;; esac
# Terraform-plan assertions in pytest — cheap guardrails your team owns
import json, subprocess, pytest

@pytest.fixture(scope="session")
def plan():
    subprocess.run(["terraform", "-chdir=infra/envs/prod", "plan", "-out=tfplan", "-input=false"], check=True)
    out = subprocess.check_output(["terraform", "-chdir=infra/envs/prod", "show", "-json", "tfplan"])
    return json.loads(out)

def resources(plan, rtype):
    return [r for r in plan["planned_values"]["root_module"].get("resources", []) if r["type"] == rtype] +            [r for m in plan["planned_values"]["root_module"].get("child_modules", []) for r in m.get("resources", []) if r["type"] == rtype]

def test_no_public_storage(plan):
    for r in resources(plan, "azurerm_storage_account"):
        assert r["values"]["public_network_access_enabled"] is False, r["address"]

def test_nothing_destroyed_in_prod(plan):
    destroyed = [c["address"] for c in plan["resource_changes"] if "delete" in c["change"]["actions"]]
    assert not destroyed, f"plan would destroy: {destroyed}"
Interview angle

Test pyramid for infrastructure; what static analysis can and cannot catch; ephemeral environments and their cost; drift sources (portal edits, auto-generated resources) and response; when a rule should be a pipeline check vs an Azure Policy deny.

Bicep vs Terraform vs Pulumi

Pick one per organisation and stick with it. Bicep: Azure-only, no state to manage, day-zero resource support, best with deployment stacks and Azure Verified Modules. Terraform: multi-cloud and SaaS providers (Entra, GitHub, Datadog…), rich ecosystem, explicit plan, state to protect. Pulumi: real languages (C#, Python) with tests and abstractions, Terraform-provider bridge, state in Pulumi Cloud or your own backend.

// Pulumi in C# — the same web tier, with a unit test
class ShopStack : Stack
{
    public ShopStack()
    {
        var cfg = new Config(); var env = cfg.Require("env");
        var rg = new ResourceGroup("rg", new() { ResourceGroupName = $"rg-shop-{env}", Location = "westeurope" });
        var plan = new AppServicePlan("plan", new() { ResourceGroupName = rg.Name, Kind = "linux", Reserved = true,
            Sku = new SkuDescriptionArgs { Name = env == "prod" ? "P1v3" : "B1", Capacity = env == "prod" ? 3 : 1 } });
        var app = new WebApp("api", new() { ResourceGroupName = rg.Name, ServerFarmId = plan.Id, HttpsOnly = true,
            Identity = new ManagedServiceIdentityArgs { Type = ManagedServiceIdentityType.SystemAssigned },
            SiteConfig = new SiteConfigArgs { LinuxFxVersion = "DOTNETCORE|9.0", MinTlsVersion = "1.2", FtpsState = "Disabled" } });
        Url = app.DefaultHostName.Apply(h => $"https://{h}");
    }
    [Output] public Output<string> Url { get; set; }
}
// Test with Pulumi.Testing mocks:  var resources = await Deployment.TestAsync<ShopStack>(new Mocks());  Assert all WebApps have HttpsOnly == true

Defend a choice for a given org (Azure-only startup vs multi-cloud enterprise); migration cost between tools; how each handles secrets, deletions and drift; team skills as a deciding factor.
