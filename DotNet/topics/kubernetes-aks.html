Kubernetes & AKS

Container Apps hides Kubernetes; AKS does not. This page is the working vocabulary — enough YAML to deploy the .NET API with config, secrets, scaling and TLS — plus the AKS-specific features that replace the "Kubernetes way" with the "Azure way" (identity, secrets, registry). Every snippet is something you would actually run.

Pods, Deployments, Services and namespaces

A Pod is one or more containers sharing a network namespace — the unit of scheduling. You never create Pods directly; a Deployment manages a ReplicaSet that keeps N Pods running and performs rolling updates. A Service gives a stable virtual IP/DNS name (orders-api.shop.svc.cluster.local) in front of the Pods selected by labels. Namespaces partition the cluster (per team/environment) for RBAC, quotas and naming.

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders-api, namespace: shop, labels: { app: orders-api } }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders-api } }
  strategy: { type: RollingUpdate, rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }   # zero-downtime
  template:
    metadata:
      labels: { app: orders-api, azure.workload.identity/use: "true" }
    spec:
      serviceAccountName: orders-api
      topologySpreadConstraints:                                  # spread across zones
        - { maxSkew: 1, topologyKey: topology.kubernetes.io/zone, whenUnsatisfiable: ScheduleAnyway, labelSelector: { matchLabels: { app: orders-api } } }
      securityContext: { runAsNonRoot: true, seccompProfile: { type: RuntimeDefault } }
      containers:
        - name: api
          image: acrshop.azurecr.io/shop-api@sha256:3f1a…            # digest-pinned by the pipeline
          ports: [{ containerPort: 8080, name: http }]
          envFrom: [{ configMapRef: { name: orders-api-config } }]
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits:   { memory: 512Mi }                              # CPU limit omitted on purpose (throttling); memory limit kept
          readinessProbe: { httpGet: { path: /health/ready, port: http }, periodSeconds: 5, failureThreshold: 3 }
          livenessProbe:  { httpGet: { path: /health/live,  port: http }, periodSeconds: 15, initialDelaySeconds: 10 }
          lifecycle: { preStop: { exec: { command: ["sleep", "5"] } } }   # let the endpoint drain before SIGTERM
          securityContext: { allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities: { drop: [ALL] } }
          volumeMounts: [{ name: tmp, mountPath: /tmp }]
      volumes: [{ name: tmp, emptyDir: {} }]
---
apiVersion: v1
kind: Service
metadata: { name: orders-api, namespace: shop }
spec:
  selector: { app: orders-api }
  ports: [{ port: 80, targetPort: http }]
  type: ClusterIP
kubectl create namespace shop
kubectl apply -f deploy/ -n shop
kubectl get deploy,rs,pods,svc -n shop -o wide
kubectl rollout status deploy/orders-api -n shop
kubectl describe pod -l app=orders-api -n shop | sed -n '/Events/,$p'
kubectl port-forward svc/orders-api 8080:80 -n shop      # hit it from your laptop
kubectl scale deploy/orders-api --replicas=5 -n shop
Interview angle

Pod vs container vs Deployment vs ReplicaSet; how a Service finds Pods (labels, Endpoints/EndpointSlices); ClusterIP vs NodePort vs LoadBalancer; what happens during a rolling update; readiness vs liveness and how a bad liveness probe causes restart storms.

ConfigMaps, Secrets, probes and resources

ConfigMaps hold non-secret config as env vars or mounted files; Secrets are base64 (not encrypted by default — use Key Vault + CSI driver on AKS, see below). Requests drive scheduling and the autoscaler; limits cap usage (memory limit → OOMKill; CPU limit → throttling). Set requests always; set memory limits; think twice about CPU limits for latency-sensitive services.

apiVersion: v1
kind: ConfigMap
metadata: { name: orders-api-config, namespace: shop }
data:
  ASPNETCORE_ENVIRONMENT: Production
  ASPNETCORE_HTTP_PORTS: "8080"
  Shop__Inventory__Url: http://inventory-api.shop.svc.cluster.local
  Logging__LogLevel__Default: Information
---
# Mounted file config (reloadOnChange works with the projected volume symlink swap)
apiVersion: v1
kind: ConfigMap
metadata: { name: orders-api-appsettings, namespace: shop }
data:
  appsettings.Production.json: |
    { "Shop": { "Checkout": { "MaxItems": 50 } } }
---
apiVersion: v1
kind: ResourceQuota
metadata: { name: shop-quota, namespace: shop }
spec: { hard: { requests.cpu: "8", requests.memory: 16Gi, limits.memory: 32Gi, pods: "50" } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget                    # keep 2 up during node upgrades / drains
metadata: { name: orders-api-pdb, namespace: shop }
spec: { minAvailable: 2, selector: { matchLabels: { app: orders-api } } }
// Health endpoints Kubernetes will probe — keep liveness trivial, readiness honest
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: new[] { "live" })
    .AddSqlServer(cs, tags: new[] { "ready" })
    .AddRedis(redisCs, tags: new[] { "ready" });
app.MapHealthChecks("/health/live",  new() { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = r => r.Tags.Contains("ready") });

// Graceful shutdown: SIGTERM → stop accepting → finish in-flight (must be < terminationGracePeriodSeconds, default 30)
builder.Host.ConfigureHostOptions(o => o.ShutdownTimeout = TimeSpan.FromSeconds(20));

// Mounted appsettings from the ConfigMap
builder.Configuration.AddJsonFile("/app/config/appsettings.Production.json", optional: true, reloadOnChange: true);
# FastAPI equivalents
@app.get("/health/live")
def live(): return {"status": "ok"}

@app.get("/health/ready")
async def ready():
    await db.execute("SELECT 1"); await redis.ping()
    return {"status": "ready"}

# uvicorn handles SIGTERM: stops accepting, waits for in-flight requests (--timeout-graceful-shutdown 20)
Interview angle

Requests vs limits and QoS classes (Guaranteed/Burstable/BestEffort); why CPU limits can hurt p99; PDBs and node upgrades; Secrets are base64, so what do you actually do; how config changes reach running Pods (env needs restart, files reload).

Ingress, Gateway API and TLS

An Ingress routes HTTP by host/path to Services through an ingress controller (NGINX, Application Gateway for Containers, Traefik). The newer Gateway API (GatewayClass → Gateway → HTTPRoute) is the successor with clearer role separation. TLS certificates come from cert-manager (Let's Encrypt) or Key Vault; on AKS the managed "application routing" add-on gives you NGINX + Key Vault certs + Azure DNS in one step.

# AKS application routing add-on (managed NGINX) with a Key Vault certificate and Azure DNS
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    kubernetes.azure.com/tls-cert-keyvault-uri: https://kv-shop.vault.azure.net/certificates/shop-tls
    nginx.ingress.kubernetes.io/proxy-body-size: 10m
    nginx.ingress.kubernetes.io/limit-rps: "50"
spec:
  ingressClassName: webapprouting.kubernetes.azure.com
  tls: [{ hosts: [api.contoso.com], secretName: keyvault-shop }]
  rules:
    - host: api.contoso.com
      http:
        paths:
          - { path: /orders,    pathType: Prefix, backend: { service: { name: orders-api,    port: { number: 80 } } } }
          - { path: /inventory, pathType: Prefix, backend: { service: { name: inventory-api, port: { number: 80 } } } }
---
# Gateway API flavour (Application Gateway for Containers / any conformant controller)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: orders, namespace: shop }
spec:
  parentRefs: [{ name: shop-gateway, namespace: infra }]
  hostnames: [api.contoso.com]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /orders } }]
      backendRefs:
        - { name: orders-api, port: 80, weight: 90 }
        - { name: orders-api-canary, port: 80, weight: 10 }        # weighted canary in the route
az aks approuting enable -g rg-shop -n aks-shop
az aks approuting update -g rg-shop -n aks-shop --enable-kv --attach-kv $(az keyvault show -n kv-shop --query id -o tsv)
az aks approuting zone add -g rg-shop -n aks-shop --ids $(az network dns zone show -g rg-dns -n contoso.com --query id -o tsv) --attach-zones
kubectl get ingress -n shop                        # ADDRESS column = public IP; DNS record is created for you
kubectl logs -n app-routing-system -l app.kubernetes.io/name=nginx --tail=100    # controller logs for 502s
Interview angle

Ingress vs Service type LoadBalancer; where TLS terminates and mTLS to Pods; Ingress vs Gateway API; how you do canary/blue-green at the routing layer; WAF placement (App Gateway for Containers / Front Door in front).

HPA, KEDA and the cluster autoscaler

Three layers: the HPA scales Pods on CPU/memory/custom metrics; KEDA scales on event sources (Service Bus queue length, Event Hubs lag, HTTP, cron) including to zero; the cluster autoscaler (or Node Autoprovisioning / Karpenter) adds nodes when Pods are unschedulable. Requests must be accurate or every layer misbehaves. VPA can recommend requests.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders-api, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders-api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
  behavior:
    scaleUp:   { stabilizationWindowSeconds: 0,   policies: [{ type: Percent, value: 100, periodSeconds: 30 }] }
    scaleDown: { stabilizationWindowSeconds: 300, policies: [{ type: Pods, value: 2, periodSeconds: 60 }] }
---
# KEDA: the order worker scales on Service Bus queue depth, to zero when idle, authenticating with workload identity
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata: { name: sb-auth, namespace: shop }
spec: { podIdentity: { provider: azure-workload, identityId: <client-id-of-user-assigned-mi> } }
---
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: order-worker, namespace: shop }
spec:
  scaleTargetRef: { name: order-worker }
  minReplicaCount: 0
  maxReplicaCount: 50
  cooldownPeriod: 120
  triggers:
    - type: azure-servicebus
      metadata: { queueName: orders, namespace: sb-shop, messageCount: "20" }     # 1 replica per 20 messages
      authenticationRef: { name: sb-auth }
az aks update -g rg-shop -n aks-shop --enable-keda                                   # managed KEDA add-on
az aks nodepool update -g rg-shop --cluster-name aks-shop -n userpool --enable-cluster-autoscaler --min-count 2 --max-count 20
az aks update -g rg-shop -n aks-shop --cluster-autoscaler-profile scale-down-delay-after-add=5m scan-interval=20s

kubectl get hpa,scaledobject -n shop
kubectl describe hpa orders-api -n shop | sed -n '/Conditions/,$p'
kubectl get events -n shop --field-selector reason=TriggeredScaleUp
kubectl top pods -n shop --sort-by=cpu
Interview angle

Why HPA needs requests; scale-up vs scale-down stabilisation; KEDA vs HPA on custom metrics; scaling to zero and cold starts; the cluster autoscaler's signal (pending Pods) and node provisioning time; over-provisioning with pause Pods.

Helm and Kustomize

Helm packages templated manifests into a chart with per-environment values.yaml, tracked as releases with history and rollback; use it for third-party software (ingress, KEDA, Prometheus) and your own services when you want one artefact. Kustomize patches plain YAML per overlay without templating and is built into kubectl. Many teams do both: Helm for vendor charts, Kustomize for their own manifests.

# charts/orders-api/values.yaml
image: { repository: acrshop.azurecr.io/shop-api, tag: "" }       # tag/digest injected by the pipeline
replicaCount: 3
resources: { requests: { cpu: 250m, memory: 256Mi }, limits: { memory: 512Mi } }
ingress: { host: api.contoso.com, path: /orders }
config:
  Shop__Inventory__Url: http://inventory-api.shop.svc.cluster.local

# charts/orders-api/templates/deployment.yaml (excerpt)
# spec:
#   replicas: {{ .Values.replicaCount }}
#   template:
#     metadata:
#       annotations: { checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }} }  # restart on config change
#     spec:
#       containers:
#         - image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
#           envFrom: [{ configMapRef: { name: {{ include "orders-api.fullname" . }} } }]

# values.prod.yaml
replicaCount: 6
resources: { requests: { cpu: 500m, memory: 512Mi }, limits: { memory: 1Gi } }
# k8s/base/kustomization.yaml
resources: [deployment.yaml, service.yaml, configmap.yaml, hpa.yaml]
commonLabels: { app.kubernetes.io/part-of: shop }

# k8s/overlays/prod/kustomization.yaml
resources: [../../base]
namespace: shop
images:
  - { name: acrshop.azurecr.io/shop-api, digest: sha256:3f1a… }
patches:
  - target: { kind: Deployment, name: orders-api }
    patch: |
      - op: replace
        path: /spec/replicas
        value: 6
configMapGenerator:
  - name: orders-api-config
    behavior: merge
    literals: [Logging__LogLevel__Default=Warning]
# Helm
helm repo add kedacore https://kedacore.github.io/charts && helm repo update
helm upgrade --install keda kedacore/keda -n keda --create-namespace --version 2.16.0 --wait
helm upgrade --install orders-api charts/orders-api -n shop -f charts/orders-api/values.prod.yaml   --set image.tag=1.4.2 --atomic --timeout 5m          # --atomic rolls back automatically if the release fails
helm history orders-api -n shop ; helm rollback orders-api 3 -n shop
helm template orders-api charts/orders-api -f values.prod.yaml | kubectl apply --dry-run=server -f -   # validate against the API server

# Kustomize
kubectl kustomize k8s/overlays/prod | kubectl diff -f - ; kubectl apply -k k8s/overlays/prod
Interview angle

Helm vs Kustomize trade-offs; release history and rollback; the config-checksum annotation trick; chart versioning vs app versioning; where you store charts (ACR supports OCI charts); GitOps (Flux/Argo CD) as the next step.

AKS specifics: node pools, identity, secrets, registry

AKS replaces several DIY pieces: system/user node pools (spot pools for batch), workload identity instead of secrets in Pods, the Key Vault CSI driver to mount secrets/certs, ACR attach for pulls, Azure CNI (Overlay) networking, Azure Policy for AKS (Gatekeeper) and Container Insights. AKS Automatic bundles most of the recommended setup.

# Cluster with the pieces you want from day one
az aks create -g rg-shop -n aks-shop --location westeurope --tier standard --zones 1 2 3   --node-count 3 --node-vm-size Standard_D4ds_v5 --nodepool-name system --nodepool-labels mode=system   --network-plugin azure --network-plugin-mode overlay --network-policy cilium --network-dataplane cilium   --enable-oidc-issuer --enable-workload-identity --enable-managed-identity   --enable-addons monitoring,azure-keyvault-secrets-provider --enable-secret-rotation   --attach-acr acrshop --enable-cluster-autoscaler --min-count 3 --max-count 6 --enable-azure-rbac --enable-aad
az aks nodepool add -g rg-shop --cluster-name aks-shop -n userpool --mode User --node-count 2 --node-vm-size Standard_D8ds_v5 --zones 1 2 3 --enable-cluster-autoscaler --min-count 2 --max-count 20
az aks nodepool add -g rg-shop --cluster-name aks-shop -n spotpool --priority Spot --eviction-policy Delete --spot-max-price -1 --node-count 0 --enable-cluster-autoscaler --min-count 0 --max-count 10   --node-taints kubernetes.azure.com/scalesetpriority=spot:NoSchedule

# Workload identity: MI + federated credential ↔ service account
az identity create -g rg-shop -n id-orders-api
ISSUER=$(az aks show -g rg-shop -n aks-shop --query oidcIssuerProfile.issuerUrl -o tsv)
az identity federated-credential create -g rg-shop --identity-name id-orders-api -n orders-api --issuer $ISSUER --subject system:serviceaccount:shop:orders-api --audiences api://AzureADTokenExchange
az role assignment create --assignee $(az identity show -g rg-shop -n id-orders-api --query principalId -o tsv) --role "Key Vault Secrets User" --scope $(az keyvault show -n kv-shop --query id -o tsv)

az aks get-credentials -g rg-shop -n aks-shop ; kubelogin convert-kubeconfig -l azurecli

Interview angle

System vs user node pools and taints; workload identity end to end (OIDC issuer, federated credential, projected token); CSI driver vs reading Key Vault from code; Azure CNI overlay vs kubenet; upgrades (node image vs Kubernetes version, surge, PDBs); AKS Automatic.

Deploying from a pipeline: rollouts and rollbacks

The pipeline builds the image, pins the digest, renders manifests (Helm/Kustomize), applies them and waits for the rollout. Rolling updates are the default; for canary or blue-green use weighted routes (Gateway API / Argo Rollouts / Flagger). Rollback is kubectl rollout undo or redeploying the previous digest. GitOps (Flux is an AKS extension) inverts the flow: the cluster pulls the desired state from git.

- stage: DeployProd
  dependsOn: Build
  jobs:
    - deployment: aks
      environment: shop-prod.shop          # AKS environment resource → approvals + Kubernetes view
      strategy:
        runOnce:
          deploy:
            steps:
              - task: AzureCLI@2
                inputs:
                  azureSubscription: sc-shop-prod
                  scriptType: bash
                  scriptLocation: inlineScript
                  inlineScript: |
                    set -euo pipefail
                    az aks get-credentials -g rg-shop -n aks-shop --overwrite-existing
                    kubelogin convert-kubeconfig -l azurecli
                    DIGEST="$(Build.imageDigest)"
                    helm upgrade --install orders-api charts/orders-api -n shop -f charts/orders-api/values.prod.yaml                       --set image.digest="$DIGEST" --atomic --timeout 10m
                    kubectl rollout status deploy/orders-api -n shop --timeout=300s
              - script: curl -fsS https://api.contoso.com/orders/health/ready
                displayName: Smoke test
# Manual rollout control
kubectl set image deploy/orders-api api=acrshop.azurecr.io/shop-api@sha256:9c2b… -n shop
kubectl rollout status deploy/orders-api -n shop
kubectl rollout history deploy/orders-api -n shop
kubectl rollout undo deploy/orders-api -n shop --to-revision=4
kubectl rollout pause deploy/orders-api -n shop   # investigate mid-rollout; resume later

# GitOps with the Flux extension: cluster reconciles k8s/overlays/prod from git every minute
az k8s-configuration flux create -g rg-shop -c aks-shop -n shop-config -t managedClusters --scope cluster   -u https://github.com/contoso/shop-deploy --branch main --kustomization name=prod path=./k8s/overlays/prod prune=true
Interview angle

Rolling vs canary vs blue-green on Kubernetes and the tooling for each; what "rollout status" waits for; digest pinning; GitOps pros/cons (drift, audit, pull vs push); database migrations relative to the rollout.

The kubectl troubleshooting loop

Pending → scheduling problem (resources, taints, PVC). CrashLoopBackOff → the process exits; read logs of the previous container. ImagePullBackOff → registry auth or wrong tag. Ready 0/1 → readiness probe failing. 502/503 from ingress → no ready endpoints. Learn the five commands and the order: get → describe → logs → exec/debug → events.

kubectl get pods -n shop -o wide                              # STATUS / RESTARTS / node
kubectl describe pod <pod> -n shop                            # Events at the bottom: FailedScheduling, Unhealthy, BackOff, Failed to pull
kubectl logs <pod> -n shop --previous --tail=200              # why did the last container die
kubectl get events -n shop --sort-by=.lastTimestamp | tail -30
kubectl get endpoints orders-api -n shop                      # empty → no ready Pods → ingress 503

kubectl exec -it <pod> -n shop -- sh                          # if the image has a shell
kubectl debug -it <pod> -n shop --image=mcr.microsoft.com/dotnet/sdk:9.0 --target=api --share-processes   # ephemeral container for chiseled images
kubectl debug node/<node> -it --image=ubuntu                  # node-level shell

kubectl top pods -n shop ; kubectl top nodes
kubectl get pod <pod> -n shop -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}'   # OOMKilled?
kubectl auth can-i create deployments -n shop --as system:serviceaccount:shop:ci     # RBAC checks

# Networking from inside the cluster
kubectl run -it --rm netshoot --image=nicolaka/netshoot -n shop -- bash

// Container Insights (Log Analytics): restarts and OOM kills in the last hour
KubePodInventory
| where TimeGenerated > ago(1h) and Namespace == "shop"
| summarize restarts = max(ContainerRestartCount) by Name, ContainerStatusReason
| where restarts > 0
| order by restarts desc

// Application stdout logs
ContainerLogV2
| where TimeGenerated > ago(30m) and PodNamespace == "shop" and PodName startswith "orders-api"
| where LogMessage has "error"
| project TimeGenerated, PodName, LogMessage
