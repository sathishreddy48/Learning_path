Modelling, normalisation and when to denormalise

Normalisation is a set of rules for removing redundancy so a fact lives in exactly one place. In practice you need 1NF–3NF and the sentence that summarises them: every non-key column depends on the key, the whole key, and nothing but the key. Past 3NF is academic for interview purposes.

The more interesting half is when you deliberately break it. Denormalising — a cached OrderTotal, a duplicated CustomerName, a counter column — trades write complexity and a consistency risk for read speed. The answer an interviewer wants is that it is a measured decision with a named mechanism to keep the copy correct, not something you do by default.

-- 3NF: each fact once, relationships by key
CREATE TABLE customers (
    id          INT IDENTITY PRIMARY KEY,
    email       NVARCHAR(256) NOT NULL UNIQUE,     -- natural key, enforced
    name        NVARCHAR(200) NOT NULL,
    created_at  DATETIME2     NOT NULL DEFAULT SYSUTCDATETIME()
);

CREATE TABLE orders (
    id          INT IDENTITY PRIMARY KEY,
    customer_id INT           NOT NULL REFERENCES customers(id),
    status      VARCHAR(20)   NOT NULL
                  CONSTRAINT ck_orders_status CHECK (status IN ('pending','paid','shipped')),
    placed_at   DATETIME2     NOT NULL DEFAULT SYSUTCDATETIME(),
    -- total is NOT stored: it is derivable from order_lines
);

CREATE TABLE order_lines (
    order_id    INT           NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    sku         VARCHAR(40)   NOT NULL,
    quantity    INT           NOT NULL CHECK (quantity > 0),
    unit_price  DECIMAL(19,4) NOT NULL,            -- never FLOAT for money
    PRIMARY KEY (order_id, sku)                    -- composite natural key
);

-- Deliberate denormalisation, with the mechanism that keeps it true
ALTER TABLE orders ADD total DECIMAL(19,4) NULL;

Joins, set operators and NULL

Join semantics are reliably tested, usually by asking for the difference between LEFT JOIN ... WHERE b.x = 1 and LEFT JOIN ... AND b.x = 1 — the first silently turns the outer join into an inner join, because a WHERE on the right-hand table filters out the NULL-extended rows the join just produced.

The other reliable trap is NOT IN with a nullable column: if the subquery returns a single NULL the whole predicate is unknown and you get zero rows. NOT EXISTS does not have this problem, which is why it is the safer default.

-- The classic: these two are NOT the same query
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';          -- customers with NO orders are filtered OUT:
                                  -- o.status is NULL for them, NULL = 'paid' is unknown
                                  -- this is an INNER JOIN wearing a disguise

SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid';
                                  -- customers with no paid orders are KEPT, with NULLs

-- "customers with no orders at all" - three ways, one of them broken
SELECT c.* FROM customers c                       -- 1. anti-join (clear + fast)
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

SELECT c.* FROM customers c                       -- 2. NOT EXISTS (clearest, NULL-safe)
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

SELECT c.* FROM customers c                       -- 3. NOT IN - BROKEN if the column
WHERE c.id NOT IN (SELECT customer_id FROM orders);  -- is nullable: one NULL in the
                                                  -- subquery returns zero rows, always

-- Set operators: UNION dedups (and sorts to do it), UNION ALL does not
SELECT sku FROM order_lines
UNION ALL                          -- always prefer ALL unless you need the dedup
SELECT sku FROM returns;

SELECT sku FROM catalogue
EXCEPT                             -- rows in the first not in the second (MINUS in Oracle)
SELECT sku FROM order_lines;

-- NULL semantics, the part people get wrong
SELECT NULL = NULL;                -- NULL, not true
SELECT NULL <> 1;                  -- NULL, not true
WHERE col IS NULL                  -- the only way to test it
SELECT COUNT(*), COUNT(coupon);    -- COUNT(*) counts rows, COUNT(col) skips NULLs
SELECT AVG(score) FROM t;          -- ignores NULLs: the denominator is non-null rows
SELECT COALESCE(coupon, 'none');   -- first non-null

-- CROSS APPLY / LATERAL: a correlated subquery you can join to.
-- "the 3 most recent orders per customer" without a window function:
SELECT c.name, o.id, o.placed_at
FROM customers c

Aggregates, GROUP BY, HAVING and CTEs

The thing to internalise is the logical order of evaluation, because it explains every error message in this area: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. That is why you cannot use a SELECT alias in a WHERE, why HAVING filters groups and WHERE filters rows, and why ORDER BY can use an alias when nothing else can.

CTEs (WITH) name a subquery so a multi-step query reads top to bottom instead of inside out. Recursive CTEs walk hierarchies — org charts, category trees, bills of materials — and are the standard "how would you query a tree" answer.

-- Logical order: FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY
SELECT   c.id,
         c.name,
         COUNT(*)              AS order_count,     -- an alias defined here...
         SUM(o.total)          AS lifetime_value
FROM     customers c
JOIN     orders o ON o.customer_id = c.id
WHERE    o.placed_at >= '2026-01-01'               -- filters ROWS, before grouping
GROUP BY c.id, c.name                              -- every non-aggregate SELECT column
HAVING   COUNT(*) >= 5                             -- filters GROUPS, after
ORDER BY lifetime_value DESC;                      -- ...is usable only here

-- CTEs: name the steps, read top to bottom
WITH monthly AS (
    SELECT customer_id,
           DATEFROMPARTS(YEAR(placed_at), MONTH(placed_at), 1) AS month,
           SUM(total) AS revenue
    FROM   orders
    GROUP BY customer_id, DATEFROMPARTS(YEAR(placed_at), MONTH(placed_at), 1)
),
ranked AS (
    SELECT *, RANK() OVER (PARTITION BY month ORDER BY revenue DESC) AS rk
    FROM   monthly
)
SELECT month, customer_id, revenue
FROM   ranked
WHERE  rk <= 3                                     -- top 3 customers per month
ORDER  BY month, rk;

-- Recursive CTE: walk a hierarchy
WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 0 AS depth, CAST(name AS NVARCHAR(MAX)) AS path
    FROM   employees
    WHERE  manager_id IS NULL                      -- anchor: the roots

    UNION ALL

    SELECT e.id, e.name, e.manager_id, org.depth + 1, org.path + ' > ' + e.name
    FROM   employees e
    JOIN   org ON e.manager_id = org.id            -- recursive member
    WHERE  org.depth < 20                          -- ALWAYS bound it
)
SELECT depth, path FROM org ORDER BY path;

Window functions and running totals

Window functions compute across a set of rows related to the current row without collapsing them — that is the whole idea, and the one-sentence definition worth having ready. GROUP BY gives you one row per group; OVER() gives you every row plus the aggregate.

Know the three ranking functions and how they differ on ties: ROW_NUMBER (1,2,3,4 — arbitrary tiebreak), RANK (1,2,2,4 — gaps), DENSE_RANK (1,2,2,3 — no gaps). Deduplication is the most common real use: number the rows per key and delete everything above 1.

-- The definition in one query: the aggregate without losing the rows
SELECT id, customer_id, total,
       SUM(total)   OVER (PARTITION BY customer_id)             AS customer_lifetime,
       AVG(total)   OVER (PARTITION BY customer_id)             AS customer_avg,
       total - AVG(total) OVER (PARTITION BY customer_id)       AS vs_their_average,
       COUNT(*)     OVER ()                                      AS total_rows
FROM   orders;

-- Ranking: the difference on ties is the question
SELECT customer_id, total,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn,  -- 1,2,3,4
       RANK()       OVER (PARTITION BY customer_id ORDER BY total DESC) AS rk,  -- 1,2,2,4
       DENSE_RANK() OVER (PARTITION BY customer_id ORDER BY total DESC) AS dr,  -- 1,2,2,3
       NTILE(4)     OVER (ORDER BY total DESC)                         AS quartile
FROM   orders;

-- Deduplication: the single most useful window-function recipe
WITH dupes AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at) AS rn
    FROM   customers
)
DELETE FROM customers WHERE id IN (SELECT id FROM dupes WHERE rn > 1);

-- Running total: the frame clause is what makes it "running"
SELECT placed_at, total,
       SUM(total) OVER (ORDER BY placed_at
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
       -- the DEFAULT frame with ORDER BY is RANGE UNBOUNDED PRECEDING, which sums
       -- all PEERS of the current row - different answer when timestamps tie.
       AVG(total) OVER (ORDER BY placed_at
                        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS moving_avg_7
FROM   orders;

-- LAG / LEAD: compare a row to its neighbours without a self-join
SELECT placed_at, total,
       LAG(total)  OVER (PARTITION BY customer_id ORDER BY placed_at) AS previous,
       total - LAG(total) OVER (PARTITION BY customer_id ORDER BY placed_at) AS delta,
       LEAD(placed_at) OVER (PARTITION BY customer_id ORDER BY placed_at) AS next_order,
       DATEDIFF(day, placed_at,
           LEAD(placed_at) OVER (PARTITION BY customer_id ORDER BY placed_at)) AS gap_days
FROM   orders;

-- FIRST_VALUE / LAST_VALUE - LAST_VALUE needs the frame or it returns the current row
SELECT customer_id, placed_at, total,
       FIRST_VALUE(total) OVER (PARTITION BY customer_id ORDER BY placed_at) AS first_order,
       LAST_VALUE(total)  OVER (PARTITION BY customer_id ORDER BY placed_at
                                ROWS BETWEEN UNBOUNDED PRECEDING
                                         AND UNBOUNDED FOLLOWING)           AS last_order
FROM   orders;

Indexes: clustered, non-clustered, covering and composite

An index is a sorted structure (a B-tree) over one or more columns, with a pointer back to the row. The clustered index is the table — the rows are physically stored in its order, so a table has exactly one. A non-clustered index is a separate structure holding the key columns plus a pointer; reading any other column means a key lookup back to the table, which is the single most common reason an index "is not being used".

The rule that answers most index questions is leftmost prefix: an index on (a, b, c) serves predicates on a, on a, b and on a, b, c — but not on b alone. Order the columns equality-first, then range, then the rest as INCLUDE.

-- The clustered index IS the table. Choose it deliberately:
-- narrow, static, ever-increasing. An IDENTITY/sequence key fits; a random GUID
-- does not (it causes page splits and fragmentation on every insert).
CREATE TABLE orders (
    id          INT IDENTITY,
    customer_id INT NOT NULL,
    status      VARCHAR(20) NOT NULL,
    placed_at   DATETIME2 NOT NULL,
    total       DECIMAL(19,4) NOT NULL,
    notes       NVARCHAR(MAX) NULL,
    CONSTRAINT pk_orders PRIMARY KEY CLUSTERED (id)
);

--   serves:     WHERE customer_id = 1
--               WHERE customer_id = 1 AND placed_at >= '2026-01-01'
--               WHERE customer_id = 1 ORDER BY placed_at       (no sort needed)
--   does NOT:   WHERE placed_at >= '2026-01-01'                (leftmost prefix)

-- Covering index: INCLUDE the columns you SELECT so there is no key lookup
CREATE INDEX ix_orders_customer_placed_cov
    ON orders (customer_id, placed_at)
    INCLUDE (status, total);
--   this query is now served entirely from the index:
--   SELECT status, total FROM orders WHERE customer_id = 1 AND placed_at >= '2026-01-01';
--   INCLUDE columns sit only in the leaf, so they cost space but not tree depth,
--   and they cannot be used for seeking or ordering.

-- Filtered index: much smaller, for a query that always carries the same predicate
CREATE INDEX ix_orders_pending ON orders (placed_at)
    WHERE status = 'pending';

-- Unique index: a constraint AND an access path
CREATE UNIQUE INDEX ux_customers_email ON customers (email);

Reading an execution plan

"This query is slow, what do you do?" The answer is always: look at the plan. You do not need to read every operator — you need to find the expensive one and recognise about six shapes.

  • Index Seek — navigated the B-tree to the rows. Good.
  • Index Scan / Table Scan — read everything. Fine on a small or mostly-returned table, a problem when the predicate should have been selective.
  • Key Lookup / RID Lookup — found rows in a non-clustered index, then went back to the table for more columns. Usually fixed by INCLUDE.
  • Sort — often removable by matching the index order to the ORDER BY.
  • Hash Match vs Nested Loops vs Merge Join — large/unsorted, small outer, both sorted respectively.
  • Estimated vs actual rows far apart — stale statistics or a non-SARGable predicate; this is the single most useful thing to look at, because a bad estimate causes every other bad choice.

SARGability and query anti-patterns

SARGable — Search ARGument able — means the predicate can be used to seek into an index. The rule is simple: keep the indexed column bare on one side of the comparison. The moment you wrap it in a function, cast it, or concatenate it, the engine can no longer map your predicate onto the index's sorted order and falls back to reading everything.

-- NOT SARGable                          -- SARGable rewrite
WHERE YEAR(placed_at) = 2026           -- WHERE placed_at >= '2026-01-01'
                                       --   AND placed_at <  '2027-01-01'

WHERE CAST(placed_at AS DATE) = @d     -- WHERE placed_at >= @d
                                       --   AND placed_at <  DATEADD(day, 1, @d)

WHERE UPPER(status) = 'PAID'           -- store it normalised, or use a
                                       -- case-insensitive collation on the column

WHERE total * 1.2 > 100                -- WHERE total > 100 / 1.2

WHERE email LIKE '%@example.com'       -- leading wildcard cannot seek.
                                       -- store a reversed column + index it,
                                       -- or use full-text search

WHERE ISNULL(coupon, '') = ''          -- WHERE coupon IS NULL OR coupon = ''

WHERE varchar_col = N'x'               -- implicit conversion: match the types

WHERE id + 0 = @id                     -- the oldest "force a scan" trick there is

-- SELECT *: forces lookups, breaks covering indexes, and ships columns nobody reads
SELECT * FROM orders WHERE customer_id = 1;          -- bad
SELECT id, total, status FROM orders WHERE customer_id = 1;    -- good

-- Functions on the column in a JOIN are just as bad
JOIN customers c ON UPPER(c.email) = UPPER(o.email)   -- no index usable on either side

-- OR across different columns often defeats a single index. UNION ALL can beat it:
SELECT * FROM orders WHERE customer_id = 1 OR external_ref = 'X';     -- likely a scan
SELECT * FROM orders WHERE customer_id = 1
UNION ALL
SELECT * FROM orders WHERE external_ref = 'X' AND customer_id <> 1;   -- two seeks

ACID in one line each: atomicity (all or nothing), consistency (constraints hold at the boundaries), isolation (concurrent transactions do not see each other's mess), durability (committed means committed). Isolation is the only one with a dial, and the dial is what gets asked.

The three anomalies, concretely: a dirty read sees uncommitted data that may be rolled back; a non-repeatable read reads the same row twice and gets different values; a phantom runs the same range query twice and gets different rows. Locking, blocking and deadlocks

Blocking is normal: one transaction waits for another's lock. Deadlock is a cycle — A holds X and wants Y, B holds Y and wants X — and the engine resolves it by killing one of them (SQL Server error 1205, "chosen as the deadlock victim"). Your job is to make cycles rare and to retry the victim.

The three fixes, in order of how often they are the right answer: access objects in a consistent order everywhere (the cycle cannot form if everyone takes locks in the same sequence); keep transactions short and never do I/O inside one; add the index that turns a scan taking many locks into a seek taking few.

-- A deadlock in two sessions ------------------------------------------------
-- Session A                             -- Session B
BEGIN TRAN;                              BEGIN TRAN;
UPDATE accounts SET bal=bal-10           UPDATE accounts SET bal=bal-10
  WHERE id=1;   -- locks row 1             WHERE id=2;   -- locks row 2
UPDATE accounts SET bal=bal+10           UPDATE accounts SET bal=bal+10
  WHERE id=2;   -- waits for B             WHERE id=1;   -- waits for A  => CYCLE
-- Msg 1205: Transaction was deadlocked on lock resources and has been chosen
--           as the deadlock victim. Rerun the transaction.

-- Fix 1: consistent ordering. Always lock the lower id first - everywhere.
DECLARE @first INT = IIF(@from < @to, @from, @to),
        @second INT = IIF(@from < @to, @to, @from);
UPDATE accounts SET bal = bal + CASE id WHEN @from THEN -10 ELSE 10 END
WHERE  id IN (@first, @second);          -- or two statements in that order

-- Fix 2: shorter transactions. Do the HTTP call BEFORE BEGIN TRAN, not inside.

-- Fix 3: the index. A scan locks every row it reads; a seek locks the one it wants.
CREATE INDEX ix_accounts_customer ON accounts (customer_id);

Paging, keyset pagination and counting at scale

OFFSET 100000 LIMIT 20 makes the database produce and discard 100,000 rows to return 20. Page 1 is instant, page 5,000 is a timeout — and the degradation is linear in the page number, which is why it survives every load test and dies in production.

Keyset (seek) pagination uses the last row you saw as the starting point: WHERE (placed_at, id) < (@lastDate, @lastId) ORDER BY placed_at DESC, id DESC LIMIT 20. Every page costs the same, it rides the index directly, and it is stable when rows are inserted while the user pages. The trade-off is that you cannot jump to an arbitrary page number — which is exactly what infinite scroll and "load more" do not need.

COUNT(*) over a large filtered set has the same problem. Options: do not show a total, cache it, or show an estimate from the statistics.

-- OFFSET: correct, and progressively slower
SELECT id, placed_at, total
FROM   orders
WHERE  customer_id = @cid
ORDER  BY placed_at DESC, id DESC
OFFSET @page * 20 ROWS FETCH NEXT 20 ROWS ONLY;
--   page 1:     ~20 rows read
--   page 5000:  ~100,020 rows read and thrown away
--   and if a row is inserted between page views, rows shift and the user sees
--   a duplicate or misses one

-- KEYSET: constant cost, stable under concurrent inserts
SELECT TOP 20 id, placed_at, total
FROM   orders
WHERE  customer_id = @cid
  AND  (placed_at < @lastPlacedAt
        OR (placed_at = @lastPlacedAt AND id < @lastId))   -- tiebreak on a unique column
ORDER  BY placed_at DESC, id DESC;
--   every page: ~20 rows read

-- PostgreSQL says the same thing far more neatly with a row constructor
SELECT id, placed_at, total FROM orders
WHERE  customer_id = :cid AND (placed_at, id) < (:last_placed_at, :last_id)
ORDER  BY placed_at DESC, id DESC
LIMIT  20;

-- The index that makes keyset paging a pure range scan

Stored procedures, views and functions

Worth having an opinion on, because you will be asked for one. Stored procedures give you a stable interface, server-side plan reuse and permissions at the procedure rather than the table — and cost you version control, testability and deployment stories that are worse than application code. The common modern position: procedures for genuinely set-based bulk work that would otherwise pull rows to the app, application code for everything else.

Views name a query; they do not store anything unless indexed/materialised. The failure mode is nesting them, where a three-level view hierarchy produces a plan nobody can read. Scalar UDFs are the real trap: before SQL Server 2019 they execute once per row and silently serialise the plan.

-- A procedure worth writing: set-based work that would otherwise be a round trip per row
CREATE OR ALTER PROCEDURE dbo.ExpireStaleCarts
    @CutoffUtc DATETIME2,
    @BatchSize INT = 5000
AS
BEGIN
    SET NOCOUNT ON;                      -- do not send rowcount messages per statement
    SET XACT_ABORT ON;                   -- roll back the whole thing on any error

    DECLARE @rows INT = 1;
    WHILE @rows > 0                      -- batched, so locks do not escalate
    BEGIN
        UPDATE TOP (@BatchSize) carts
        SET    status = 'expired', expired_at = SYSUTCDATETIME()
        WHERE  status = 'active' AND updated_at < @CutoffUtc;

        SET @rows = @@ROWCOUNT;
    END
END;

SQL vs NoSQL: choosing the store

The question is never "which is better" — it is "what is your access pattern". Relational gives you joins, constraints, transactions across tables and an optimiser that adapts when you ask a new question. Document and key-value stores give you horizontal scale and a denormalised shape read in one hop, provided you knew the access pattern in advance.

The best answer names the default and then the exceptions: start relational, because it is the only option that does not need you to know the queries up front, and move specific workloads out when they have an access pattern that relational serves badly — a cache, a document read whole and never joined, a time series, a graph traversal, a full-text search.

    row = session.execute(select(Order).where(Order.id == oid)).scalar_one_or_none()
    if row:
        await r.set(f"order:{oid}", json.dumps(row.as_dict()), ex=300)
    return row.as_dict() if row else None

Interview angle

Answer with access patterns, never with "NoSQL scales better". The strongest line: relational is the only store that does not require you to know the queries in advance, so it is the default, and you move a workload out when it has a specific pattern relational serves badly. Two credibility details: in Cosmos DB the partition key is the design decision and a cross-partition query can cost orders of magnitude more RU; and a surprising amount of "we need a document store" is answered by JSONB with a GIN index. Expect CAP to come up — see Key-Value Store for that side of it.

Practice
  • Take a feature you have built and write down which store each of its access patterns wants.
  • Model the same data relationally and as a document, then write the three queries your product actually needs against both.
  • Store a JSON blob in a relational column with a GIN/computed index and query into it.
