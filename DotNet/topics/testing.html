What to test: the pyramid, the trophy and the ice-cream cone

Before any syntax: what deserves a test. The pyramid says many fast unit tests, fewer integration tests, very few end-to-end — because cost and flakiness rise with scope while the chance of catching a bug does not rise as fast. The testing trophy argues the middle layer should be the fattest, because most real bugs live in the wiring between units rather than inside them. The ice-cream cone is the anti-pattern: a handful of unit tests under a mountain of slow, flaky UI tests.

The useful answer in an interview is not which diagram you prefer, but the heuristic: test behaviour at the boundary where it is observable, with the least machinery that gives you confidence. For most .NET services that means a lot of plain unit tests on domain logic and a healthy number of integration tests through WebApplicationFactory against a real database.

Interview angle

"How do you decide what to test?" is a judgement question and a surprising number of answers are "everything, aim for 100% coverage". A better one: test behaviour that has rules in it, at the boundary where the behaviour is observable, and skip tests that only restate the implementation. Two things worth volunteering — a test that recomputes the expected value with the same algorithm passes when both are wrong, and a test asserting a sequence of mock calls breaks on every refactor while catching nothing.

Practice
  • Find a test in your codebase that would break under a pure refactor and rewrite it to assert behaviour.
  • Delete every test that only exercises a property getter and see whether coverage tells you anything useful.
  • Categorise your suite into unit / integration / e2e and work out which shape it actually is.

TDD: red, green, refactor on a real example

Write a failing test, make it pass in the simplest way, then clean up with the test as your safety net. The discipline that makes it work is the first step: run the test and watch it fail, because a test you never saw fail might be asserting nothing.

You do not need to claim you practise TDD on everything — few people do. What is worth being able to say is where it genuinely pays: a pure function with fiddly rules, a bug you are about to fix (write the failing test first, and you have a regression test for free), and any API whose shape you are unsure of, because writing the call site first is the fastest way to find out it is awkward.

Interview angle

"Do you do TDD?" is best answered honestly and specifically rather than yes or no. The version that lands: not for everything, but always for a bug fix — reproduce it as a failing test first, so the fix is verified and the regression test is free — and for pure logic with fiddly rules, where the tests drive out the edge cases faster than reading the requirements does. If you are asked to demonstrate it live, narrate the red step explicitly; people forget to run the failing test and that is the step being assessed.

Practice
  • Take your next bug and write the failing test before touching the code.
  • TDD a small pure function and resist implementing more than the current test demands.
  • Deliberately write a test that cannot fail (assert on a constant) and notice how it looks identical to a real one in the CI output.

xUnit basics and Arrange-Act-Assert

A test class per unit, a [Fact] per behaviour, named so a failure reads like a sentence. Structure every test as Arrange / Act / Assert. xUnit creates a new instance of the class per test, so the constructor is your setup and IDisposable is teardown.

Data-driven tests: [Theory], [InlineData], [MemberData]

One test body, many inputs. [InlineData] for literals, [MemberData]/[ClassData] for objects. Each case shows up as its own test in the runner. pytest's @pytest.mark.parametrize is identical.

Test doubles: dummy, stub, spy, mock, fake — and when to stop

People say "mock" for all five, and being precise is a cheap way to sound experienced. Dummy: passed to satisfy a signature, never used. Stub: returns canned answers, no assertions. Spy: a stub that records what happened so you can check afterwards. Mock: pre-programmed with expectations that fail the test if unmet. Fake: a real working implementation that is unsuitable for production — an in-memory repository, SQLite in place of SQL Server.

The judgement half: mock what you own and what has a side effect you cannot afford — a payment gateway, an email sender, the clock. Do not mock value objects, the language, or types you do not own (mock your own wrapper around them instead). Over-mocking produces a suite that passes while the system is broken, because every collaborator has been replaced by your assumption about it.

// DUMMY: required by the signature, never touched
var sut = new OrderService(repo, logger: NullLogger<OrderService>.Instance);

// STUB: canned answers, no assertions about how it was used

// NSubstitute: catalogue.GetPrice("ABC").Returns(new Money(10m, "USD"));

public class InMemoryOrderRepository : IOrderRepository
{

    public Task<Order?> Get(OrderId id, CancellationToken ct)
        => Task.FromResult(_store.GetValueOrDefault(id));

Interview angle

Using the vocabulary precisely is a quick credibility win: stub returns, spy records, mock asserts, fake implements. The question with a wrong answer is "how much do you mock?" — and the wrong answer is "everything that is not the class under test". Say that you mock what you own and what has an expensive or irreversible side effect, that you wrap third-party types rather than mocking them directly, and that a test with six mocks is telling you the class has six collaborators. Be ready to say what over-mocking costs: a green suite over a broken system, because every collaborator was replaced by your assumption about it.

Practice
  • Take a test with four mocks and rewrite it with real objects and one fake; compare which breaks on a refactor.
  • Write a fake repository that enforces the real contract — duplicate keys, concurrency, the lot.
  • Find a test that mocks a type you do not own and move the seam to a wrapper you do.

Isolating with Moq

Mock the interfaces around the unit so the test runs fast and deterministically. Set up return values, verify calls, and — importantly — do not over-verify; assert outcomes, not implementation details. Python's unittest.mock is built in.

Testing time, async and randomness

Anything that reads the ambient clock, sleeps, or uses a random number is untestable until you inject it. Thread.Sleep(5000) in a test is both slow and flaky; DateTime.UtcNow inside the code under test means you cannot write "what happens the day a subscription expires" without waiting for it.

.NET 8 added TimeProvider, which is now the standard answer: inject it, use FakeTimeProvider in tests, and advance time instantly. It covers GetUtcNow, CreateTimer and Delay, so a PeriodicTimer-driven background service becomes testable without sleeping.

Integration testing with Testcontainers and a real database

The in-memory database provider is the trap here. UseInMemoryDatabase is not a relational database: it ignores constraints, foreign keys, column types, transactions, concurrency tokens and raw SQL, and it translates LINQ differently. Tests pass against it and fail against SQL Server — which is the exact opposite of what an integration test is for. EF's own documentation now recommends against it.

Testcontainers starts the real database in Docker for the test run, so you test against the engine you ship on. Combine it with WebApplicationFactory (already covered below) and you have a test that exercises routing, DI, middleware, EF translation and real SQL — the layer where most bugs actually live.

Resetting state between tests

Once tests share a database they share state, and order-dependence creeps in: the suite passes locally and fails in CI because the runner parallelised differently. Every test must leave the database as it found it, and there are three ways to arrange that.

Respawn deletes the data in dependency order and is the usual choice — fast, keeps the schema, no transaction constraints. A transaction per test, rolled back is faster still but breaks as soon as the code under test manages its own transaction, which an integration test usually does. A fresh container or database per test is bulletproof and far too slow for anything but a handful of tests.

// RESPAWN: delete all data between tests, keep the schema
// dotnet add package Respawn

public class DatabaseFixture : IAsyncLifetime
{
    private Respawner _respawner = null!;
    private DbConnection _connection = null!;

    public async Task InitializeAsync()
    {
        await Container.StartAsync();
        await Migrate();

        _connection = new SqlConnection(ConnectionString);
        await _connection.OpenAsync();

        _respawner = await Respawner.CreateAsync(_connection, new RespawnerOptions
        {
            DbAdapter = DbAdapter.SqlServer,
            TablesToIgnore = ["__EFMigrationsHistory", "Countries"],   // reference data
            SchemasToInclude = ["dbo"],
        });
    }

    public Task ResetAsync() => _respawner.ResetAsync(_connection);
}

Stubbing outbound HTTP

Code that calls another service needs the call controlled: real calls make tests slow, flaky, and dependent on someone else's uptime and data. There are two good seams and one bad habit.

The bad habit is mocking HttpClient — its methods are not virtual in a useful way and you end up testing the mock. The two good seams: a custom DelegatingHandler injected through IHttpClientFactory (fast, in-process, no network, and it also tests your HttpClient configuration), or WireMock.Net, a real HTTP server on localhost (slower, but it exercises serialisation, headers, status codes and timeouts for real — and it can simulate latency and failures).

// --- SEAM 1: a DelegatingHandler. Fast, in-process, no socket. ---

    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        Requests.Add(request);
        return Task.FromResult(respond(request));
    }
}

Snapshot testing with Verify

When the thing under test produces a large object, document or payload, asserting property by property is tedious and misses the properties you forgot. Snapshot testing serialises the result, stores it as a committed file, and fails the test when the output changes — turning review of the diff into the assertion.

It fits generated output: API responses, serialised DTOs, generated SQL, source-generator output, emails, reports. It fits badly where the output is small (a plain assertion is clearer) or genuinely volatile (you end up re-approving noise, and people start approving without reading — which is the failure mode to name).

Coverage, mutation testing and what the numbers mean

Coverage measures which lines executed during the test run. It does not measure whether anything was asserted. A test that calls every method and asserts nothing reports 100% — which is why coverage is useful as a floor and a finder of untested areas, and useless as a target.

Mutation testing is the honest version: it changes your code — flips a > to >=, removes a statement, inverts a condition — reruns the tests, and reports which mutants survived. A surviving mutant is a change to your logic that no test noticed. It is slow, so run it on the domain layer and in nightly CI rather than per commit.

Flaky tests: causes and fixes

A flaky test is worse than no test, because it trains the team to re-run the build instead of reading the failure — and then a real failure gets re-run too. Treat flakiness as a bug with a root cause, not as background noise.

The causes are a short list and nearly always one of: time (sleeps, real clocks, timezone or DST), shared state (test order, a static field, a shared database row), concurrency (a race between the test and a background task), external dependencies (a real network call), non-determinism (unseeded randomness, Guid.NewGuid() in an assertion, dictionary ordering), and resources (ports, files, CI agents slower than your laptop).

Retry attributes are the wrong fix and worth saying so: they hide the signal, and a flaky test retried three times is a 1-in-8 failure you will now see only on the worst day.

// 1. TIME ------------------------------------------------------------------
// flaky: passes on a fast machine, fails on a loaded CI agent
await _sut.StartBackgroundWork();
await Task.Delay(100);
_result.Should().NotBeNull();

// fixed: wait for the condition, with a generous timeout
await WaitUntilAsync(() => _result is not null, TimeSpan.FromSeconds(5));

static async Task WaitUntilAsync(Func<bool> condition, TimeSpan timeout)
{
    using var cts = new CancellationTokenSource(timeout);
    while (!condition())
    {
        cts.Token.ThrowIfCancellationRequested();
        await Task.Delay(10, cts.Token);
    }
}

// flaky: fails at midnight, and for anyone outside your timezone
var expected = DateTime.Today.AddDays(30);
// fixed: inject the clock (see the TimeProvider section)

// flaky: fails on 29 February and when DST shifts

// flaky: a static field carries across tests, and xUnit parallelises collections

NUnit and MSTest: what differs from xUnit

Worth 60 seconds of preparation because you may well join a team using one of the others, and the differences are small but visible. The one that matters conceptually is test class lifetime: xUnit constructs a new instance of the test class for every test, which makes shared mutable state impossible by default; NUnit and MSTest reuse one instance and give you explicit setup/teardown attributes instead.

The other difference worth naming is parallelism: xUnit parallelises across collections by default, which is why shared-fixture tests must be grouped into a collection.

// ---------------- xUnit ----------------
public class CartTests : IDisposable            // ctor = setup, Dispose = teardown

    [InlineData(1, 2, 3)]

//  concept           xUnit                 NUnit              MSTest
//  ---------------   -------------------   ----------------   -------------------
//  test              [Fact]                [Test]             [TestMethod]
//  parameterised     [Theory]+[InlineData] [TestCase]         [DataRow]
//  per-test setup    constructor           [SetUp]            [TestInitialize]
//  per-test teardown IDisposable           [TearDown]         [TestCleanup]
//  class setup       IClassFixture         [OneTimeSetUp]     [ClassInitialize]
//  instance lifetime NEW per test          ONE per fixture    ONE per class
//  skip              [Fact(Skip="...")]    [Ignore("...")]    [Ignore]
//  expected throw    Assert.Throws         Assert.Throws      Assert.ThrowsException
//  parallelism       collections, default  opt-in, [Parallelizable]  opt-in

// view is that a test needing a retry is a broken test, so the framework does
// not make hiding it convenient.

Interview angle

Rarely asked directly, but "we use NUnit here, is that a problem?" is common and the right answer is a confident no plus one substantive difference. The one to give: xUnit constructs a new test-class instance per test so shared mutable state cannot leak, whereas NUnit reuses the fixture instance and relies on [SetUp] to reset it. A good follow-on is xUnit's deliberate omission of [Retry] — the position being that a test needing a retry is a broken test — which signals you have thought about flakiness rather than just the API.

  • Find out what your test framework does about parallelism by default.
  • Write the same parameterised test in all three frameworks.

Tests in CI: parallelism, categories and what gates the build

The suite has to be fast enough that people run it and reliable enough that a red build means something. That is a pipeline design problem as much as a testing one: split by speed, run the fast tests on every push, gate the merge on the right subset, and publish results so a failure is readable without opening logs.

The decision to be able to defend is what blocks a merge. Unit and integration tests, yes. End-to-end against a shared environment, usually not — they are slow and flaky enough that gating on them means the team routinely overrides the gate, which is worse than not having it.

Interview angle

A pipeline question as much as a testing one, and the differentiating part is what gates the merge. Say: build, analyzers, unit and integration tests gate; end-to-end tests and mutation scores run but do not block, because gating on something flaky teaches the team to override gates and you lose the ones that worked. Practical details that land: categorise tests so the fast ones run on every push, give CI agents more generous timeouts than your laptop, and never let a snapshot tool auto-approve in a pipeline.

Practice
  • Split your suite into fast and slow jobs and measure the time to first red.
  • Add a test-results reporter so a CI failure is readable from the PR without opening logs.
  • Write down what currently blocks a merge in your pipeline and whether each gate earns it.
