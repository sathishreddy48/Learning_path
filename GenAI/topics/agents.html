Anatomy of an agent

An agent is a model in a loop with tools, able to act and observe the result. Four components, and it is worth naming them separately because each is a distinct design decision with its own failure mode.

ComponentWhat it isDecisionFails as
ModelThe thing that decides what to do nextWhich model, what temperature, reasoning or notPicks the wrong tool; loops
ToolsWhat it can perceive and doWhich capabilities, and which need approvalMisused tools; unbounded authority
MemoryWhat it knows about this and past interactionsHow much history, summarised or truncated, persisted whereContext overflow; forgotten constraints
Guard-railsWhat it is not allowed to do or sayInput checks, output validation, approval gatesThe failure you only find in production

The useful mental model is the one from module 1's human analogy: perception is the input and the tool results, cognition is the model plus whatever state you re-supply, action is the tools. The loop closes it — perceive, decide, act, observe, repeat.

Start simpler than an agent

This is the point most worth making in an interview, and Anthropic's own guidance leads with it. There is a ladder, and you should climb it only as far as the problem requires:

PatternWhat it isUse when
Single callOne prompt, one responseThe task is one step. Most tasks
ChainFixed sequence of calls, output to inputSteps are known in advance and never vary
RouterClassify, then dispatch to a specialised handlerDistinct input types needing different treatment
WorkflowCode controls the path; the model fills in stepsThe path is knowable; you want it auditable
AgentThe model decides the path, in a loopThe steps genuinely cannot be known in advance

An agent is the most capable and the least predictable option. You give up the ability to know what will happen, to test exhaustively, and to bound cost precisely. Take that trade only when the problem actually has an open-ended shape — and say so, because "I'd use a workflow here, not an agent, because the steps are known" is a judgement answer that stands out against a field that reaches for agents by default.

Interview angle

When handed an agent prompt, spend your first thirty seconds on whether it needs one. If the steps are fixed, say you would build a workflow and keep the model inside individual steps, because it is cheaper, testable and debuggable. If the steps genuinely vary with what is found along the way, say that, and then design the agent. Either way you have shown you know the trade exists.

Memory and context engineering

Models are stateless. Nothing persists between calls. Everything an agent appears to remember is text you re-send on every single request — which makes memory a cost and capacity problem before it is a feature.

The consequence people miss: conversation cost grows quadratically with turns. Turn 20 re-sends the whole of turns 1–19, so total tokens across a conversation is O(n²) even though each turn feels linear.

# Why unbounded history is not an option.
avg_turn = 300            # tokens per message pair
total = sum(avg_turn * i for i in range(1, 51))
print(f"50 turns, naive: {total:,} tokens billed")   # 382,500
print(f"vs if each turn were independent: {avg_turn * 50:,}")  # 15,000
# 25x the cost, and turn ~40 hits a 32k window anyway.

The four strategies

StrategyHowLosesGood for
Full historySend everythingNothing — until it breaksShort conversations only
Sliding windowKeep the last N turnsAnything said early, silentlySupport chat where recency dominates
SummarisationCompress old turns into a running summaryDetail, irrecoverablyLong conversations that need continuity
Retrieval over historyIndex past turns; fetch the relevant onesFlow and orderingVery long-running assistants

Production systems combine them: a verbatim window of recent turns, a running summary of what came before, and pinned facts that must never be dropped.

class Memory:
    """Window + summary + pinned facts -- the combination that actually works."""

    def __init__(self, window_turns=10, pin_budget=500):
        self.turns, self.summary, self.pinned = [], "", []
        self.window, self.pin_budget = window_turns, pin_budget

    def add(self, role, content):
        self.turns.append({"role": role, "content": content})
        if len(self.turns) > self.window * 2:
            old, self.turns = self.turns[:-self.window * 2], self.turns[-self.window * 2:]
            self.summary = summarise(self.summary, old)

    def pin(self, fact):
        """Constraints that must survive compaction: 'user is in the EU',
        'budget is 5000', 'do not contact them by phone'. These are exactly
        what summarisation drops, and dropping them causes the worst bugs."""
        self.pinned.append(fact)

    def messages(self, system):
        head = system
        if self.pinned:
            head += "\n\nEstablished facts:\n" + "\n".join(f"- {f}" for f in self.pinned)
        if self.summary:
            head += f"\n\nEarlier in this conversation:\n{self.summary}"
        return [{"role": "system", "content": head}, *self.turns]

The pinned-facts idea is the one worth raising. Summarisation reliably drops exactly the constraints that matter — a budget, a deadline, a stated preference, a prior refusal — because they are short and unglamorous next to the narrative. An agent that forgets the user already said no is a memorable failure.

Context engineering

The broader discipline: deciding what goes into the window, in what order, within a fixed budget. System prompt, pinned facts, summary, recent turns, retrieved documents, tool schemas — all competing. The design question is not "how do I fit more in" but "what gets dropped first, and does the user find out?" Have an answer; most candidates do not.

Interview angle

"Models are stateless, so memory is something I re-send on every request, and that cost grows quadratically with conversation length" is a precise, slightly surprising sentence that immediately signals you have built one of these. Follow with the window plus summary plus pinned facts structure and the eviction question, and that is a complete answer in forty seconds.

Guard-rails and validation

Guard-rails are the checks around the model — before input reaches it, and before output reaches anything else. They are ordinary code, and the key design point is that they live outside the model, where no amount of text can disable them.

WhereChecksOn failure
InputLength, rate limit, obvious abuse, PII you must not storeReject before spending a token
Tool callIs this tool allowed for this user? Are the arguments in range?Deny, and tell the model why
OutputSchema validity, citation support, leaked secrets, policyRetry, degrade, or escalate
ActionIs this irreversible? Does it need a human?Pause for approval

The most valuable of these is the cheapest: validate output against a schema and retry with the error. Showing the model its own validation failure is remarkably effective, because the failure is usually a format slip rather than a misunderstanding.

from pydantic import ValidationError

def generate_validated(prompt, schema, *, max_retries=2):
    messages = [{"role": "user", "content": prompt}]

    for attempt in range(max_retries + 1):
        raw = call_model(messages, temperature=0)
        try:
            return schema.model_validate_json(raw)
        except ValidationError as e:
            if attempt == max_retries:
                raise OutputInvalid(raw) from e     # degrade LOUDLY, never silently
            # Feed the error back: the model can almost always fix its own
            # schema violation when shown precisely what was wrong.
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user",
                 "content": f"That did not validate:\n{e}\nReturn only valid JSON."},
            ]

Note the bound. Unlimited retries turn a bad day into an expensive bad day; two attempts then a loud failure is a defensible policy. And the failure must be loud — an agent that silently returns a degraded answer when validation fails is worse than one that errors, because nobody finds out.

Validating against the source

For RAG, the highest-value output guard-rail is checking that cited ids were actually retrieved. It is a set membership test, it costs nothing, and it catches a specific and common failure — the model inventing a plausible-looking citation.

Interview angle

Distinguish guard-rails (checks in code) from prompt instructions (requests to the model). An instruction is a preference the model usually honours; a guard-rail is a constraint it cannot violate because it is enforced outside the model. "Do not reveal the system prompt" in a prompt is a request. A regex over the output is a guard-rail. Most candidates conflate them, and the distinction is exactly what makes a design safe rather than hopeful.

When an agent should be a state machine

An open-ended agent loop is the right answer when the path genuinely cannot be known in advance. Often it can, and then a state machine is better in every way that matters: you can enumerate the states, test the transitions, resume after a crash, and tell a user where their request is.

The signals that a prompt is really a state machine: the domain has named stages, some transitions are illegal, something must be durable across a restart, or a human has to approve a step in the middle.

from enum import Enum, auto

class S(Enum):
    RECEIVED = auto(); CLASSIFIED = auto(); INFO_NEEDED = auto()
    RESOLVED = auto(); AWAITING_APPROVAL = auto(); ESCALATED = auto(); CLOSED = auto()

# The model decides WITHIN a state. Code decides WHICH state is next, and
# which transitions exist at all. That is the whole idea.
ALLOWED = {
    S.RECEIVED:          {S.CLASSIFIED},
    S.CLASSIFIED:        {S.INFO_NEEDED, S.RESOLVED, S.AWAITING_APPROVAL, S.ESCALATED},
    S.INFO_NEEDED:       {S.CLASSIFIED, S.ESCALATED},
    S.AWAITING_APPROVAL: {S.RESOLVED, S.ESCALATED},      # cannot self-approve
    S.RESOLVED:          {S.CLOSED},
    S.ESCALATED:         {S.CLOSED},
    S.CLOSED:            set(),
}

def transition(ticket, to):
    if to not in ALLOWED[ticket.state]:
        raise IllegalTransition(f"{ticket.state} -> {to}")
    ticket.state = to
    ticket.save()        # durable: survives a crash, and is auditable

The property worth naming: the model chooses within a state; code owns the transitions. An agent cannot reason its way from AWAITING_APPROVAL to RESOLVED, because that edge does not exist in the table. No prompt can create it. That is a far stronger guarantee than instructing the model not to self-approve.

Open loopState machine
PathModel decidesCode constrains
TestingSample and hopeEnumerate transitions
DurabilityIn-memory conversationPersisted state; resumable
ObservabilityRead the traceQuery the state column
Human stepsAwkwardNatural — a state that waits
FlexibilityHandles the unanticipatedOnly what you modelled
Interview angle

In any agent prompt involving a process with stages — tickets, orders, onboarding, approvals — propose the state machine and say why: "illegal transitions become impossible rather than discouraged, the state is durable so a crash does not lose the request, and an approval step is just a state that waits." It is the more senior answer, and it is the one that makes the human-in-the-loop requirement fall out naturally instead of being bolted on.

Multi-agent: delegation, hand-off, and when not to

Multi-agent systems are the most over-applied pattern in this field. They solve real problems; they also multiply cost, latency and failure modes, and the honest default is a single agent with good tools.

The two patterns

Delegation (sub-agent)Hand-off
ControlCaller keeps it; sub-agent returns a resultTransferred; the new agent owns the conversation
Looks likeA function call that happens to be an agentA transfer to a different department
ContextSub-agent gets only what it needsUsually the whole conversation
Use forA bounded subtask: research this, summarise thatA genuinely different specialisation and toolset

Delegation is the more useful of the two, and the reason is context isolation. A sub-agent that reads twenty documents and returns three sentences has kept nineteen documents' worth of tokens out of the parent's window. That is a real architectural benefit and the strongest argument for the pattern.

What it costs

  • Every hand-off loses information. The receiving agent gets a summary or a transcript, never the full reasoning. Errors compound across hops.
  • Cost multiplies. Each agent has its own system prompt, tool schemas and history. Three agents is far more than three times one agent's tokens.
  • Debugging gets much harder. A wrong answer could originate in any agent or in any hand-off between them.
  • Latency is additive, and usually serial.

When it genuinely helps: when subtasks are parallel and independent — research five suppliers at once, where the wall-clock win is real; when context isolation is the point; when specialisations need genuinely different tools and system prompts; and when a separation is a security boundary, which is the strongest case of all.

# The strongest reason for two agents: a privilege boundary.
#
# READER sees untrusted content and holds NO dangerous tools. Whatever a
# malicious document tells it to do, it cannot do.
reader = Agent(tools=[fetch_page, search], output_type=ExtractedFacts)

# ACTOR holds the dangerous tools and never sees raw untrusted text --
# only the validated, structured output of the reader.
actor  = Agent(tools=[send_email, create_ticket], requires_approval=["send_email"])

facts  = reader.run(f"Extract the customer's request from: {untrusted_email}")
result = actor.run(f"Handle this request: {facts.model_dump_json()}")

# A prompt injection in the email can corrupt `facts`. It cannot reach
# send_email, because the agent holding that tool never reads the email.
# That is an architectural guarantee, not a prompting one.
Interview angle

Resist multi-agent as a first answer. Say: "I'd start with one agent and good tools; I would split it only for parallelism, context isolation, or a privilege boundary." Then, if the prompt involves untrusted input and dangerous tools, propose the split above as a security measure. That ordering — default to simple, split for a named reason — is the judgement being graded, and the privilege-boundary case is the one that makes multi-agent clearly correct rather than fashionable.

MCP: tools as a protocol

Function calling is how one application describes its tools to a model. MCP — the Model Context Protocol — is a standard for exposing tools and data so that any client can use them. The distinction is worth being precise about, because candidates routinely conflate the two.

The problem it solves is combinatorial. Without a protocol, every application that wants to talk to every data source needs its own integration: M clients × N sources. With one, each source implements a server once and each client speaks the protocol once — M + N. It is the same argument as LSP made for editors and language tooling, and saying that is a good shorthand.

MCP exposesWhat it isAnalogy
ToolsFunctions the model can invokePOST — has effects
ResourcesData the client can readGET — no effects
PromptsReusable templates the server offersA saved query

Transports are stdio — the server is a subprocess, which is how local integrations work and means no network exposure — and HTTP with Server-Sent Events for remote servers, which is where authentication becomes a real concern.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("orders")

@mcp.tool()
def get_order(order_id: int) -> dict:
    """Look up an order by id. Returns status, total_cents and placed_at."""
    return db.fetch_order(order_id)

@mcp.resource("orders://recent")
def recent() -> str:
    """The 50 most recent orders, as JSON."""     # read-only: a RESOURCE, not a tool
    return json.dumps(db.recent(50))

if __name__ == "__main__":
    mcp.run()        # stdio by default -- a subprocess, no port, no network

The part that matters in an interview

MCP moves the trust boundary. An MCP server is third-party code with access to your data, invoked by a model. Three consequences worth naming: the server defines its own tool descriptions, so a malicious or compromised server can describe a tool misleadingly to induce the model to call it; a remote server needs real authentication and per-user authorisation, not a shared token; and tool results are untrusted input to your agent, exactly like retrieved documents.

Interview angle

Give the one-line distinction first — "function calling is the wire format between an app and a model; MCP is a protocol so tools can be written once and used by any client" — and then the M×N to M+N argument. If the conversation goes further, the security framing is where the credit is: the tool descriptions come from the server and go into your prompt, so installing an MCP server is closer to installing a dependency than to configuring an API.

Human-in-the-loop and approvals

Every agent that can do something irreversible needs a point where a human says yes. The design question is where that point is, what it shows, and what happens while it waits.

Where the gate goes

Between the tool call and its execution — in your code, at step 3 of the wire-format loop. Not in the prompt. A gate the model can be talked out of is not a gate, and that is precisely the distinction prompt injection exploits.

NEEDS_APPROVAL = {"send_email", "issue_refund", "delete_record", "deploy"}

def execute(call, ctx):
    if call.name not in NEEDS_APPROVAL:
        return dispatch(call)

    # Persist and SUSPEND. A human approval is minutes to days -- this
    # cannot be an in-memory await.
    req = ApprovalRequest.create(
        run_id=ctx.run_id,
        tool=call.name,
        arguments=call.arguments,          # the EXACT payload, shown verbatim
        preview=render_preview(call),      # "To: a@b.com / Subject: ... / Body: ..."
        requested_by=ctx.user_id,
        expires_at=now() + timedelta(hours=24),
    )
    raise Suspended(req.id)

# On approval, the run RESUMES from the persisted state: the tool executes
# and its result is appended as if it had returned immediately. The model
# never knows it waited.

Three properties that make this work and that are worth stating:

  • Show the exact payload. "The agent wants to send an email" is unreviewable. Recipient, subject and body is a decision someone can actually make. An approval a human cannot evaluate is a rubber stamp, and a rubber stamp is worse than no gate because it creates the appearance of oversight.
  • Suspend durably. Approval takes minutes to days. The run state must survive a restart, so it is a persisted record, not a blocked coroutine — which is another reason the state-machine shape fits.
  • Expire pending requests. An approval sitting for a week should lapse rather than fire when someone finally clicks it.

Calibrating it

Too many approvals and people click through without reading, which is worse than none. Reserve the gate for the genuinely irreversible, and use the other levers for the rest: scope limits (refunds under £50 auto-approve), rate limits, dry-run modes, and after-the-fact review of a sample. The aim is that every approval a human sees is one worth their attention.

Interview angle

Two sentences that land together. "The gate is in code, between the model's request and execution, so no prompt can open it." And "it shows the exact payload, because an approval the human cannot evaluate is a rubber stamp." Add that the run suspends durably because approval is slow, and you have covered the mechanism, the security property and the operational reality — which is more than most candidates manage on this topic.

Practice
  • List the tools of an agent you have built and mark which are irreversible. Then check: is the gate in code, or in the prompt?
  • Write the approval preview for your most dangerous tool. If you cannot render it in three lines a human can judge, the tool is too coarse.
