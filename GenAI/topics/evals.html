Why evals, and what they replace

In ordinary software a change is either correct or it is not, and a test asserts the difference. With a model in the loop, "correct" is a distribution and every change — a new prompt, a new chunk size, a model upgrade you did not choose — moves it a little in several directions at once. Some outputs get better, some get worse, and the aggregate is invisible without measurement.

Evals are what replace the unit test. That framing is the one to lead with, because it tells the interviewer you understand what is different about this kind of system rather than that you have heard of a tool.

Three questions you cannot answer without them, all of which come up in real work:

  • "Did that prompt change help?" You tried five examples and they looked better. Five examples cannot distinguish a 5% improvement from a 5% regression.
  • "Can we switch to the cheaper model?" Possibly — it depends entirely on how much quality you lose, which is a number you either have or do not.
  • "The provider updated the model. Are we still fine?" This one happens to you rather than being chosen, which is why the gate needs to be automatic.

The cost argument is worth making too. Building a golden set is a day or two of unglamorous work, and teams skip it because there is always something more urgent. The result is that every subsequent change is a guess, and the team's velocity degrades as the system grows — they become afraid to touch the prompt. A day spent on evals early is the highest-return day in an LLM project.

Interview angle

"How do you know it works?" is the most reliably under-prepared question in this round. Have a concrete answer, with numbers: "a golden set of about two hundred cases drawn from real queries, retrieval measured separately from generation, deterministic checks where I can have them and an LLM judge where I cannot, run in CI on every prompt change with a gate on regression." Say that unprompted while describing the architecture and the follow-up never comes.

Golden datasets worth having

A golden set is a collection of inputs with known-good outputs, or at least known-good properties of outputs. It is the asset the whole eval story rests on, and the common mistake is to generate it synthetically because that is faster.

Where the cases come from, best first

SourceQualityNote
Real user queries from logsBestThe actual distribution, including the ugly ones. Requires you to have logged them
Production failuresBestEvery bug becomes a permanent regression test. This is how the set should grow
Domain experts writing questionsGoodCovers what matters; expensive; skews toward the interesting
LLM-generated from your documentsAcceptable to bootstrapBiased toward what is easy to answer; verify a sample by hand

The trap with the last row is subtle: a model asked to generate questions from a document produces questions that document answers cleanly. Your eval set then systematically omits the queries that actually fail — ambiguous ones, multi-hop ones, ones whose answer is spread across documents, and ones with no answer at all. Measured against it, your system looks excellent.

What a case needs

from dataclasses import dataclass, field

@dataclass
class Case:
    question:        str
    expected:        str | None            # None when there is no right answer
    must_contain:    list[str] = field(default_factory=list)   # cheap exact checks
    must_not_contain: list[str] = field(default_factory=list)
    gold_doc_ids:    list[str] = field(default_factory=list)   # for RETRIEVAL eval
    category:        str = "general"       # slice results by this
    should_refuse:   bool = False          # the negative cases

GOLDEN = [
    Case("What is the refund window for Acme Pro?",
         expected="30 days from delivery",
         must_contain=["30 days"],
         gold_doc_ids=["policy-returns#acme-pro"],
         category="policy"),

    # Multi-hop: the answer needs two documents. These are where systems fail.
    Case("Is the Acme Pro refund window longer than Acme Lite's?",
         expected="Yes -- 30 days versus 14",
         gold_doc_ids=["policy-returns#acme-pro", "policy-returns#acme-lite"],
         category="multi-hop"),

    # NEGATIVE case: the corpus does not contain this. The system must decline.
    Case("What is the refund window for Acme Enterprise?",
         expected=None, should_refuse=True,
         must_not_contain=["30 days", "14 days"],
         category="unanswerable"),
]

The should_refuse cases are the ones teams forget, and they are the most informative. A system scoring 95% on answerable questions while confidently inventing answers to the other 5% is not a 95% system. Roughly 10–20% of a golden set should be unanswerable, and the refusal rate on that slice is one of the most useful numbers you can track.

On size: 50 cases is enough to catch gross regressions, 200 is a reasonable working target, and beyond about 500 you are usually better off spending the effort on coverage of distinct categories than on more cases of the same kind. Slicing by category is what makes the number actionable — "overall 84%" tells you nothing, "multi-hop 61%, everything else 92%" tells you what to fix.

Interview angle

Mention that every production bug becomes a permanent case. It is how the set stays aligned with reality instead of ossifying, it is free, and it is exactly what an engineer who has operated one of these systems does. Pair it with the negative-case point and you have said two things most candidates do not.

Metrics: deterministic, then semantic

Reach for the cheapest metric that can detect the failure you care about. The ladder, in order — and the discipline is to exhaust each rung before climbing:

RungMetricCostUse when
1Exact / schema validityFreeStructured output, classification, extraction. Parses or does not
2Substring / regex / numericFreeThe answer must contain a figure, date or id
3Retrieval metricsFreeRecall@k, MRR, nDCG — they need no model at all
4Embedding similarityCheapRough semantic closeness; noisy, use as a signal not a gate
5LLM-as-judgeExpensiveOpen-ended quality, faithfulness, tone — nothing cheaper works
6Human reviewVery expensiveCalibrating the judge; high-stakes release decisions

People jump to rung 5 because it is the interesting one, and they end up with an eval suite that is slow, costs money per run, and is itself non-deterministic. A good suite is mostly rungs 1–3 with judges used sparingly where they earn it.

import numpy as np

def recall_at_k(retrieved_ids, gold_ids, k=10):
    """Did we get the supporting documents into the top k? The single most
    important RAG number: it is the ceiling on everything downstream."""
    if not gold_ids:
        return None
    return len(set(retrieved_ids[:k]) & set(gold_ids)) / len(set(gold_ids))

def mrr(retrieved_ids, gold_ids):
    """Reciprocal rank of the FIRST relevant hit. Sensitive to ordering,
    which recall is not -- use both."""
    for i, doc in enumerate(retrieved_ids, start=1):
        if doc in gold_ids:
            return 1.0 / i
    return 0.0

def ndcg_at_k(retrieved_ids, relevance: dict, k=10):
    """Handles GRADED relevance -- some documents are more relevant than
    others -- and discounts by position."""
    gains = [relevance.get(d, 0) for d in retrieved_ids[:k]]
    dcg  = sum(g / np.log2(i + 2) for i, g in enumerate(gains))
    best = sorted(relevance.values(), reverse=True)[:k]
    idcg = sum(g / np.log2(i + 2) for i, g in enumerate(best))
    return dcg / idcg if idcg else 0.0

Recall@k is the number to quote in an interview if you quote only one, because it bounds everything else: if the supporting document is not in the context, no model and no prompt can produce a grounded answer. It also needs no LLM to compute, so it is free to run on every commit.

Interview angle

Say the ladder out loud and emphasise the discipline: "I'd use deterministic checks wherever the task permits one, and reserve a judge for the genuinely open-ended parts, because a judge is slow, costs money per run and is itself non-deterministic." That is the opposite of the instinct and it reads as someone who has maintained a suite rather than written one.

LLM-as-judge: when it works, how it lies

For open-ended output there is often no deterministic check — "is this summary faithful to the source?" has no regex. So you use another model as the grader. It works, it is standard, and it lies in specific, known ways that you should be able to name.

How it lies

BiasWhat happensMitigation
PositionIn A/B comparison it favours whichever answer came firstRun both orders and average, or discard disagreements
VerbosityLonger answers score higher, independent of qualityScore against explicit criteria, not overall "quality"; control for length
Self-preferenceA model rates its own family's output higherJudge with a different family than the generator
Scale compressionEverything gets a 7 or 8 out of 10Use a binary or 3-point rubric, not 1–10
Shared blind spotsIt confidently misses errors the generator also missesCalibrate against human labels; never fully trust the number

Writing a judge that works

The single biggest improvement is to ask a narrow, factual question rather than a quality rating. "Rate this answer 1–10" produces noise. "Is every claim in this answer supported by the context? Answer yes or no, then list any unsupported claim" produces something you can act on and verify.

FAITHFULNESS = """You are checking whether an answer is grounded in its source.

CONTEXT:
{context}

ANSWER:
{answer}

List every factual claim in the ANSWER. For each, say whether the CONTEXT
supports it. Then give a verdict.

A claim is SUPPORTED only if the context states it or directly entails it.
Plausible, true-sounding, or generally-known is NOT supported.

Respond as JSON:
{{"claims": [{{"claim": "...", "supported": true/false}}],
  "verdict": "grounded" | "partially_grounded" | "unsupported"}}"""

# Why this works better than a 1-10 rating:
#   - narrow and factual, so there is a right answer
#   - claim-by-claim, so the output is actionable, not just a score
#   - the definition of "supported" is stated, closing the obvious loophole
#   - structured output, so it parses and can be aggregated
#   - temperature=0, always -- you cannot measure through sampling noise


def validate_judge(judge, human_labelled_cases):
    """Never ship a judge you have not checked against humans.

    Label 50 cases by hand, run the judge, and report agreement. Below
    ~80% the judge is measuring something other than what you think, and
    tuning your system against it will make the system worse.
    """
    agree = sum(judge(c) == c.human_label for c in human_labelled_cases)
    return agree / len(human_labelled_cases)
Validate the judge before you trust it

An unvalidated judge is a measurement instrument with unknown error. Hand-label fifty cases, measure agreement, and quote that agreement number whenever you quote the judge's scores. If a team optimises against a judge that disagrees with humans a third of the time, they will reliably make the product worse while watching the metric improve — and that is a genuinely common outcome.

Interview angle

Naming two or three specific judge biases — position, verbosity, self-preference — and then saying "so I'd validate it against human labels on about fifty cases and report the agreement" is one of the strongest few sentences available in this round. It shows you treat your own measurement as something requiring evidence, which is the distinction between measuring and performing measurement.

Evaluating retrieval separately from generation

The central discipline: evaluate retrieval and generation separately. An end-to-end score tells you the system is 72% correct and nothing about what to fix. Separated, you learn that retrieval recall is 68% and that generation given correct context is 96% — which says unambiguously that the work is in retrieval and that tuning the prompt would be a waste of a week.

StageQuestionMetricNeeds an LLM?
RetrievalDid the supporting documents reach the context?Recall@k, MRR, nDCGNo
GenerationGiven correct context, is the answer right and grounded?Faithfulness, correctnessUsually
End to endIs the user's answer right?Correctness, refusal rateUsually

The generation row has a trick in it worth knowing: evaluate generation with oracle context — hand the model the known-correct documents rather than whatever retrieval produced. That isolates the generator completely, so its score cannot be dragged down by a retrieval problem. The gap between oracle-context accuracy and end-to-end accuracy is exactly your retrieval loss.

def evaluate(cases):
    r = {"recall": [], "mrr": [], "oracle_ok": [], "e2e_ok": [],
         "faithful": [], "refused_when_should": []}

    for c in cases:
        hits = retrieve(c.question)
        ids  = [h.id for h in hits]

        if c.gold_doc_ids:                                  # RETRIEVAL
            r["recall"].append(recall_at_k(ids, c.gold_doc_ids, k=10))
            r["mrr"].append(mrr(ids, c.gold_doc_ids))

            # GENERATION in isolation: hand it the right context
            oracle = generate(c.question, context=fetch(c.gold_doc_ids))
            r["oracle_ok"].append(correct(oracle, c.expected))

        answer = generate(c.question, context=hits)         # END TO END
        if c.should_refuse:
            r["refused_when_should"].append(is_refusal(answer))
        else:
            r["e2e_ok"].append(correct(answer, c.expected))
            r["faithful"].append(judge_faithfulness(answer, hits) == "grounded")

    return {k: sum(v) / len(v) for k, v in r.items() if v}

# A result that tells you what to do:
#   recall 0.68 | oracle_ok 0.96 | e2e_ok 0.71
#
# Generation is nearly perfect when given the right context. Every point of
# end-to-end loss is retrieval. Do not touch the prompt -- fix chunking,
# add hybrid search, raise k.
Interview angle

Quote a decomposition like the one in that comment. "If recall is 68% and oracle accuracy is 96%, I know the problem is retrieval and I will not waste a week on prompts" is a complete, concrete answer to "how would you improve this system?" and it demonstrates the diagnostic habit the round is actually testing. It also sets up the retrieval fixes — hybrid search, chunking, reranking — as justified rather than arbitrary.

Evals in CI, and regression gates

An eval suite that is run by hand when someone remembers is a document, not a gate. The value comes from it running automatically on every change that could affect quality — prompts, retrieval parameters, model versions, chunking, tool definitions.

What to gate on

Not absolute scores, which fluctuate. Regressions against the committed baseline, with a tolerance that accounts for the suite's own noise:

import json, sys

TOLERANCE = {          # how much a metric may drop before CI fails
    "recall":    0.02,
    "e2e_ok":    0.03,
    "faithful":  0.02,
    "refused_when_should": 0.05,
}

def gate(current, baseline):
    failures = []
    for metric, allowed in TOLERANCE.items():
        drop = baseline[metric] - current[metric]
        if drop > allowed:
            failures.append(
                f"{metric}: {baseline[metric]:.3f} -> {current[metric]:.3f} "
                f"(-{drop:.3f}, allowed {allowed})")
    return failures

results  = evaluate(GOLDEN)
baseline = json.load(open("evals/baseline.json"))

if failures := gate(results, baseline):
    print("EVAL REGRESSION\n" + "\n".join(failures)); sys.exit(1)

print("ok " + "  ".join(f"{k}={v:.3f}" for k, v in results.items()))
# Baseline is a COMMITTED file, updated deliberately in a PR when an
# improvement is accepted. That makes every quality change visible in
# review history -- which is most of the point.

Two practical notes. Run the deterministic rungs (schema validity, substring checks, retrieval metrics) on every commit — they are free and fast. Run the judge-based ones on pull requests and nightly, because they cost money and take minutes. And set temperature=0 everywhere in the suite: you cannot detect a 3% regression through sampling noise.

The part that is not CI

Offline evals measure what you thought to ask. Production has a different distribution, and the loop that closes the gap runs the other way: log real queries and outputs, sample them for review, and feed every failure back into the golden set as a permanent case. A suite that only grows when someone writes new test questions drifts away from reality; one fed by production failures tracks it.

Interview angle

Finish an eval answer with the loop, not the suite: "deterministic checks on every commit, judges on PRs, a gate on regression against a committed baseline, and every production failure becomes a new case." That describes a system that improves over time rather than a test run, and it is the answer of someone who has maintained one.

Practice
  • Write the tolerance table for a system you have built. Deciding how much regression is acceptable forces you to decide what the system is actually for.
  • Take your last three production bugs and write them as cases. If you cannot, you are not logging enough to build evals from.
