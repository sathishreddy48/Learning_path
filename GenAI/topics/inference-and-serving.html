The constraint: bandwidth, not compute

Almost everything about LLM serving follows from one fact, and it is the fact most candidates do not know:

Generating a token requires reading every weight in the model out of memory, and doing almost no arithmetic with each one. Generation is therefore memory-bandwidth-bound, not compute-bound. The GPU's arithmetic units sit idle waiting for weights to arrive.

# Why decoding is bandwidth-bound -- the arithmetic intensity argument.
params        = 7e9
bytes_per_w   = 2                     # fp16
model_bytes   = params * bytes_per_w  # 14 GB read PER TOKEN

a100_bandwidth = 2.0e12               # 2 TB/s
a100_flops     = 3.12e14              # 312 TFLOP/s (fp16 tensor cores)

# One token: ~2 FLOPs per parameter (a multiply and an add).
flops_per_token = 2 * params                 # 1.4e10

time_memory  = model_bytes / a100_bandwidth  # 7.0 ms  <- the real cost
time_compute = flops_per_token / a100_flops  # 0.045 ms

print(f"memory : {time_memory*1000:.2f} ms")
print(f"compute: {time_compute*1000:.3f} ms")
print(f"=> {time_memory/time_compute:.0f}x bound by MEMORY")
print(f"theoretical ceiling: {1/time_memory:.0f} tokens/s single stream")
# ~156x bound by memory. The compute units are idle ~99% of the time.

Prefill versus decode

The other half of the picture, and the distinction that makes serving metrics make sense:

Prefill (prompt)Decode (generation)
OperationMatrix × matrix over all prompt tokens at onceMatrix × vector, one token at a time
Bound byComputeMemory bandwidth
Parallel?Yes — the whole prompt in one passNo — inherently serial
MetricTime to first token (TTFT)Inter-token latency, tokens/second
Scales withPrompt lengthOutput length

Once you have this distinction, the rest of the page follows. Quantization helps because it reduces bytes read. Batching helps enormously because the weights are read once and amortised across the batch — which is why throughput can rise 10× with barely any increase in per-token latency. The KV cache exists because without it decode would redo prefill every step. And MoE works because reading only the active experts is less memory traffic.

Interview angle

Lead any serving question with this: "generation is memory-bandwidth-bound, not compute-bound — you read the whole model per token and do about two FLOPs per weight, so the arithmetic units are idle." Then derive a number: 14 GB at 2 TB/s is 7 ms, so about 140 tokens per second as a single-stream ceiling for a 7B at fp16. Deriving a ballpark figure from first principles is one of the strongest things you can do in this round, and it makes every subsequent answer — quantization, batching, MoE — follow naturally.

Quantization: INT8, INT4, k-quants

Store weights at lower precision. It is usually introduced as a way to make models fit, and the more interesting half is that it also makes generation faster — because generation is bandwidth-bound and fewer bytes means less to read.

INT4 / Q4_K_M~0.5~4 GBSmall but measurable loss; the usual sweet spot

How it works, and why blocks matter

import numpy as np

def quantize_block(w, bits=4):
    """Affine quantization of ONE block, with its own scale and zero point."""
    qmax = 2 ** bits - 1
    lo, hi = w.min(), w.max()
    scale = (hi - lo) / qmax
    zero  = lo
    q = np.clip(np.round((w - zero) / scale), 0, qmax).astype(np.uint8)
    return q, scale, zero

def dequantize(q, scale, zero):
    return q.astype(np.float32) * scale + zero

# WHY PER-BLOCK rather than per-tensor: one outlier ruins everything.
w = np.random.randn(256).astype(np.float32)
w[0] = 40.0                                   # a single large weight

q, s, z = quantize_block(w)                   # whole tensor, one scale
err_tensor = np.abs(dequantize(q, s, z) - w).mean()

# Same data, blocks of 32 -- the outlier only damages ITS block.
errs = []
for i in range(0, 256, 32):
    qb, sb, zb = quantize_block(w[i:i+32])
    errs.append(np.abs(dequantize(qb, sb, zb) - w[i:i+32]).mean())

print(f"per-tensor: {err_tensor:.4f}")
print(f"per-block : {np.mean(errs):.4f}")     # ~an order of magnitude better

That outlier experiment is the heart of it. A single large weight stretches the scale so that every other weight in the tensor is crushed into a few levels. Quantizing in blocks of 32 or 64 with a scale each confines the damage — and it is why real formats always store scales alongside the weights, and why the scales themselves become worth compressing (see QLoRA's double quantization).

k-quants

The Q4_K_M naming in llama.cpp refers to k-quants, which add two refinements worth knowing: super-blocks (blocks are grouped, and the block scales are themselves quantized against a super-block scale), and mixed precision by importance — the _M suffix means attention and some FFN tensors are kept at higher precision than the rest, because they are more sensitive. So the effective bits-per-weight is not a round number.

MethodNeeds calibration data?Note
RTN (round to nearest)NoSimplest; what the code above does
GPTQYesQuantizes layer by layer, compensating error using second-order information
AWQYesProtects the ~1% of weights that matter most, identified by activation magnitude
k-quantsOptional (imatrix)The llama.cpp family; super-blocks plus mixed precision
Interview angle

Two points, in this order. "Quantization is not only a size win — generation is bandwidth-bound, so halving the bytes roughly halves the time to read the weights." And "it is always done per block, because a single outlier weight would otherwise destroy the resolution for the whole tensor." The second shows you understand the mechanism rather than the menu of options.

GGUF and llama.cpp

GGUF is a single-file format holding quantized weights plus everything needed to run them — architecture, hyperparameters, the tokenizer, the chat template, and the quantization metadata. It is the reason running a model locally is one command rather than an afternoon of matching config files to checkpoints.

It succeeded GGML (the earlier format from the same project) and fixed its main weakness: GGML had no extensible metadata, so every architecture change broke compatibility. GGUF stores typed key-value metadata, so new fields do not break old files.

GGUF containsWhy it matters
Quantized tensors + per-block scalesThe weights, ready to use
Architecture and hyperparametersThe loader configures itself; no separate config
The tokenizer, embeddedNo separate vocab file to mismatch
The chat templatePrompts get formatted the way the model was trained — a common source of silent quality loss
Typed metadataForward compatible

The chat-template row is worth dwelling on. Every instruction-tuned model was trained with a specific format of special tokens around turns. Get it wrong and the model still answers — just noticeably worse, with no error anywhere. Shipping the template inside the weights file removes a whole class of silent failures.

# llama.cpp -- the reference GGUF runtime. Runs on CPU, CUDA, Metal, ROCm.
#
#   llama-cli -m model.Q4_K_M.gguf -p "Explain the KV cache."
#   llama-server -m model.Q4_K_M.gguf --n-gpu-layers 35 --ctx-size 8192
#
# n_gpu_layers is the knob that matters on a machine where the model does
# not fit in VRAM: offload the first N transformer layers to the GPU and
# run the rest on CPU. Because decoding is bandwidth-bound and CPU RAM
# bandwidth is ~10x lower than VRAM, the fraction offloaded dominates
# throughput -- going from 20 to 35 of 32 layers can double tokens/sec.

from llama_cpp import Llama

llm = Llama(model_path="model.Q4_K_M.gguf",
            n_ctx=8192,
            n_gpu_layers=-1)       # -1 = offload everything that fits

out = llm.create_chat_completion(
    messages=[{"role": "user", "content": "Explain the KV cache in two sentences."}],
    temperature=0,
)
print(out["choices"][0]["message"]["content"])

llama.cpp also exposes an OpenAI-compatible HTTP server, which is why local models drop into existing code with a base-URL change. That compatibility — rather than any property of the format — is most of why the local ecosystem consolidated on it. Ollama wraps the same engine with model management on top.

Interview angle

If local deployment comes up: GGUF is a single self-describing file containing quantized weights, tokenizer and chat template, run by llama.cpp across CPU, CUDA and Metal, with an OpenAI-compatible server so client code does not change. Mention n_gpu_layers and why it dominates throughput — it connects straight back to the bandwidth argument and shows the reasoning is joined up.

The KV cache

Attention at position t needs the keys and values of every previous token. Those do not change as generation proceeds — token 5's key is the same whether you are generating token 6 or token 600. So cache them.

Without a cache, generating token n reprocesses all n−1 previous tokens: generating a 1,000-token response would be a thousand prefills, and total work would be O(n²) in the output length. With a cache, each step processes exactly one new token and reads the cache. It is the difference between unusable and real-time, and it is not an optimisation you can skip.

def generate_cached(model, prompt_ids, max_new=100):
    # PREFILL: process the whole prompt once, populate the cache.
    out = model(prompt_ids, use_cache=True)
    cache = out.past_key_values                   # K,V for every prompt token
    nxt = out.logits[:, -1].argmax(-1, keepdim=True)
    generated = [nxt]

    # DECODE: feed ONE token per step. The cache supplies the rest.
    for _ in range(max_new - 1):
        out = model(nxt, past_key_values=cache, use_cache=True)
        cache = out.past_key_values               # grows by one position
        nxt = out.logits[:, -1].argmax(-1, keepdim=True)
        generated.append(nxt)
        if nxt.item() == EOS:
            break
    return torch.cat(generated, dim=1)

# The win: each step is O(1) in the prefix instead of O(n).
# The cost: MEMORY, and it is larger than people expect.

What it costs

def kv_cache_bytes(layers, kv_heads, head_dim, seq_len, batch, dtype_bytes=2):
    #        2 = one K and one V
    return 2 * layers * kv_heads * head_dim * seq_len * batch * dtype_bytes

# Llama-3-8B: 32 layers, 32 heads, head_dim 128 -- WITHOUT grouped-query
print(kv_cache_bytes(32, 32, 128, 8192, 1) / 1e9, "GB")     # 4.3 GB for ONE
print(kv_cache_bytes(32, 32, 128, 8192, 32) / 1e9, "GB")    # 137 GB for 32!

# WITH grouped-query attention (8 KV heads instead of 32):
print(kv_cache_bytes(32, 8, 128, 8192, 32) / 1e9, "GB")     # 34 GB -- 4x less

Those numbers explain a lot. At long context and realistic batch sizes the KV cache can exceed the model weights, and because it grows with every token it is also the thing that decides your maximum batch size — which, since throughput comes from batching, means the KV cache ultimately caps your throughput.

Hence the mitigations, all of which are worth naming:

  • Grouped-query attention (GQA) — several query heads share one K/V head. Llama 3 uses 8 KV heads for 32 query heads, cutting the cache 4× for a small quality cost. This is now standard, and it is why multi-head attention is no longer symmetric in modern models.
  • Multi-query attention (MQA) — the extreme: one K/V head for all queries.
  • PagedAttention — vLLM's contribution: store the cache in fixed-size pages like virtual memory instead of one contiguous block per sequence. Removes the fragmentation and over-allocation that came from reserving max-length buffers, and raised achievable batch sizes several-fold.
  • KV cache quantization — store it at 8 or 4 bits.
Interview angle

"What is the KV cache and what does it cost?" is a standard internals question. Give both halves: it makes each decode step O(1) rather than O(n) in the prefix, and it costs memory that grows linearly with sequence length and batch size and can exceed the weights themselves. Then connect it: since batching is where throughput comes from and the cache limits batch size, the KV cache is often what actually caps a serving system. Finish with GQA and PagedAttention as the two responses.

Prompt caching and prefix reuse

Distinct from the KV cache, and routinely confused with it. The KV cache lives within one generation. Prompt caching reuses the prefill work across requests.

The observation: in most applications a large prefix is identical on every request — the system prompt, the tool schemas, few-shot examples, a document being discussed. Prefill is compute-bound and scales with prompt length, so recomputing an identical 10,000-token prefix for every request is pure waste. Cache the computed KV for that prefix and start from it.

KV cachePrompt caching
ScopeWithin one generationAcross requests
CachesK/V for tokens generated so farK/V for a shared prefix
SavesQuadratic recomputation during decodePrefill time and input-token cost
LifetimeOne requestMinutes to hours
Typical savingMakes generation feasible at allUp to ~90% off cached input tokens; much faster TTFT

The one rule: prefixes must match exactly

# GOOD -- the cacheable prefix is byte-identical on every request, and
# everything variable comes after it.
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},     # static
    {"role": "system", "content": FEW_SHOT_EXAMPLES}, # static
    {"role": "system", "content": POLICY_DOCUMENT},   # static, large
    {"role": "user",   "content": user_question},     # varies -- LAST
]

# BAD -- one timestamp at the top invalidates the entire cache, every time.
messages = [
    {"role": "system", "content": f"Current time: {datetime.now()}\n{SYSTEM_PROMPT}"},
    ...
]
# Caching is PREFIX-based: the first differing token ends the reusable
# region. Anything dynamic belongs at the END of the prompt, always.

That mistake — a timestamp, a request id, or a per-user greeting at the top of the system prompt — is extremely common and silently costs the entire benefit. The rule is one sentence: static first, dynamic last.

For agents the effect compounds. An agent loop re-sends the growing conversation on every step, so by step ten the prefix is large and almost entirely unchanged. Prompt caching turns that from the dominant cost into a rounding error, which is why it matters more for agents than for single-shot calls.

Interview angle

Raise this when asked about cost. "The system prompt, tool schemas and retrieved document are identical across requests, so I would order the prompt static-first and let prefix caching absorb them — and I would be careful not to put anything dynamic like a timestamp at the top, because that invalidates the whole prefix." It is concrete, it is an easily-missed optimisation, and the failure mode shows you have actually used it.

Batching and continuous batching

Here is the consequence of the bandwidth argument that surprises people: because the weights are read once per forward pass regardless of how many sequences are in it, processing 32 sequences together costs barely more wall-clock time than processing one. Throughput rises almost linearly with batch size until you run out of memory or saturate compute.

# One forward pass reads 14 GB of weights whether the batch is 1 or 32.
# The per-sequence arithmetic is tiny by comparison.
for batch in (1, 8, 32, 64):
    weight_read_ms = 7.0                       # constant: bandwidth-bound
    compute_ms     = 0.045 * batch             # scales with batch
    step_ms        = max(weight_read_ms, compute_ms)
    print(f"batch {batch:3d}: {step_ms:5.2f} ms/step  "
          f"{batch / step_ms * 1000:7.0f} tok/s total  "
          f"{1 / step_ms * 1000:5.0f} tok/s per user")

# batch   1:  7.00 ms    143 tok/s total    143 tok/s per user
# batch  32:  7.00 ms   4571 tok/s total    143 tok/s per user
#
# 32x the throughput at IDENTICAL per-user latency. This is why serving
# economics are entirely about keeping the batch full -- and why the KV
# cache, which caps batch size, caps throughput.

Static versus continuous batching

Naive (static) batching waits for a batch to fill, runs it to completion, then starts the next. It wastes enormously, because sequences in a batch finish at different times — a batch where one response is 500 tokens and the rest are 20 leaves most slots idle for most of the run.

Continuous batching (also called in-flight batching) works at the level of the decode step: when any sequence finishes, a waiting request takes its slot immediately. The batch stays full. This is vLLM's other main contribution alongside PagedAttention, and together they are why it is the default answer for GPU serving.

MetricMeansImproved by
TTFTTime to first tokenPrompt caching; prefill optimisation; smaller queues
ITL / TPOTInter-token latencyQuantization; faster memory; smaller models
ThroughputTotal tokens/sec across usersBatching, overwhelmingly
GoodputThroughput meeting an SLAThe one that actually matters

The tension worth naming: throughput and latency pull against each other. A bigger batch means more total tokens per second but a longer queue wait, so TTFT suffers. Serving systems expose this as a scheduling policy, and "which do you optimise for?" is a reasonable design question to ask back.

Interview angle

"How would you reduce cost per token?" — batching, first and by a wide margin, because weights are read once per step and amortised across the batch. Then quantization (fewer bytes to read), then prompt caching (skip repeated prefill), then a smaller model. Giving them in that order, with the bandwidth reason attached to each, is a complete and well-grounded answer.

Mixture of Experts

A dense model uses every parameter for every token, so capacity and cost per token are welded together. Mixture of Experts breaks that link: replace the feed-forward block with N parallel FFNs plus a small router, and send each token to only the top k.

Recall from the internals page that the FFN holds roughly two thirds of a transformer's parameters. That is precisely why MoE sparsifies that layer and not attention.

import torch, torch.nn as nn, torch.nn.functional as F

class MoELayer(nn.Module):
    def __init__(self, d_model=512, d_ff=2048, n_experts=8, top_k=2):
        super().__init__()
        self.experts = nn.ModuleList(Expert(d_model, d_ff) for _ in range(n_experts))
        self.router  = nn.Linear(d_model, n_experts, bias=False)   # tiny
        self.top_k   = top_k

    def forward(self, x):                       # x: (tokens, d_model)
        logits = self.router(x)
        topk_logits, idx = torch.topk(logits, self.top_k, dim=-1)
        w = F.softmax(topk_logits, dim=-1)
        # softmax AFTER topk, over the SELECTION only -- so the weights sum
        # to 1 across the chosen experts. Softmax-then-truncate would leave
        # them summing to less than 1 and quietly scale the output down.

        out = torch.zeros_like(x)
        for e in range(len(self.experts)):
            # Expert-major: gather this expert's tokens, ONE batched matmul.
            # Token-major would be one tiny matmul per token -- hopeless.
            tok, rank = torch.where(idx == e)
            if tok.numel() == 0:
                continue
            out[tok] += w[tok, rank].unsqueeze(-1) * self.experts[e](x[tok])
        return out


# The arithmetic that is the whole argument (d_model=512, d_ff=2048, 8 experts, k=2):
one_expert = 512*2048 + 2048 + 2048*512 + 512          #  2,099,712
dense      = one_expert                                 #  2,099,712
moe_total  = 8*one_expert + 512*8                       # 16,801,792
moe_active = 512*8 + 2*one_expert                       #  4,203,520

print(f"{moe_total/dense:.2f}x parameters, {moe_active/dense:.2f}x compute, "
      f"{moe_active/moe_total:.0%} active")
# 8.00x parameters, 2.00x compute, 25% active

Eight times the capacity for twice the per-token compute. That is why Mixtral 8×7B is 46.7B total parameters with 12.9B active, and DeepSeek-V3 is 671B total with 37B active.

The three costs

  • Memory tracks total parameters, not active ones. Every expert must be resident even though most are idle, so MoE trades memory for compute — and memory is frequently the binding constraint. This is the point people miss.
  • Load balancing. Nothing stops the router collapsing onto a few favoured experts, and it will: a marginally better expert gets more tokens, more gradient, improves faster, attracts more tokens. Real implementations add an auxiliary load-balancing loss, and often a capacity factor that caps tokens per expert.
  • Kernels. A naive expert loop issues N small kernel launches and can be slower than the dense baseline despite fewer FLOPs. Production uses fused grouped-GEMM kernels — MegaBlocks, vLLM's fused MoE.

One more thing worth knowing: experts are not specialised by design. Every expert is an identical ordinary FFN; any specialisation emerges because the router consistently sends similar tokens to the same one. Published analyses find the emergent splits are often syntactic — punctuation, numerals, whitespace — rather than the tidy semantic division the name suggests.

Interview angle

Quote total and active parameters together, always: "Mixtral is 46.7B total, 12.9B active — you get the knowledge capacity of the large number and roughly the inference compute of the small one, but you pay VRAM for the large one." Then name load balancing as the thing that makes it trainable at all. Candidates who describe MoE as "making models smaller" have it backwards, and saying the memory point correctly is an easy way to be on the right side of that.

Choosing a serving stack

The choice is mostly determined by two questions: where does it run, and how many concurrent users.

StackBest forWhy
Provider APIAlmost everything, to startNo ops, frontier quality, pay per token. The right default until a reason appears
vLLMGPU serving at concurrencyPagedAttention + continuous batching; the throughput default
SGLangHeavy prefix reuse, structured outputRadixAttention shares KV across requests with common prefixes

Sizing the hardware

def vram_needed_gb(params_b, bits, ctx, batch, layers, kv_heads, head_dim):
    weights = params_b * 1e9 * bits / 8 / 1e9
    kv      = 2 * layers * kv_heads * head_dim * ctx * batch * 2 / 1e9  # fp16
    overhead = 2.0                     # activations, fragmentation, CUDA context
    return weights, kv, weights + kv + overhead

w, kv, total = vram_needed_gb(8, 4, 8192, 16, 32, 8, 128)
print(f"weights {w:.1f} GB + KV {kv:.1f} GB + 2 GB = {total:.1f} GB")
# weights 4.0 GB + KV 8.6 GB + 2 GB = 14.6 GB
#
# Note the KV cache is TWICE the quantized weights here. Sizing on model
# size alone is the classic mistake -- at realistic context and batch the
# cache dominates, and it is what actually sets your concurrency limit.

The decision, in order

  1. Start with a provider API. Self-hosting is justified by data residency, cost at real volume, latency without a network hop, or needing a pinned model version — not by preference.
  2. If self-hosting on GPU for more than one user, use vLLM. Continuous batching and PagedAttention are not things to reimplement.
  3. Quantize to 4-bit unless you have measured that you cannot. It is both a memory and a speed win.
  4. Size for the KV cache, not just the weights. It is what caps batch size, and batch size is throughput.
  5. Measure TTFT and inter-token latency separately. They have different causes and different fixes.
Interview angle

If asked to design serving, start by asking the two questions that determine everything — concurrency and where it must run — and then justify self-hosting rather than assuming it. "At ten requests a second with a privacy requirement, I'd self-host: vLLM on A100s, a 4-bit quantized 8B, sized for the KV cache at my target batch, and I'd watch goodput rather than raw throughput." Naming goodput — throughput that meets the latency SLA — is a small detail that reads as operational experience.

Practice
  • Run one model locally at Q4 and at fp16 and time both. Watching a 4-bit model generate faster, not just smaller, makes the bandwidth argument permanent.
  • Compute the VRAM table above for a model and context you care about. Being able to say "that needs about 15 GB" without hedging is worth a lot in this round.
