Tokens: the unit of everything

A language model does not see characters or words. It sees tokens — sub-word units produced by a tokenizer that was itself trained, usually with byte-pair encoding, to carve frequent sequences into single units and rare ones into several. Everything downstream is counted in tokens: what you pay, what fits in context, how fast you generate.

The ratios worth carrying in your head:

ContentRoughlyWhy
English prose1 token ≈ 0.75 words, or ~4 charactersCommon words are single tokens
Code1 token ≈ 2–3 charactersPunctuation, indentation and identifiers fragment badly
Non-Latin scriptsoften 1 token per character, sometimes worseTokenizers are trained on web text dominated by English
JSON~1.5× the equivalent proseBraces, quotes and keys are all tokens

That last-but-one row has a real consequence people miss: the same question costs several times more in Hindi or Japanese than in English, and fits far less history into the same context window. If you are building for a non-English market, measure it rather than assuming the English ratio.

# Never estimate tokens by word count — count them.
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")

samples = {
    "english": "The quick brown fox jumps over the lazy dog.",
    "code":    "def f(x): return [i**2 for i in range(x) if i % 3 == 0]",
    "json":    '{"user_id": 12345, "status": "active", "roles": ["admin"]}',
}

for name, text in samples.items():
    n = len(enc.encode(text))
    print(f"{name:8s} {len(text):4d} chars  {len(text.split()):3d} words  ->  {n:3d} tokens"
          f"   ({len(text)/n:.1f} chars/token)")

Tokenization also explains a family of behaviours that look like reasoning failures and are not. A model miscounts the letters in a word because it never saw the letters — it saw two or three opaque tokens. Arithmetic on long numbers is unreliable partly because digits group into tokens inconsistently. These are tokenizer artefacts, and naming them as such is a good signal.

Interview angle

When you estimate cost in a design round, do it in tokens and say the conversion out loud: "about 3,000 tokens of retrieved context plus a 500-token answer, so roughly 3,500 tokens a request." That one sentence shows you think in the unit the system is actually billed and bounded in. Candidates who estimate in "requests" without ever converting to tokens cannot answer the follow-up about what happens when documents get longer.

Practice
  • Run the snippet above on a page of your own documentation and on the same page translated. The ratio difference is the thing to internalise.
  • Take a prompt you use and count its tokens. Most people are surprised by how much of the budget the system prompt takes.

The context window, and what fills it

The context window is the maximum number of tokens the model can attend over in one forward pass — prompt and generation together. It is a hard limit, not a soft one: exceed it and the request fails or is silently truncated, depending on the client.

Two things about it are routinely misunderstood.

First, it is shared. A 128k window does not mean 128k of input; it means input plus output. If you need a 4,000-token answer you have 124,000 for everything else, and "everything else" is a longer list than people expect:

ConsumerTypicalNotes
System prompt200–2,000Fixed per request; a good prompt-caching target
Tool schemas100–200 per toolTen tools is a meaningful slice of the budget
Conversation historygrows without boundThe one that actually breaks things
Retrieved context1,000–8,000Your k × chunk size; the knob you control
The question10–200Negligible
Reserved for output500–4,000Must be subtracted up front

Second, performance is not flat across it. Models reliably attend better to the beginning and the end of their context than to the middle — the "lost in the middle" effect. A fact buried at 60% depth in a long context is measurably less likely to be used than the same fact at the start or the end. This has a direct design consequence: put the most important retrieved material first or last, not in the middle, and do not assume a bigger window removes the need for good retrieval. It changes what is possible, not what is reliable.

# Budget the window explicitly rather than discovering the limit in production.
WINDOW        = 128_000
RESERVE_OUT   =   4_000      # the answer must fit too
SYSTEM        =     800
TOOLS         =   1_200      # ~8 tool schemas

available_for_context = WINDOW - RESERVE_OUT - SYSTEM - TOOLS
print(f"available for history + retrieval: {available_for_context:,} tokens")

# Of that, decide the split deliberately. History grows; retrieval is a knob.
HISTORY_CAP   = 8_000        # beyond this, summarise older turns
chunk_tokens  = 400
k             = 12
retrieval     = chunk_tokens * k

print(f"retrieval: {k} x {chunk_tokens} = {retrieval:,}")
print(f"history cap: {HISTORY_CAP:,}")
print(f"headroom: {available_for_context - HISTORY_CAP - retrieval:,}")
# Headroom is not slack to be filled. Long contexts cost money and attention
# quality, and 'lost in the middle' means stuffing the window can make
# answers worse, not better.
Interview angle

"Why not just put everything in the context now that windows are huge?" is a common probe, and there are three good answers to give together: cost, because you pay per input token on every request; latency, because prefill time scales with context length; and quality, because of the lost-in-the-middle effect and because irrelevant context measurably distracts the model. Large windows reduce the engineering pressure on retrieval; they do not remove the reason for it.

Practice
  • Write the budget table above for a system you have built, with real numbers. Most people find history is the uncontrolled term.
  • Decide, for that system, what you drop first when the budget is exceeded — oldest turns, lowest-scoring chunks, or the tool schemas. Having an answer is the point.

Sampling: temperature, top-k, top-p

The model's forward pass ends with a vector of logits — one real number per vocabulary token. Decoding is the process of turning that vector into one chosen token, and it is pure post-processing: the model is unchanged, only the selection rule differs.

Temperature

Temperature divides the logits before the softmax:

import numpy as np

def softmax(x):
    e = np.exp(x - x.max())
    return e / e.sum()

logits = np.array([3.0, 2.0, 1.0, 0.5])

for T in (0.1, 0.7, 1.0, 2.0):
    p = softmax(logits / T)           # <-- divide the LOGITS, then softmax
    print(f"T={T:<4} {np.round(p, 3)}  max={p.max():.3f}")

# T=0.1  [0.999 0.    0.    0.   ]  max=1.000   near-deterministic
# T=1.0  [0.574 0.211 0.078 0.047]  max=0.574   the model's own distribution
# T=2.0  [0.396 0.24  0.146 0.113]  max=0.396   flattened toward uniform

The detail that is worth free credit in an interview: the division must happen before the softmax. If you apply softmax first and then divide the probabilities by T and renormalise, you get back exactly the distribution you started with — the division cancels in the normalisation. It is a no-op, and it is a real bug people ship.

Top-k and top-p

Both truncate the distribution before sampling; they differ in how they choose where to cut.

RuleBehaviour on a peaked distributionBehaviour on a flat one
top-kKeep the k highest-probability tokensKeeps k−1 tokens that were never plausibleCuts off plausible alternatives arbitrarily
top-pKeep the smallest set summing to pKeeps very few — correctlyKeeps many — correctly

That is why top-p (nucleus sampling) is generally preferred: the cut adapts to how confident the model is at that position. When the next token is obvious, it keeps one or two; when the text could genuinely go several ways, it keeps the several.

def top_p_filter(probs, p=0.9):
    """Keep the smallest prefix of the sorted distribution summing to >= p."""
    order = np.argsort(probs)[::-1]           # descending
    sorted_p = probs[order]
    cum = np.cumsum(sorted_p)

    # Keep everything up to and INCLUDING the token that crosses p.
    # Off-by-one here is the classic bug: cutting at `cum <= p` can keep
    # nothing at all when the top token already exceeds p.
    keep = cum <= p
    keep[0] = True                            # always keep the argmax

    out = np.zeros_like(probs)
    out[order[keep]] = sorted_p[keep]
    return out / out.sum()                    # renormalise

probs = softmax(np.array([4.0, 2.0, 1.5, 1.0, 0.2]))
print(np.round(probs, 3))                     # [0.76  0.103 0.062 0.038 0.017]
print(np.round(top_p_filter(probs, 0.9), 3))  # [0.881 0.119 0.    0.    0.   ]

What to actually set

TaskSettingWhy
Structured extraction, classification, tool callstemperature=0You want the same input to give the same output; there is one right answer
Summarisation, RAG answerstemperature 0–0.3Grounded tasks; variation adds nothing and costs reproducibility
Drafting, brainstorming, creative texttemperature 0.7–1.0, top_p 0.9Variety is the product
Evals and debuggingtemperature=0, alwaysYou cannot measure a change through sampling noise
Temperature 0 is not determinism

It is greedy decoding, which is as close as the sampler gets — but the same prompt can still produce different output across runs. Floating-point reduction order varies with batch composition on GPU, so the argmax can flip when two logits are close; mixture-of-experts routing can depend on which other sequences are in the batch; and providers change model versions underneath a stable alias. Say "temperature 0 removes sampling noise but is not a determinism guarantee" and you have answered the question better than the person who says "yes, deterministic".

Practice
  • Run the temperature snippet and watch the distribution move. Then write the one-sentence explanation of why dividing after the softmax does nothing.
  • Implement top-p yourself, including the keep[0] = True guard. Getting the off-by-one wrong is the standard bug and it silently produces an all-false mask.

Prompting that survives production

Prompt engineering is the least durable skill in this field and still worth a few hundred words, because the parts that survive model upgrades are design decisions rather than incantations.

What reliably helps

  • Say the task, the format, and the constraints explicitly. Most prompt failures are underspecification, not model weakness.
  • Give examples when the task has a shape the words do not capture. Two or three well-chosen few-shot examples outperform a paragraph of description for formatting and edge-case handling. They cost context on every request, so they are a trade.
  • Let the model reason before it answers on multi-step problems. Whether you do it with an explicit instruction or by using a reasoning model, the mechanism is the same — the intermediate tokens are computation, and forcing an immediate answer skips it.
  • Put the instruction after long context, or repeat it. Lost-in-the-middle applies to your instructions too.
  • Separate data from instructions structurally — delimiters, XML-ish tags, or distinct message roles — so the model can tell what it is meant to obey from what it is meant to process.

What does not survive

Politeness, threats, offers of payment, "you are a world-class expert", and most of what circulates as prompt tricks. Some of it worked on specific older models; none of it is a design decision you would defend in a review.

# The structure that matters: role separation, explicit format, and a clear
# boundary between instructions and untrusted data.
SYSTEM = """You answer questions using ONLY the provided context.
If the context does not contain the answer, say "Not in the provided documents."
Cite the source id for every claim, like [doc-12].
Answer in at most four sentences."""

USER = """<context>
{context}
</context>

<question>
{question}
</question>"""

# Three things are doing real work here:
#  1. "ONLY the provided context" + an explicit escape hatch. Without the
#     escape hatch the model invents an answer rather than admitting a gap.
#  2. Citations, which make the answer checkable — the whole point.
#  3. Delimited context, so retrieved text reads as DATA. It is still not a
#     security boundary: see the prompt-injection note below.
Delimiters are not a security boundary

Wrapping retrieved text in tags helps the model tell data from instructions, and it stops honest mistakes. It does not stop a determined prompt injection, because the tags are just more tokens and a document can contain its own closing tag. If the agent holds tools that do anything irreversible, the defence is architectural — the privileged action needs an approval the content cannot grant — not textual. Saying this distinction out loud is one of the clearest seniority signals in the round.

Interview angle

If asked "how would you improve this prompt?", resist the urge to rewrite the wording. The high-value answers are structural: add an explicit escape hatch so the model can decline, require citations so the answer is checkable, constrain the output to a schema so a failure is loud, and move the instruction after the context. Each of those is a correctness mechanism; adjective choice is not.

Practice
  • Take a prompt you use and add an explicit "say you do not know" path. Measure how often it fires — on most RAG systems it should fire several percent of the time, and if it never fires your model is covering gaps.

Structured output: making answers checkable

Free text has to be read by a human to be checked. A typed object either parses or raises. That difference is why structured output is a correctness mechanism and not a convenience, and framing it that way is what the round is looking for.

from typing import Literal
from pydantic import BaseModel, Field

class Invoice(BaseModel):
    """A supplier invoice extracted from a scanned document."""
    invoice_number: str
    supplier:       str
    total_cents:    int = Field(ge=0, description="Total in minor units, never a float")
    currency:       Literal["GBP", "USD", "EUR"]
    confidence:     float = Field(ge=0, le=1)

# Two things to notice, both of which get asked about:
#
# 1. The class docstring and every Field(description=...) are sent to the
#    model as part of the JSON schema. They are prompt, not comments — which
#    means a vague docstring is a vague instruction.
#
# 2. Field(ge=0) is enforced AFTER generation, locally. Constrained decoding
#    can guarantee the SHAPE is valid JSON matching the schema; it cannot
#    guarantee the VALUES are right. Validation is still load-bearing.

print(Invoice.model_json_schema()["description"])
# -> "A supplier invoice extracted from a scanned document."

How providers actually enforce it

MechanismHowGuarantees
Prompted JSONAsk nicely, parse, retry on failureNothing. Works most of the time with capable models, fails often with small ones
Tool / function callingSchema sent as a tool definition; model emits a callUsually well-formed; provider-dependent
Constrained decodingMask logits so only tokens that keep the output schema-valid can be sampledShape is guaranteed. Values are not

Constrained decoding is the one worth being able to explain, because the mechanism is neat and shows you understand decoding: at each step the sampler is given a mask that zeroes the probability of any token which would make the partial output unparseable against the schema. The model cannot emit invalid JSON because invalid tokens are unreachable. What it can still do is emit a syntactically perfect object containing a hallucinated invoice number.

Interview angle

The sentence that lands: "a schema makes failure loud rather than silent." Without one, a model that misunderstands returns prose your parser mangles into plausible-looking garbage that flows downstream. With one, it raises at the boundary and you can retry, fall back, or route to a human. Then add the honest limit — the schema constrains structure, not truth — because volunteering the limit of your own mechanism is exactly the judgement being graded.

Practice
  • Take a schema you use and read its generated JSON schema. If the descriptions are vague, your prompt is vague — they are the same thing.
  • Deliberately make a small local model fail validation, and decide what your retry policy is. Two retries then degrade is a defensible answer; unlimited retries is not.

Hallucination, and what actually reduces it

A hallucination is fluent output that is not grounded in anything true. The framing that gets credit is that it is not a bug — it is a direct consequence of what the model does. Generation samples from a distribution over plausible continuations, and plausibility and truth are different properties. A model asked about something absent from its training data has no mechanism for silence; the distribution still has a mode, and sampling finds it.

So the goal is reduction and detection, never elimination. What actually works, in rough order of effect:

TechniqueWhy it helpsLimit
Retrieval groundingPuts the true answer in context, so the plausible continuation is also the correct oneOnly as good as retrieval; a wrong document produces a confident wrong answer
CitationsMakes claims checkable, and measurably reduces unsupported onesModels can cite a real source for a claim it does not make
An explicit escape hatchGives the model a licensed alternative to inventingNeeds to be in the prompt and reinforced; models default to answering
Structured outputNarrows the space; a schema with no free-text field cannot rambleConstrains shape, not truth
Low temperatureReduces sampling into the tailA confidently wrong mode stays wrong at T=0
Verification passCheck each claim against the source with a second call or a deterministic checkDoubles cost and latency; the checker shares the generator's blind spots

Why the model cannot just tell you

Asked how confident it is, a model produces a plausible-sounding number — it is generating text about confidence, not reporting a calibrated probability. Token logprobs are better but measure fluency more than correctness: a confident hallucination has high logprobs by construction. The signals that actually correlate with correctness are external — whether the claim appears in a retrieved source, and whether several independent samples agree.

# Self-consistency: sample n times and measure agreement. Disagreement across
# samples is a far better unsupported-claim signal than anything the model
# says about its own confidence.
from collections import Counter

def consistency(ask, prompt, n=5):
    answers = [ask(prompt, temperature=0.8) for _ in range(n)]
    top, count = Counter(answers).most_common(1)[0]
    return top, count / n          # agreement in [1/n, 1.0]

# answer, agreement = consistency(ask, "In what year was X founded?")
# if agreement < 0.6:  route to a human / say "uncertain"
#
# Costs n times as much, so reserve it for high-stakes claims. The useful
# property: it needs no ground truth, so it works in production where you
# have no labels.
Interview angle

"How do you stop it hallucinating?" is near-universal, and the strong answer has three parts. First reframe: you reduce and detect, you do not eliminate, because it follows from sampling. Then name the ladder — grounding, citations, an escape hatch, schemas — in order of effect. Then close on measurement: "and I would measure it, by scoring what fraction of claims are supported by the retrieved context on a golden set, so I can tell whether a change helped." Candidates who promise elimination are marked down; candidates who end on measurement are marked up.

Practice
  • Ask a model ten questions you know the answers to and ten about things that do not exist. Count how often it declines on the second set. That number is why the escape hatch matters.
  • Rehearse the three-part answer above in under sixty seconds.
