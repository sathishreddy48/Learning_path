Why retrieval, and when not to

Retrieval-augmented generation is one idea: find text relevant to the question, put it in the prompt, and ask the model to answer from it. Everything else is engineering around that sentence.

It exists because models have three gaps that no amount of prompting closes — a training cutoff, no knowledge of your private data, and no mechanism for citing a source. Retrieval fixes all three at once, which is why it is the default architecture and the most-asked design question in the round.

The two paths

Draw these separately. They have different latencies, different costs, and different failure modes, and keeping them apart makes the whole design easier to discuss.

Ingestion (offline)Query (per request)
StepsLoad → parse → chunk → embed → indexEmbed query → retrieve → rerank → assemble → generate
RunsOn a schedule, or on document changeEvery request
Latency budgetHours is fineHundreds of milliseconds
Cost driverEmbedding the whole corpusInput tokens, every single time
Expensive to changeYes — chunking or embedding model means a full re-indexNo — k, reranking and prompts are hot knobs

When not to use it

Saying this unprompted is worth real credit, because the reflex in this field is to reach for RAG unconditionally:

SituationBetter answer
The corpus is small and static — a few thousand tokensPut it all in the prompt and cache the prefix. Retrieval adds latency, complexity and a failure mode for nothing
Answers need aggregation — "how many tickets mention X?"That is a query, not a retrieval. Text-to-SQL over structured data; top-k chunks cannot count
You need format or tone, not factsFine-tuning or few-shot examples. Retrieval does not teach behaviour
The question is a lookup with an exact keyJust look it up. A model in the path makes it slower, costlier and less reliable

That second row is the sharpest one. "How many of our contracts expire this quarter?" sounds like a document question and is not — it needs every matching row, and retrieval returns the top k most similar chunks. Spotting that an apparently RAG-shaped question is actually an aggregation is a distinguishing answer.

Interview angle

Open the design by splitting the board into ingestion and query, and say why: "the ingestion decisions are expensive to change because they mean a re-index, so I want to get chunking and the embedding model right; the query-side knobs are cheap and I will tune them against evals." That single framing shows you have operated one of these rather than built one once.

Embeddings and vector search

An embedding model maps text to a dense vector — typically 384 to 3,072 dimensions — trained so that semantically similar text lands close together. Retrieval is then a nearest-neighbour search in that space.

Cosine similarity is the usual metric: the cosine of the angle between two vectors, ignoring magnitude. If the vectors are normalised to unit length — most embedding APIs return them that way — cosine similarity is just a dot product, which is why vector search is fast.

import numpy as np

def cosine(a, b):
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

# If vectors are already unit-normalised (most APIs do this), it is a dot
# product -- and a whole index is one matrix multiply.
def search(query_vec, matrix, k=10):
    """matrix: (n_chunks, dim), unit-normalised. Returns (indices, scores)."""
    scores = matrix @ query_vec          # (n_chunks,)  one GEMV
    top = np.argpartition(-scores, k)[:k]      # O(n), not a full sort
    top = top[np.argsort(-scores[top])]        # sort only the k
    return top, scores[top]

# Brute force is O(n * dim). At 100k chunks x 768 dims that is ~77M flops --
# about a millisecond, so you genuinely do not need an ANN index at that size.
# Say so in an interview; reaching for a vector DB at 10k documents is a
# complexity tell.

Exact versus approximate

Corpus sizeUseWhy
< ~100k chunksBrute force, or pgvector with no indexMilliseconds. Exact results. No tuning, no extra service
100k – 10MHNSW (pgvector, Qdrant, Weaviate)Sub-linear and high recall; memory-hungry but simple
> 10MIVF-PQ, DiskANN, or a managed serviceCompressed vectors; recall traded for memory

HNSW is the one to be able to describe: a multi-layer graph where upper layers are sparse long-range links and lower layers dense local ones, so a search descends from a coarse layer to a fine one — a skip list in high dimensions. It is approximate, so there is a recall knob (ef_search), and it is worth saying that you would measure recall against brute force on a sample rather than trusting the default.

Choosing the model

What actually matters: the input limit (often 512 tokens — chunk above it and the tail is silently truncated), the dimension (storage and search cost scale with it), whether it was trained for asymmetric search (short query against long passage, which is what you are doing), and whether your domain is represented at all. Code, legal text and medical text all do badly with general-purpose models.

The silent truncation trap

Embed a 900-token chunk with a 512-token model and you get a vector for the first 512 tokens. No error, no warning — the rest of the chunk is simply not represented, and that content is unfindable. This is one of the most common real RAG bugs and it is invisible until you measure recall. Always assert chunk length against the model's limit at ingestion time.

Interview angle

If asked which vector database you would use, the strong answer starts with "how many chunks?" — and for anything under a few hundred thousand, "Postgres with pgvector, because the data is already relational, I get transactions and metadata filtering for free, and I do not add a service to operate." Reaching for a dedicated vector store at small scale reads as resume-driven design.

Chunking: the decision that sets your ceiling

Chunking is the decision that sets your ceiling, and it is made before any model is chosen. If the answer to a question is split across two chunks and neither contains enough to answer alone, no reranker and no frontier model will recover it.

The trade-off, stated plainly

Small chunks (100–300 tokens)Large chunks (800–2000)
Embedding qualityBetter — one topic per vector, so the vector means somethingWorse — an average of several topics, close to nothing in particular
PrecisionHigher — less irrelevant text per hitLower — you pay tokens for surrounding noise
Context completenessWorse — answers get split; pronouns lose their referentBetter — the answer is more likely to be whole
Cost per queryLower per chunk, but you need more of themHigher per chunk

Defaults worth stating: 300–500 tokens with 10–20% overlap is a reasonable starting point for prose, and overlap exists so that a sentence straddling a boundary appears whole in at least one chunk.

Respect the document's own structure

Fixed-size splitting is the baseline and it is the wrong default for anything with structure. Markdown has headings; code has functions; contracts have clauses; transcripts have turns. Splitting on those boundaries beats splitting on a character count, because a chunk that is one semantic unit embeds into a vector that means one thing.

import re, tiktoken
enc = tiktoken.get_encoding("cl100k_base")
def ntok(s): return len(enc.encode(s))

def chunk_markdown(doc: str, target=400, overlap=60, hard_limit=512):
    """Split on headings first, then pack paragraphs up to `target` tokens.

    Two things this does that naive splitters do not:
      - carries the heading trail into every chunk, so a chunk about
        "Refunds" still says which product it belongs to;
      - asserts against the EMBEDDING MODEL's limit, so nothing is
        silently truncated at embed time.
    """
    sections, trail = [], []
    for part in re.split(r"^(#{1,6} .*)$", doc, flags=re.M):
        if part.startswith("#"):
            level = len(part) - len(part.lstrip("#"))
            trail = trail[: level - 1] + [part.lstrip("# ").strip()]
        elif part.strip():
            sections.append((list(trail), part.strip()))

    chunks = []
    for trail, body in sections:
        prefix = " > ".join(trail)
        buf, size = [], 0
        for para in re.split(r"\n\s*\n", body):
            p = ntok(para)
            if size + p > target and buf:
                chunks.append((prefix, "\n\n".join(buf)))
                # overlap: carry the tail paragraph into the next chunk
                buf, size = ([buf[-1]], ntok(buf[-1])) if overlap else ([], 0)
            buf.append(para); size += p
        if buf:
            chunks.append((prefix, "\n\n".join(buf)))

    out = []
    for prefix, text in chunks:
        full = f"{prefix}\n\n{text}" if prefix else text
        assert ntok(full) <= hard_limit, f"chunk exceeds embedder limit: {ntok(full)}"
        out.append(full)
    return out

The heading trail in that snippet is doing the single highest-value thing in chunking, and it has a name — contextual retrieval. A chunk that reads "You may return items within 30 days" is ambiguous across a corpus covering six products. Prefix it with "Acme Pro > Returns" and it is both findable and unambiguous. Anthropic reported this kind of context-prefixing cutting retrieval failures substantially, and it costs nothing at query time.

Interview angle

Give a number and a reason, then say how you would revise it: "I'd start at 400 tokens with 60 of overlap, split on headings rather than character count, and prefix each chunk with its heading trail — then tune against retrieval recall on a golden set, because the right size depends on how answers are distributed in the corpus and I cannot know that in advance." Candidates who name a number with no justification and candidates who refuse to name one both score worse than this.

Practice
  • Take twenty questions over your corpus and check by hand whether a single chunk contains each answer. The fraction that do not is your ceiling, and it is usually lower than people expect.

Hybrid search: BM25, vectors, and RRF

Vector search finds semantically similar text. It is bad at exactly the things keyword search is good at: product codes, error numbers, people's names, rare acronyms, exact quoted phrases. Searching for ERR_4821 in a semantic index returns chunks about errors in general, because the embedding of a rare token carries almost no signal.

Hybrid search runs both and fuses the results. It is close to free and it is the highest-value single upgrade to a naive RAG system.

Good atBad at
BM25 / full-textExact terms, codes, names, rare words, quoted phrasesSynonyms, paraphrase, "how do I cancel" vs "terminating your subscription"
Dense / vectorMeaning, paraphrase, cross-lingualExact identifiers, rare tokens, negation

Reciprocal Rank Fusion

The problem with combining two result lists is that their scores are not comparable — BM25 is unbounded and corpus-dependent, cosine is in [−1, 1]. Normalising them is fiddly and fragile. RRF ignores the scores entirely and uses only the ranks, which is why it is the standard answer:

def rrf(result_lists, k=60, top_n=20):
    """Reciprocal Rank Fusion. Scores are discarded; only RANK is used.

        score(d) = sum over lists of  1 / (k + rank(d))

    k=60 is the value from the original paper and is a sensible default. It
    damps the top ranks so one list cannot dominate on a single confident
    hit -- the gap between rank 1 and 2 is 1/61 vs 1/62, not 10x.
    """
    scores = {}
    for results in result_lists:                 # e.g. [bm25_hits, vector_hits]
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)[:top_n]


bm25_hits  = ["d9", "d3", "d1"]        # exact match on an error code
vector_hits = ["d1", "d7", "d3"]       # semantic match
print(rrf([bm25_hits, vector_hits]))
# -> ['d1', 'd3', 'd9', 'd7']
# d1 wins: mid-rank in BOTH lists beats rank-1 in only one. That is the
# property you want -- agreement across different retrieval methods is a
# stronger relevance signal than confidence within one.

The property to articulate: documents found by both methods rise to the top. Agreement between two retrieval systems that fail in different ways is a better relevance signal than a high score from either alone.

In Postgres this is one query — tsvector/ts_rank for the keyword side, pgvector for the dense side, fused in SQL — which is another reason pgvector is a good default when the data is already relational.

Interview angle

Be ready for "why not just normalise the scores and take a weighted sum?" The answer: BM25 scores are unbounded and depend on corpus statistics, so any normalisation you pick is a tuned constant that drifts as the corpus grows, and the weight becomes another thing to maintain. RRF needs no tuning, is scale-free, and generalises to three or four retrievers without re-calibration. If you do want weights, RRF takes per-list weights cleanly.

Practice
  • Implement RRF from memory — it is six lines and it comes up often.
  • Find five queries where your vector search fails and keyword search succeeds. They will all be identifiers, names or rare terms, and the pattern is the thing to internalise.

Reranking and the two-stage pipeline

Retrieval optimises for speed over a large corpus; it therefore uses a bi-encoder, which embeds the query and each document separately and compares vectors. That separation is what makes it fast — document vectors are computed once, offline — and it is also its limitation: the document was embedded without any knowledge of the query.

A cross-encoder reranker puts the query and the document through the model together, so attention runs across both and the score reflects their actual interaction. It is far more accurate and far too slow to run over a corpus — which gives the standard two-stage design:

StageModelOverCostJob
1 · RetrieveBi-encoder + BM25Whole corpus~10 msHigh recall: get the answer into the top 50 somewhere
2 · RerankCross-encoderThose 50~100 msHigh precision: get it into the top 5, in order
def retrieve(query, k_recall=50, k_final=5):
    # Stage 1 -- cheap and wide. Optimise for RECALL: the answer must be in
    # here somewhere, order does not matter yet.
    dense  = vector_search(embed(query), k=k_recall)
    sparse = bm25_search(query, k=k_recall)
    candidates = rrf([dense, sparse], top_n=k_recall)

    # Stage 2 -- expensive and narrow. Optimise for PRECISION.
    # The cross-encoder sees (query, doc) TOGETHER, so it can tell
    # "returns within 30 days" from "returns are not accepted after 30 days"
    # -- a distinction cosine similarity on separate embeddings misses,
    # because the two sentences share almost all their tokens.
    scored = cross_encoder.predict([(query, text_of(c)) for c in candidates])
    ranked = [c for _, c in sorted(zip(scored, candidates), reverse=True)]
    return ranked[:k_final]

The negation example in that comment is the clearest illustration of why reranking earns its latency. "Returns are accepted within 30 days" and "returns are not accepted after 30 days" have nearly identical embeddings — same vocabulary, same topic — but a cross-encoder reading them alongside the query can tell which one answers it.

Reranking also lets you retrieve wider and send narrower. Fetching 50 candidates and sending the best 5 gives better context than fetching 5 directly, at the cost of one extra model call. That is usually a good trade, and it is the standard way to improve a RAG system that is "nearly right".

Interview angle

The sentence that demonstrates understanding: "a bi-encoder embeds the query and the document separately, so the document's vector was computed without knowing the question; a cross-encoder scores them together." Follow it with the cost argument — one is O(corpus) offline, the other is O(candidates) per query — and you have explained both why two stages exist and why they are in that order.

Assembling the context, and citing it

You have your top chunks. What you do with them before the model sees them is a surprisingly large fraction of answer quality, and it is the part people skip.

Order matters

Because of the lost-in-the-middle effect, relevance order is not the best presentation order. If you are sending ten chunks, put the strongest at the start and the end rather than ranking them 1 to 10 top to bottom.

def assemble(chunks, question, *, budget_tokens=4000):
    """Pack chunks into the context budget, strongest at the edges."""
    kept, used = [], 0
    for c in chunks:                       # already in relevance order
        t = ntok(c.text)
        if used + t > budget_tokens:
            break                          # drop the tail -- do not truncate
        kept.append(c); used += t

    # Strongest first AND last: 1, 3, 5, ... then ... 6, 4, 2
    ends = kept[0::2] + kept[1::2][::-1]

    body = "\n\n".join(
        f"[{c.id}] source: {c.source} ({c.heading_trail})\n{c.text}"
        for c in ends
    )
    return f"<context>\n{body}\n</context>\n\n<question>\n{question}\n</question>"

# Three deliberate choices:
#   - DROP whole chunks at the budget, never truncate one mid-sentence;
#     a half chunk is often worse than no chunk.
#   - Every chunk carries a stable [id] so the model can cite it and you
#     can verify the citation points at text that supports the claim.
#   - Source and heading trail travel with the text, so the model can say
#     WHICH product or version an answer applies to.

Citations are the verification mechanism

Requiring [doc-12]-style citations does two things. It measurably reduces unsupported claims, because the model must point at something. More importantly it makes the answer checkable: you can programmatically confirm every cited id was actually retrieved, and you can show the user the source. An uncited RAG answer is indistinguishable from a hallucination until a human reads the corpus.

Worth knowing the limit: a model can cite a real document for a claim that document does not make. Citation presence is a weak guarantee; citation support — checking that the cited chunk entails the claim — is the strong one, and that is an eval, covered on the next page.

Interview angle

Mention deduplication. Real corpora contain near-duplicates — the same policy in three documents, a page and its PDF export — and without a dedupe step your top 10 can be five copies of one passage, which wastes most of the context budget and starves the answer of the other facts it needs. A similarity threshold between selected chunks, or grouping by source document, fixes it. Almost nobody raises this and it is unmistakably a from-production detail.

Where RAG fails, and how you find out

When a RAG system gives a wrong answer, there are exactly two possibilities, and the first diagnostic move is to determine which:

  1. Retrieval failure — the answer was not in the retrieved context. The model never had a chance.
  2. Generation failure — the answer was there and the model got it wrong anyway.

They have completely different fixes, and a system that cannot tell them apart cannot be improved except by guessing. This is why retrieval is evaluated separately from generation, and saying so is the single best answer to "your RAG system returns a wrong answer — debug it."

FailureSymptomFix
Answer split across chunksPartially right, missing a condition or an exceptionLarger chunks, more overlap, or a parent-document strategy
Exact term not foundFails on codes, names, versionsHybrid search — this is the single commonest fix
Near-duplicates flood top-kContext is five copies of one passageDeduplicate before assembly
Silent embed truncationContent in long chunks is simply unfindableAssert chunk length against the embedder limit at ingestion
Ambiguous chunksRight topic, wrong product or versionHeading-trail prefixes; metadata filters
Stale indexConfidently cites something that changed last weekRe-index on change; show document dates in context
Needs aggregation"How many…" answered from ten chunksRoute to SQL. Top-k cannot count
Model ignores contextAnswers from parametric knowledge insteadStronger instruction, citations required, lower temperature

The diagnostic

def diagnose(question, gold_answer, gold_doc_ids):
    """Attribute a wrong answer to retrieval or generation. Run this first."""
    chunks = retrieve(question)
    got = {c.id for c in chunks}

    if not (got & set(gold_doc_ids)):
        return "RETRIEVAL: the supporting document was never retrieved"

    # The answer WAS in context. Confirm the model can use it when it is
    # handed the right context with nothing else competing.
    oracle = generate(question, context=[c for c in chunks if c.id in gold_doc_ids])
    if correct(oracle, gold_answer):
        return "RETRIEVAL: right doc retrieved but ranked too low / crowded out"
    return "GENERATION: correct context, wrong answer"

That three-way split — never retrieved, retrieved but out-ranked, retrieved and misused — maps onto three different fixes: improve recall, improve the reranker or raise k, and improve the prompt or the model.

Interview angle

"Your RAG system returns a wrong answer. Debug it." is a near-certain question and most candidates start listing fixes. Start instead with the attribution: "first I would check whether the supporting document was in the retrieved context at all, because retrieval failures and generation failures have different fixes and I do not want to tune a prompt to solve a recall problem." Then walk the three-way split. That is a methodology rather than a list, and it is what the question is testing.

Practice
  • For your own pipeline, take ten wrong answers and attribute each one. The distribution will surprise you — in most systems the large majority are retrieval failures, which is why people who tune prompts first make slow progress.
