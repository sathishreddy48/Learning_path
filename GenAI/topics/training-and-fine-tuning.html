Training & Fine-Tuning

The three stages

A chat model is built in three stages, and they do different jobs. Candidates who can name all three and say what each changes are immediately distinguishable from those who treat "training" as one undifferentiated thing.

Pre-trainingInstruction tuning (SFT)Preference tuning
DataTrillions of tokens of raw textThousands–millions of (instruction, response) pairsComparisons: response A preferred to B
ObjectivePredict the next tokenPredict the next token — on the response onlyRaise the preferred response's likelihood relative to the rejected one
TeachesLanguage, facts, reasoning — nearly all capabilityTo follow instructions rather than continue textTone, helpfulness, refusal, what "good" looks like
CostMillions of dollars, thousands of GPUsHundreds to thousands of dollarsSimilar to SFT, plus collecting preferences
Who does itA handful of labsAnyoneMostly labs; increasingly accessible via DPO

The framing worth stating: pre-training creates the capability; the later stages shape how it is expressed. Instruction tuning does not make a model smarter — it makes a text-continuation engine behave like something you can ask questions. The knowledge was already there.

You can see this directly in a base model. Prompt GPT-2 with "What is the capital of France?" and it may continue with more questions, because it is completing a document that looks like a quiz. The facts are present; the instruction-following behaviour is not. That example is a clean way to make the distinction concrete in an interview.

Interview angle

"What is the difference between a base model and a chat model?" is a common opener. The answer: a base model only continues text; instruction tuning teaches it to treat input as a request, and preference tuning shapes tone, helpfulness and refusal. Add that capability comes almost entirely from pre-training — the later stages are about expression — because that is the point that explains why fine-tuning cannot make a small model smart.

Pre-training: data, objective, loop

You will not do this, and you should still be able to describe it, because the questions about data, objective and scale are standard.

The objective

Next-token prediction, with cross-entropy loss, over everything. The targets are the inputs shifted by one:

import torch, torch.nn.functional as F

# A batch of token ids: (batch, block_size + 1)
chunk = get_batch()
x, y = chunk[:, :-1], chunk[:, 1:]       # inputs, and the SAME tokens shifted
                                          # left by one -- the labels are free

logits = model(x)                         # (B, T, vocab)
loss = F.cross_entropy(
    logits.reshape(-1, logits.size(-1)),  # (B*T, vocab)
    y.reshape(-1),                        # (B*T,)
)

# Thanks to the causal mask, EVERY position contributes a prediction
# conditioned only on its own prefix -- B*T training signals from one
# forward pass. That is why this is self-supervised: no labels, just text.
#
# Sanity check: an untrained model should have loss ~ ln(vocab_size).
# For a 50257-token vocab that is ~10.8. If initial loss is far off,
# initialisation or the loss shape is wrong.

That ln(vocab_size) check is worth remembering — a uniform distribution over the vocabulary gives exactly that cross-entropy, and it is the fastest way to catch a broken training setup.

Data

The quality story matters more than the quantity story now. The pipeline is deduplication (near-duplicates waste compute and encourage memorisation), quality filtering (classifier-based, often "does this look like a reference text?"), decontamination against benchmark sets, and mixing — code improves reasoning even for non-code tasks, which is one of the more interesting empirical findings in the field.

Scaling

Two papers to be able to contrast. The Kaplan scaling laws (2020) suggested making models bigger was the dominant lever. Chinchilla (2022) showed that models were systematically under-trained — for a fixed compute budget, the optimal ratio is roughly 20 tokens per parameter, far more data and a smaller model than people were using. That finding redirected the field toward smaller, longer-trained models, which is why a modern 7B outperforms a 2020-era 175B on many tasks. Current practice trains well past Chinchilla-optimal because inference cost, not training cost, is what you pay forever.

Interview angle

"Why is a 7B model today better than GPT-3 at 175B?" is a great question to have an answer for: more and better data (Chinchilla-optimal and beyond), heavy deduplication and quality filtering, better architecture details (RoPE, RMSNorm, SwiGLU), and instruction plus preference tuning on top. Parameter count is not capability — the training recipe is, and being able to say that with the Chinchilla ratio attached is a strong signal.

When to fine-tune, and when not to

This is the question you are most likely to actually be asked, and the correct answer is usually "I would not". Getting to that answer by reasoning rather than reflex is the whole exercise.

The ladder — exhaust each rung first

RungApproachCostIterationFixes
1Better promptFreeSecondsMost problems, genuinely
2Few-shot examplesTokens per requestMinutesFormat and edge cases
3RetrievalInfrastructureHoursMissing knowledge
4Fine-tuningGPU time + data + a model to hostDaysConsistent behaviour, format, tone, latency

What fine-tuning is and is not for

Good atBad at
A consistent output format you cannot reliably prompt forTeaching facts — unreliable, and they go stale
A domain's tone, idiom or styleKnowledge that changes — you would retrain on every update
A narrow, repetitive task done at volumeMaking a small model broadly capable
Distilling a big model's behaviour into a cheaper oneAnything you have fewer than ~1,000 good examples for
Dropping latency and cost by replacing a long promptProblems you have not first tried to prompt your way out of

The crisp version: fine-tuning teaches behaviour; retrieval supplies knowledge. "The model does not know about our products" is a retrieval problem and answering it with fine-tuning is the single most common wrong answer in this round. Facts installed by fine-tuning are entangled with everything else, cannot be cited, cannot be updated without retraining, and are not reliably recalled.

The honest costs

Say these, because they are what makes the decision real: you now host a model, or pay a provider to; every base-model upgrade means redoing the work; you need an eval suite to know whether it helped, so you cannot skip the evals anyway; and catastrophic forgetting is real — a model tuned hard on one task gets worse at others, which is a particular risk when the task data is narrow.

Interview angle

When asked "would you fine-tune for this?", walk the ladder out loud and land on a reason. "If the problem is that it does not know our data, that is retrieval. If the problem is that it will not reliably produce our output format even with few-shot examples, that is fine-tuning — and I would want at least a thousand good examples and an eval suite before starting, because otherwise I cannot tell whether it worked." Confidently declining is the stronger answer, and the specificity is what makes it credible.

LoRA: why a low-rank update is enough

Full fine-tuning updates every weight, which means storing optimizer state for every weight. With Adam that is roughly 16 bytes per parameter — weights, gradients, and two moment estimates in fp32 — so a 7B model needs well over 100 GB before activations. That is several A100s for a model that fits on one card at inference.

LoRA freezes the base model and trains a small low-rank update instead.

The idea

The observation is that the change a fine-tune makes to a weight matrix has low intrinsic rank — you are adapting behaviour, not relearning language. So instead of learning ΔW directly (d×k parameters), learn two thin matrices whose product has the same shape:

W' = W + BA, where B is d×r, A is r×k, and r ≪ min(d, k).

import torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=8, alpha=16, dropout=0.05):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False                  # FROZEN

        d_out, d_in = base.weight.shape
        self.A = nn.Parameter(torch.empty(r, d_in))
        self.B = nn.Parameter(torch.zeros(d_out, r))
        nn.init.kaiming_uniform_(self.A, a=5 ** 0.5)
        # B starts at ZERO, so BA = 0 and the adapted model is EXACTLY the
        # base model at step 0. Training starts from a known-good point
        # instead of perturbing a trained network randomly.

        self.scale   = alpha / r
        self.dropout = nn.Dropout(dropout)

    def forward(self, x):
        return self.base(x) + self.dropout(x) @ self.A.T @ self.B.T * self.scale


# The arithmetic that makes it worth it:
d_out = d_in = 4096
full = d_out * d_in                          # 16,777,216
lora = 8 * d_in + d_out * 8                  #     65,536   (r=8)
print(f"{full/lora:.0f}x fewer trainable parameters")   # 256x

Three details that get asked about:

  • B is initialised to zero. So the product BA is zero and the model starts out exactly equal to the base. Initialising both randomly would perturb a trained network before learning anything.
  • alpha/r is the scaling factor. It decouples the learning rate from the rank, so changing r does not require re-tuning everything. A common convention is alpha = 2r.
  • Which matrices to adapt. The original paper used the attention Q and V projections; current practice often targets all linear layers including the FFN, which costs more parameters and generally works better.

Why it is operationally good

The adapter is tens of megabytes rather than tens of gigabytes. That means you can keep many task-specific adapters over one base model and swap them per request, which is a genuinely different deployment story from hosting many fine-tuned models. And because W + BA is just a matrix, the adapter can be merged into the base weights after training for zero added inference latency — at the cost of losing the ability to swap it.

Interview angle

"Why does LoRA work?" — because the weight update needed to adapt behaviour has low intrinsic rank; you are not relearning language, you are nudging a model that already has the capability. Then give the operational consequence, which is the part that matters in practice: a 30 MB adapter per task over one shared base model, swappable per request, mergeable for zero inference overhead. Mentioning the zero-init of B shows you have read the implementation and not just the abstract.

QLoRA: NF4 and one GPU

LoRA removes the optimizer state. The frozen base model still has to sit in memory, and at fp16 a 7B model is 14 GB before activations — so a 24 GB consumer card is tight and a 70B is impossible. QLoRA quantizes the frozen base to 4 bits and trains the LoRA adapters in 16-bit on top.

Approach7B memoryFits on
Full fine-tune (Adam, fp32 states)~112 GBSeveral A100s
LoRA, fp16 base~16 GBOne A100 / 24 GB card, just
QLoRA, NF4 base~6 GBA consumer GPU

Three ideas make it work, and naming all three is the answer to "what is QLoRA?":

1 · NF4 — 4-bit NormalFloat. A data type whose 16 levels are placed at the quantiles of a normal distribution rather than spaced uniformly. Neural-network weights are approximately normally distributed, so information-theoretically optimal spacing for that distribution loses less than uniform INT4 does. This is the part people miss — NF4 is not "INT4 with a different name", it is a different placement of the levels.

2 · Double quantization. Quantization needs a scale factor per block. Those scales are themselves fp32 and add up, so QLoRA quantizes the scales too — saving roughly another 0.4 bits per parameter.

3 · Paged optimizers. Optimizer state is paged to CPU memory on a spike, so a long sequence does not kill the run with an out-of-memory error.

from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
import torch

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",            # NOT "fp4" -- quantile-spaced levels
    bnb_4bit_use_double_quant=True,       # quantize the scales too
    bnb_4bit_compute_dtype=torch.bfloat16,
    # ^ Weights are STORED in 4-bit and DEQUANTIZED to bf16 for each matmul.
    #   The arithmetic is never done in 4 bits. This is the detail people
    #   get wrong: QLoRA saves MEMORY, it does not do 4-bit math.
)

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B",
                                             quantization_config=bnb,
                                             device_map="auto")
model = prepare_model_for_kbit_training(model)

model = get_peft_model(model, LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05, bias="none",
    task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],   # attention + FFN
))
model.print_trainable_parameters()
# trainable: 41,943,040 || all: 8,072,204,288 || trainable%: 0.52
The thing to get right

The base model is stored in 4 bits and dequantized to bf16 for every matmul. No arithmetic happens at 4-bit precision. This is why QLoRA is slower per step than plain LoRA despite using less memory — you are paying dequantization on every forward pass — and saying so distinguishes understanding the mechanism from having read the headline.

Interview angle

"What does QLoRA quantize?" — the frozen base model, to NF4; the adapters stay in 16-bit because they are what you are training. Add the three components (NF4, double quantization, paged optimizers), the memory number (a 7B fine-tune in about 6 GB), and the trade (slower per step, because of dequantization). That is a complete answer in thirty seconds.

Preference tuning: RLHF and DPO

Instruction tuning teaches the model to answer. It does not teach it which of two reasonable answers is better — more helpful, better formatted, appropriately cautious. That requires comparisons, because "better" is far easier for a human to judge than to demonstrate.

RLHF

Three steps: collect preferences (humans rank model outputs), train a reward model to predict those preferences, then optimise the language model against that reward with reinforcement learning — PPO — with a KL penalty keeping it from drifting too far from the SFT model.

It works and it is complicated: three models in play (policy, reward, reference), RL training that is notoriously unstable, and reward hacking, where the policy finds outputs that score highly under the reward model without being better. Verbosity is the classic example — reward models reliably prefer longer answers, so unconstrained RLHF produces models that pad.

DPO

Direct Preference Optimization is the one to understand, because it is what most open fine-tuning now uses. The insight is that the RLHF objective has a closed-form optimal policy, and you can rearrange it so that the language model is implicitly its own reward model. No separate reward model, no RL loop — just a classification-style loss on preference pairs.

import torch.nn.functional as F

def dpo_loss(policy_chosen_logps, policy_rejected_logps,
             ref_chosen_logps,    ref_rejected_logps, beta=0.1):
    """One supervised-looking loss over (prompt, chosen, rejected) triples."""

    # How much MORE the policy prefers `chosen` than the reference does...
    chosen_rel   = policy_chosen_logps   - ref_chosen_logps
    # ...minus the same quantity for `rejected`.
    rejected_rel = policy_rejected_logps - ref_rejected_logps

    # Push the gap up. beta controls how far the policy may drift from the
    # reference -- it plays the role of the KL penalty in PPO.
    return -F.logsigmoid(beta * (chosen_rel - rejected_rel)).mean()

# The frozen reference model is why this is stable: the loss is defined
# RELATIVE to the SFT starting point, so the policy cannot wander into
# degenerate text that happens to score well.

Interview angle

The one-line distinction: "RLHF trains a separate reward model and optimises against it with RL; DPO shows that the optimal policy has a closed form, so you can train directly on preference pairs with the model acting as its own implicit reward model — no RL loop." Then mention reward hacking and the verbosity bias, because knowing the failure mode of a technique is better evidence of understanding than knowing the technique.

Knowing whether it worked

Fine-tuning without evaluation is guessing with a GPU bill. You need a baseline before you start, and the comparison has to be on data the model never saw.

What to measure

MeasureWhy
Task metric on a held-out setThe point of the exercise. Define it before training
The prompted baselineIf a good prompt on the base model matches your tune, you have wasted the work
General capabilityCatastrophic forgetting — did it get worse at everything else?
Format complianceOften the actual goal: does it now produce valid output every time?
Latency and costSometimes the real win — a tuned 3B replacing a prompted frontier model

The second row is the comparison people skip and it is the one that decides whether the project was worth doing. The honest baseline is a seriously-tried prompt on the base model, not the first thing you wrote.

The third row is the one that bites later. A model tuned hard on a narrow task degrades elsewhere, and if your eval set only covers the target task you will not see it until something else breaks in production. Keep a small general suite and run it every time.

def report(base_model, tuned_model, task_set, general_set):
    rows = {
        "task / base + prompt": evaluate(base_model,  task_set, prompt=BEST_PROMPT),
        "task / tuned":         evaluate(tuned_model, task_set),
        "general / base":       evaluate(base_model,  general_set),
        "general / tuned":      evaluate(tuned_model, general_set),   # forgetting
        "format / base":        format_ok(base_model,  task_set),
        "format / tuned":       format_ok(tuned_model, task_set),
    }
    for k, v in rows.items():
        print(f"{k:24s} {v:.3f}")

# A result that says "ship it":
#   task / base + prompt    0.71
#   task / tuned            0.89      <- clear gain over a SERIOUS baseline
#   general / base          0.80
#   general / tuned         0.78      <- small, acceptable forgetting
#   format / base           0.84
#   format / tuned          1.00      <- often the real prize

Overfitting, which happens fast

Fine-tuning datasets are small and LoRA converges quickly. One to three epochs is usually right; beyond that the model starts reproducing training examples rather than generalising. Watch validation loss and stop when it turns, and be suspicious of a training loss that goes very low — on a few thousand examples that means memorisation.

Interview angle

If a fine-tuning question comes up, close on measurement: "I'd define the metric and build the held-out set before training, compare against a seriously-tried prompt on the base model rather than against nothing, and keep a general suite to catch forgetting." The prompted-baseline point in particular signals that you would be willing to conclude the project was unnecessary — which is exactly the judgement the round is probing for.

Practice
  • Do one LoRA run on a 1–3B model with a few thousand examples, just to see the knobs move. The point is not the model; it is being able to speak concretely about rank, epochs, loss curves and how fast it overfits.
