Principles & Patterns Under Pressure

Six patterns cover almost every LLD prompt, and picking one is a response to a force in the design rather than a name you drop. Strategy and State do most of the work; constructor injection is what makes the result testable — and "how would you test this?" is asked in nearly every round.

The patterns that actually come up — and the ones that do not

There are twenty-three Gang of Four patterns. In an LLD interview you will use about six, and recognising which from the wording is most of the value. The others are worth knowing for a vocabulary question but are rarely the answer to "design a vending machine".

The C# & .NET patterns page covers the catalogue properly, with before/after code for each. This page is about selection under time pressure: which one the prompt is asking for, and how to apply it without over-engineering.

Two of those deserve a warning.

Singleton, and pattern-dropping

Singleton is the pattern candidates reach for most and interviewers like least. It is global mutable state: it makes testing hard, hides dependencies, and in a threaded design needs careful initialisation for no benefit. If there genuinely is one parking lot, say "the application constructs one ParkingLot and injects it" — same outcome, no global, and it is testable. Naming this trade-off unprompted is itself a good signal.

Pattern-dropping is the other failure: announcing "I'll use an abstract factory with a decorator" before there is a problem to solve. Patterns are a response to a force in the design. Describe the force first — "pricing varies independently of the rest, so I'll put it behind an interface" — and only then, optionally, name it. An interviewer who hears the force knows you understand the pattern; one who hears only the name does not.

Interview angle

The highest-value sentence in this round is "this varies independently, so it goes behind an interface", because it is the justification for Strategy, and Strategy is the answer to a large majority of LLD follow-ups. Get comfortable saying it and you will handle "now add X" calmly. Conversely, if you cannot articulate what force a pattern is relieving, do not use it — an unjustified pattern reads as cargo cult and costs you more than the plain code would have. The honest position "a conditional is fine here, there is only one axis of change" is a strong answer when it is true.

Practice
  • For each of the six core patterns, write the one sentence of wording that signals it. Then check yourself against the prompts in the worked designs on this site.
  • Find a Singleton in code you have written and rewrite it as an injected instance. Note what became testable.

Strategy: the workhorse

If you learn one pattern for this round, learn this one. A strategy turns a policy that varies into an object you can swap, and nearly every LLD follow-up question — "now pricing is hourly", "now pick the nearest spot", "now evict by frequency" — becomes "I add one small class" instead of "I edit the core".

The shape is trivial: an interface with one method, implementations that hold no state they do not need, and a holder that takes it through the constructor. The judgement is in choosing the right method signature — it should take exactly what every implementation needs and nothing more, because a strategy that needs the whole world back is a sign the split is in the wrong place.

// The seam. One method; the parameters are what EVERY implementation needs.
public interface IPricingStrategy
{
    Money Price(Ticket ticket, DateTime now);
}

// Implementation 1: flat hourly, part hours rounded up.
public sealed class FlatHourlyPricing(decimal perHour) : IPricingStrategy
{
    public Money Price(Ticket ticket, DateTime now)
    {
        var hours = Math.Ceiling(ticket.Duration(now).TotalHours);
        return new Money(perHour * (decimal)Math.Max(1, hours));
    }
}

// Implementation 2: per vehicle type. The follow-up question, answered by
// ADDING this class — nothing else in the system changes.
public sealed class PerVehicleTypePricing(IReadOnlyDictionary<SpotSize, decimal> rates)
    : IPricingStrategy
{
    public Money Price(Ticket ticket, DateTime now)
    {
        var rate = rates[ticket.Spot.Size];
        var hours = Math.Ceiling(ticket.Duration(now).TotalHours);
        return new Money(rate * (decimal)Math.Max(1, hours));
    }
}

// Implementation 3: free for the first 15 minutes, then delegate. Strategies
// compose — this is Decorator applied to a Strategy, and it is a strong answer
// to "can you add a grace period?" because nothing else is touched.
public sealed class WithGracePeriod(IPricingStrategy inner, TimeSpan grace) : IPricingStrategy
{
    public Money Price(Ticket ticket, DateTime now) =>
        ticket.Duration(now) <= grace ? Money.Zero() : inner.Price(ticket, now);
}

// The holder depends on the INTERFACE and is constructed with an implementation.
public sealed class ParkingLot(IPricingStrategy pricing /* , ... */)
{
    public Money Leave(string ticketId, DateTime now)
    {
        var ticket = Find(ticketId);
        var fee = pricing.Price(ticket, now);     // no conditional, ever
        ticket.Close(now, fee);
        ticket.Spot.Release();
        return fee;
    }
}

// Wiring, at the composition root:
//   var lot = new ParkingLot(new WithGracePeriod(
//       new PerVehicleTypePricing(rates), TimeSpan.FromMinutes(15)));
from abc import ABC, abstractmethod
from datetime import datetime, timedelta
import math

class PricingStrategy(ABC):
    @abstractmethod
    def price(self, ticket: "Ticket", now: datetime) -> "Money": ...

class FlatHourlyPricing(PricingStrategy):
    def __init__(self, per_hour: float) -> None:
        self._per_hour = per_hour

    def price(self, ticket: "Ticket", now: datetime) -> "Money":
        hours = max(1, math.ceil(ticket.duration(now).total_seconds() / 3600))
        return Money(self._per_hour * hours)

class PerVehicleTypePricing(PricingStrategy):
    """The follow-up question, answered by ADDING a class."""
    def __init__(self, rates: dict["SpotSize", float]) -> None:
        self._rates = rates

    def price(self, ticket: "Ticket", now: datetime) -> "Money":
        hours = max(1, math.ceil(ticket.duration(now).total_seconds() / 3600))
        return Money(self._rates[ticket.spot.size] * hours)

class WithGracePeriod(PricingStrategy):
    """Decorator over a Strategy: strategies compose."""
    def __init__(self, inner: PricingStrategy, grace: timedelta) -> None:
        self._inner, self._grace = inner, grace

    def price(self, ticket: "Ticket", now: datetime) -> "Money":
        if ticket.duration(now) <= self._grace:
            return Money(0.0)
        return self._inner.price(ticket, now)

class ParkingLot:
    def __init__(self, pricing: PricingStrategy) -> None:
        self._pricing = pricing               # depends on the INTERFACE

    def leave(self, ticket_id: str, now: datetime) -> "Money":
        ticket = self._find(ticket_id)
        fee = self._pricing.price(ticket, now)   # no conditional, ever
        ticket.close(now, fee)
        ticket.spot.release()
        return fee

# Wiring, at the composition root:
#   lot = ParkingLot(WithGracePeriod(PerVehicleTypePricing(rates),
#                                    timedelta(minutes=15)))
Strategy versus a plain function

In both C# and Python a strategy with a single method can be a delegate (Func<Ticket, DateTime, Money>) or a plain callable. That is often the better engineering choice, and saying so shows range. Prefer the named interface when the strategy needs several related methods, when implementations carry configuration worth naming, or when you want the type name to document intent in the constructor signature — all three are usually true in an interview, which is why the interface is the default here. Prefer the function when it is genuinely one-off.

Interview angle

Expect to be asked where the strategy is chosen. The answer you want is "at the composition root — whoever builds the ParkingLot decides", because it keeps the lot ignorant of the catalogue of policies. If selection must happen at runtime (different pricing per floor, per customer tier), do not put a switch back into the lot: inject a small resolver, or key a dictionary of strategies. The anti-pattern to avoid out loud is a strategy interface whose implementations are chosen by a conditional inside the class that was supposed to be decoupled from them — it is a surprisingly common way to get all the ceremony and none of the benefit.

Practice
  • Add a "first 15 minutes free" rule to a design two ways: inside the pricing class, and as a decorator. Say which you would defend and why.
  • Write a strategy whose method signature is wrong — it needs the whole ParkingLot back — and work out what that tells you about the split.

State machines: the second most useful shape

Whenever a prompt says an object "can only do X when it is in Y", you have a state machine, and modelling it explicitly is worth a lot of credit. Vending machines, elevators, orders, parking tickets and document workflows are all this shape.

There are two legitimate implementations and you should be able to pick between them. A transition table is compact, easy to validate and easy to print — good when the states have little behaviour of their own. The State pattern — one class per state, each knowing which events it accepts — is better when each state behaves differently, and it is what interviewers usually mean when they ask about a vending machine.

// --- Option A: an explicit transition table. ---------------------------
// Compact, trivially testable, and the whole machine is visible at a glance.
public enum OrderState { Created, Paid, Shipped, Delivered, Cancelled }
public enum OrderEvent { Pay, Ship, Deliver, Cancel }

public sealed class Order
{
    private static readonly Dictionary<(OrderState, OrderEvent), OrderState> Transitions = new()
    {
        [(OrderState.Created,  OrderEvent.Pay)]     = OrderState.Paid,
        [(OrderState.Created,  OrderEvent.Cancel)]  = OrderState.Cancelled,
        [(OrderState.Paid,     OrderEvent.Ship)]    = OrderState.Shipped,
        [(OrderState.Paid,     OrderEvent.Cancel)]  = OrderState.Cancelled,
        [(OrderState.Shipped,  OrderEvent.Deliver)] = OrderState.Delivered,
        // Anything absent is illegal — the table IS the specification.
    };

    public OrderState State { get; private set; } = OrderState.Created;

    public void Handle(OrderEvent e)
    {
        if (!Transitions.TryGetValue((State, e), out var next))
            throw new InvalidOperationException($"Cannot {e} an order that is {State}.");
        State = next;
    }
}

// --- Option B: the State pattern. --------------------------------------
// One class per state. Prefer this when states have DIFFERENT behaviour,
// not just different legal transitions.
public interface IVendingState
{
    IVendingState InsertCoin(VendingMachine m, Money coin);
    IVendingState SelectItem(VendingMachine m, string code);
    IVendingState Dispense(VendingMachine m);
}

public sealed class IdleState : IVendingState
{
    public IVendingState InsertCoin(VendingMachine m, Money coin)
    {
        m.AddCredit(coin);
        return new HasCreditState();                 // transition
    }
    // Illegal here, and the compiler cannot help — so throw loudly.
    public IVendingState SelectItem(VendingMachine m, string code) =>
        throw new InvalidOperationException("Insert a coin first.");
    public IVendingState Dispense(VendingMachine m) =>
        throw new InvalidOperationException("Nothing selected.");
}

public sealed class HasCreditState : IVendingState
{
    public IVendingState InsertCoin(VendingMachine m, Money coin)
    {
        m.AddCredit(coin);
        return this;                                 // self-transition
    }
    public IVendingState SelectItem(VendingMachine m, string code)
    {
        var item = m.Inventory.Require(code);
        if (m.Credit.Amount < item.Price.Amount)
            return this;                             // not enough: stay put
        m.Select(item);
        return new DispensingState();
    }
    public IVendingState Dispense(VendingMachine m) =>
        throw new InvalidOperationException("Select an item first.");
}

// The machine just delegates and stores whatever comes back.
public sealed class VendingMachine
{
    private IVendingState _state = new IdleState();
    public void InsertCoin(Money c) => _state = _state.InsertCoin(this, c);
    public void SelectItem(string code) => _state = _state.SelectItem(this, code);
    public void Dispense() => _state = _state.Dispense(this);
}
from enum import Enum, auto
from abc import ABC, abstractmethod

# --- Option A: an explicit transition table. ---------------------------
class OrderState(Enum):
    CREATED = auto(); PAID = auto(); SHIPPED = auto()
    DELIVERED = auto(); CANCELLED = auto()

class OrderEvent(Enum):
    PAY = auto(); SHIP = auto(); DELIVER = auto(); CANCEL = auto()

TRANSITIONS = {
    (OrderState.CREATED, OrderEvent.PAY):     OrderState.PAID,
    (OrderState.CREATED, OrderEvent.CANCEL):  OrderState.CANCELLED,
    (OrderState.PAID,    OrderEvent.SHIP):    OrderState.SHIPPED,
    (OrderState.PAID,    OrderEvent.CANCEL):  OrderState.CANCELLED,
    (OrderState.SHIPPED, OrderEvent.DELIVER): OrderState.DELIVERED,
    # Anything absent is illegal — the table IS the specification.
}

class Order:
    def __init__(self) -> None:
        self.state = OrderState.CREATED

    def handle(self, event: OrderEvent) -> None:
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None:
            raise RuntimeError(f"Cannot {event.name} an order that is {self.state.name}.")
        self.state = nxt

# --- Option B: the State pattern. --------------------------------------
class VendingState(ABC):
    @abstractmethod
    def insert_coin(self, m: "VendingMachine", coin) -> "VendingState": ...
    @abstractmethod
    def select_item(self, m: "VendingMachine", code: str) -> "VendingState": ...
    @abstractmethod
    def dispense(self, m: "VendingMachine") -> "VendingState": ...

class IdleState(VendingState):
    def insert_coin(self, m, coin):
        m.add_credit(coin)
        return HasCreditState()                      # transition
    def select_item(self, m, code):
        raise RuntimeError("Insert a coin first.")
    def dispense(self, m):
        raise RuntimeError("Nothing selected.")

class HasCreditState(VendingState):
    def insert_coin(self, m, coin):
        m.add_credit(coin)
        return self                                  # self-transition
    def select_item(self, m, code):
        item = m.inventory.require(code)
        if m.credit < item.price:
            return self                              # not enough: stay put
        m.select(item)
        return DispensingState()
    def dispense(self, m):
        raise RuntimeError("Select an item first.")

class VendingMachine:
    def __init__(self) -> None:
        self._state: VendingState = IdleState()
    def insert_coin(self, coin): self._state = self._state.insert_coin(self, coin)
    def select_item(self, code): self._state = self._state.select_item(self, code)
    def dispense(self):          self._state = self._state.dispense(self)

Interview angle

Say the words "this is a state machine" as soon as you spot it — it is a recognition signal interviewers listen for. Then enumerate the illegal transitions explicitly, because that is where the thinking shows: "you cannot dispense before selecting, and you cannot select with no credit, so both throw." A design that silently ignores illegal events looks identical to one that handles them, right up until the interviewer asks what happens if you press dispense twice. Have an answer for whether illegal events throw, return false, or are no-ops — any of the three is defensible, but you should have chosen on purpose.

Practice
  • Draw the vending machine states and every legal transition, then list the illegal ones and say what each does.
  • Implement an order flow as a transition table, then convert it to the State pattern, and say which you prefer for that problem.
  • Add a "refunding" state to the vending machine both ways and compare how much code changed.

Dependency injection and testability

"How would you test this?" is asked in most LLD rounds and answered badly in most of them. The answer is not a testing framework — it is that your design already has the seams, because every collaborator came in through the constructor rather than being constructed inside.

Two dependencies make code untestable more often than anything else, and both have the same cure: the clock and randomness. A method that calls DateTime.Now inside cannot be tested for "what happens after two hours" without actually waiting. Pass time in, or inject a clock.

// UNTESTABLE — three hidden dependencies: the clock, the id generator, and
// a concrete pricing policy constructed on the spot.
public class BadParkingLot
{
    public Ticket Park(Vehicle v)
    {
        var spot = FindSpot(v);
        return new Ticket(Guid.NewGuid().ToString(),     // hidden: randomness
                          spot,
                          DateTime.Now);                  // hidden: the clock
    }
    public Money Leave(string id, DateTime now) =>
        new FlatHourlyPricing(10m).Price(Find(id), now);  // hidden: policy
}

// TESTABLE — every dependency is visible in the constructor signature,
// which doubles as documentation of what this class actually needs.
public interface IClock { DateTime Now { get; } }
public sealed class SystemClock : IClock { public DateTime Now => DateTime.UtcNow; }

public sealed class ParkingLot(
    IReadOnlyList<Floor> floors,
    ISpotAllocationStrategy allocation,
    IPricingStrategy pricing,
    IClock clock,
    Func<string> newTicketId)
{
    public Ticket Park(Vehicle vehicle)
    {
        var spot = allocation.Find(floors, vehicle)
                   ?? throw new InvalidOperationException("Lot full.");
        if (!spot.TryOccupy(vehicle))
            throw new InvalidOperationException("Spot taken concurrently.");
        return new Ticket(newTicketId(), spot, clock.Now);
    }
}

// The test writes itself, and runs in microseconds.
public sealed class FakeClock(DateTime start) : IClock
{
    public DateTime Now { get; private set; } = start;
    public void Advance(TimeSpan by) => Now += by;
}

// public void Charges_two_hours_for_a_two_hour_stay()

//     var ticket = lot.Park(new Car("KA-01"));

from datetime import datetime, timedelta
from typing import Callable, Protocol
import uuid

# UNTESTABLE — the clock, the id source and the policy are all hidden.
class BadParkingLot:
    def park(self, vehicle):
        spot = self._find_spot(vehicle)
        return Ticket(str(uuid.uuid4()),      # hidden: randomness
                      spot,
                      datetime.now())          # hidden: the clock

# TESTABLE — every dependency is visible in __init__.
class Clock(Protocol):
    def now(self) -> datetime: ...

class SystemClock:
    def now(self) -> datetime:
        return datetime.utcnow()

class FakeClock:
    def __init__(self, start: datetime) -> None:
        self._now = start
    def now(self) -> datetime:
        return self._now
    def advance(self, by: timedelta) -> None:
        self._now += by

class ParkingLot:
    def __init__(self, floors, allocation, pricing,
                 clock: Clock, new_ticket_id: Callable[[], str]) -> None:
        self._floors = floors
        self._allocation = allocation
        self._pricing = pricing
        self._clock = clock
        self._new_ticket_id = new_ticket_id

    def park(self, vehicle) -> "Ticket":
        spot = self._allocation.find(self._floors, vehicle)
        if spot is None:
            raise RuntimeError("Lot full.")
        if not spot.try_occupy(vehicle):
            raise RuntimeError("Spot taken concurrently.")
        return Ticket(self._new_ticket_id(), spot, self._clock.now())

What to say when asked "how would you test this?"

Name three layers, briefly:

  1. Unit — the invariants, directly. "A ticket cannot be closed twice." "A spot cannot be occupied by two vehicles." These are the tests that justify your rich domain objects.
  2. Policy — each strategy in isolation, with a fake clock. Pricing is pure arithmetic once time is injected, so it is the easiest thing in the system to test exhaustively.
  3. Flow — one end-to-end test per use case: park, wait, leave, pay. These catch wiring mistakes that unit tests cannot.

Then add the concurrency sentence: "and I would have a test that spawns N threads all trying to take the last spot, and asserts exactly one wins." That one is memorable because almost nobody mentions it.

Interview angle

Constructor injection is the point, not a DI container — if you start talking about container registration you have drifted out of the round. The signal is simply that a reader can see every dependency a class has by looking at its constructor, and that a test can therefore substitute any of them. When an interviewer pushes with "that is a lot of constructor parameters", that is a real critique and there is a real answer: too many parameters usually means the class has too many responsibilities, so either it should be split, or several parameters are really one concept that deserves its own type.

Practice
  • Take any class you have written that calls DateTime.Now and inject a clock. Write the test that was impossible before.
  • Count the constructor parameters in your parking lot. If it is more than five, find the two that belong together as one type.
  • Write the "N threads race for the last spot" test and run it a thousand times.
