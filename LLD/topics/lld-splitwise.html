Design Splitwise

An expense splitter, where the obvious model is instructively wrong: keep an append-only history and a derived pairwise balance, never use floats for money, make every split sum exactly — and when asked to settle up, say "NP-hard" before you say "greedy".

Requirements, and the modelling decision that defines the design

Splitwise is asked because the obvious model is wrong in an instructive way. The naive design keeps a list of expenses and recomputes who owes whom on demand; the good design keeps a net balance between every pair and updates it as expenses arrive. Both are defensible, and knowing the trade-off is the point.

Never use floating point for money

Say this in the first two minutes. 0.1 + 0.2 != 0.3 in IEEE 754, and over thousands of splits the error is visible and unexplainable to users. Use integer cents (or C#'s decimal, which is base-10 and exact for this range). It also makes the remainder problem explicit: splitting 100 cents three ways is 34/33/33, not 33.33 each, and someone has to get the extra cent. Deciding who — deterministically, usually the payer or the first participant in a stable order — is a small detail interviewers notice because it means you thought about the sum having to come out exactly right.

Interview angle

Lead with the balance-versus-history distinction, because it reframes the whole problem: "I will keep an append-only list of expenses for history, and a derived pairwise net balance for queries, because 'what do I owe Alice?' should not be a scan over every expense ever." That is a materialised view over an event log, which is a genuinely transferable idea and connects this round to the system design one. The second thing to volunteer is cents-not-floats, with the remainder rule. Those two sentences front-load most of the credit available in this problem.

The model: expenses in, balances out

The key structural choice is that a balance is directional and antisymmetric: if Alice owes Bob 500, then Bob owes Alice −500. Storing both directions invites them to disagree, so store one canonical direction and negate on read. That one decision removes an entire class of bug.

The invariant that catches every bug in this problem

The sum of all balances is always zero, and every split sums exactly to the expense. Both are cheap to assert and between them they catch rounding errors, double-counting, and asymmetric updates. Say you would assert them after every mutation in debug builds — it is the kind of answer that shows you have debugged money code before, and it gives you an obvious thing to test.

The implementation

The split strategies first — they carry the remainder logic, which is where the subtlety is — then the book.

public readonly record struct Split(string Participant, long AmountCents);

public sealed record Expense(
    string Id, string Description, string PaidBy,
    long AmountCents, IReadOnlyList<Split> Shares);

public interface ISplitStrategy
{
    IReadOnlyList<Split> Split(long amountCents, IReadOnlyList<string> participants,
                               IReadOnlyList<long>? args = null);
}

/// Equal split. The remainder goes to the first participants, one cent each,
/// so the portions ALWAYS sum exactly to the amount.
public sealed class EqualSplit : ISplitStrategy
{
    public IReadOnlyList<Split> Split(long amount, IReadOnlyList<string> people,
                                      IReadOnlyList<long>? _ = null)
    {
        if (people.Count == 0) throw new ArgumentException("No participants.");
        long each = amount / people.Count;
        long remainder = amount - each * people.Count;   // 0 .. people.Count-1
        return people.Select((p, i) =>
            new Split(p, each + (i < remainder ? 1 : 0))).ToList();
    }
}

/// Exact amounts supplied by the caller. Rejected unless they sum exactly.
public sealed class ExactSplit : ISplitStrategy
{
    public IReadOnlyList<Split> Split(long amount, IReadOnlyList<string> people,
                                      IReadOnlyList<long>? amounts = null)
    {
        ArgumentNullException.ThrowIfNull(amounts);
        if (amounts.Count != people.Count) throw new ArgumentException("Length mismatch.");
        if (amounts.Sum() != amount)
            throw new ArgumentException($"Shares sum to {amounts.Sum()}, expected {amount}.");
        return people.Zip(amounts, (p, a) => new Split(p, a)).ToList();
    }
}

/// Weights: [2,1,1] splits 4:1:1... no — 2 parts, 1 part, 1 part of the total.
/// Largest-remainder apportionment, so the parts still sum exactly.
public sealed class ShareSplit : ISplitStrategy
{
    public IReadOnlyList<Split> Split(long amount, IReadOnlyList<string> people,
                                      IReadOnlyList<long>? weights = null)
    {
        ArgumentNullException.ThrowIfNull(weights);
        if (weights.Count != people.Count) throw new ArgumentException("Length mismatch.");
        long total = weights.Sum();
        if (total <= 0) throw new ArgumentException("Weights must be positive.");

        var floors = weights.Select(w => amount * w / total).ToArray();
        long distributed = floors.Sum();
        long remainder = amount - distributed;

        // Give the leftover cents to the largest fractional parts first.
        var order = Enumerable.Range(0, people.Count)
            .OrderByDescending(i => amount * weights[i] % total)
            .ThenBy(i => i)                             // deterministic tie-break
            .ToArray();
        for (int k = 0; k < remainder; k++) floors[order[k]]++;

        return people.Select((p, i) => new Split(p, floors[i])).ToList();
    }
}

public sealed class ExpenseBook
{
    private readonly List<Expense> _expenses = [];
    private readonly Dictionary<(string, string), long> _balances = [];
    private int _nextId;

    public IReadOnlyList<Expense> Expenses => _expenses;

    private static (string, string) Key(string a, string b) =>
        string.CompareOrdinal(a, b) <= 0 ? (a, b) : (b, a);

    /// Positive result: 'debtor' owes 'creditor' that many cents.
    public long Owes(string debtor, string creditor)
    {
        var key = Key(debtor, creditor);
        long v = _balances.GetValueOrDefault(key);
        return key.Item1 == debtor ? v : -v;            // antisymmetric on read
    }

    public Expense Add(string description, string paidBy, long amountCents,
                       IReadOnlyList<string> participants,
                       ISplitStrategy strategy, IReadOnlyList<long>? args = null)
    {
        if (amountCents <= 0) throw new ArgumentException("Amount must be positive.");
        var shares = strategy.Split(amountCents, participants, args);
        if (shares.Sum(s => s.AmountCents) != amountCents)
            throw new InvalidOperationException("Split does not sum to the amount.");

        var expense = new Expense($"E{++_nextId}", description, paidBy, amountCents, shares);
        _expenses.Add(expense);
        Apply(expense, +1);
        return expense;
    }

    /// Reverse an expense. History is append-only, so we do not delete —
    /// we apply the inverse, which keeps the audit trail intact.
    public void Reverse(string expenseId)
    {
        var expense = _expenses.SingleOrDefault(e => e.Id == expenseId)
                      ?? throw new ArgumentException($"No expense {expenseId}.");
        Apply(expense, -1);
    }

    private void Apply(Expense e, int sign)
    {
        foreach (var (participant, share) in e.Shares)
        {
            if (participant == e.PaidBy) continue;      // nobody owes themselves
            Adjust(participant, e.PaidBy, sign * share);
        }
    }

    private void Adjust(string debtor, string creditor, long cents)
    {
        var key = Key(debtor, creditor);
        long delta = key.Item1 == debtor ? cents : -cents;
        long next = _balances.GetValueOrDefault(key) + delta;
        if (next == 0) _balances.Remove(key);           // keep the map sparse
        else _balances[key] = next;
    }

    /// What one person owes (negative) or is owed (positive), net.
    public long NetBalance(string person) =>
        _balances.Sum(kv => kv.Key.Item1 == person ? -kv.Value
                          : kv.Key.Item2 == person ? kv.Value : 0);

    public IReadOnlyDictionary<string, long> AllNetBalances()
    {
        var net = new Dictionary<string, long>();
        foreach (var ((a, b), v) in _balances)
        {
            net[a] = net.GetValueOrDefault(a) - v;      // a owes v  -> a is down
            net[b] = net.GetValueOrDefault(b) + v;      // b is owed v
        }
        return net;
    }

    public void Settle(string debtor, string creditor, long cents) =>
        Adjust(debtor, creditor, -cents);
}
from __future__ import annotations
from dataclasses import dataclass
from typing import Protocol, Sequence

@dataclass(frozen=True)
class Split:
    participant: str
    amount_cents: int

@dataclass(frozen=True)
class Expense:
    id: str
    description: str
    paid_by: str
    amount_cents: int
    shares: tuple[Split, ...]

class SplitStrategy(Protocol):
    def split(self, amount_cents: int, participants: Sequence[str],
              args: Sequence[int] | None = None) -> list[Split]: ...

class EqualSplit:
    """Remainder goes to the first participants, one cent each, so the
    portions ALWAYS sum exactly to the amount."""
    def split(self, amount: int, people: Sequence[str],
              args: Sequence[int] | None = None) -> list[Split]:
        if not people:
            raise ValueError("No participants.")
        each, remainder = divmod(amount, len(people))
        return [Split(p, each + (1 if i < remainder else 0))
                for i, p in enumerate(people)]

class ExactSplit:
    def split(self, amount: int, people: Sequence[str],
              args: Sequence[int] | None = None) -> list[Split]:
        if args is None or len(args) != len(people):
            raise ValueError("Length mismatch.")
        if sum(args) != amount:
            raise ValueError(f"Shares sum to {sum(args)}, expected {amount}.")
        return [Split(p, a) for p, a in zip(people, args)]

class ShareSplit:
    """Weights, apportioned by largest remainder so parts sum exactly."""
    def split(self, amount: int, people: Sequence[str],
              args: Sequence[int] | None = None) -> list[Split]:
        if args is None or len(args) != len(people):
            raise ValueError("Length mismatch.")
        total = sum(args)
        if total <= 0:
            raise ValueError("Weights must be positive.")

        floors = [amount * w // total for w in args]
        remainder = amount - sum(floors)

        # Leftover cents go to the largest fractional parts first.
        order = sorted(range(len(people)),
                       key=lambda i: (-(amount * args[i] % total), i))
        for k in range(remainder):
            floors[order[k]] += 1
        return [Split(p, floors[i]) for i, p in enumerate(people)]

class ExpenseBook:
    def __init__(self) -> None:
        self.expenses: list[Expense] = []
        self._balances: dict[tuple[str, str], int] = {}
        self._next_id = 0

    @staticmethod
    def _key(a: str, b: str) -> tuple[str, str]:
        return (a, b) if a <= b else (b, a)

    def owes(self, debtor: str, creditor: str) -> int:
        """Positive: debtor owes creditor that many cents."""
        key = self._key(debtor, creditor)
        v = self._balances.get(key, 0)
        return v if key[0] == debtor else -v        # antisymmetric on read

    def add(self, description: str, paid_by: str, amount_cents: int,
            participants: Sequence[str], strategy: SplitStrategy,
            args: Sequence[int] | None = None) -> Expense:
        if amount_cents <= 0:
            raise ValueError("Amount must be positive.")
        shares = strategy.split(amount_cents, participants, args)
        if sum(s.amount_cents for s in shares) != amount_cents:
            raise RuntimeError("Split does not sum to the amount.")

        self._next_id += 1
        expense = Expense(f"E{self._next_id}", description, paid_by,
                          amount_cents, tuple(shares))
        self.expenses.append(expense)
        self._apply(expense, +1)
        return expense

    def reverse(self, expense_id: str) -> None:
        """History is append-only: apply the inverse rather than deleting."""
        expense = next((e for e in self.expenses if e.id == expense_id), None)
        if expense is None:
            raise ValueError(f"No expense {expense_id}.")
        self._apply(expense, -1)

    def _apply(self, e: Expense, sign: int) -> None:
        for share in e.shares:
            if share.participant == e.paid_by:
                continue                            # nobody owes themselves
            self._adjust(share.participant, e.paid_by, sign * share.amount_cents)

    def _adjust(self, debtor: str, creditor: str, cents: int) -> None:
        key = self._key(debtor, creditor)
        delta = cents if key[0] == debtor else -cents
        nxt = self._balances.get(key, 0) + delta
        if nxt == 0:
            self._balances.pop(key, None)           # keep the map sparse
        else:
            self._balances[key] = nxt

    def net_balance(self, person: str) -> int:
        total = 0
        for (a, b), v in self._balances.items():
            if a == person: total -= v
            elif b == person: total += v
        return total

    def all_net_balances(self) -> dict[str, int]:
        net: dict[str, int] = {}
        for (a, b), v in self._balances.items():
            net[a] = net.get(a, 0) - v              # a owes v -> a is down
            net[b] = net.get(b, 0) + v              # b is owed v
        return net

    def settle(self, debtor: str, creditor: str, cents: int) -> None:
        self._adjust(debtor, creditor, -cents)
Interview angle

Point at EqualSplit's remainder line deliberately. divmod(amount, n) and then handing the leftover cents to the first remainder people is three lines, it is deterministic, and it guarantees the shares sum exactly — which is the invariant that keeps balances summing to zero. Candidates who write amount / n and move on have introduced money that quietly vanishes. The same reasoning scales up to ShareSplit, where the technique has a name (largest-remainder apportionment, the same method used to allocate parliamentary seats) and mentioning it is a nice flourish. Also note Reverse applies the inverse rather than deleting: an append-only history with compensating entries is how real ledgers work, and saying so is a transferable point.

Practice
  • Split 100 cents three ways and check the shares sum to 100, not 99.
  • Split 100 cents with weights [1,1,1] and then [2,1,1]; verify both sum exactly and the tie-break is deterministic.
  • Add an expense, reverse it, and assert every balance is back to zero and the map is empty.

Settle up: minimising the number of transactions

The classic follow-up. Given everyone's net balance, produce a set of payments that clears all debts with as few transactions as possible. Two things to say immediately:

  1. The pairwise balances do not matter here, only the net per person. If Alice owes Bob 10 and Bob owes Carol 10, Alice can simply pay Carol 10 — one transaction instead of two. Collapsing to net balances is the whole first insight.
  2. The exact minimum is NP-hard — it contains the partition problem, because any subset of people whose balances sum to zero can be settled among themselves. So the honest answer is a greedy heuristic that is optimal in the number of people (at most n−1 transactions) but not always in the true minimum.

The greedy: repeatedly match the largest creditor with the largest debtor, settle the smaller of the two amounts, repeat. At least one person is zeroed per transaction, so it terminates in at most n−1 payments.

public readonly record struct Payment(string From, string To, long Cents);

public static class Settlement
{
    /// Greedy: match the biggest debtor with the biggest creditor each round.
    /// At most n-1 payments. Not always the true minimum (that is NP-hard),
    /// but optimal in n and what every real app ships.
    public static IReadOnlyList<Payment> MinimalTransfers(
        IReadOnlyDictionary<string, long> netBalances)
    {
        // Positive = is owed; negative = owes. They must sum to zero.
        if (netBalances.Values.Sum() != 0)
            throw new ArgumentException("Balances do not sum to zero.");

        var debtors = new PriorityQueue<string, long>();    // most negative first
        var creditors = new PriorityQueue<string, long>();  // most positive first
        var owed = new Dictionary<string, long>(netBalances);

        foreach (var (person, amount) in netBalances)
        {
            if (amount < 0) debtors.Enqueue(person, amount);        // min-heap on amount
            else if (amount > 0) creditors.Enqueue(person, -amount);
        }

        var payments = new List<Payment>();
        while (debtors.Count > 0 && creditors.Count > 0)
        {
            var debtor = debtors.Dequeue();
            var creditor = creditors.Dequeue();

            long transfer = Math.Min(-owed[debtor], owed[creditor]);
            payments.Add(new Payment(debtor, creditor, transfer));

            owed[debtor] += transfer;
            owed[creditor] -= transfer;

            // Whoever is not yet square goes back in. At least one is zeroed.
            if (owed[debtor] < 0) debtors.Enqueue(debtor, owed[debtor]);
            if (owed[creditor] > 0) creditors.Enqueue(creditor, -owed[creditor]);
        }
        return payments;
    }
}
from __future__ import annotations
import heapq
from dataclasses import dataclass

@dataclass(frozen=True)
class Payment:
    frm: str
    to: str
    cents: int

def minimal_transfers(net_balances: dict[str, int]) -> list[Payment]:
    """Greedy: match the biggest debtor with the biggest creditor each round.
    At most n-1 payments. Not always the true minimum (that is NP-hard), but
    optimal in n and what every real app ships."""
    if sum(net_balances.values()) != 0:
        raise ValueError("Balances do not sum to zero.")

    owed = dict(net_balances)
    debtors = [(amt, p) for p, amt in net_balances.items() if amt < 0]
    creditors = [(-amt, p) for p, amt in net_balances.items() if amt > 0]
    heapq.heapify(debtors)      # most negative first
    heapq.heapify(creditors)    # most positive first (negated)

    payments: list[Payment] = []
    while debtors and creditors:
        _, debtor = heapq.heappop(debtors)
        _, creditor = heapq.heappop(creditors)

        transfer = min(-owed[debtor], owed[creditor])
        payments.append(Payment(debtor, creditor, transfer))

        owed[debtor] += transfer
        owed[creditor] -= transfer

        # Whoever is not yet square goes back. At least one is zeroed.
        if owed[debtor] < 0:
            heapq.heappush(debtors, (owed[debtor], debtor))
        if owed[creditor] > 0:
            heapq.heappush(creditors, (-owed[creditor], creditor))

    return payments
Why greedy is not optimal, with the smallest counterexample

Take net balances A: −10, B: −10, C: +10, D: +10. The true minimum is two payments (A→C 10, B→D 10). The largest-first greedy also finds two here, but add A: −15, B: −5, C: +10, D: +10: greedy pairs A with C (10), leaving A −5, then A with D (5), then B with D (5) — three payments, where A→C 10, A→D 5, B→D 5 is also three but A: −15, B: −5 against C: +10, D: +10 genuinely needs three. The real wins come from spotting subsets that sum to zero and settling them internally, and finding those subsets is exactly subset-sum. State that, say the exponential solution is O(2ⁿ) bitmask DP over subsets, and note that n in a friend group is small enough that it is actually tractable if anyone cared.

Interview angle

Say "NP-hard, so I will use a greedy that is optimal in n" — that is the sentence the follow-up is fishing for. Then prove termination out loud: each transaction zeroes at least one person, so it cannot exceed n−1. Interviewers are checking whether you will claim optimality you cannot deliver; candidates who confidently assert the greedy is minimal are marked down, and candidates who say "this is a heuristic, here is its bound, here is why exact is exponential" are marked up — even though the code is identical. This is the same honesty-about-bounds move as the greedy-coin discussion on the vending machine page, and it comes up constantly.
