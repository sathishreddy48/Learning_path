Design a Vending Machine

The canonical State-pattern prompt, and secretly two problems: a state machine whose illegal transitions you must choose on purpose, and a change-making algorithm where greedy is wrong in two different ways once the coin float is finite.

Requirements, and why this one is really two problems

A vending machine is asked because it is a state machine with a real algorithm inside it. The state machine is the obvious half; the change-making is the half candidates forget until the interviewer asks "what if you cannot make exact change?" and the design has no answer.

You askTypical answerWhat it decides
Which coins/notes are accepted?A fixed denomination setChange-making operates over a known list
Must it give exact change?Yes, or refuse the saleA dispense can fail after payment — a whole state
Can the user cancel?Yes, full refundA cancel transition from most states
Does the machine track its own coin float?YesChange-making is bounded by stock, not infinite
Multiple items at once?No, one per transactionCuts a lot of complexity — take it
Restocking / operator mode?Nice to haveMention it; implement only if time

The states fall out immediately. Write them and the legal transitions on the board before any code — this is the one prompt where the diagram is genuinely worth the minutes.

Interview angle

Enumerate the illegal transitions out loud, not just the legal ones. Any candidate can draw three boxes and three arrows; the discriminating question is what happens when someone presses Dispense twice, and a design that silently no-ops is indistinguishable from one that throws until you ask. Decide and say it. The second thing to volunteer early is that a sale can fail after the money is in — out of stock, or no change available — because that is the requirement that forces a refund path through the state machine, and retrofitting it later is painful.

Practice
  • Draw the machine and label every illegal transition with what it does. Three minutes, from memory.
  • Decide what happens if the item runs out between select and dispense, and where in your design that is detected.

The state machine

One class per state, each returning the next state. The machine holds no transition logic at all — it delegates and stores whatever comes back, which is what keeps it from growing a switch.

The piece worth getting right is that the state object decides, the machine executes. A state never mutates the machine's state field; it returns a successor. That makes every transition visible at one line in the machine and makes the states trivially unit-testable.

public sealed record Item(string Code, string Name, int PriceCents);

public interface IVendingState
{
    string Name { get; }
    IVendingState InsertCoin(VendingMachine m, int cents);
    IVendingState Select(VendingMachine m, string code);
    IVendingState Dispense(VendingMachine m);
    IVendingState Cancel(VendingMachine m);
}

public sealed class IdleState : IVendingState
{
    public string Name => "Idle";
    public IVendingState InsertCoin(VendingMachine m, int cents)
    {
        m.AddCredit(cents);
        return new HasCreditState();
    }
    public IVendingState Select(VendingMachine m, string code) =>
        throw new InvalidOperationException("Insert a coin first.");
    public IVendingState Dispense(VendingMachine m) =>
        throw new InvalidOperationException("Nothing selected.");
    public IVendingState Cancel(VendingMachine m) => this;        // no-op
}

public sealed class HasCreditState : IVendingState
{
    public string Name => "HasCredit";

    public IVendingState InsertCoin(VendingMachine m, int cents)
    {
        m.AddCredit(cents);
        return this;                                              // self-transition
    }

    public IVendingState Select(VendingMachine m, string code)
    {
        var item = m.Inventory.Find(code);
        if (item is null) { m.Report($"Unknown code {code}."); return this; }
        if (m.Inventory.StockOf(code) == 0) { m.Report($"{item.Name} is sold out."); return this; }
        if (m.CreditCents < item.PriceCents)
        {
            m.Report($"Need {item.PriceCents - m.CreditCents} more cents.");
            return this;                                          // stay, keep credit
        }

        // Can we actually return the change? Check BEFORE committing the sale.
        var change = m.Bank.MakeChange(m.CreditCents - item.PriceCents);
        if (change is null)
        {
            m.Report("Cannot make exact change; refunding.");
            m.RefundAll();
            return new IdleState();
        }

        m.Hold(item, change);
        return new DispensingState();
    }

    public IVendingState Dispense(VendingMachine m) =>
        throw new InvalidOperationException("Select an item first.");

    public IVendingState Cancel(VendingMachine m)
    {
        m.RefundAll();
        return new IdleState();
    }
}

public sealed class DispensingState : IVendingState
{
    public string Name => "Dispensing";
    public IVendingState InsertCoin(VendingMachine m, int cents) =>
        throw new InvalidOperationException("Wait for the current sale to finish.");
    public IVendingState Select(VendingMachine m, string code) =>
        throw new InvalidOperationException("Already dispensing.");

    public IVendingState Dispense(VendingMachine m)
    {
        m.CompleteSale();          // commits stock, bank and change in one step
        return new IdleState();
    }

    // Too late: the sale is committed in Dispense, so cancelling here would
    // need a compensating action. Simplest defensible rule is to refuse.
    public IVendingState Cancel(VendingMachine m) =>
        throw new InvalidOperationException("Cannot cancel while dispensing.");
}
from __future__ import annotations
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass(frozen=True)
class Item:
    code: str
    name: str
    price_cents: int

class VendingState(ABC):
    name: str
    @abstractmethod
    def insert_coin(self, m: "VendingMachine", cents: int) -> "VendingState": ...
    @abstractmethod
    def select(self, m: "VendingMachine", code: str) -> "VendingState": ...
    @abstractmethod
    def dispense(self, m: "VendingMachine") -> "VendingState": ...
    @abstractmethod
    def cancel(self, m: "VendingMachine") -> "VendingState": ...

class IdleState(VendingState):
    name = "Idle"
    def insert_coin(self, m, cents):
        m.add_credit(cents)
        return HasCreditState()
    def select(self, m, code):
        raise RuntimeError("Insert a coin first.")
    def dispense(self, m):
        raise RuntimeError("Nothing selected.")
    def cancel(self, m):
        return self                                   # no-op

class HasCreditState(VendingState):
    name = "HasCredit"

    def insert_coin(self, m, cents):
        m.add_credit(cents)
        return self                                   # self-transition

    def select(self, m, code):
        item = m.inventory.find(code)
        if item is None:
            m.report(f"Unknown code {code}.")
            return self
        if m.inventory.stock_of(code) == 0:
            m.report(f"{item.name} is sold out.")
            return self
        if m.credit_cents < item.price_cents:
            m.report(f"Need {item.price_cents - m.credit_cents} more cents.")
            return self                               # stay, keep credit

        # Can we actually return the change? Check BEFORE committing.
        change = m.bank.make_change(m.credit_cents - item.price_cents)
        if change is None:
            m.report("Cannot make exact change; refunding.")
            m.refund_all()
            return IdleState()

        m.hold(item, change)
        return DispensingState()

    def dispense(self, m):
        raise RuntimeError("Select an item first.")

    def cancel(self, m):
        m.refund_all()
        return IdleState()

    name = "Dispensing"
    def insert_coin(self, m, cents):
        raise RuntimeError("Wait for the current sale to finish.")
    def select(self, m, code):
        raise RuntimeError("Already dispensing.")
    def dispense(self, m):
        m.complete_sale()        # commits stock, bank and change in one step
        return IdleState()
    def cancel(self, m):
        raise RuntimeError("Cannot cancel while dispensing.")
Check change before committing, not after

The ordering in Select is the part interviewers probe. It is tempting to deduct the price, dispense, and then try to make change — at which point you may have taken the money and have no way to return the remainder. Checking MakeChange first, while the transaction is still abortable, means the failure path is a clean full refund. This is the same reasoning as validating before mutating anywhere else, and saying so connects the toy problem to real practice.

Practice
  • Write a test for every illegal transition and assert the exact message.
  • Add a "exact change only" lamp that lights when the bank cannot make common change amounts. Where does it belong?

Making change: greedy, and when greedy is wrong

The algorithmic half. Given a set of denominations with limited stock, return a multiset of coins summing exactly to the change due, or fail. Two facts to have ready:

  1. Greedy (take the largest coin that fits, repeatedly) is not always correct. With coins {1, 3, 4} and 6 due, greedy gives 4+1+1 = three coins; the optimum is 3+3 = two. Greedy is provably optimal only for canonical systems, which real currencies happen to be — so greedy is fine for {1, 5, 10, 25}, and you should say why it is fine rather than assuming.
  2. Limited stock breaks greedy even on canonical systems. Suppose the float holds one quarter and three dimes, and 30 cents is due. Greedy takes the quarter, then cannot make the remaining 5 and gives up — even though 10+10+10 is sitting right there. That is not a suboptimal answer, it is no answer for an amount that was perfectly makeable. With bounded coins you need DP or backtracking to be correct.

So: implement greedy, say both caveats, and offer the DP as the correct-under-stock version. That sequence is worth far more than silently writing either one.

/// The machine's coin float. Denominations in cents, with counts.
public sealed class CoinBank(IDictionary<int, int> initial)
{
    private readonly SortedDictionary<int, int> _counts =
        new(initial.ToDictionary(kv => kv.Key, kv => kv.Value),
            Comparer<int>.Create((a, b) => b.CompareTo(a)));   // descending

    public int TotalCents => _counts.Sum(kv => kv.Key * kv.Value);

    public void Add(int cents, int n = 1) =>
        _counts[cents] = _counts.GetValueOrDefault(cents) + n;

    /// Greedy: correct for canonical systems with UNLIMITED stock.
    /// Returns null when it cannot make the amount exactly.
    public IReadOnlyDictionary<int, int>? MakeChangeGreedy(int amount)
    {
        if (amount == 0) return new Dictionary<int, int>();
        var take = new Dictionary<int, int>();
        foreach (var (coin, available) in _counts)
        {
            int n = Math.Min(amount / coin, available);
            if (n == 0) continue;
            take[coin] = n;
            amount -= coin * n;
        }
        return amount == 0 ? take : null;          // could not finish exactly
    }

    /// Correct under LIMITED stock: bounded-knapsack DP, one layer per
    /// denomination so the count of each coin is explicitly bounded.
    ///   dp[i, a] = fewest coins to make 'a' using the first i denominations.
    /// O(denominations x amount x maxCount) — tiny for a vending machine.
    public IReadOnlyDictionary<int, int>? MakeChange(int amount)
    {
        if (amount == 0) return new Dictionary<int, int>();

        var coins = _counts.Keys.ToArray();
        int n = coins.Length;
        const int Inf = int.MaxValue / 2;

        var dp = new int[n + 1, amount + 1];
        var take = new int[n + 1, amount + 1];   // how many of coin i-1 we took
        for (int i = 0; i <= n; i++)
            for (int a = 0; a <= amount; a++) dp[i, a] = Inf;
        dp[0, 0] = 0;

        for (int i = 1; i <= n; i++)
        {
            int coin = coins[i - 1], available = _counts[coin];
            for (int a = 0; a <= amount; a++)
            {
                int best = dp[i - 1, a], bestK = 0;
                for (int k = 1; k <= available && k * coin <= a; k++)
                {
                    int prev = dp[i - 1, a - k * coin];
                    if (prev + k < best) { best = prev + k; bestK = k; }
                }
                dp[i, a] = best;
                take[i, a] = bestK;
            }
        }

        if (dp[n, amount] >= Inf) return null;

        // Walk the layers back: each one says exactly how many it contributed.
        var result = new Dictionary<int, int>();
        for (int i = n, a = amount; i > 0; i--)
        {
            int k = take[i, a];
            if (k > 0) { result[coins[i - 1]] = k; a -= k * coins[i - 1]; }
        }
        return result;
    }

    public void Remove(IReadOnlyDictionary<int, int> coins)
    {
        foreach (var (coin, n) in coins)
        {
            if (_counts.GetValueOrDefault(coin) < n)
                throw new InvalidOperationException($"Not enough {coin}c coins.");
            _counts[coin] -= n;
        }
    }
}
from __future__ import annotations

class CoinBank:
    """The machine's coin float: denominations in cents, with counts."""

    def __init__(self, initial: dict[int, int]) -> None:
        self._counts = dict(initial)

    @property
    def total_cents(self) -> int:
        return sum(c * n for c, n in self._counts.items())

    def add(self, cents: int, n: int = 1) -> None:
        self._counts[cents] = self._counts.get(cents, 0) + n

    def make_change_greedy(self, amount: int) -> dict[int, int] | None:
        """Correct for canonical systems with UNLIMITED stock. None on failure."""
        if amount == 0:
            return {}
        take: dict[int, int] = {}
        for coin in sorted(self._counts, reverse=True):
            n = min(amount // coin, self._counts[coin])
            if n:
                take[coin] = n
                amount -= coin * n
        return take if amount == 0 else None

    def make_change(self, amount: int) -> dict[int, int] | None:
        """Correct under LIMITED stock: bounded-knapsack DP, one layer per
        denomination so each coin's count is explicitly bounded.
            dp[i][a] = fewest coins to make 'a' using the first i denominations.
        O(denominations x amount x max_count) — tiny for a vending machine.
        """
        if amount == 0:
            return {}

        coins = list(self._counts)
        n = len(coins)
        INF = float("inf")

        dp = [[INF] * (amount + 1) for _ in range(n + 1)]
        take = [[0] * (amount + 1) for _ in range(n + 1)]   # count of coin i-1
        dp[0][0] = 0

        for i, coin in enumerate(coins, start=1):
            available = self._counts[coin]
            for a in range(amount + 1):
                best, best_k = dp[i - 1][a], 0
                for k in range(1, available + 1):
                    if k * coin > a:
                        break
                    prev = dp[i - 1][a - k * coin]
                    if prev + k < best:
                        best, best_k = prev + k, k
                dp[i][a], take[i][a] = best, best_k

        if dp[n][amount] == INF:
            return None

        # Walk the layers back: each says exactly how many it contributed.
        result: dict[int, int] = {}
        a = amount
        for i in range(n, 0, -1):
            k = take[i][a]
            if k:
                result[coins[i - 1]] = k
                a -= k * coins[i - 1]
        return result

    def remove(self, coins: dict[int, int]) -> None:
        for coin, n in coins.items():
            if self._counts.get(coin, 0) < n:
                raise RuntimeError(f"Not enough {coin}c coins.")
            self._counts[coin] -= n
Greedy fails in two different ways — know which is which
  • Non-canonical denominations ({1,3,4}, amount 6): greedy returns a suboptimal but valid answer. You get change, just more coins than necessary.
  • Limited stock (one 25c and three 10c in the float, amount 30c): greedy takes the quarter, strands itself on 5c and returns no answer at all — for an amount 10+10+10 makes exactly. That is a correctness bug, not an efficiency one, and it is the one that matters in a vending machine.

Keeping these two straight is a real discriminator. Many candidates know "greedy coin change can be suboptimal" and stop there, missing that the stock constraint is the one their own design just introduced.

Interview angle

This is where the vending machine stops being a toy. Write greedy first — it is four lines and it is right for US or Euro coins — then say: "this is only optimal because the denominations are canonical, and it can fail outright once stock is limited, so the correct version is a bounded-knapsack DP." That one sentence links an LLD round to the knapsack family and shows you can tell an efficiency bug from a correctness bug. If they want the DP, the complexity is O(amount × total coins), which for a vending machine is trivially small — worth saying, because it justifies choosing correctness over cleverness.

Practice
  • Construct a stock level where greedy fails and the DP succeeds. Then write that as a test.
  • Work out why a one-array DP with a single parent pointer gets this wrong — the per-coin layer is not ceremony, it is what makes reconstruction respect the stock bound.
  • Extend make_change to prefer returning the machine's most plentiful coins, keeping scarce ones in the float.

The machine, and the follow-ups

The machine itself is small — it holds state, credit, inventory and bank, and delegates every event. The only logic it owns is committing a sale atomically.

public sealed class Inventory(IDictionary<string, (Item item, int count)> initial)
{
    private readonly Dictionary<string, (Item item, int count)> _stock = new(initial);
    public Item? Find(string code) => _stock.TryGetValue(code, out var e) ? e.item : null;
    public int StockOf(string code) => _stock.TryGetValue(code, out var e) ? e.count : 0;
    public void Take(string code)
    {
        var e = _stock[code];
        if (e.count == 0) throw new InvalidOperationException("Sold out.");
        _stock[code] = (e.item, e.count - 1);
    }
    public void Restock(string code, int n)
    {
        var e = _stock[code];
        _stock[code] = (e.item, e.count + n);
    }
}

public sealed class VendingMachine(Inventory inventory, CoinBank bank)
{
    private IVendingState _state = new IdleState();
    private readonly List<int> _inserted = [];
    private Item? _held;
    private IReadOnlyDictionary<int, int>? _heldChange;

    public Inventory Inventory { get; } = inventory;
    public CoinBank Bank { get; } = bank;
    public string State => _state.Name;
    public int CreditCents => _inserted.Sum();
    public List<string> Messages { get; } = [];

    // --- events: delegate, store the successor. No logic here. ---
    public void InsertCoin(int cents) => _state = _state.InsertCoin(this, cents);
    public void Select(string code)   => _state = _state.Select(this, code);
    public void Dispense()            => _state = _state.Dispense(this);
    public void Cancel()              => _state = _state.Cancel(this);

    // --- operations the states call back into ---
    internal void AddCredit(int cents) => _inserted.Add(cents);
    internal void Report(string msg) => Messages.Add(msg);

    internal void Hold(Item item, IReadOnlyDictionary<int, int> change)
    {
        _held = item;
        _heldChange = change;
    }

    internal void RefundAll()
    {
        _inserted.Clear();
        _held = null;
        _heldChange = null;
    }

    /// Commit: stock out, coins in, change out — all or nothing.
    internal void CompleteSale()
    {
        var item = _held ?? throw new InvalidOperationException("Nothing held.");
        var change = _heldChange!;

        Inventory.Take(item.Code);
        foreach (var c in _inserted) Bank.Add(c);     // the user's coins join the float
        Bank.Remove(change);                           // change leaves it

        Report($"Dispensed {item.Name}; change {change.Sum(kv => kv.Key * kv.Value)}c.");
        _inserted.Clear();
        _held = null;
        _heldChange = null;
    }
}
class Inventory:
    def __init__(self, initial: dict[str, tuple[Item, int]]) -> None:
        self._stock = dict(initial)
    def find(self, code: str) -> Item | None:
        entry = self._stock.get(code)
        return entry[0] if entry else None
    def stock_of(self, code: str) -> int:
        entry = self._stock.get(code)
        return entry[1] if entry else 0
    def take(self, code: str) -> None:
        item, count = self._stock[code]
        if count == 0:
            raise RuntimeError("Sold out.")
        self._stock[code] = (item, count - 1)
    def restock(self, code: str, n: int) -> None:
        item, count = self._stock[code]
        self._stock[code] = (item, count + n)

class VendingMachine:
    def __init__(self, inventory: Inventory, bank: CoinBank) -> None:
        self.inventory = inventory
        self.bank = bank
        self.messages: list[str] = []
        self._state: VendingState = IdleState()
        self._inserted: list[int] = []
        self._held: Item | None = None
        self._held_change: dict[int, int] | None = None

    @property
    def state(self) -> str: return self._state.name
    @property
    def credit_cents(self) -> int: return sum(self._inserted)

    # --- events: delegate, store the successor. No logic here. ---
    def insert_coin(self, cents: int) -> None: self._state = self._state.insert_coin(self, cents)
    def select(self, code: str) -> None:       self._state = self._state.select(self, code)
    def dispense(self) -> None:                self._state = self._state.dispense(self)
    def cancel(self) -> None:                  self._state = self._state.cancel(self)

    # --- operations the states call back into ---
    def add_credit(self, cents: int) -> None: self._inserted.append(cents)
    def report(self, msg: str) -> None: self.messages.append(msg)

    def hold(self, item: Item, change: dict[int, int]) -> None:
        self._held, self._held_change = item, change

    def refund_all(self) -> None:
        self._inserted.clear()
        self._held = self._held_change = None

    def complete_sale(self) -> None:
        """Commit: stock out, coins in, change out — all or nothing."""
        if self._held is None or self._held_change is None:
            raise RuntimeError("Nothing held.")
        item, change = self._held, self._held_change

        self.inventory.take(item.code)
        for c in self._inserted:
            self.bank.add(c)                      # the user's coins join the float
        self.bank.remove(change)                  # change leaves it

        given = sum(c * n for c, n in change.items())
        self.report(f"Dispensed {item.name}; change {given}c.")
        self._inserted.clear()
        self._held = self._held_change = None
Follow-upThe answer
"Cannot make exact change"Already handled: checked before committing, full refund
"Add card payment"An IPaymentMethod seam; coins become one implementation
"Operator restocks and empties the float"A maintenance state, plus restock/collect operations
"Two people use it at once"Physically impossible for one machine — but say it: a lock around the event methods, or a single-threaded event loop
"Make it a bank of machines with shared stock"Now stock is contended and you need the same CAS reasoning as the parking lot
"Prices change at runtime"Item is a value object, so replace it; or a pricing strategy if it varies by time of day
Interview angle

Two things to volunteer at the end. First, CompleteSale is the transaction boundary — stock, float and change all move together, and if any step could fail you would need them ordered so that the recoverable failure happens first. Naming a transaction boundary in a design with no database is exactly the kind of transfer interviewers are looking for. Second, the concurrency answer here is "don't": one physical machine has one user, so a lock around the four event methods is both sufficient and honest. Candidates sometimes invent elaborate concurrency for this problem; recognising that the domain does not need it is the better answer, and it is a different skill from being able to build it.

Practice
  • Drive the machine through: insert 100, select a 65c item with the bank holding only 25c coins. Check you get a refund, not a half-sale.
  • Add a maintenance mode and work out which transitions it must block.
  • Make CompleteSale fail halfway (stock taken, change unavailable) and decide how you would make it safe.
