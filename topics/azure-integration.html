API Management: gateway, products and subscriptions

API Management is a managed gateway: import an OpenAPI spec, group operations into products, hand out subscription keys or validate JWTs, and apply policies (rate limits, caching, rewriting) without touching the backend. Tiers: Consumption (serverless, per-call), Basic v2/Standard v2 (fast provisioning), Developer/Premium (VNet, multi-region, self-hosted gateway).

# Create an instance (v2 tiers provision in minutes; classic Developer/Premium take ~45 min)
az apim create -g rg-shop -n apim-shop --publisher-email api@contoso.com --publisher-name Contoso --sku-name StandardV2

# Import the API from the running service's OpenAPI document
az apim api import -g rg-shop --service-name apim-shop --api-id orders --path orders   --specification-format OpenApiJson --specification-url https://shop-api.azurewebsites.net/swagger/v1/swagger.json   --service-url https://shop-api.azurewebsites.net

# Product = a bundle of APIs with its own access rules and quota
az apim product create -g rg-shop --service-name apim-shop --product-id partners --product-name "Partner APIs"   --subscription-required true --approval-required true --state published
az apim product api add -g rg-shop --service-name apim-shop --product-id partners --api-id orders

# Backend, named values (secrets from Key Vault) and the developer portal
az apim nv create -g rg-shop --service-name apim-shop --named-value-id backend-key --display-name backend-key --secret true --value "<key>"

Policies: the part you will actually write

Policies are XML applied at global, product, API or operation scope with <base /> chaining them. The ones you will use weekly: validate-jwt, rate-limit-by-key, cache-lookup/cache-store, set-backend-service, rewrite-uri, cors, mock-response, and send-request for a side call. Expressions are C# snippets in @(…).

<policies>
  <inbound>
    <base />
    <cors allow-credentials="true"><allowed-origins><origin>https://shop.contoso.com</origin></allowed-origins>
      <allowed-methods><method>*</method></allowed-methods><allowed-headers><header>*</header></allowed-headers></cors>

    <!-- Validate Entra tokens; the backend still validates too -->
    <validate-azure-ad-token tenant-id="{{tenant-id}}" failed-validation-httpcode="401">
      <audiences><audience>api://shop-api</audience></audiences>
      <required-claims><claim name="scp" match="any" separator=" "><value>Orders.Read</value><value>Orders.ReadWrite</value></claim></required-claims>
    </validate-azure-ad-token>

    <!-- Rate limit per caller (oid claim), plus a hard quota per subscription -->
    <rate-limit-by-key calls="100" renewal-period="60" increment-condition="@(context.Response.StatusCode < 400)"
      counter-key="@(context.Request.Headers.GetValueOrDefault("Authorization","").AsJwt()?.Claims.GetValueOrDefault("oid","anon"))" />
    <quota calls="100000" renewal-period="2592000" />

    <!-- Cache GETs for 30 s, vary by the id in the URL -->
    <cache-lookup vary-by-developer="false" vary-by-developer-groups="false" downstream-caching-type="none" />

    <set-header name="X-Gateway-Key" exists-action="override"><value>{{backend-key}}</value></set-header>
    <set-header name="X-Correlation-Id" exists-action="skip"><value>@(context.RequestId.ToString())</value></set-header>
    <set-backend-service base-url="https://shop-api.azurewebsites.net" />
  </inbound>
  <backend><base /></backend>
  <outbound>
    <base />
    <cache-store duration="30" />
    <set-header name="Server" exists-action="delete" />
  </outbound>
  <on-error>
    <base />
    <set-header name="X-Error" exists-action="override"><value>@(context.LastError.Message)</value></set-header>
  </on-error>
</policies>

from azure.identity import DefaultAzureCredential

tok = DefaultAzureCredential().get_token("api://shop-api/.default").token
client = httpx.Client(base_url="https://apim-shop.azure-api.net/orders",
                      headers={"Ocp-Apim-Subscription-Key": SUB_KEY, "Authorization": f"Bearer {tok}"})

def get(path):
    for attempt in range(5):
        r = client.get(path)
        if r.status_code != 429:
            r.raise_for_status(); return r.json()
        time.sleep(int(r.headers.get("Retry-After", 2 ** attempt)))
    raise RuntimeError("rate limited")

Event Grid: push-based eventing

Event Grid delivers discrete events (a blob was created, an order was placed) to subscribers over HTTPS (webhooks, Functions, Service Bus, Event Hubs, Storage Queues) with retry and dead-lettering. Publish your own on a custom topic or an Event Grid namespace (MQTT + pull delivery). It complements Service Bus (commands, ordering) and Event Hubs (streams): use Event Grid for "something happened" fan-out with many subscribers.

// Publish CloudEvents to a custom topic
var publisher = new EventGridPublisherClient(new Uri("https://eg-shop.westeurope-1.eventgrid.azure.net/api/events"), new DefaultAzureCredential());
await publisher.SendEventAsync(new CloudEvent("/shop/orders", "Shop.OrderPlaced", new { OrderId = 42, Total = 99.5m }) { Subject = "orders/42" });

// Receive via webhook: handle the validation handshake, then the events

Logic Apps and Durable Functions: which workflow engine?

Logic Apps are low-code workflows with 1,000+ connectors (SAP, Salesforce, Office 365, SQL, FTP) — ideal for integration and approvals that business analysts can read. Durable Functions are code-first orchestrations (fan-out/fan-in, human interaction, eternal orchestrations) with replay semantics. Rule of thumb: connectors and visual flow → Logic Apps; complex logic, tests, and versioning in git → Durable Functions.

// Durable Functions (isolated worker): order fulfilment with a timeout and compensation
[Function(nameof(FulfilOrder))]
public static async Task<string> FulfilOrder([OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var order = ctx.GetInput<Order>()!;
    var retry = new TaskOptions(new TaskRetryOptions(new RetryPolicy(3, TimeSpan.FromSeconds(5), backoffCoefficient: 2)));

    await ctx.CallActivityAsync(nameof(ReserveStock), order, retry);
    try
    {
        // Wait for payment webhook, max 30 minutes
        using var cts = new CancellationTokenSource();
        var paid = ctx.WaitForExternalEvent<bool>("PaymentConfirmed");
        var timeout = ctx.CreateTimer(ctx.CurrentUtcDateTime.AddMinutes(30), cts.Token);
        if (await Task.WhenAny(paid, timeout) == timeout || !paid.Result)
            throw new InvalidOperationException("payment not received");
        cts.Cancel();
        await ctx.CallActivityAsync(nameof(Ship), order, retry);
        return "shipped";
    }
    catch
    {
        await ctx.CallActivityAsync(nameof(ReleaseStock), order, retry);    // compensate
        return "cancelled";
    }
}
// Orchestrator rules: deterministic only — no DateTime.Now, Guid.NewGuid(), I/O or Task.Delay; use ctx.* equivalents.

App Configuration: central settings and feature flags

Azure App Configuration stores key-values with labels (environment/version), references Key Vault secrets, and hosts feature flags with targeting and percentage filters. Apps load it at startup and refresh on a sentinel key change — no redeploy to flip a flag or turn down a timeout. Combine with managed identity; never put the connection string in the app.

builder.Configuration.AddAzureAppConfiguration(o =>
{
    o.Connect(new Uri("https://appcs-shop.azconfig.io"), new DefaultAzureCredential())
     .Select("Shop:*", labelFilter: builder.Environment.EnvironmentName)     // Shop:* with label "Production"
     .Select("Shop:*", LabelFilter.Null)                                       // fall back to unlabelled defaults
     .ConfigureKeyVault(kv => kv.SetCredential(new DefaultAzureCredential())) // resolve Key Vault references
     .ConfigureRefresh(r => r.Register("Shop:Sentinel", refreshAll: true).SetRefreshInterval(TimeSpan.FromSeconds(30)))
     .UseFeatureFlags(f => f.SetRefreshInterval(TimeSpan.FromSeconds(30)));
});

Azure Cache for Redis / Azure Managed Redis

A managed Redis for cache-aside, session state, distributed locks, rate limiting and pub/sub. Use IDistributedCache for simple cases and StackExchange.Redis directly when you need data structures, Lua or pub/sub. Watch the timeouts: cache misses must be cheap, and the cache going away must not take the app with it. Azure Managed Redis (Redis 7.4+ Enterprise) is the newer tier with active geo-replication and vector search modules.

from azure.identity import DefaultAzureCredential

cred = DefaultAzureCredential()
def token_provider():
    t = cred.get_token("https://redis.azure.com/.default")
    return "<user-or-object-id>", t.token           # Entra auth: username = principal id, password = token

r = redis.Redis(host="redis-shop.redis.cache.windows.net", port=6380, ssl=True,
                credential_provider=redis.UsernamePasswordCredentialProvider(*token_provider()),
                socket_timeout=2, socket_connect_timeout=2, retry_on_timeout=True)

def get_product(pid: int) -> dict:                  # cache-aside with a stampede guard
    key = f"product:{pid}"
    if (hit := r.get(key)):
        return json.loads(hit)
    with r.lock(f"lock:{key}", timeout=5, blocking_timeout=2):
        if (hit := r.get(key)):
            return json.loads(hit)
        product = db.fetch_product(pid)
        r.set(key, json.dumps(product), ex=600)
        return product

# Rate limit with a Lua script (atomic)
RL = r.register_script("local c=redis.call('INCR',KEYS[1]) if c==1 then redis.call('EXPIRE',KEYS[1],ARGV[1]) end return c")

Real-time: Azure SignalR Service and Web PubSub

SignalR works in-process, but scaled-out App Service needs sticky sessions and a backplane. Azure SignalR Service takes over the connections (hundreds of thousands per unit) and your app just calls hub methods; in serverless mode Functions push messages via REST. Web PubSub is the protocol-agnostic sibling (raw WebSocket, MQTT) with Python and JS server SDKs.

// Default mode: your ASP.NET Core hub, connections held by the service

Which messaging service?

The question you will be asked in every Azure design interview. The answer is about semantics, not throughput numbers.

NeedServiceWhy
Simple work queue, huge volume, cheapStorage Queue64 KB messages, at-least-once, 7-day TTL, no ordering or sessions
Commands with ordering, transactions, dead-letter, duplicate detectionService Bus queue / topicPeek-lock, sessions (FIFO per key), scheduled and deferred messages, pub/sub via topics + filters
Discrete events fanned out to many reactive subscribersEvent GridPush over HTTPS to any endpoint, per-subscription filtering, 24h retry, pennies per million
High-throughput telemetry / stream processed in order with replayEvent HubsPartitioned log with offsets, consumer groups, Kafka protocol, capture to storage
Long-running workflow with connectors / human stepsLogic Apps / Durable FunctionsState and retries handled by the engine
Real-time push to browsers / devicesSignalR Service / Web PubSubWebSocket fan-out managed for you

// Idempotency is the common thread — every consumer must tolerate redelivery:
public async Task Handle(OrderPlaced e, CancellationToken ct)
{
    if (await db.ProcessedEvents.AnyAsync(p => p.EventId == e.Id, ct)) return;      // dedupe table
    await mailer.SendAsync(e.CustomerEmail, ct);
    db.ProcessedEvents.Add(new ProcessedEvent(e.Id, DateTime.UtcNow));
    await db.SaveChangesAsync(ct);
}
