Docker & Containers

Every DevOps topic after this one assumes you can produce a small, secure image and run it locally with its dependencies. This page is the Dockerfile you should be shipping for a .NET API and a Python service, the compose file that spins up the API with SQL and Redis, and the ACR workflow that gets the image into Azure.

Images, layers, containers and registries

An image is an immutable stack of read-only layers (each Dockerfile instruction adds one); a container is a process started from an image with a thin writable layer on top. Layers are content-addressed and cached — order instructions from least to most frequently changing. A registry (Docker Hub, ACR, GHCR) stores images by name:tag; the immutable identity is the digest (sha256:…).

docker build -t shop-api:dev .                                # build from ./Dockerfile
docker run --rm -p 8080:8080 -e ASPNETCORE_ENVIRONMENT=Development shop-api:dev
docker ps ; docker logs -f <id> ; docker exec -it <id> sh     # look inside
docker image history shop-api:dev                             # layer sizes — find what bloats the image
docker image inspect shop-api:dev --format '{{.RepoDigests}} {{.Size}}'
docker system df ; docker system prune -f                     # reclaim disk

# Tag by immutable identity in deployments
docker pull shop-api@sha256:3f1a…                             # digest never changes; tags do
docker tag shop-api:dev acrshop.azurecr.io/shop-api:1.4.2 && docker push acrshop.azurecr.io/shop-api:1.4.2

# Multi-platform (Apple Silicon → Azure amd64)
docker buildx build --platform linux/amd64,linux/arm64 -t acrshop.azurecr.io/shop-api:1.4.2 --push .
# A container is "just" a process with namespaces + cgroups — you can see it from the host
import subprocess, json
info = json.loads(subprocess.check_output(["docker", "inspect", "shop-api"]))[0]
print(info["State"]["Pid"], info["HostConfig"]["Memory"], info["Config"]["User"])
# ps -p <pid> on the host shows the same process; /proc/<pid>/cgroup shows its cgroup limits.
Interview angle

Image vs container; layer caching and why COPY order matters; tags vs digests and why prod deploys pin a digest; what a registry stores; how a container differs from a VM (shared kernel, namespaces, cgroups).

Production Dockerfiles for .NET and Python

Multi-stage: build with the SDK image, run on a runtime image. Restore dependencies before copying source so the cache survives code changes. Run as non-root, listen on a high port, set a HEALTHCHECK, and pin base image versions. For .NET use the chiseled Ubuntu images (no shell, no package manager); for Python use slim with a locked requirements file or uv.

# syntax=docker/dockerfile:1.7
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
# restore first — this layer is cached until a .csproj changes
COPY Directory.Packages.props Directory.Build.props nuget.config ./
COPY src/Shop.Api/Shop.Api.csproj src/Shop.Api/
COPY src/Shop.Domain/Shop.Domain.csproj src/Shop.Domain/
RUN --mount=type=cache,target=/root/.nuget/packages dotnet restore src/Shop.Api/Shop.Api.csproj
COPY src/ src/
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish src/Shop.Api/Shop.Api.csproj -c Release -o /app --no-restore /p:UseAppHost=false

# chiseled: no shell, no apt, non-root user "app" (uid 1654) already configured
FROM mcr.microsoft.com/dotnet/aspnet:9.0-noble-chiseled AS final
WORKDIR /app
COPY --from=build /app .
ENV ASPNETCORE_HTTP_PORTS=8080 DOTNET_gcServer=1 DOTNET_EnableDiagnostics=0
EXPOSE 8080
USER app
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s CMD ["dotnet", "Shop.Api.dll", "--healthcheck"]  # or curl on a non-chiseled base
ENTRYPOINT ["dotnet", "Shop.Api.dll"]
# syntax=docker/dockerfile:1.7
FROM python:3.12-slim AS build
COPY --from=ghcr.io/astral-sh/uv:0.5 /uv /bin/uv
WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
# deps first (cached), then the code
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv uv sync --frozen --no-dev --no-install-project
COPY src/ src/
RUN --mount=type=cache,target=/root/.cache/uv uv sync --frozen --no-dev

FROM python:3.12-slim AS final
RUN useradd --uid 1000 --create-home app
WORKDIR /app
COPY --from=build --chown=app:app /app /app
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
USER app
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8080/health').status==200 else 1)"
CMD ["uvicorn", "shop.main:app", "--host", "0.0.0.0", "--port", "8080", "--workers", "2", "--proxy-headers", "--forwarded-allow-ips=*"]
# .dockerignore — keep the build context small and secrets out of the image
**/bin
**/obj
**/.git
**/node_modules
**/.venv
**/__pycache__
**/*.user
.env
*.md
tests/
Interview angle

Why multi-stage; layer ordering for cache hits; running as non-root and what breaks (ports < 1024, file permissions); chiseled/distroless trade-offs (no shell to debug — use ephemeral debug containers); reproducible builds (lock files, pinned bases); image size targets.

docker compose for local development

Compose declares the whole local stack: the API, SQL Server (or Postgres), Redis, Azurite for storage, maybe the Service Bus emulator, with health-checked start order and named volumes so data survives restarts. Developers run one command; CI can run the same file for integration tests. Keep secrets in an untracked .env.

services:
  api:
    build: { context: ., target: final }
    ports: ["8080:8080"]
    environment:
      ASPNETCORE_ENVIRONMENT: Development
      ConnectionStrings__Shop: "Server=sql;Database=shop;User Id=sa;Password=${SA_PASSWORD};TrustServerCertificate=true"
      Redis: "redis:6379"
      AzureWebJobsStorage: "UseDevelopmentStorage=true;DevelopmentStorageProxyUri=http://azurite"
    depends_on:
      sql:   { condition: service_healthy }
      redis: { condition: service_started }
    develop:
      watch:                                  # docker compose watch → rebuild/sync on change
        - { action: rebuild, path: ./src }

  sql:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment: { ACCEPT_EULA: "Y", MSSQL_SA_PASSWORD: "${SA_PASSWORD}" }
    ports: ["1433:1433"]
    volumes: [ "sqldata:/var/opt/mssql" ]
    healthcheck:
      test: ["CMD-SHELL", "/opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P \"$$MSSQL_SA_PASSWORD\" -C -Q 'SELECT 1' || exit 1"]
      interval: 10s
      retries: 10

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  azurite:
    image: mcr.microsoft.com/azure-storage/azurite
    command: azurite --blobHost 0.0.0.0 --queueHost 0.0.0.0 --tableHost 0.0.0.0 --skipApiVersionCheck
    ports: ["10000:10000", "10001:10001", "10002:10002"]

volumes:
  sqldata:
echo "SA_PASSWORD=Your_password123" > .env          # untracked
docker compose up -d --build
docker compose logs -f api
docker compose exec sql /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P "$SA_PASSWORD" -C -Q "SELECT name FROM sys.databases"
docker compose watch                                # live rebuild loop
docker compose down -v                              # tear down including volumes

# Integration tests in CI against the same stack
docker compose -f compose.yaml -f compose.ci.yaml up -d --wait && dotnet test tests/Shop.IntegrationTests
// Alternative for tests: Testcontainers spins the same dependencies from code, no compose needed
public sealed class SqlFixture : IAsyncLifetime
{
    public MsSqlContainer Sql { get; } = new MsSqlBuilder().WithImage("mcr.microsoft.com/mssql/server:2022-latest").Build();
    public RedisContainer Redis { get; } = new RedisBuilder().Build();
    public async Task InitializeAsync() { await Task.WhenAll(Sql.StartAsync(), Redis.StartAsync()); }
    public async Task DisposeAsync()    { await Task.WhenAll(Sql.DisposeAsync().AsTask(), Redis.DisposeAsync().AsTask()); }
}
// tests get Sql.GetConnectionString() / Redis.GetConnectionString() — identical engine to production.
Interview angle

Compose vs Kubernetes locally (Kind/minikube) — when compose is enough; health-checked dependencies; volumes and data reset; how the same file serves CI; Testcontainers vs compose for integration tests.

Azure Container Registry: push, build, scan

ACR is the private registry your App Service, Container Apps, Functions and AKS pull from with managed identity (AcrPull). ACR Tasks build in the cloud (no Docker on the agent), Defender for Containers scans images, retention policies and content trust / notation signing keep it clean. Premium adds private endpoints, geo-replication and zone redundancy.

az acr create -g rg-shop -n acrshop --sku Premium --admin-enabled false --zone-redundancy Enabled
az acr login -n acrshop                                                  # token via your Entra login

# Cloud build (also runs the Dockerfile's multi-stage build) and push
az acr build -r acrshop -t shop-api:{{.Run.ID}} -t shop-api:1.4.2 -f Dockerfile .

# Let the runtime pull without secrets
az role assignment create --assignee $(az webapp identity show -g rg-shop -n shop-api --query principalId -o tsv) --role AcrPull --scope $(az acr show -n acrshop --query id -o tsv)
az webapp config container set -g rg-shop -n shop-api --container-image-name acrshop.azurecr.io/shop-api:1.4.2 --container-registry-url https://acrshop.azurecr.io
az webapp config set -g rg-shop -n shop-api --generic-configurations '{"acrUseManagedIdentityCreds": true}'
az aks update -g rg-shop -n aks-shop --attach-acr acrshop                # AKS: kubelet identity gets AcrPull

# Housekeeping and hygiene
az acr repository show-tags -n acrshop --repository shop-api --orderby time_desc --top 5
az acr manifest list-metadata -r acrshop -n shop-api --query "[?tags==null].digest" -o tsv | xargs -I{} az acr repository delete -n acrshop --image shop-api@{} -y   # untagged
az acr config retention update -r acrshop --status enabled --days 7 --type UntaggedManifests
az acr import -n acrshop --source docker.io/library/redis:7-alpine -t base/redis:7-alpine   # mirror public bases you depend on
az acr task create -r acrshop -n rebuild-on-base --image shop-api:latest --context https://github.com/contoso/shop.git#main -f Dockerfile --git-access-token $PAT   # rebuild when the base image updates
# Azure Pipelines: build with Docker@2 or ACR Tasks, then scan and push by digest
steps:
  - task: AzureCLI@2
    displayName: Build & push (ACR Tasks)
    inputs:
      azureSubscription: sc-shop
      scriptType: bash
      scriptLocation: inlineScript
      inlineScript: |
        set -euo pipefail
        az acr build -r acrshop -t shop-api:$(Build.BuildNumber) -f Dockerfile .
        DIGEST=$(az acr manifest show-metadata -r acrshop -n shop-api:$(Build.BuildNumber) --query digest -o tsv)
        echo "##vso[task.setvariable variable=imageDigest;isOutput=true]$DIGEST"
    name: build
  - script: |
      trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed acrshop.azurecr.io/shop-api@$(build.imageDigest)
    displayName: Vulnerability scan (fail on HIGH/CRITICAL)
Interview angle

Why pull with managed identity rather than the admin user; tags vs digests in deployments; scanning at build vs continuous scanning in the registry; base-image drift and automated rebuilds; geo-replication for multi-region AKS; retention and cost.

Configuration and secrets in containers

Twelve-factor: config comes from the environment, the image is identical across environments. Never bake secrets into layers (they remain in history). In Azure the runtime injects secrets from Key Vault (App Service Key Vault references, Container Apps secrets, AKS CSI driver) or the app reads them with managed identity. Locally, an untracked .env or dotnet user-secrets.

// ASP.NET Core reads env vars with "__" as the section separator: ConnectionStrings__Shop, Redis__Host
var cs = builder.Configuration.GetConnectionString("Shop");

// Layered config in containers: appsettings.json (defaults) → env vars (per environment) → Key Vault (secrets)
if (!builder.Environment.IsDevelopment())
    builder.Configuration.AddAzureKeyVault(new Uri(builder.Configuration["KeyVault:Uri"]!), new DefaultAzureCredential());

// Strongly typed + validated at startup so a missing env var fails fast, not on the first request
builder.Services.AddOptions<ShopOptions>().BindConfiguration("Shop").ValidateDataAnnotations().ValidateOnStart();

// Read secrets mounted as files (AKS CSI / Container Apps volume) — works with reloadOnChange
builder.Configuration.AddKeyPerFile("/mnt/secrets", optional: true, reloadOnChange: true);
# pydantic-settings: env vars with a nested delimiter, .env for local, Key Vault when running in Azure
from pydantic import BaseModel, Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Db(BaseModel):
    host: str
    password: str = Field(repr=False)          # never print it

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_nested_delimiter="__", env_file=".env", secrets_dir="/mnt/secrets", extra="ignore")
    env: str = "dev"
    db: Db
    redis_host: str = "localhost"

settings = Settings()      # fails loudly at import time if DB__HOST / DB__PASSWORD are missing
# In Azure: Container Apps secrets → env or mounted files; App Service → @Microsoft.KeyVault(SecretUri=...) references.
# Build-time secrets without leaking them into layers (private NuGet/PyPI feed token)
docker build --secret id=nuget,env=NUGET_TOKEN .
#   RUN --mount=type=secret,id=nuget dotnet restore --configfile <(sed "s/%TOKEN%/$(cat /run/secrets/nuget)/" nuget.config)

# Runtime: env file locally, never committed
docker run --env-file .env shop-api:dev

# Container Apps: secret from Key Vault via managed identity, surfaced as an env var
az containerapp secret set -g rg-shop -n shop-api --secrets db-password=keyvaultref:https://kv-shop.vault.azure.net/secrets/DbPassword,identityref:system
az containerapp update -g rg-shop -n shop-api --set-env-vars "ConnectionStrings__Shop=secretref:db-password"

# Check nothing sensitive is in the image
docker history --no-trunc shop-api:dev | grep -i -E "token|password|secret" || echo clean
Interview angle

Why env vars over config files in images; how ARG/ENV leak into history and the BuildKit secret mount; Key Vault reference vs SDK; validating configuration at startup; rotating a secret without redeploying.

Debugging and resource limits

Containers die for three reasons: the process exited (check logs and exit code), the health check failed, or the OOM killer hit the memory limit. Set CPU/memory limits explicitly, tell .NET about them (it reads cgroups automatically; tune DOTNET_GCHeapHardLimit if needed) and size Python worker counts to the CPU limit. Use docker stats, exec, and dotnet-counters/py-spy inside the container.

docker run --rm --memory=512m --cpus=1 -p 8080:8080 shop-api:dev
docker stats --no-stream                                     # CPU/mem per container
docker inspect --format '{{.State.ExitCode}} {{.State.OOMKilled}}' <id>    # 137 + OOMKilled=true → raise limit or fix the leak
docker logs --since 10m --timestamps <id>

# Chiseled image has no shell: attach a debug sidecar sharing the PID namespace
docker run --rm -it --pid=container:<id> --net=container:<id> mcr.microsoft.com/dotnet/sdk:9.0 bash
  # inside: dotnet tool install -g dotnet-counters dotnet-dump; dotnet-counters monitor -p 1; dotnet-dump collect -p 1
# Python: py-spy dump --pid 1   (needs SYS_PTRACE: docker run --cap-add SYS_PTRACE)

# Networking inside: curl the peer service by compose name
docker compose exec api sh -c "getent hosts sql && wget -qO- http://redis:6379 || true"
// .NET is container-aware: Environment.ProcessorCount and GC heap limits come from cgroups.
// Log what the runtime sees at startup — it prevents a class of "works on my machine" tickets.
app.Logger.LogInformation("CPU={Cpu} GC={Gc} Limit={Limit}MB",
    Environment.ProcessorCount, GCSettings.IsServerGC ? "server" : "workstation",
    GC.GetGCMemoryInfo().TotalAvailableMemoryBytes / 1024 / 1024);

// Small containers (< 2 cores): workstation GC usually wins;  DOTNET_gcServer=0 or <ServerGarbageCollection>false</ServerGarbageCollection>
// Memory-limited: DOTNET_GCHeapHardLimitPercent=75 leaves headroom for native memory so the OOM killer doesn't fire first.
// Thread pool under limits: ThreadPool.SetMinThreads if you see starvation when ProcessorCount is 1.
Interview angle

Exit code 137 and OOM diagnosis; CPU limits vs requests and throttling; how .NET/Python detect container limits; debugging a distroless image; log to stdout/stderr, not files; graceful shutdown and SIGTERM handling.

Image security and supply chain

Minimise the attack surface (chiseled/slim, non-root, read-only filesystem, drop capabilities), scan continuously (Defender, Trivy, Grype), produce an SBOM, and sign images (Notation/cosign) so the cluster admits only what your pipeline built. Pin base images by digest and rebuild on base updates; the vulnerability is usually in the base, not your code.

# Scan + SBOM + sign in the pipeline
trivy image --severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed acrshop.azurecr.io/shop-api:1.4.2
syft acrshop.azurecr.io/shop-api:1.4.2 -o spdx-json > sbom.spdx.json
grype sbom:sbom.spdx.json --fail-on high

# Sign with Notation using a Key Vault certificate; verify before deploy (or with an AKS admission policy)
notation key add --plugin azure-kv --id https://kv-shop.vault.azure.net/keys/signing-cert/<version> shop-signer
notation sign --key shop-signer acrshop.azurecr.io/shop-api@sha256:3f1a…
notation verify acrshop.azurecr.io/shop-api@sha256:3f1a…

# Runtime hardening flags (also expressible in Kubernetes securityContext / Container Apps)
docker run --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges -u 1654 shop-api:1.4.2
# Pin the base image by digest and let Dependabot / Renovate bump it
# Dockerfile:  FROM mcr.microsoft.com/dotnet/aspnet:9.0-noble-chiseled@sha256:5b2e…
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: nuget
    directory: /
    schedule: { interval: weekly }
    groups: { minor-and-patch: { update-types: [minor, patch] } }
Interview angle

What an SBOM is for; scanning in CI vs registry vs runtime; image signing and admission control; why base image updates matter more than your code for CVEs; read-only root filesystem and what your app must change (temp paths).
