DbContext and entities

A DbContext is a unit of work plus an identity map: it tracks the entities you load, and SaveChanges writes the diff. It is cheap to create, not thread-safe, and scoped per request in ASP.NET Core. Entities are plain classes; navigation properties express relationships. SQLAlchemy's Session plays the same role.

public class Blog
{
    public int Id { get; set; }
    public required string Url { get; set; }
    public List<Post> Posts { get; } = new();          // one-to-many navigation
}

public class Post
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public string? Content { get; set; }
    public DateTime Created { get; set; } = DateTime.UtcNow;
    public int BlogId { get; set; }                    // FK by convention
    public Blog Blog { get; set; } = null!;            // reference navigation
}

public class AppDb(DbContextOptions<AppDb> options) : DbContext(options)
{
    public DbSet<Blog> Blogs => Set<Blog>();
    public DbSet<Post> Posts => Set<Post>();
}

Model configuration: conventions, attributes, Fluent API

EF discovers the model by convention (Id = key, BlogId = FK). Override with data annotations for simple things or the Fluent API in OnModelCreating for everything else — keys, indexes, value conversions, owned types, table splitting, global query filters. Keep configuration in IEntityTypeConfiguration<T> classes so the context stays small.

public class PostConfiguration : IEntityTypeConfiguration<Post>
{
    public void Configure(EntityTypeBuilder<Post> b)
    {
        b.ToTable("Posts", "blog");
        b.HasKey(p => p.Id);
        b.Property(p => p.Title).HasMaxLength(200).IsRequired();
        b.Property(p => p.Content).HasColumnType("nvarchar(max)");
        b.HasIndex(p => new { p.BlogId, p.Created }).IsDescending(false, true);

        b.HasOne(p => p.Blog)
         .WithMany(bl => bl.Posts)
         .HasForeignKey(p => p.BlogId)
         .OnDelete(DeleteBehavior.Cascade);

        // Enum stored as string
        b.Property(p => p.Status).HasConversion<string>();

        // Owned type (value object stored in the same table)
        b.OwnsOne(p => p.Author, a => { a.Property(x => x.Email).HasColumnName("AuthorEmail"); });

        // Concurrency token
        b.Property(p => p.RowVersion).IsRowVersion();

        // Soft delete via global query filter
        b.HasQueryFilter(p => !p.IsDeleted);
    }
}

public class AppDb : DbContext

# Soft delete "global filter": use a with_loader_criteria hook on every query
from sqlalchemy.orm import with_loader_criteria
@event.listens_for(Session, "do_orm_execute")
def _soft_delete(state):
    if state.is_select and not state.execution_options.get("include_deleted"):
        state.statement = state.statement.options(
            with_loader_criteria(Post, lambda cls: cls.is_deleted == False, include_aliases=True))

Migrations

Migrations version your schema alongside the code. dotnet ef migrations add diffs the model against the last snapshot and generates Up/Down; dotnet ef database update applies them. In production apply via a migration bundle or SQL script in the pipeline — not Migrate() at startup on multiple instances. Alembic is the SQLAlchemy equivalent.

# Tooling
dotnet tool install --global dotnet-ef
dotnet add package Microsoft.EntityFrameworkCore.Design

# Create and apply
dotnet ef migrations add AddPostStatus
dotnet ef database update

# Roll back to a specific migration
dotnet ef database update AddBlogs

# Production: idempotent SQL script or a bundle executable
dotnet ef migrations script --idempotent -o migrate.sql
dotnet ef migrations bundle --self-contained -r linux-x64 -o efbundle
./efbundle --connection "$CONNECTION_STRING"

# Remove the last (unapplied) migration
dotnet ef migrations remove

CRUD and SaveChanges

Add/Update/Remove only change tracker state; SaveChangesAsync issues the SQL in a transaction. Load-then-modify is the normal update path (EF sends only changed columns). For bulk work, EF 7+ has ExecuteUpdateAsync/ExecuteDeleteAsync which skip the tracker entirely.

// Create
var blog = new Blog { Url = "https://example.com" };
blog.Posts.Add(new Post { Title = "Hello" });
db.Blogs.Add(blog);                       // graph is tracked, FK set automatically
await db.SaveChangesAsync();              // INSERT blog; INSERT post

// Read
var post = await db.Posts.FindAsync(1);   // checks tracker first, then DB by PK
var recent = await db.Posts.Where(p => p.Created > DateTime.UtcNow.AddDays(-7))
                           .OrderByDescending(p => p.Created).Take(10).ToListAsync();

// Update (tracked): only the changed column is in the UPDATE
post!.Title = "Hello, world";
await db.SaveChangesAsync();              // UPDATE Posts SET Title = @p0 WHERE Id = @p1

// Update (disconnected, e.g. from a PUT body)
db.Posts.Update(dto.ToEntity());          // marks ALL columns modified
db.Entry(entity).Property(p => p.Title).IsModified = true;   // or be surgical

// Delete
db.Posts.Remove(post);
await db.SaveChangesAsync();

// Bulk without tracking (EF 7+)
await db.Posts.Where(p => p.Created < cutoff).ExecuteDeleteAsync();
await db.Posts.Where(p => p.BlogId == 1).ExecuteUpdateAsync(s => s.SetProperty(p => p.Status, "archived"));

// Upsert pattern
var existing = await db.Tags.SingleOrDefaultAsync(t => t.Name == name);
if (existing is null) db.Tags.Add(new Tag { Name = name }); else existing.Touched = DateTime.UtcNow;
await db.SaveChangesAsync();

// Inspect the tracker
foreach (var e in db.ChangeTracker.Entries()) Console.WriteLine($"{e.Entity.GetType().Name}: {e.State}");

    db.execute(delete(Post).where(Post.created < cutoff))

    db.commit()

    existing = db.scalar(select(Tag).where(Tag.name == name))
    if existing is None: db.add(Tag(name=name))
    else: existing.touched = datetime.now(timezone.utc)
    db.commit()

    # Inspect the unit of work
    print(db.new, db.dirty, db.deleted)

LINQ to SQL translation and IQueryable

An IQueryable is an expression tree; EF translates it to SQL when you enumerate. Everything before ToList()/AsEnumerable() runs in the database; anything after runs in memory. Project with Select to fetch only needed columns. Watch for client evaluation of things EF cannot translate (custom methods) — EF Core throws instead of silently pulling the whole table.

// Translated to SQL — fast
var titles = await db.Posts
    .Where(p => p.Blog.Url.StartsWith("https") && p.Title.Contains("EF"))   // LIKE
    .OrderBy(p => p.Created)
    .Select(p => new PostSummary(p.Id, p.Title, p.Blog.Url))               // projection → only 3 columns
    .ToListAsync();

// Aggregates and grouping translate too
var perBlog = await db.Posts
    .GroupBy(p => p.BlogId)
    .Select(g => new { BlogId = g.Key, Count = g.Count(), Latest = g.Max(p => p.Created) })
    .ToListAsync();

// Paging
var page = await db.Posts.OrderBy(p => p.Id).Skip((pageNo - 1) * size).Take(size).ToListAsync();

// Client evaluation: this throws — Slugify can't be translated
// var bad = db.Posts.Where(p => Slugify(p.Title) == slug).ToList();
var ok = db.Posts.AsEnumerable().Where(p => Slugify(p.Title) == slug);   // explicit: runs in memory (pulls all rows!)

// Raw SQL when LINQ can't express it (still composable)
var hot = db.Posts.FromSql($"SELECT * FROM blog.Posts WHERE Views > {minViews}").Where(p => !p.IsDeleted);

// See the SQL
Console.WriteLine(db.Posts.Where(p => p.Id > 5).ToQueryString());

// Compiled query for hot paths

Relationships and loading strategies

Three ways to load related data: eager (Include/ThenInclude), explicit (Entry(x).Collection(...).LoadAsync()), lazy (proxies, load on first access — convenient, dangerous). Or skip all three and project with Select. Use AsSplitQuery when includes create a cartesian explosion.

// Eager
var blogs = await db.Blogs
    .Include(b => b.Posts.Where(p => !p.IsDeleted).OrderByDescending(p => p.Created).Take(5))   // filtered include
        .ThenInclude(p => p.Tags)
    .AsSplitQuery()          // one query per collection instead of a giant JOIN
    .ToListAsync();

// Explicit
var blog = await db.Blogs.FirstAsync();
await db.Entry(blog).Collection(b => b.Posts).LoadAsync();
await db.Entry(post).Reference(p => p.Blog).LoadAsync();

// Lazy (opt-in): Microsoft.EntityFrameworkCore.Proxies + virtual navigations
builder.Services.AddDbContext<AppDb>(o => o.UseLazyLoadingProxies().UseSqlServer(cs));

Change tracking vs AsNoTracking

Every tracked entity costs memory and a snapshot for diffing. Read-only queries should use AsNoTracking() — or set it as the default and opt in to tracking for writes. AsNoTrackingWithIdentityResolution still de-duplicates references. Tracked entities also give you the identity map: the same row is the same object within a context.

// Read-only: no tracking, ~2x faster, less memory
var posts = await db.Posts.AsNoTracking().Where(p => p.BlogId == 1).ToListAsync();
posts[0].Title = "changed";
await db.SaveChangesAsync();          // nothing happens — not tracked

// Keep identity resolution without tracking
var withRefs = await db.Posts.AsNoTrackingWithIdentityResolution().Include(p => p.Blog).ToListAsync();

// Make no-tracking the default for the context
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cs)
    .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking));
var editable = await db.Posts.AsTracking().FirstAsync(p => p.Id == id);   // opt in for writes

// Identity map: same row → same instance
var a = await db.Posts.FirstAsync(p => p.Id == 1);
var b = await db.Posts.FirstAsync(p => p.Id == 1);
Console.WriteLine(ReferenceEquals(a, b));   // True (tracked)

// Attach / detach
db.Attach(entityFromCache);                  // state Unchanged, now tracked
db.Entry(entity).State = EntityState.Detached;
db.ChangeTracker.Clear();                    // drop everything (long-running contexts)

// Projections are never tracked
var dtos = await db.Posts.Select(p => new PostDto(p.Id, p.Title)).ToListAsync();
from sqlalchemy import select
from sqlalchemy.orm import Session

with SessionLocal() as db:
    # Every ORM object loaded is tracked (in the identity map) by default
    a = db.get(Post, 1)
    b = db.scalar(select(Post).where(Post.id == 1))
    print(a is b)          # True — identity map

    # "No tracking": query columns/tuples instead of entities
    rows = db.execute(select(Post.id, Post.title).where(Post.blog_id == 1)).all()

    # Or expunge after loading
    post = db.get(Post, 1)
    db.expunge(post)       # detached; changes no longer flushed
    post.title = "changed"
    db.commit()            # nothing happens

    # Attach a detached object
    db.add(post)           # or db.merge(post) to copy state onto the tracked instance

    # Clear the unit of work in long-running sessions
    db.expunge_all()

    # Read-only sessions: autoflush=False and never commit
    ro = Session(engine, autoflush=False)

Transactions and optimistic concurrency

SaveChanges is already atomic. Wrap multiple saves (or EF + Dapper) in BeginTransactionAsync. For concurrent edits, use a concurrency token (rowversion) so the second writer gets DbUpdateConcurrencyException instead of silently overwriting — then resolve (client wins, store wins, merge). Use the execution strategy for transient-failure retries on Azure SQL.

// Explicit transaction across multiple operations
await using var tx = await db.Database.BeginTransactionAsync(IsolationLevel.ReadCommitted);
try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync();
    await db.Database.ExecuteSqlAsync($"UPDATE Inventory SET Qty = Qty - {order.Qty} WHERE Sku = {order.Sku}");
    await tx.CommitAsync();
}
catch { await tx.RollbackAsync(); throw; }

// With retries on transient errors (Azure SQL): wrap the whole unit in the strategy
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cs, s => s.EnableRetryOnFailure(3)));
var strategy = db.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () =>
{
    await using var tx = await db.Database.BeginTransactionAsync();
    /* ... */
    await tx.CommitAsync();
});

// Optimistic concurrency with rowversion
public class Product { public byte[] RowVersion { get; set; } = null!; }   // b.Property(p => p.RowVersion).IsRowVersion();

var product = await db.Products.FindAsync(id);
product!.Price = newPrice;
try
{
    await db.SaveChangesAsync();   // UPDATE ... WHERE Id = @id AND RowVersion = @rv  → 0 rows = conflict
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var dbValues = await entry.GetDatabaseValuesAsync();
    if (dbValues is null) return Results.NotFound();            // deleted meanwhile
    // Store wins: entry.Reload();   Client wins: entry.OriginalValues.SetValues(dbValues); retry save
    return Results.Conflict(new { current = dbValues.ToObject() });
}

The N+1 problem and other performance traps

N+1: one query for the list, then one query per item for a navigation — 101 round-trips for 100 rows. Caused by lazy loading or by looping over entities and touching navigations. Fix with Include, projection, or batching. Other traps: loading whole entities to count them, Contains with huge lists, missing indexes, and ToList() too early.

// N+1 — 1 + N queries
var blogs = await db.Blogs.ToListAsync();
foreach (var b in blogs)
    Console.WriteLine($"{b.Url}: {b.Posts.Count}");       // lazy-load or empty list — either way wrong

// Fix 1: Include
var blogs2 = await db.Blogs.Include(b => b.Posts).ToListAsync();

// Fix 2: projection (best — one query, minimal columns)
var counts = await db.Blogs.Select(b => new { b.Url, Count = b.Posts.Count }).ToListAsync();

// Fix 3: batch load then join in memory
var ids = blogs.Select(b => b.Id).ToList();
var posts = await db.Posts.Where(p => ids.Contains(p.BlogId)).ToListAsync();
var byBlog = posts.ToLookup(p => p.BlogId);

// Other traps
var n = (await db.Posts.ToListAsync()).Count;               // ✗ loads everything
var n2 = await db.Posts.CountAsync();                        // ✓
bool exists = await db.Posts.AnyAsync(p => p.Id == id);     // ✓ not FirstOrDefault != null

var all = db.Posts.ToList().Where(p => p.Title.Contains("x"));   // ✗ filter in memory
var some = db.Posts.Where(p => p.Title.Contains("x")).ToList();  // ✓ filter in SQL

// Huge IN lists: chunk or use a temp table / TVP
foreach (var chunk in ids.Chunk(1000)) { /* query per chunk */ }

Dapper and when to skip the ORM

Dapper maps SQL results to objects with almost no overhead; you write the SQL. Use it for reporting queries, hot read paths, stored procedures and anywhere EF's generated SQL is not good enough. Mixing is normal: EF for writes and the domain model, Dapper for reads. In Python the equivalent is SQLAlchemy Core or the raw DB-API driver.
