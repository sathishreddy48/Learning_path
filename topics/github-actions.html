Workflow anatomy: triggers, jobs, steps, runners

A workflow is a YAML file in .github/workflows/ with on: triggers (push, pull_request, schedule, workflow_dispatch, workflow_call), jobs that run in parallel unless they needs: each other, and steps that are either run: shell or uses: an action. Runners are GitHub-hosted (ubuntu/windows/macos, larger runners) or self-hosted. Contexts (github, env, secrets, vars, needs) feed expressions ${{ }}.

name: ci
on:
  push:
    branches: [main]
    paths-ignore: ["docs/**", "*.md"]
  pull_request:
    branches: [main]
  workflow_dispatch:
    inputs:
      environment: { description: Target, type: choice, options: [staging, production], default: staging }
  schedule:
    - cron: "0 3 * * 1"          # weekly Monday 03:00 UTC (dependency audit)

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true       # a new push cancels the running PR build

permissions:                     # least privilege for GITHUB_TOKEN; add per job as needed
  contents: read

defaults: { run: { shell: bash } }

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    outputs:
      version: ${{ steps.ver.outputs.version }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }                       # full history for versioning tools
      - id: ver
        run: echo "version=1.4.${{ github.run_number }}" >> "$GITHUB_OUTPUT"
      - run: echo "Building ${{ steps.ver.outputs.version }} on ${{ runner.os }} for ${{ github.event_name }}"

  lint:
    runs-on: ubuntu-latest
    steps: [ { uses: actions/checkout@v4 }, { run: echo lint } ]

  package:
    needs: [build, lint]                               # fan-in
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - run: echo "packaging ${{ needs.build.outputs.version }}"
# Local iteration
gh workflow list ; gh workflow run ci.yml -f environment=staging
gh run list --workflow ci.yml --limit 5 ; gh run watch ; gh run view --log-failed
act -j build                                   # run jobs locally with nektos/act (approximation)

# Step-level API you will use in scripts
echo "name=value" >> "$GITHUB_OUTPUT"         # step output
echo "MY_VAR=value" >> "$GITHUB_ENV"          # env for later steps
echo "$HOME/.dotnet/tools" >> "$GITHUB_PATH"  # PATH
echo "::error file=src/a.cs,line=10::Bad thing"  ;  echo "::warning::Heads up"  ;  echo "::group::Details" ; echo ... ; echo "::endgroup::"
echo "## Summary" >> "$GITHUB_STEP_SUMMARY"    # markdown on the run page
Interview angle

Jobs vs steps and where state is shared (not across jobs — use artifacts/outputs); triggers and the pull_request vs pull_request_target security difference; concurrency groups; GITHUB_TOKEN permissions; hosted vs self-hosted runners and when you need the latter (VNet access).

Build and test .NET and Python with caching and a matrix

Setup actions install toolchains and cache package restores. Publish test results and coverage as artifacts (or with a reporter action) so PRs show failures inline. A matrix runs the same job across versions/OSes; use fail-fast: false when you want the whole picture.

jobs:
  dotnet:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: 9.0.x
          cache: true
          cache-dependency-path: "**/packages.lock.json"     # enable lock files: <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
      - run: dotnet restore --locked-mode
      - run: dotnet build --no-restore -c Release -warnaserror
      - run: dotnet format --verify-no-changes --no-restore
      - run: dotnet test --no-build -c Release --logger "trx;LogFileName=test.trx" --collect:"XPlat Code Coverage" --results-directory TestResults
      - uses: dorny/test-reporter@v1
        if: always()
        with: { name: .NET tests, path: TestResults/*.trx, reporter: dotnet-trx }
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: coverage, path: TestResults/**/coverage.cobertura.xml }
      - run: dotnet publish src/Shop.Api -c Release -o publish --no-build
      - uses: actions/upload-artifact@v4
        with: { name: shop-api, path: publish, retention-days: 7 }
jobs:
  python:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python: ["3.11", "3.12", "3.13"]
        exclude: [{ os: windows-latest, python: "3.11" }]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: { enable-cache: true, cache-dependency-glob: uv.lock }
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python }}" }
      - run: uv sync --frozen --all-extras
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run mypy src
      - run: uv run pytest -q --junitxml=junit.xml --cov=src --cov-report=xml
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: test-results-${{ matrix.os }}-${{ matrix.python }}, path: junit.xml }

  # Integration tests against real dependencies with service containers
  integration:
    runs-on: ubuntu-latest
    services:
      redis: { image: redis:7-alpine, ports: ["6379:6379"], options: --health-cmd "redis-cli ping" --health-interval 5s }
      sql:
        image: mcr.microsoft.com/mssql/server:2022-latest
        env: { ACCEPT_EULA: "Y", MSSQL_SA_PASSWORD: "Your_password123" }
        ports: ["1433:1433"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: 9.0.x }
      - run: dotnet test tests/Shop.IntegrationTests -c Release
        env: { ConnectionStrings__Shop: "Server=localhost;Database=shop;User Id=sa;Password=Your_password123;TrustServerCertificate=true", Redis: "localhost:6379" }
Interview angle

What to cache and what not to (package caches yes, build outputs rarely); lock files for reproducibility; matrix design and cost; service containers vs Testcontainers; test result reporting on PRs; keeping PR builds under ten minutes.

OIDC login to Azure: no secrets in GitHub

Give the job id-token: write, register a federated credential on the app registration or a user-assigned managed identity whose subject matches the workflow (branch, environment, tag or PR), and azure/login exchanges GitHub's OIDC token for an Azure token. Nothing sensitive is stored; the trust is scoped to exactly that repo + branch/environment.

# One identity per environment, each trusting a specific subject
az identity create -g rg-shop -n id-gh-shop-prod
az identity federated-credential create -g rg-shop --identity-name id-gh-shop-prod -n gh-prod-env   --issuer https://token.actions.githubusercontent.com --subject repo:contoso/shop:environment:production --audiences api://AzureADTokenExchange
az identity federated-credential create -g rg-shop --identity-name id-gh-shop-prod -n gh-main-branch   --issuer https://token.actions.githubusercontent.com --subject repo:contoso/shop:ref:refs/heads/main --audiences api://AzureADTokenExchange
az role assignment create --assignee $(az identity show -g rg-shop -n id-gh-shop-prod --query principalId -o tsv) --role Contributor --scope /subscriptions/<sub>/resourceGroups/rg-shop-prod

# Store non-secret IDs as repository/environment *variables*
gh variable set AZURE_CLIENT_ID --env production --body $(az identity show -g rg-shop -n id-gh-shop-prod --query clientId -o tsv)
gh variable set AZURE_TENANT_ID --body $(az account show --query tenantId -o tsv)
gh variable set AZURE_SUBSCRIPTION_ID --body $(az account show --query id -o tsv)
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      id-token: write            # request the OIDC token
      contents: read
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: az account show --query "{sub:name, identity:user.name}"
      # Subsequent steps: az cli, azure/webapps-deploy, azure/container-apps-deploy-action, azure/aks-set-context all reuse the login.

      # Terraform / SDKs pick up the same token via env:
      - run: terraform apply -auto-approve
        env: { ARM_USE_OIDC: "true", ARM_CLIENT_ID: "${{ vars.AZURE_CLIENT_ID }}", ARM_TENANT_ID: "${{ vars.AZURE_TENANT_ID }}", ARM_SUBSCRIPTION_ID: "${{ vars.AZURE_SUBSCRIPTION_ID }}" }
Interview angle

Explain the OIDC exchange and what the subject claim protects against (a fork or another branch using prod credentials); why environment-scoped subjects; secrets vs variables; rotating nothing; the equivalent in Azure Pipelines (workload identity federation service connection).

Reusable workflows and composite actions

Stop copy-pasting. A composite action bundles steps (setup + restore + build) and is called with uses: ./.github/actions/dotnet-build. A reusable workflow (on: workflow_call) bundles whole jobs with inputs, secrets and outputs, callable across repos from a central .github repository — the equivalent of Azure Pipelines templates. Pin versions by tag or SHA.

# contoso/.github/.github/workflows/dotnet-service.yml
name: dotnet-service
on:
  workflow_call:
    inputs:
      project:      { type: string, required: true }
      dotnet:       { type: string, default: 9.0.x }
      image-name:   { type: string, required: true }
    secrets:
      SONAR_TOKEN:  { required: false }
    outputs:
      image-digest: { value: ${{ jobs.build.outputs.digest }} }

jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write, id-token: write }
    outputs: { digest: ${{ steps.push.outputs.digest }} }
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/dotnet-build            # composite (below)
        with: { project: ${{ inputs.project }}, dotnet: ${{ inputs.dotnet }} }
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - id: push
        run: |
          az acr build -r acrshop -t ${{ inputs.image-name }}:${{ github.sha }} -f Dockerfile .
          echo "digest=$(az acr manifest show-metadata -r acrshop -n ${{ inputs.image-name }}:${{ github.sha }} --query digest -o tsv)" >> "$GITHUB_OUTPUT"

# Caller — in contoso/shop/.github/workflows/ci.yml
# jobs:
#   service:
#     uses: contoso/.github/.github/workflows/dotnet-service.yml@v3
#     with: { project: src/Shop.Api/Shop.Api.csproj, image-name: shop-api }
#     secrets: inherit
# .github/actions/dotnet-build/action.yml
name: dotnet-build
description: Restore, build and test a .NET project with caching
inputs:
  project: { required: true }
  dotnet:  { default: 9.0.x }
runs:
  using: composite
  steps:
    - uses: actions/setup-dotnet@v4
      with: { dotnet-version: ${{ inputs.dotnet }}, cache: true, cache-dependency-path: "**/packages.lock.json" }
    - run: dotnet restore ${{ inputs.project }} --locked-mode
      shell: bash
    - run: dotnet build ${{ inputs.project }} --no-restore -c Release -warnaserror
      shell: bash
    - run: dotnet test ${{ inputs.project }} --no-build -c Release
      shell: bash
Interview angle

Composite action vs reusable workflow (steps vs jobs; secrets handling; nesting limits); versioning shared workflows and rolling out changes safely; how this maps to Azure Pipelines template/extends; governance of allowed actions in an org.

Environments, protection rules and secrets

An environment (staging, production) carries its own secrets and variables plus protection rules: required reviewers, wait timers, branch restrictions, and custom rules via deployment-protection apps (e.g. a health check). A job with environment: pauses until rules pass and records a deployment with history and URL. This is the Azure DevOps "environment + approvals" equivalent.

jobs:
  staging:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: staging, url: https://shop-api-staging.azurewebsites.net }
    permissions: { id-token: write, contents: read }
    steps:
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - uses: actions/download-artifact@v4
        with: { name: shop-api, path: publish }
      - uses: azure/webapps-deploy@v3
        with: { app-name: shop-api, slot-name: staging, package: publish }
      - run: curl -fsS --retry 10 --retry-delay 6 --retry-all-errors https://shop-api-staging.azurewebsites.net/health/ready

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment: { name: production, url: https://shop-api.azurewebsites.net }     # required reviewers + main-only branch rule
    permissions: { id-token: write, contents: read }
    steps:
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - run: az webapp deployment slot swap -g rg-shop -n shop-api --slot staging --target-slot production
      - run: curl -fsS https://shop-api.azurewebsites.net/health/ready
# Configure environments and rules from the CLI / API
gh api -X PUT repos/contoso/shop/environments/production   -f 'deployment_branch_policy[protected_branches]=true' -f 'deployment_branch_policy[custom_branch_policies]=false'   --input - <<'JSON'
{ "wait_timer": 5, "reviewers": [ { "type": "Team", "id": 123456 } ], "prevent_self_review": true }
JSON
gh secret set SONAR_TOKEN --env production < token.txt
gh variable set APP_NAME --env production --body shop-api
gh api repos/contoso/shop/deployments --jq '.[] | {env: .environment, ref: .ref, created: .created_at}' | head -5
Interview angle

Environment vs repository secrets; protection rules and who can bypass them; deployment history as an audit trail; custom deployment protection rules (e.g. gate on error rate); branch restrictions preventing a feature branch from deploying to prod.

Deploying to App Service, Container Apps and AKS

Three first-party actions cover most targets: azure/webapps-deploy (zip/package or container), azure/container-apps-deploy-action (build + deploy, or just point at an image), and azure/aks-set-context + azure/k8s-deploy (or plain kubectl/helm). Always deploy an immutable artifact by digest, run a smoke test, and make the rollback path a one-liner.

      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - name: Deploy new revision with 10% traffic
        run: |
          az containerapp update -g rg-shop -n orders-api --image acrshop.azurecr.io/shop-api@${{ needs.build.outputs.digest }} --revision-suffix ${{ github.run_number }}
          az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight latest=10
      - name: Bake and check error rate
        run: |
          sleep 300
          ERR=$(az monitor metrics list --resource $(az containerapp show -g rg-shop -n orders-api --query id -o tsv) --metric Requests --filter "statusCodeCategory eq '5xx'" --interval PT5M --query "value[0].timeseries[0].data[-1].total" -o tsv)
          [ "${ERR:-0}" -lt 5 ] || { echo "::error::error rate too high"; exit 1; }
      - name: Promote
        run: az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight latest=100
      - name: Roll back
        if: failure()
        run: |
          PREV=$(az containerapp revision list -g rg-shop -n orders-api --query "[?properties.trafficWeight==\`90\`].name | [0]" -o tsv)
          az containerapp ingress traffic set -g rg-shop -n orders-api --revision-weight $PREV=100
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - uses: azure/use-kubelogin@v1
        with: { kubelogin-version: v0.1.4 }
      - uses: azure/aks-set-context@v4
        with: { resource-group: rg-shop, cluster-name: aks-shop, admin: false, use-kubelogin: true }
      - uses: azure/setup-helm@v4
      - run: |
          helm upgrade --install orders-api charts/orders-api -n shop -f charts/orders-api/values.prod.yaml             --set image.digest=${{ needs.build.outputs.digest }} --atomic --timeout 10m
          kubectl rollout status deploy/orders-api -n shop --timeout=300s
      - uses: actions/download-artifact@v4
        with: { name: shop-api, path: publish }
      - uses: actions/download-artifact@v4
        with: { name: migrations, path: migrations }          # produced in build: dotnet ef migrations script --idempotent -o migrations/migrate.sql
      - uses: azure/login@v2
        with: { client-id: ${{ vars.AZURE_CLIENT_ID }}, tenant-id: ${{ vars.AZURE_TENANT_ID }}, subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }} }
      - uses: azure/sql-action@v2.3
        with: { connection-string: "Server=tcp:sql-shop.database.windows.net;Database=shopdb;Authentication=Active Directory Default;", path: migrations/migrate.sql }
      - uses: azure/webapps-deploy@v3
        with: { app-name: shop-api, slot-name: staging, package: publish }
      - run: az webapp deployment slot swap -g rg-shop -n shop-api --slot staging --target-slot production
Interview angle

Slot swap vs revision traffic split vs rolling update — rollback for each; where database migrations run relative to the deploy (expand/contract); smoke tests and automated rollback; deploying by digest; keeping the deploy job short-lived and idempotent.

Supply-chain hygiene: pinning, Dependabot, CodeQL, secrets

Actions run third-party code with your token. Pin actions to a commit SHA (Dependabot keeps them fresh), restrict allowed actions at the org, keep GITHUB_TOKEN read-only by default, never use pull_request_target with checkout of the PR head, and turn on CodeQL, secret scanning with push protection and Dependabot alerts/updates. Sign releases and build provenance with attest-build-provenance.

# Pinned actions with a version comment (Dependabot updates both)
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
- uses: actions/setup-dotnet@3e891b0cb619bf60e2c25674b222b8940e2c1c25 # v4.1.0

# CodeQL
name: codeql
on: { push: { branches: [main] }, pull_request: { branches: [main] }, schedule: [{ cron: "0 4 * * 2" }] }
permissions: { security-events: write, contents: read, actions: read }
jobs:
  analyze:
    runs-on: ubuntu-latest
    strategy: { matrix: { language: [csharp, python] } }
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with: { languages: ${{ matrix.language }}, queries: security-extended }
      - uses: github/codeql-action/autobuild@v3
      - uses: github/codeql-action/analyze@v3

# Build provenance (SLSA) for the published artifact
- uses: actions/attest-build-provenance@v2
  with: { subject-path: publish/**/*.dll }
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: nuget
    directory: /
    schedule: { interval: weekly }
    groups: { minor-and-patch: { update-types: [minor, patch] } }
    open-pull-requests-limit: 5
  - package-ecosystem: pip          # uv.lock is supported via the pip ecosystem
    directory: /
    schedule: { interval: weekly }
  - package-ecosystem: docker
    directory: /
    schedule: { interval: weekly }
# Org/repo policy checks
gh api repos/contoso/shop/actions/permissions            # allowed actions
gh api repos/contoso/shop/actions/permissions/workflow   # default GITHUB_TOKEN permissions (should be "read")
gh api repos/contoso/shop --jq '.security_and_analysis'  # secret scanning / push protection status
gh secret list ; gh secret list --env production
Interview angle

Why SHA-pin actions; the pull_request_target injection class; least-privilege GITHUB_TOKEN; secret scanning push protection; SBOM/provenance and what consumers do with them; how you would respond to a compromised popular action.

GitHub Actions vs Azure Pipelines: translation table

Both are YAML, both have stages/jobs/steps, approvals, templates and marketplace tasks. The differences that matter in practice are below. Many organisations run both: Azure DevOps for Boards and legacy pipelines, GitHub for code, Actions and security features.

ConceptAzure PipelinesGitHub Actions
Groupingstages → jobs → stepsjobs → steps (stages implied via needs)
Reusetemplate, extendsreusable workflows (workflow_call), composite actions
ApprovalsEnvironments with checksEnvironments with protection rules
Cloud authService connection (workload identity federation)azure/login with OIDC federated credential
Secrets/configVariable groups, Key Vault-linked groupsRepo/env secrets and variables; Key Vault via az
ArtifactsPipeline artifacts, Azure Artifacts feedsupload-artifact, GitHub Packages
TasksTasks (DotNetCoreCLI@2)Actions (setup-dotnet) + plain run:
RunnersMicrosoft-hosted, self-hosted agents, scale setsGitHub-hosted, larger runners, self-hosted, ARC on AKS
Triggerstrigger/pr/schedules, resourceson: with 30+ event types
Security scanningMarketplace / GitHub Advanced Security for ADOCodeQL, Dependabot, secret scanning built in

Interview angle

Given a pipeline in one system, sketch it in the other; when you would keep Azure DevOps (Boards, on-prem agents, existing governance) vs move to GitHub; migration tools (GitHub Actions Importer); running self-hosted runners inside a VNet for private endpoints.
