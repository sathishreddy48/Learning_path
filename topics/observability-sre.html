Logs, metrics, traces — and structured logging

Logs are events with context; metrics are cheap numeric time series for dashboards and alerts; traces tie a request together across services via a propagated traceparent. Emit logs as structured properties (not string concatenation), always with a correlation/trace ID, never with secrets or PII, and at a level you can afford to store. Metrics for anything you alert on; logs for the "why".

// Structured logging with message templates — properties become queryable columns, not text
public partial class OrderService(ILogger<OrderService> log)
{
    [LoggerMessage(Level = LogLevel.Information, Message = "Order {OrderId} placed for {CustomerId} with {ItemCount} items totalling {Total:C}")]
    partial void LogPlaced(int orderId, string customerId, int itemCount, decimal total);       // source-generated, zero-alloc when disabled

    public async Task PlaceAsync(Order o)
    {
        using var scope = log.BeginScope(new Dictionary<string, object> { ["OrderId"] = o.Id, ["Tenant"] = o.Tenant });   // attached to every log line inside
        LogPlaced(o.Id, o.CustomerId, o.Items.Count, o.Total);
        ...
    }
}

// Custom metrics with System.Diagnostics.Metrics — picked up by OpenTelemetry and Azure Monitor
public class ShopMetrics
{
    private readonly Counter<long> _orders;  private readonly Histogram<double> _checkout;
    public ShopMetrics(IMeterFactory f)
    {
        var m = f.Create("Shop.Orders");
        _orders = m.CreateCounter<long>("shop.orders.placed", unit: "{order}");
        _checkout = m.CreateHistogram<double>("shop.checkout.duration", unit: "ms");
    }
    public void OrderPlaced(string channel) => _orders.Add(1, new KeyValuePair<string, object?>("channel", channel));
    public void Checkout(double ms) => _checkout.Record(ms);
}
// Never:  log.LogInformation("Order " + id + " for " + email)   — unqueryable, and email is PII.

OpenTelemetry → Azure Monitor

OpenTelemetry is the vendor-neutral standard for traces, metrics and logs; the Azure Monitor OpenTelemetry distro configures exporters, auto-instrumentation (HTTP, SQL, Redis, Service Bus) and live metrics in one call. Sampling keeps cost sane: keep 100% of errors and slow requests, sample the rest. Set the cloud role name so the application map shows real services.

// Azure.Monitor.OpenTelemetry.AspNetCore — one line, then customise
builder.Services.AddOpenTelemetry()
    .UseAzureMonitor(o =>
    {
        o.ConnectionString = builder.Configuration["APPLICATIONINSIGHTS_CONNECTION_STRING"];
        o.SamplingRatio = 0.2f;                                         // 20% of traces (errors/dependencies inside them kept consistently)
        o.Credential = new DefaultAzureCredential();                    // Entra auth for ingestion (disable local auth on the resource)
    })
    .ConfigureResource(r => r.AddService("orders-api", serviceVersion: typeof(Program).Assembly.GetName().Version?.ToString())
                              .AddAttributes(new Dictionary<string, object> { ["deployment.environment"] = builder.Environment.EnvironmentName }))
    .WithMetrics(m => m.AddMeter("Shop.Orders"))                         // your custom meter
    .WithTracing(t => t.AddSource("Shop.Orders")                          // your ActivitySource
                       .AddProcessor(new PiiScrubbingProcessor()));      // drop/mask attributes before export

// Manual spans for business steps
private static readonly ActivitySource Source = new("Shop.Orders");
using var act = Source.StartActivity("checkout.pricing");
act?.SetTag("order.id", order.Id);
act?.AddEvent(new ActivityEvent("coupon.applied"));

KQL you will actually run

Application Insights (workspace-based) lands in Log Analytics tables: AppRequests, AppDependencies, AppExceptions, AppTraces, AppMetrics, joined by OperationId. Learn a dozen shapes — filter, summarize by bin, percentiles, join on operation, render — and you can answer most production questions in minutes. Save the good ones as functions.

// 1) Golden signals per endpoint, last hour
AppRequests
| where TimeGenerated > ago(1h) and AppRoleName == "orders-api"
| summarize count(), errors = countif(Success == false), p50 = percentile(DurationMs, 50), p95 = percentile(DurationMs, 95), p99 = percentile(DurationMs, 99) by Name
| extend errorRate = round(100.0 * errors / count_, 2)
| order by p95 desc

// 2) Requests per minute and error rate over time (chart)
AppRequests
| where TimeGenerated > ago(6h)
| summarize rpm = count(), errRate = 100.0 * countif(Success == false) / count() by bin(TimeGenerated, 1m)
| render timechart

// 3) Everything about one failed request: request, dependencies, exceptions, traces
let op = "a1b2c3d4e5f6...";
union AppRequests, AppDependencies, AppExceptions, AppTraces
| where OperationId == op
| project TimeGenerated, Type, Name, DurationMs, Success, ResultCode, Message = coalesce(Message, OuterMessage, Name), Properties
| order by TimeGenerated asc

// 4) Slowest dependencies (SQL, HTTP, Redis) and who calls them
AppDependencies
| where TimeGenerated > ago(1h)
| summarize calls = count(), p95 = percentile(DurationMs, 95), fails = countif(Success == false) by DependencyType, Target, Name
| top 15 by p95

// 5) New exceptions after the last deploy
AppExceptions
| where TimeGenerated > ago(24h)
| summarize n = count(), first = min(TimeGenerated), sample = any(OuterMessage) by ProblemId, AppVersion = tostring(Properties["service.version"])
| order by first desc

// 6) Custom metric and structured log properties
AppMetrics | where Name == "shop.checkout.duration" | summarize percentile(Sum / ItemCount, 95) by bin(TimeGenerated, 5m) | render timechart
AppTraces  | where Message has "Order" | extend OrderId = toint(Properties["OrderId"]), Tenant = tostring(Properties["Tenant"]) | summarize count() by Tenant

// 7) Availability from the outside (standard tests)
AppAvailabilityResults | where TimeGenerated > ago(7d) | summarize availability = 100.0 * countif(Success) / count() by Name, bin(TimeGenerated, 1d)
# Run KQL from the CLI / a script (handy in runbooks and pipelines)
WS=$(az monitor log-analytics workspace show -g rg-platform-logs -n law-platform --query customerId -o tsv)
az monitor log-analytics query -w $WS --analytics-query 'AppRequests | where TimeGenerated > ago(15m) | summarize errRate = 100.0*countif(Success==false)/count()' -o tsv

# App Insights REST for the classic resource id
az monitor app-insights query --app ai-shop -g rg-shop --analytics-query 'requests | where timestamp > ago(15m) | count' --offset 15m

Alerts, action groups and avoiding fatigue

Alert on symptoms users feel (error rate, latency, availability, queue age) rather than causes (CPU), with thresholds tied to your SLO and a duration window that filters blips. Action groups route to on-call (PagerDuty/Opsgenie/Teams/email/webhook/Function). Use severity consistently (Sev0–1 pages, Sev2–3 tickets), add alert processing rules for maintenance windows, and review noisy alerts weekly.

# Action group: page on-call via webhook + email the team
az monitor action-group create -g rg-shop -n ag-shop-oncall --short-name shop-oncall   --action email team shop-team@contoso.com --action webhook pagerduty https://events.pagerduty.com/integration/<key>/enqueue

# Log alert: error rate > 2% for 10 minutes, evaluated every 5 (Sev1 → pages)
az monitor scheduled-query create -g rg-shop -n "orders-api error rate" --severity 1 --action-groups ag-shop-oncall   --scopes $(az monitor log-analytics workspace show -g rg-platform-logs -n law-platform --query id -o tsv)   --evaluation-frequency 5m --window-size 10m --auto-mitigate true   --condition "count 'Placeholder' > 0" --condition-query 'Placeholder=AppRequests | where AppRoleName == "orders-api" | summarize err = 100.0*countif(Success==false)/count() | where err > 2'

# Metric alert: p95 latency (dynamic threshold learns the daily pattern)
az monitor metrics alert create -g rg-shop -n "orders-api p95 latency" --severity 2 --action ag-shop-oncall   --scopes $(az monitor app-insights component show -g rg-shop -a ai-shop --query id -o tsv)   --condition "avg requests/duration > dynamic medium 2 of 4 since 2026-09-01" --window-size 15m --evaluation-frequency 5m

# Availability test + alert (external synthetic probe from 5 regions)
az monitor app-insights web-test create -g rg-shop -n ready-probe --defined-web-test-name ready-probe --location westeurope --kind standard   --request-url https://api.contoso.com/health/ready --frequency 300 --timeout 30 --retry-enabled true --enabled true   --locations Id=emea-nl-ams-azr Id=us-va-ash-azr Id=apac-sg-sin-azr Id=emea-gb-db3-azr Id=us-ca-sjc-azr --tags "hidden-link:$(az monitor app-insights component show -g rg-shop -a ai-shop --query id -o tsv)=Resource"

# Service Bus: oldest message age (backlog users will notice) and dead-letter growth
az monitor metrics alert create -g rg-shop -n "orders queue backlog" --severity 2 --action ag-shop-oncall   --scopes $(az servicebus namespace show -g rg-shop -n sb-shop --query id -o tsv) --condition "max ActiveMessages > 1000 where EntityName includes orders" --window-size 15m

# Maintenance window: suppress everything in the RG during the deploy
az monitor alert-processing-rule create -g rg-shop -n suppress-deploy --rule-type RemoveAllActionGroups --scopes /subscriptions/<sub>/resourceGroups/rg-shop-prod   --schedule-recurrence-type Weekly --schedule-recurrence Tuesday --schedule-start-time 02:00 --schedule-end-time 03:00
// Alerts belong in IaC next to the service they protect
resource errRate 'Microsoft.Insights/scheduledQueryRules@2023-03-15-preview' = {
  name: 'orders-api-error-rate', location: location
  properties: {
    severity: 1, enabled: true, evaluationFrequency: 'PT5M', windowSize: 'PT10M', autoMitigate: true
    scopes: [ logAnalyticsId ]
    criteria: { allOf: [ {
      query: 'AppRequests | where AppRoleName == "orders-api" | summarize err = 100.0*countif(Success==false)/count()'
      timeAggregation: 'Average', metricMeasureColumn: 'err', operator: 'GreaterThan', threshold: 2, failingPeriods: { numberOfEvaluationPeriods: 2, minFailingPeriodsToAlert: 2 } } ] }
    actions: { actionGroups: [ actionGroupId ], customProperties: { runbook: 'https://wiki.contoso.com/runbooks/orders-api-errors' } }
  }
}

SLIs, SLOs and error budgets

An SLI is a measurement of user-visible behaviour (fraction of successful requests, fraction under 500 ms). An SLO is the target over a window (99.9% of requests succeed over 30 days). The error budget is what is left (0.1% ≈ 43 min/month of full outage); burning it fast pages, burning it steadily triggers a reliability conversation. SLOs make "is it reliable enough" a number rather than an argument.

// Availability SLI over 30 days, plus remaining error budget for a 99.9% SLO
let slo = 0.999;
AppRequests
| where TimeGenerated > ago(30d) and AppRoleName == "orders-api" and Name !has "health"
| summarize total = count(), good = countif(Success == true and DurationMs < 500)          // "good" = succeeded AND fast enough
| extend sli = 1.0 * good / total, budget = (1 - slo) * total, burned = total - good
| extend budgetRemainingPct = round(100.0 * (budget - burned) / budget, 1)

// Multi-window burn-rate alert (Google SRE style): page when both 1h and 5m burn > 14.4× (2% of monthly budget in 1 hour)
let slo = 0.999;
let burn = (w: timespan) {
    AppRequests
    | where TimeGenerated > ago(w) and AppRoleName == "orders-api" and Name !has "health"
    | summarize errRate = 1.0 * countif(Success == false or DurationMs >= 500) / count()
    | extend burnRate = errRate / (1 - slo)
};
burn(1h) | extend win = "1h" | union (burn(5m) | extend win = "5m")
| summarize minBurn = min(burnRate)
| where minBurn > 14.4
# Error budget maths you should be able to do in your head
def budget_minutes(slo: float, days: int = 30) -> float:
    return (1 - slo) * days * 24 * 60

for slo in (0.99, 0.995, 0.999, 0.9999):
    print(f"{slo:.2%}: {budget_minutes(slo):7.1f} min/month of total outage")
# 99.00%:   432.0 min   99.50%: 216.0 min   99.90%: 43.2 min   99.99%: 4.3 min

# Burn rate: how fast are we consuming the budget relative to "exactly on target"?
def burn_rate(error_rate: float, slo: float) -> float:
    return error_rate / (1 - slo)
print(burn_rate(0.0144, 0.999))   # 14.4 → at this rate the whole monthly budget goes in ~2 days

Dashboards, workbooks and Grafana

Dashboards answer "is it healthy now" in five seconds: the golden signals per service, SLO status, deploy markers, dependency health. Azure Workbooks are parameterised, KQL-backed and versionable as JSON; Azure Managed Grafana is the choice when teams already speak Grafana or need multi-source panels (Prometheus from AKS + Log Analytics). Keep dashboards in IaC and delete the ones nobody opens.

Incident response, runbooks and postmortems

Roles: incident commander (decides, communicates), ops lead (hands on keyboard), comms (status page, stakeholders). Process: detect → triage severity → mitigate first (roll back, scale, fail over, feature-flag off) → diagnose later → resolve → blameless postmortem with action items that actually get scheduled. Runbooks live next to the alert that fires and start with the mitigation, not the theory.

# runbooks/orders-api-error-rate.md
title: orders-api — elevated error rate (Sev1)
alert: "orders-api error rate"  (fires when 5xx > 2% for 10 min)
impact: customers cannot place orders; checkout shows a generic error

first 5 minutes:
  - Acknowledge in PagerDuty; open the incident channel #inc-<date>; post "investigating" on the status page
  - Dashboard: Orders API workbook → error rate, p95, dependencies panel
  - Did we deploy in the last 60 min?  →  az webapp deployment slot swap --slot staging --target-slot production  (swap back)  OR  containerapp traffic set to previous revision
  - Is a dependency failing? AppDependencies | where Success == false | summarize count() by Target
      • SQL: check failover group state, DTU/CPU; consider read-only degradation flag  Shop:Checkout:ReadOnly=true (App Configuration)
      • Service Bus: dead-letter growth → pause consumer, drain DLQ later
      • Redis: fail open — flag Shop:Cache:Enabled=false
  - Traffic spike? scale out: az appservice plan update --number-of-workers 6; enable WAF rate-limit rule
escalation: DB on-call (#db-oncall), platform on-call (#platform-oncall); Sev1 → engineering manager after 30 min
comms cadence: status page every 30 min until resolved
after: schedule postmortem within 48 h using the template; link the timeline export from the incident channel
# postmortems/2026-09-17-orders-api-outage.md
summary: 41 minutes of failed checkouts for ~12% of users after a deploy introduced a connection-pool leak
severity: Sev1        detected by: alert (orders-api error rate) at 14:02, 7 min after deploy

Load testing and chaos engineering

Prove capacity and resilience before customers do. Azure Load Testing runs JMeter/Locust scripts at scale with server-side metrics and pass/fail criteria in the pipeline. Azure Chaos Studio injects faults (CPU pressure, network latency, kill AKS pods, Cosmos failover, Key Vault deny) under an experiment you can gate and abort. Start small: one hypothesis, one fault, steady-state metrics before and after.

# loadtest/locustfile.py — runs locally or in Azure Load Testing
from locust import HttpUser, task, between

class Shopper(HttpUser):
    wait_time = between(0.5, 2)
    host = "https://api-staging.contoso.com"

    def on_start(self):
        self.client.headers["Authorization"] = f"Bearer {TOKEN}"

    @task(5)
    def browse(self):
        with self.client.get("/products?page=1", name="/products", catch_response=True) as r:
            if r.elapsed.total_seconds() > 0.5: r.failure("slow")

    @task(1)
    def checkout(self):
        self.client.post("/orders", json={"items": [{"sku": "JKT-001", "qty": 1}]}, name="/orders")
