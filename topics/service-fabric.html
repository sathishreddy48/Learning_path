Azure Service Fabric

Service Fabric is Microsoft's distributed-systems platform: it hosts, scales, heals and upgrades services, and — uniquely — lets you keep state inside the service with replicated Reliable Collections. This page is C#-only (the SDK is .NET); Python sits this one out. Focus on the concepts an interviewer will probe: partitions, replicas, quorum, and why stateful services are different.

Cluster, nodes, applications and services

A cluster is a set of VMs (nodes). An application type (versioned package of service types + manifests) is instantiated as a named application, which contains named services. Each service has partitions; each partition has replicas (stateful) or instances (stateless) spread across nodes. The Cluster Resource Manager places and balances them; the Failover Manager handles node loss. The system services (Naming, Failover Manager, Image Store) run in the cluster itself.

No Python equivalent
// ApplicationManifest.xml — the application type: parameters + which services to create
// <ApplicationManifest ApplicationTypeName="ShopType" ApplicationTypeVersion="1.0.0">
//   <Parameters>
//     <Parameter Name="Orders_PartitionCount" DefaultValue="10" />
//     <Parameter Name="Orders_MinReplicaSetSize" DefaultValue="3" />
//     <Parameter Name="Orders_TargetReplicaSetSize" DefaultValue="3" />
//   </Parameters>
//   <ServiceManifestImport><ServiceManifestRef ServiceManifestName="OrdersPkg" ServiceManifestVersion="1.0.0" /></ServiceManifestImport>
//   <DefaultServices>
//     <Service Name="Orders">
//       <StatefulService ServiceTypeName="OrdersType" TargetReplicaSetSize="[Orders_TargetReplicaSetSize]" MinReplicaSetSize="[Orders_MinReplicaSetSize]">
//         <UniformInt64Partition PartitionCount="[Orders_PartitionCount]" LowKey="0" HighKey="9" />
//       </StatefulService>
//     </Service>
//     <Service Name="Web"><StatelessService ServiceTypeName="WebType" InstanceCount="-1"><SingletonPartition /></StatelessService></Service>
//   </DefaultServices>
// </ApplicationManifest>

// Program.cs — register the service type with the runtime on this node
internal static class Program
{
    private static void Main()
    {
        ServiceRuntime.RegisterServiceAsync("OrdersType", ctx => new Orders(ctx)).GetAwaiter().GetResult();
        ServiceEventSource.Current.ServiceTypeRegistered(Environment.ProcessId, typeof(Orders).Name);
        Thread.Sleep(Timeout.Infinite);      // the host process stays alive; SF creates replicas inside it
    }
}

Interview angle

Know the vocabulary cold: application type vs application, service type vs service, partition vs replica vs instance, primary vs secondary, and what the Naming service does.

Stateless vs stateful services

A stateless service keeps state in an external store (SQL, Cosmos) — like any web API; SF just runs N instances. A stateful service keeps state locally in Reliable Collections that SF replicates to secondaries; writes go to the primary and are acknowledged only after a quorum of replicas has persisted the log. That removes the database hop from the hot path and gives you a partitioned, in-memory-fast store with durability — at the cost of learning the programming model.

No Python equivalent
// Stateless: override CreateServiceInstanceListeners + RunAsync (optional)
internal sealed class Web(StatelessServiceContext ctx) : StatelessService(ctx)
{
    protected override IEnumerable<ServiceInstanceListener> CreateServiceInstanceListeners() =>
        new[]
        {
            new ServiceInstanceListener(serviceContext =>
                new KestrelCommunicationListener(serviceContext, "ServiceEndpoint", (url, listener) =>
                    WebApplication.CreateBuilder().ConfigureSfHost(serviceContext, url).Build()))
        };
}

// Stateful: StateManager is your replicated store; RunAsync runs on the PRIMARY only
internal sealed class Orders(StatefulServiceContext ctx) : StatefulService(ctx)
{
    protected override IEnumerable<ServiceReplicaListener> CreateServiceReplicaListeners() =>
        this.CreateServiceRemotingReplicaListeners();          // remoting listener (see Communication)

    protected override async Task RunAsync(CancellationToken cancellationToken)
    {
        var counters = await StateManager.GetOrAddAsync<IReliableDictionary<string, long>>("counters");
        while (true)
        {
            cancellationToken.ThrowIfCancellationRequested();     // primary is being demoted/moved: stop cleanly
            using (var tx = StateManager.CreateTransaction())
            {
                await counters.AddOrUpdateAsync(tx, "heartbeat", 1, (k, v) => v + 1);
                await tx.CommitAsync();                          // replicated to a quorum before returning
            }
            await Task.Delay(TimeSpan.FromSeconds(1), cancellationToken);
        }
    }
}

// Lifecycle to remember
//  stateless instance: CreateServiceInstanceListeners → OpenAsync → RunAsync → CloseAsync/OnAbort
//  stateful replica:   OpenAsync → ChangeRoleAsync(Primary/ActiveSecondary/IdleSecondary) → RunAsync (primary) → …
//  RunAsync's CancellationToken fires on role change; ignoring it is the #1 bug.
Interview angle

When would you choose a stateful service over stateless + database? Low-latency, high-throughput state that partitions naturally (carts, game sessions, IoT device state), or when you need a durable queue without an external broker.

Reliable Collections

IReliableDictionary<K,V>, IReliableQueue<T>, IReliableConcurrentQueue<T> — replicated, transactional, persisted collections that live in the primary's memory and on disk on every replica. All operations take a transaction; commit replicates. Values must be immutable once handed to the collection (or you will mutate the in-memory copy without replication). Locks are held for the transaction's lifetime, so keep transactions short.

No Python equivalent
public interface IOrdersService : IService
{
    Task<Guid> Place(Order order);
    Task<Order?> Get(Guid id);
    Task<int> CountOpen();
}

internal sealed class Orders : StatefulService, IOrdersService
{
    public async Task<Guid> Place(Order order)
    {
        var orders = await StateManager.GetOrAddAsync<IReliableDictionary<Guid, Order>>("orders");
        var queue  = await StateManager.GetOrAddAsync<IReliableConcurrentQueue<Guid>>("toInvoice");

        using var tx = StateManager.CreateTransaction();
        await orders.AddAsync(tx, order.Id, order);          // takes an exclusive lock on the key
        await queue.EnqueueAsync(tx, order.Id);
        await tx.CommitAsync();                              // both or neither, replicated
        return order.Id;
    }

    public async Task<Order?> Get(Guid id)
    {
        var orders = await StateManager.GetOrAddAsync<IReliableDictionary<Guid, Order>>("orders");
        using var tx = StateManager.CreateTransaction();
        var result = await orders.TryGetValueAsync(tx, id);   // shared lock; no commit needed for reads
        return result.HasValue ? result.Value : null;
    }

    public async Task<int> CountOpen()
    {
        var orders = await StateManager.GetOrAddAsync<IReliableDictionary<Guid, Order>>("orders");
        using var tx = StateManager.CreateTransaction();
        var e = (await orders.CreateEnumerableAsync(tx, EnumerationMode.Unordered)).GetAsyncEnumerator();
        int n = 0;
        while (await e.MoveNextAsync(CancellationToken.None)) if (e.Current.Value.Status == "open") n++;
        return n;                                             // full scans hold locks — prefer a maintained counter
    }

    // Consumer loop on the primary
    protected override async Task RunAsync(CancellationToken ct)
    {
        var queue = await StateManager.GetOrAddAsync<IReliableConcurrentQueue<Guid>>("toInvoice");
        while (!ct.IsCancellationRequested)
        {
            using var tx = StateManager.CreateTransaction();
            var item = await queue.TryDequeueAsync(tx, ct);
            if (!item.HasValue) { await Task.Delay(500, ct); continue; }
            await Invoice(item.Value);                        // if this throws, tx is not committed → item stays
            await tx.CommitAsync();
        }
    }
}

// Rules
//  • Values are copied by reference in memory: treat them as immutable (records are perfect).
//  • Keep transactions short; TimeoutException = lock contention.
//  • Backup/restore: BackupAsync(...) to Azure Storage; restore via OnDataLossAsync.
//  • Custom serialization for versioned types: IStateSerializer<T>, registered in the constructor.
Interview angle

What does a Reliable Collection transaction guarantee (atomic across collections in one partition, durable after quorum)? Why not across partitions (no distributed transactions — use a saga)? What is the in-memory vs disk story (all in memory on the primary, log + checkpoint on disk)?

Practice
  • Build a stateful Counter service on the local dev cluster, kill the primary node in Service Fabric Explorer, and observe the failover with no data loss.

Reliable Actors

The virtual-actor model (from Orleans): millions of tiny single-threaded stateful objects, each addressed by an ID, activated on demand and garbage-collected when idle. Turn-based concurrency means no locks inside an actor. State goes through the StateManager (persisted, volatile or none). Great for per-entity logic (a device, a user session, a game); poor for fan-out queries or long-running operations that block the actor.

No Python equivalent
// Interface project (shared with clients)
public interface IThermostatActor : IActor
{
    Task<double> GetTemperature();
    Task Report(double celsius);
    Task SetTarget(double celsius);
}

// Actor implementation
[StatePersistence(StatePersistence.Persisted)]
internal class ThermostatActor(ActorService service, ActorId id) : Actor(service, id), IThermostatActor, IRemindable
{
    private const string TempKey = "temp", TargetKey = "target";

    protected override async Task OnActivateAsync()
    {
        await StateManager.TryAddStateAsync(TargetKey, 21.0);       // default on first activation
        await RegisterReminderAsync("check", null, TimeSpan.FromMinutes(1), TimeSpan.FromMinutes(1));
    }

    public Task<double> GetTemperature() => StateManager.GetOrAddStateAsync(TempKey, 0.0);

    public async Task Report(double celsius)
    {
        await StateManager.SetStateAsync(TempKey, celsius);          // saved at end of the turn
        var target = await StateManager.GetStateAsync<double>(TargetKey);
        if (Math.Abs(celsius - target) > 3) ActorEventSource.Current.Message($"{Id} out of range");
    }

    public Task SetTarget(double celsius) => StateManager.SetStateAsync(TargetKey, celsius);

    // Reminders survive deactivation and failover (timers do not)
    public async Task ReceiveReminderAsync(string name, byte[] state, TimeSpan due, TimeSpan period)
    {
        var t = await GetTemperature(); /* ... */
    }
}

// Registration
ActorRuntime.RegisterActorAsync<ThermostatActor>((ctx, info) => new ActorService(ctx, info)).GetAwaiter().GetResult();

// Client — any service or external app with the interface assembly
var actor = ActorProxy.Create<IThermostatActor>(new ActorId("device-42"), new Uri("fabric:/Shop/ThermostatActorService"));
await actor.Report(23.5);

// Anti-patterns: one "manager" actor everything calls (hotspot), holding an actor turn on I/O to another actor
// (reentrancy deadlocks), enumerating all actors (use an external index or a stateful service instead).
Interview angle

Explain turn-based concurrency, virtual activation, reminders vs timers, and why an actor that calls another actor synchronously can deadlock (reentrancy). Compare to Orleans and Dapr actors.

Partitioning, replicas and quorum

A stateful service scales by partitioning state: ranged (UniformInt64, key ranges), named, or singleton. Each partition is an independent replica set with one primary (serves reads and writes) and N secondaries. A write commits when a write quorum (⌈N/2⌉+1) acknowledges. Partition count is fixed at creation — choose it for the eventual scale (e.g. 20–50 partitions on a 5-node cluster) and let SF pack many partitions per node.

No Python equivalent
// Choosing a partition for a key: hash it into the Int64 range
static long PartitionKeyFor(string customerId)
{
    // stable hash; MD5 is fine here (not security) and stable across processes unlike string.GetHashCode()
    var bytes = MD5.HashData(Encoding.UTF8.GetBytes(customerId));
    return BitConverter.ToInt64(bytes, 0) & long.MaxValue % 10;     // 0..9 to match LowKey/HighKey above
}

// Client resolves the partition, then talks to its primary
var proxy = ServiceProxy.Create<IOrdersService>(
    new Uri("fabric:/Shop/Orders"),
    new ServicePartitionKey(PartitionKeyFor(order.CustomerId)));
await proxy.Place(order);

// Inside the service: which partition am I?
var info = (Int64RangePartitionInformation)Context.PartitionId /* via Partition.PartitionInfo */;
var range = (Int64RangePartitionInformation)Partition.PartitionInfo;
Console.WriteLine($"{range.LowKey}-{range.HighKey}, replica {Context.ReplicaId}, role {/* current */ ""}");

// Replica set sizes (in ApplicationManifest): TargetReplicaSetSize=3, MinReplicaSetSize=3 for production.
//   3 replicas → tolerate 1 loss with write quorum 2.  5 → tolerate 2.
//   MinReplicaSetSize < Target lets writes continue while SF rebuilds a lost replica.

// Placement constraints and metrics steer the Cluster Resource Manager
//   <StatefulService ...><PlacementConstraints>(NodeType==Backend)</PlacementConstraints>
//   <ServiceLoadMetric Name="MemoryMB" Weight="High" PrimaryDefaultLoad="512" SecondaryDefaultLoad="256" />
// Report live load from code:
Partition.ReportLoad(new[] { new LoadMetric("MemoryMB", currentMb) });

// Fan-out query across all partitions (avoid on hot paths)
var fabric = new FabricClient();
var partitions = await fabric.QueryManager.GetPartitionListAsync(new Uri("fabric:/Shop/Orders"));
var counts = await Task.WhenAll(partitions.Select(p =>
    ServiceProxy.Create<IOrdersService>(new Uri("fabric:/Shop/Orders"),
        new ServicePartitionKey(((Int64RangePartitionInformation)p.PartitionInformation).LowKey)).CountOpen()));
Interview angle

Why is the partition count fixed (state would have to be re-split)? How do you handle a hot partition? What happens when a primary dies (secondary promoted from the replicated log; in-flight uncommitted writes are lost — the client retries)?

Communication: remoting, reverse proxy, Kestrel

Services expose listeners. Service Remoting is the RPC stack: define an interface, ServiceProxy.Create resolves the partition/primary via the Naming service and retries on failover. For HTTP, host Kestrel inside the service and let clients find the address via the reverse proxy (http://localhost:19081/App/Service/...) or a ServicePartitionResolver. External traffic comes in through a load balancer to a stateless front-end.

No Python equivalent
// Remoting listener (V2, interface-compatible). Interface assembly referenced by both sides.
// [assembly: FabricTransportServiceRemotingProvider(RemotingListenerVersion = RemotingListenerVersion.V2_1, RemotingClientVersion = RemotingClientVersion.V2_1)]
protected override IEnumerable<ServiceReplicaListener> CreateServiceReplicaListeners() =>
    this.CreateServiceRemotingReplicaListeners();

// Client — retries transient failures and re-resolves on failover automatically
var orders = ServiceProxy.Create<IOrdersService>(new Uri("fabric:/Shop/Orders"), new ServicePartitionKey(3));
var order = await orders.Get(id);

// Kestrel listener inside a service (ServiceManifest: <Endpoint Name="ServiceEndpoint" Protocol="http" Port="8080" />)
new ServiceReplicaListener(ctx => new KestrelCommunicationListener(ctx, "ServiceEndpoint", (url, listener) =>
{
    var b = WebApplication.CreateBuilder();
    b.Services.AddSingleton<StatefulServiceContext>(ctx).AddSingleton(StateManager);
    b.WebHost.UseKestrel().UseUrls(url);
    var app = b.Build();
    app.MapGet("/orders/{id:guid}", async (Guid id, IReliableStateManager sm) => { /* ... */ });
    return app;
}), listenOnSecondary: true);      // allow reads from secondaries

// Reverse proxy (enable in cluster manifest; port 19081):
//   GET http://localhost:19081/Shop/Orders/orders/{id}?PartitionKey=3&PartitionKind=Int64Range
//   GET http://localhost:19081/Shop/Web/api/health           (stateless singleton: no partition params)
// Add ?ListenerName=... for multiple listeners; ?Timeout=20 for the resolution timeout.

// Manual resolution (e.g. gRPC or custom protocol)
var resolver = ServicePartitionResolver.GetDefault();
var partition = await resolver.ResolveAsync(new Uri("fabric:/Shop/Orders"), new ServicePartitionKey(3), CancellationToken.None);
var endpoint = partition.GetEndpoint();      // JSON: {"Endpoints":{"ServiceEndpoint":"http://10.0.0.5:8080"}}
// Re-resolve with (previousRsp) when a call fails — the address may have moved.

// Exceptions to handle on the client: FabricNotPrimaryException, FabricTransientException,
// FabricObjectClosedException → retry after re-resolve (ServiceProxy does this for you).

Upgrades, health and monitoring

Application upgrades are rolling by upgrade domain: SF upgrades one UD, waits for health checks to pass, then moves on — and rolls back automatically if health degrades (Monitored mode). Health is a hierarchy (cluster → node/application → service → partition → replica) fed by system reports and your own ReportReplicaHealth. Service Fabric Explorer shows all of it; ship events and health to Application Insights/Log Analytics.

# Package and upgrade (PowerShell)
Copy-ServiceFabricApplicationPackage -ApplicationPackagePath .\pkg -ImageStoreConnectionString fabric:ImageStore -ApplicationPackagePathInImageStore Shop_1.1.0
Register-ServiceFabricApplicationType -ApplicationPathInImageStore Shop_1.1.0
Start-ServiceFabricApplicationUpgrade -ApplicationName fabric:/Shop -ApplicationTypeVersion 1.1.0 `
    -Monitored -FailureAction Rollback -HealthCheckStableDurationSec 60 -UpgradeDomainTimeoutSec 1200 -UpgradeTimeoutSec 3600
Get-ServiceFabricApplicationUpgrade -ApplicationName fabric:/Shop     # progress per upgrade domain

# sfctl equivalents
sfctl application upload --path ./pkg
sfctl application provision --application-type-build-path pkg
sfctl application upgrade --app-id Shop --app-version 1.1.0 --parameters '{}' --mode Monitored --failure-action Rollback

# Only the changed service package versions need to bump; unchanged code packages are not restarted.
# Config-only upgrade: bump ConfigPackage version + ServiceManifest version + ApplicationManifest version.
// Report custom health from inside a replica
Partition.ReportReplicaHealth(new HealthInformation("Orders", "QueueDepth",
    queueDepth > 10_000 ? HealthState.Warning : HealthState.Ok)
{
    Description = $"queue depth {queueDepth}",
    TimeToLive = TimeSpan.FromMinutes(2),
    RemoveWhenExpired = true                // stale report disappears rather than sticking
});

// React to configuration package changes without restart
Context.CodePackageActivationContext.ConfigurationPackageModifiedEvent += (s, e) =>
{
    var settings = e.NewPackage.Settings.Sections["Orders"].Parameters;
    _maxLines = int.Parse(settings["MaxLines"].Value);
};

// Health policy (ApplicationManifest / upgrade parameters)
//   MaxPercentUnhealthyServices, MaxPercentUnhealthyPartitionsPerService, ConsiderWarningAsError
// Upgrade rollback triggers when the aggregated health is Error.

// Diagnostics: EventSource → EventFlow / Azure Diagnostics → Application Insights or Log Analytics
[EventSource(Name = "Shop-Orders")]
internal sealed class ServiceEventSource : EventSource
{
    public static readonly ServiceEventSource Current = new();
    [Event(1, Level = EventLevel.Informational, Message = "{0}")]
    public void Message(string message) => WriteEvent(1, message);
}
// Cluster-level: Service Fabric Explorer (https://cluster:19080/Explorer), Get-ServiceFabricClusterHealth,
// Azure Monitor "Service Fabric analytics" for node/partition/replica events.
Interview angle

Upgrade domains vs fault domains (UD = rolling upgrade unit, FD = shared failure unit like a rack); what makes an upgrade roll back; how a stateful service survives an upgrade (secondaries take over while the primary's node is upgraded).

Configuration, secrets and containers

Settings live in the service's Config package (Settings.xml) and are overridden per environment in ApplicationParameters/*.xml. Encrypted parameters use a cluster certificate; better, read secrets from Key Vault with a managed identity. Service Fabric can also host containers and guest executables alongside Reliable Services, and Service Fabric Managed Clusters simplify the infrastructure side.

No Python equivalent
// PackageRoot/Config/Settings.xml
// <Settings>
//   <Section Name="Orders">
//     <Parameter Name="MaxLines" Value="50" />
//     <Parameter Name="SqlConnection" Value="" IsEncrypted="true" />
//   </Section>
// </Settings>
// ApplicationParameters/Cloud.xml overrides:  <Parameter Name="Orders_MaxLines" Value="100" />
// wired through ApplicationManifest <ConfigOverrides> ... <Parameter Name="MaxLines" Value="[Orders_MaxLines]" />

// Read configuration
var config = Context.CodePackageActivationContext.GetConfigurationPackageObject("Config");
var section = config.Settings.Sections["Orders"];
int maxLines = int.Parse(section.Parameters["MaxLines"].Value);
string cs = section.Parameters["SqlConnection"].DecryptValue().ToUnsecureString();   // encrypted with the cluster cert

// Bridge into IConfiguration for ASP.NET-style options
var builder = WebApplication.CreateBuilder();
builder.Configuration.AddServiceFabricConfiguration(Context);     // Microsoft.ServiceFabric.AspNetCore.Configuration
builder.Services.Configure<OrdersOptions>(builder.Configuration.GetSection("Config:Orders"));

// Preferred for secrets: Key Vault via managed identity on the VM scale set
var kv = new SecretClient(new Uri("https://shop-kv.vault.azure.net/"), new DefaultAzureCredential());
string sql = (await kv.GetSecretAsync("SqlConnection")).Value.Value;

// Encrypting a value for Settings.xml (PowerShell):
//   Invoke-ServiceFabricEncryptText -Text "Server=..." -CertThumbprint <thumb> -CertStore -StoreLocation LocalMachine -StoreName My

// Containers in ServiceManifest.xml
// <CodePackage Name="Code" Version="1.0.0">
//   <EntryPoint><ContainerHost><ImageName>myacr.azurecr.io/orders:1.0.0</ImageName></ContainerHost></EntryPoint>
// </CodePackage>
// ApplicationManifest: <ContainerHostPolicies CodePackageRef="Code"><RepositoryCredentials .../><PortBinding ContainerPort="8080" EndpointRef="ServiceEndpoint"/></ContainerHostPolicies>

// When to pick SF today: existing SF estates, stateful services/actors, Windows-heavy workloads.
// New greenfield container workloads usually go to AKS or Azure Container Apps (see Azure Services page).
